The Rendering Strategies lesson earlier in this course covers CSR, SSR, SSG,
and ISR as if you pick exactly one for a page. Real production frontends
don't work that way. A single page might render at the edge, stream its
HTML in pieces, and hydrate only three of its twenty components — all at
once. The strategies aren't mutually exclusive tools you choose between;
they're layers you combine. This lesson covers the architectural patterns
that do the combining: islands, streaming SSR, resumability, and edge
rendering. All four exist to answer the same underlying question — how do
you get content on screen fast *and* make it interactive fast, without one
goal taxing the other.

## Why hydration became the bottleneck

Classic SSR solved "content appears fast" by rendering HTML on the server.
But it left a second cost on the table: the browser still has to download
the same component JavaScript that rendered the page, execute it, rebuild
an in-memory tree, and attach event handlers to DOM nodes that already
exist. That process — hydration — used to scale with total page size: a
page with 200 components meant hydrating 200 components, whether or not
most of them were static text and images. As apps grew, hydration itself
became the dominant cost on time-to-interactive, even when first paint was
fast. Every pattern below is a different answer to "how do we stop paying
for hydration we don't need."

## Islands architecture

An islands-based framework treats the page as static HTML by default and
lets you opt individual components into hydration, one at a time. Each
"island" ships its own small JS bundle and hydrates independently, using
its own trigger — on page load, when it scrolls into view, when the browser
is idle, or on first interaction. Everything that isn't an island — the
article body, the nav, the footer — is plain HTML with zero attached JS,
because it never needed to respond to input in the first place.

This course's own site is a working example. It's built on Astro, and every
interactive piece — the `Quiz` component, the `Mermaid` diagram renderer,
the theme toggle — is a separate island that only hydrates once it's
visible on screen (the `client:visible` directive you'll see throughout
these lessons). The surrounding lesson prose, headings, and code samples
ship as inert HTML. If this lesson had 40 paragraphs and 2 quiz questions,
the browser only ever executes JS for those 2 quiz components, not the 40
paragraphs around them. Compare that to a monolithic React SSR app, where
hydrating "the page" typically means re-running the render function for
the entire component tree, static text included.

The trade-off: islands need explicit boundaries, so cross-island
communication (an island in the header needs to know about state in an
island in the body) has to go through some shared mechanism — a store, URL
state, or custom events — since islands don't share a component tree the
way a single-page app does.

## Streaming SSR

Streaming addresses a different problem: what happens when part of the
page is fast to render and part of it is slow, because it's waiting on a
slow data source? Classic SSR is all-or-nothing — the server can't send any
HTML until the *entire* page has finished rendering, so one slow API call
anywhere on the page delays the whole response.

Streaming SSR sends HTML in chunks as each part becomes ready, instead of
waiting for the full page. The shell, header, and any content with data
already in hand go out immediately; a slower section (think a
personalized recommendations block, or a comments count) is sent later,
along with a script that swaps a loading placeholder for the real content
once it resolves — all inside the same response, no extra round-trip. The
browser starts parsing and painting the fast parts of the page while the
server is still working on the slow part.

Streaming changes *when HTML arrives*, not how much JS the client executes

the islands inside each chunk as it lands) rather than replacing them.

## Resumability

Islands still pay one cost: each island's component code has to run on the
client to figure out what the DOM should look like and attach listeners —
even though the server already rendered that exact output. Resumability,
the model Qwik is built around, removes that step. The server serializes
not just HTML but a snapshot of the framework's internal state (what
listeners are needed, where, and what data they close over) directly into
the page. The client never re-executes component render logic to "catch
up" — it lazily wires up a listener only at the moment a user actually
interacts with that element, using the serialized state that's already
sitting in the HTML.

The distinction from islands matters: an island still hydrates (runs JS to
attach handlers) even if that hydration is scoped to a small piece of the
page and deferred until visible. A resumable app skips the
attach-handlers-by-re-running-code step almost entirely — interactivity is
"resumed" from serialized state on demand, not rebuilt from scratch. The
payoff is a time-to-interactive curve that barely rises with page
complexity, at the cost of a framework built from the ground up around
serializable state (you can't easily bolt resumability onto an existing
component model).

## Edge rendering

Edge rendering runs your server-render step — SSR, streaming, or a
lightweight per-request personalization layer — inside a CDN's points of
presence instead of one central origin server. A user in Singapore hitting
an edge function running in a Singapore PoP saves the round trip to a
single origin server that might be in Virginia; that round trip is often
100-200ms right there, before any rendering work even starts.

Edge rendering is orthogonal to the other three patterns: it's about
*where* rendering happens, not *how much* JS the client runs afterward. You
can (and often should) combine it with streaming — start streaming the
response from the nearest edge location — and with islands or resumability
for the client-side story. None of this replaces SSG/ISR for content that
truly doesn't need per-request logic; edge rendering earns its cost for
requests that need some server-side decision (auth check, A/B bucketing,
locale) but don't need a full origin round trip to make it.

## Worked example: a global news homepage

Say you're designing a news homepage read by users worldwide, with a
personalized "recommended for you" rail and a global top-story section
that's the same for everyone.

- The top-story section and page shell are edge-rendered from a cache
  close to the reader — no origin round trip, sub-100ms TTFB almost
  everywhere.
- The personalized rail depends on a per-user recommendation service call
  that takes 150-300ms. Rather than blocking the whole page on it, the
  server streams the shell and top stories immediately, then streams the
  rail's HTML in a second chunk once the recommendation call resolves.
- On the client, the rail and a handful of interactive widgets (a "save
  article" button, a comments-count badge) are islands, hydrating with
  `client:visible` as the user scrolls. The article bodies themselves are
  plain HTML — never hydrated, because they're never interactive.

The result: fast global TTFB (edge), no single slow dependency blocking the
whole response (streaming), and a time-to-interactive that only pays for
the few components that actually need JS (islands) — three different
patterns, each solving a distinct piece of the problem, composed on one
page.

<Callout type="warning">
  A common mistake is treating these as a menu where you pick exactly one
  ("we're an islands app" or "we're an edge-rendered app") instead of a set
  of independent axes. Edge rendering without streaming still forces a slow
  data dependency to block the entire response — you've moved rendering
  physically closer to the user but kept the same all-or-nothing wait.
  Islands without any server rendering at all still leaves you with an
  empty shell for first paint. Ask "where does rendering happen," "does
  HTML arrive in one piece or many," and "how much JS does the client
  execute to become interactive" as three separate questions — an
  architecture usually needs an answer to each.
</Callout>
