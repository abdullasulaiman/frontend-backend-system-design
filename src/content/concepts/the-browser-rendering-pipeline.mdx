Every frontend performance conversation eventually comes back to the same question: why is this scrolling janky, why does this animation stutter, why did that one CSS change make everything slow? You can't answer any of that without a mental model of what the browser actually does between "the JS finished running" and "pixels changed on screen." That gap is the rendering pipeline, and it's the single most useful piece of browser internals knowledge for a frontend engineer — it explains almost every performance bug you'll debug and most of the "don't do that" rules you've absorbed without knowing why.

The pipeline isn't one monolithic step; it's a sequence of stages, and — critically — different kinds of changes only need to re-run *part* of that sequence. Knowing which part is what separates "I added `will-change` because a blog post said so" from actually understanding your app's performance.

## The stages, in order

A browser turns markup into pixels in six broad stages:

1. **Parse HTML into the DOM** — the HTML text is tokenized and turned into the Document Object Model, a tree of node objects.
2. **Parse CSS into the CSSOM** — every stylesheet (external, inline, `<style>` tags) is parsed into the CSS Object Model, a tree of matched style rules.
3. **Construct the render tree** — the DOM and CSSOM are combined into a tree of only the nodes that will actually be visible, each annotated with its computed styles.
4. **Layout (a.k.a. reflow)** — the browser walks the render tree and computes the exact geometry (position and size in pixels) of every node.
5. **Paint** — the browser fills in pixels for each node: text, colors, borders, shadows, images — recorded as a set of paint instructions, typically across multiple layers.
6. **Composite** — the painted layers are combined in the correct order (respecting stacking context, transforms, opacity) and handed to the GPU to produce the final frame.

### Why the render tree isn't just the DOM

The render tree drops nodes that never produce visible output — `<head>`, `<script>` tags, and anything styled `display: none`. This is a meaningful distinction: an element with `display: none` isn't in the render tree at all and costs nothing in layout or paint, while `visibility: hidden` *is* in the render tree — it still occupies layout space, it's just skipped during paint. If you're conditionally hiding a large subtree for performance reasons, `display: none` is the cheaper choice.

### Layout: the expensive one

Layout is where the browser figures out the box model for every element — where it sits, how wide and tall it is — and that computation cascades. A parent's width can depend on its content; a sibling's position can depend on an element before it changing height. That's why layout is often called reflow: a single geometry change can force the browser to recompute geometry for a large chunk of the tree, not just the element you touched.

### Paint and layers

Once geometry is settled, paint fills in the actual visual detail — text glyphs, background colors, box shadows, borders. The browser doesn't paint into one giant canvas; it splits content into layers (driven by things like `position: fixed`, `transform`, `will-change`, or elements with their own stacking context) so that later stages can update one layer without repainting everything.

### Compositing: the cheap one

Compositing takes the already-painted layers and assembles the final image, applying transforms and opacity as GPU operations on the existing layer bitmaps. Crucially, this step doesn't need to re-run layout or paint — it just repositions or fades pre-rendered layers. That's the entire reason `transform` and `opacity` are the two properties you'll hear recommended for animation: a well-set-up animation on those properties can skip straight to compositing every frame.

## What triggers what

The pipeline doesn't always restart from HTML parsing — that only happens once per page load (plus incremental parsing as streamed HTML arrives, or when you use `innerHTML` to inject new markup). What matters day to day is which *later* stage a given change forces the browser to re-enter:

- **Layout-triggering changes**: anything that can change an element's geometry — `width`, `height`, `top`/`left` in normal or absolute positioning, `font-size`, `padding`, `border-width`, adding or removing DOM nodes, or reflowing text content. These force layout, then paint, then composite.
- **Paint-only changes**: changes that affect appearance but not geometry — `background-color`, `color`, `box-shadow`, `visibility`. These skip layout but still require paint and composite.
- **Composite-only changes**: `transform` and `opacity` (when the element already has its own layer). These skip both layout and paint entirely.

This is why "just add `transform: translateX()` instead of animating `left`" isn't a superstition — it's the difference between forcing layout and paint on every animation frame versus doing pure GPU compositing.

<Callout type="warning">
  A common mistake is reading a layout-dependent property (`el.offsetHeight`, `el.getBoundingClientRect()`, `getComputedStyle()`) immediately after writing a style change, inside a loop over multiple elements. Each read forces the browser to synchronously flush any pending layout work to give you an up-to-date answer — even though it would otherwise have batched all the pending style writes into a single layout pass at the end of the frame. Do this for `N` elements in a loop (write, read, write, read...) and you force `N` synchronous layouts instead of one. This is called layout thrashing, and it's covered in depth, with a before/after fix, in the <a href="/concepts/dom-manipulation">DOM Manipulation</a> lesson.
</Callout>

## Worked example: one line, three different costs

Say you have a card component and you want to highlight it on hover. Three ways to write that highlight produce three very different pipeline costs:

**Option A — resize the card:**
```css
.card:hover { width: 320px; padding: 24px; }
```
Changing `width` and `padding` changes geometry. The browser re-runs layout for the card and likely its siblings (their position may depend on this card's size), then repaints, then recomposites. On a page with many cards, this can visibly stutter.

**Option B — change the background:**
```css
.card:hover { background-color: #1e293b; }
```
No geometry changed, so layout is skipped — but the browser still has to repaint the card's layer and recomposite. Cheaper than A, not free.

**Option C — scale with a transform:**
```css
.card:hover { transform: scale(1.03); }
```
If the card already has its own compositor layer (common once it has a `transform`, or you hint it with `will-change: transform`), this skips layout *and* paint. The browser just tells the GPU to redraw the existing layer bitmap slightly larger. This is the version that stays smooth even on a page with hundreds of cards, because the per-frame cost doesn't scale with layout complexity — it's a constant-cost GPU operation.

Same visual goal — "make the card look highlighted" — three different pipeline paths, and the difference between A and C is often the entire explanation for "why does this one interaction feel janky."

## Why this matters beyond animations

This pipeline knowledge shows up any time you're diagnosing jank in a performance profiler: a "Layout" or "Recalculate Style" block eating milliseconds in a flame chart tells you exactly which stage a piece of code is forcing, and points you at the specific CSS or DOM operation to fix. It also explains framework internals — a lot of what virtual-DOM diffing, batched state updates, and CSS-in-JS libraries optimize for is *minimizing how often and how much of this pipeline gets re-entered per update*, which is the subject of the <a href="/concepts/dom-manipulation">DOM Manipulation</a> lesson right after this one. And it directly informs layout choices: the <a href="/concepts/css-layout-and-positioning">CSS Layout & Positioning</a> lesson builds on this to explain which layout properties and positioning schemes are layout-cheap versus layout-expensive.

At a practical level: a 60fps target gives you roughly 16.7ms per frame for the browser to do layout, paint, and composite (on top of whatever your JS does). Forcing full-page layout every frame from expensive CSS or thrashing script easily blows that budget, and the frame drops as visible stutter.
