Every frontend eventually needs to answer one question: how does the browser find out that something changed on the server? A stock ticker, a chat thread, a shipment tracker, and a "you have unread notifications" badge all need fresh data, but they don't need it the same way or at the same frequency. Picking the wrong communication model shows up as either a laggy UI (you polled too slowly) or a backend getting hammered by requests that mostly return "nothing changed" (you polled too aggressively, or you should've used a push model in the first place).

This lesson covers the three communication models a frontend engineer reaches for — short polling, long-polling, and persistent connections (WebSocket and SSE) — and how to decide between them based on two questions: how often does the data change, and does the client ever need to send data back on the same channel?

## Short polling: ask again on a timer

Short polling is the simplest model: the client sends a request on a fixed interval (`setInterval`, a `useEffect` timer, whatever), gets a response, and repeats. There's no persistent connection — each poll is its own independent HTTP request/response pair, complete with its own TCP handshake (or reused keep-alive connection) and HTTP headers.

The appeal is that it needs nothing special on either end: any REST endpoint already supports it. The cost is a straight trade-off between freshness and waste. Poll every 5 seconds and you'll see updates up to 5 seconds late; poll every 500ms and you're fresher but now sending 10x the requests, most of which return "nothing new" if updates are infrequent. There's no way to tune polling that removes this trade-off — you can only shift where you sit on the freshness/waste curve.

Short polling is the right default for data that changes occasionally and where a few seconds of staleness is fine: a dashboard tile, an order-status page, a "check if the export is ready" flow.

## Long-polling: hold the request open

Long-polling changes the server's behavior, not the client's request shape. The client still sends a plain HTTP request, but instead of answering immediately, the server *holds the request open* until either new data is available or a timeout elapses (commonly 20 to 60 seconds). When the server finally responds — either with data or an empty timeout response — the client immediately opens a new request and the cycle repeats.

This gets you much better freshness than short polling without needing a new connection type: as soon as the server has something to say, it says it, rather than waiting for the client's next scheduled poll. The cost is that the server now needs to keep a request (and usually a thread or async handler) parked per waiting client, and every request that resolves — even from a timeout — requires immediately reopening a new one, so under high volume it isn't dramatically cheaper than aggressive short polling in total connection churn.

Long-polling is a good fit when updates are irregular and you want low latency without standing up a new protocol on the server — it was, for years, the standard way to fake "real-time" over plain HTTP before WebSocket support was universal, and it's still a reasonable fallback path today.

## Persistent connections: WebSocket and SSE

Both models above pay a repeated setup cost: a new request (and its headers, and possibly a new TLS handshake) every cycle. A persistent connection avoids that by opening the connection once and keeping it open for the life of the session.

### WebSocket: bidirectional, message-based

A WebSocket starts as a normal HTTP request that asks to be upgraded (`Upgrade: websocket`), and once the server agrees, the underlying TCP connection stays open as a full-duplex channel — either side can send a message at any time, without waiting for a "request" from the other. This is the model for anything where the client is also a frequent sender: a chat app, a collaborative document where every keystroke or cursor move needs to reach other clients, a multiplayer game syncing state, or a trading UI that both subscribes to price ticks and submits orders on the same channel.

The cost is operational complexity: WebSocket connections are stateful, so load balancers need sticky routing or a shared pub/sub backplane, connections need explicit heartbeat/ping-pong to detect silently-dead links, and the client needs its own reconnect-with-backoff logic since the browser won't retry a dropped WebSocket for you.

### SSE: one-way, server-to-client streaming

Server-Sent Events run over plain HTTP — the client opens a normal request with `Accept: text/event-stream`, and the server keeps writing chunks of a text-based event stream to that same response indefinitely. The browser's built-in `EventSource` API even handles automatic reconnection for you. The catch is directionality: SSE is server-to-client only. If the client needs to send something back, that's a separate, ordinary HTTP request — SSE just isn't a channel for client-to-server messages.

SSE fits notifications feeds, live sports scores, a progress bar for a long-running job, or a live-updating activity log — anywhere the server needs to keep pushing updates but the client isn't sending a comparable stream back.

## Worked example: a live order-tracking page

Say you're building the order-tracking page for a food delivery app. Requirements: show order status ("preparing" → "out for delivery" → "delivered"), and once it's out for delivery, show the driver's live location on a map.

Order status changes maybe 3–4 times over 30 minutes and there's no client-to-server data involved — a customer never "sends" a status update. Short polling every 15–20 seconds is more than good enough here; anything fancier is wasted engineering effort for a value that changes a handful of times.

Driver location is a different profile entirely: it updates every 1–3 seconds while out for delivery, is strictly server-to-client (the customer's browser never pushes location data), and needs low latency so the pin doesn't visibly jump. That's SSE territory — one persistent stream, server pushes coordinates as they arrive, no need for the client to send anything back on that channel. If this same app also had an in-app chat between customer and driver, *that* feature — two-way, frequent, low-latency — is the one place on this page that would justify WebSocket.

Notice the app doesn't need one model for the whole page. Communication models are chosen per data stream, based on that stream's own update frequency and directionality, not applied uniformly across a whole feature.

<Callout type="warning">
  A common mistake is reaching for WebSocket as the default "real-time" solution and standing up a socket server for data that's actually one-way and infrequent — e.g. a notification bell that updates a few times an hour. That adds a stateful connection to scale, load-balance, and reconnect-handle for no benefit the user can perceive. Match the model to the actual traffic shape: one-way and infrequent is polling; one-way and frequent is SSE; two-way and frequent is WebSocket. Don't skip straight to the most powerful tool.
</Callout>

## Choosing between them

Two questions settle most of these decisions:

1. **How often does the data actually change?** Rare or occasional changes rarely justify anything beyond polling. Frequent or continuous changes push you toward a persistent connection.
2. **Does the client need to send data on the same channel, not just receive it?** If yes, and it's frequent, that's WebSocket. If the client only receives, SSE (or long-polling as a fallback) covers it without the operational overhead of a bidirectional socket.

Latency requirements matter too, but they usually follow from question 1: if updates need to be reflected within a second or two of happening, you're already past what polling can offer without extreme resource waste.
