Ask five engineers "where should this piece of state live?" and you'll often get five different answers, followed by a Redux store that holds a modal's open/closed flag next to a cached list of API results next to the current page number. That's not a Redux problem — it's a category error. Picking a mechanism before naming the category is how small apps end up with global stores nobody trusts and re-renders nobody can explain.

This lesson builds that vocabulary: the four categories of frontend state, the trade-offs between the common ways to share state across components, and when a purpose-built server-state cache beats a general-purpose store. The follow-up lesson on state architecture patterns builds concrete designs on top of what's introduced here.

## The four categories of frontend state

### Local component state

State that only one component (and maybe its direct children) cares about: whether a dropdown is open, the current value of a text input before it's submitted, whether a hover tooltip is visible. It's created when the component mounts and dies when it unmounts — nothing outside the tree needs to read or write it.

This is the easiest category to get right and the most commonly over-engineered — pulling a component's internal toggle into a global store "just in case" adds a dependency and an indirection layer for zero benefit.

### Shared / global UI state

State that multiple, often distant, components need to read or write, but that still describes the *application's UI*, not data from a server: the current theme, whether a sidebar is collapsed, which item in a list is selected, the contents of a multi-step form wizard. It doesn't come from an API and doesn't need cache invalidation — it just needs to be reachable from more than one place in the tree.

This is the category where prop drilling, context, and dedicated stores actually compete, covered in the next section.

### Server / remote cache state

Data that lives on a server and that your app is merely holding a *copy* of: a user's profile, a list of orders, search results. The defining trait is that it can go stale — someone else can change it, and the "correct" value is asynchronous, from a network call, not your app's own logic. It needs things local and UI state don't: loading/error states, retries, deduplication of in-flight requests, and cache invalidation when the underlying data changes.

Treating server data like ordinary state is the single most common source of frontend state bugs: stale lists after a mutation, duplicate fetches from two components that both "own" the same data, and race conditions from out-of-order responses.

### URL state

State that describes *where the user is*: the current route, a search query, active filters, the selected tab, the page number. It deserves its own category because the URL is a serialization format with properties no other state has — it survives a refresh, it's shareable via a link, and back/forward navigation should move through it naturally.

Storing "current filter" in `useState` instead of a query param works until someone refreshes the page, shares a link, or hits back expecting the previous filter — and it silently breaks all three.

## Sharing UI state: prop drilling vs. context vs. a store

Once you've identified state as "shared UI state," you still need a way to move it across the tree. Three common options trade off differently.

### Prop drilling

Passing a value (and its setter) down through props, component by component, until it reaches the consumer. It's the default and often the right choice: it's explicit — you can see exactly where a value comes from and where it's used just by reading the component tree — and it adds no new concept for a reader to learn.

It breaks down when the tree between producer and consumer gets deep or has many unrelated branches. Passing `currentUser` through four layers of components that don't use it themselves, just to get it to a fifth, means every middle component now carries an irrelevant prop, and a rename or refactor has to touch all of them.

### Context

Context lets a value skip the intermediate layers: a provider higher up the tree makes a value available, and any descendant can read it directly with no props threaded through. It solves prop drilling's "irrelevant middle props" problem cleanly.

The trade-off is re-render granularity. Every component that consumes a context re-renders whenever that context's value changes, even if it only cares about part of it. A single `AppContext` holding theme, user, and notification count means a component that only reads `theme` still re-renders every time `notificationCount` ticks up. The fix is to split contexts by what changes together (a `ThemeContext`, a separate `UserContext`), not to have one context swallow everything a component might need.

### Dedicated state libraries

Libraries like Redux, Zustand, or Jotai add selective subscriptions (a component re-renders only when the specific slice of state it reads changes), devtools for inspecting state changes over time, and patterns for updating state outside of React's render cycle entirely. They cost a new dependency, a new concept for every contributor to learn, and — for the more structured ones — boilerplate per action.

The practical rule: reach for a dedicated store when shared UI state is genuinely complex (many independent pieces, frequent updates, cross-cutting reads) and context's re-render-everything behavior becomes a measurable performance problem, not a hypothetical one. Plenty of apps never need to cross that line.

## Why server state needs its own tool

Server state looks like it fits the "shared UI state" mold — it's just a value some components need to read — but it has requirements the other mechanisms weren't built for:

- **Staleness**: the data can be outdated the moment it arrives, and different consumers might need different freshness guarantees.
- **Deduplication**: two components mounting at once and requesting the same resource should share one network call, not fire two.
- **Loading and error states**: every fetch has a lifecycle (idle → loading → success/error) tracked per request, not per component.
- **Invalidation on mutation**: after a `POST`/`PUT`/`DELETE`, cached copies elsewhere in the app need to be told they're stale.

Reimplementing this with `useState` + `useEffect` means hand-rolling all four, per feature, forever. Server-state libraries (React Query, SWR, Apollo's cache, RTK Query) exist to own this lifecycle: you describe *what* to fetch and *when it's stale*, and the library handles deduplication, caching, background refetch, and invalidation.

Rule of thumb: once you're writing `isLoading`/`error` state and a `useEffect` fetch-on-mount pattern more than once or twice, that's the signal to bring in a server-state tool instead.

## Worked example: a product listing page

Say you're building a product listing page with filters, a sidebar, and paginated results. A first pass might put everything in one Redux store: `products`, `isFilterSidebarOpen`, `selectedCategory`, `currentPage`, `isLoading`. It works, but every piece behaves differently under the hood, and the store hides that.

Split by category instead:

- **`isFilterSidebarOpen`** — local component state. Nothing outside that UI region cares.
- **`selectedCategory` and `currentPage`** — URL state, as query params (`?category=shoes&page=2`). A user refreshing, sharing a link, or hitting back should land on the same filtered, paginated view — that only happens if it lives in the URL.
- **`products`** — server cache state, owned by a query hook keyed on `category` and `page`. When the category changes, the hook fetches the new page; the library handles loading/error state and caches earlier pages so paging back doesn't refetch.
- **A cart item count shown in the header** — shared UI state, read by the header (far from the listing page) and written by an "add to cart" button on each product card. Context fits here since it changes rarely enough that its whole-subtree re-render cost is a non-issue.

Four kinds of state, four different mechanisms, none fighting for ownership. Categorizing state up front is what makes each individual choice easy.
