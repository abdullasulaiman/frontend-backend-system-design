Ask a room of frontend engineers what "system design" means and half will describe drawing boxes for a load balancer and a database. That's backend system design. Frontend system design is a different discipline entirely, and it's the subject of this whole course: how do you architect a client application — its rendering strategy, its data flow, its state, its failure modes — so that it stays fast, correct, and maintainable as the product, the team, and the user base all grow.

This distinction matters for two reasons. First, if you're interviewing for a senior or staff frontend role, more and more companies now run a dedicated frontend system design round, and it's graded on criteria that a generic "design a URL shortener" answer won't satisfy. Second, and more importantly, it's a real skill you use on the job every time you decide how a feature should fetch its data, whether a page should render on the server, or how a client should behave when the network drops mid-request.

## What frontend system design actually covers

Think of it as everything between "the API exists" and "the user successfully sees and interacts with the right thing on screen." That includes:

- **Rendering strategy** — client-side rendering, server-side rendering, static generation, or some hybrid (streaming SSR, islands, partial hydration), and which parts of a page need which strategy.
- **State management** — separating server-derived data (cached, revalidated, potentially stale) from local UI state (a modal being open, a form's draft value), and choosing tools that match each kind.
- **API shape** — what the client asks for and how: REST vs. GraphQL vs. RPC-style endpoints, how much aggregation happens server-side vs. client-side, pagination and batching strategy.
- **Performance** — what loads first, what's deferred, what's code-split, and what budget (in milliseconds or kilobytes) each piece is held to.
- **Client-side reliability** — what happens on a flaky connection, a slow API, a partial failure, or a stale cache; how errors are surfaced and recovered from without losing user input.

None of this is about backend infrastructure, and none of it is about choosing a font size. It's the architecture layer that sits between those two things.

## Contrast with backend system design

Backend system design centers on data: how it's stored, replicated, partitioned, and served reliably to many clients at once. A backend design interview asks about things like consistency models, sharding, and queueing — problems that exist because a service has to handle concurrent access to shared state across many machines.

Frontend system design has almost none of that. There's exactly one client per session, running on hardware and a network you don't control, and the "distributed systems" problem you actually face is different in kind: keeping a local cache in sync with a server that other users are also mutating, recovering gracefully when a request fails partway through, and doing meaningful work within a UI thread's frame budget instead of across a fleet of servers.

Where the two disciplines connect is at the API boundary. A frontend engineer designing how a page fetches data needs to know enough about the backend's data model to shape a sane request (don't ask for a full user graph to render a username), but the actual work — normalizing that data into a store, deciding when to refetch it, deciding what renders before it arrives — is frontend system design, not backend.

## Contrast with UI/visual design

The other line people blur is between frontend system design and UI/visual design — typography, spacing, color, interaction micro-details. That's a real and valuable skill, but it's largely orthogonal to this course.

A component can be visually flawless and architecturally broken: a beautifully styled comment thread that re-fetches its entire dataset on every keystroke in the reply box, or a pixel-perfect dashboard that blocks the whole page behind one slow, unbatched request. Conversely, a component can look plain but be architecturally sound: it fetches once, caches correctly, degrades gracefully offline, and only re-renders the parts of the tree that actually changed.

Interviewers treat frontend system design as a distinct skill precisely because these two things don't correlate. Someone can nail the visual craft and never have thought about cache invalidation, or vice versa. The system design round is checking for the architectural half specifically.

## A worked example: the same feature, two very different designs

Say the feature is a product detail page for an e-commerce site: title, images, price, stock status, and a "reviews" section below the fold.

A design that ignores frontend system design might: fetch everything — product data and all reviews — in one client-side request after the page mounts, render nothing until it resolves, store reviews in the same component state as the add-to-cart button, and have no plan for what happens if the request times out.

A design that applies it deliberately might: server-render the product title, price, and images so they're visible immediately (this is the content that matters for both users and SEO), defer the reviews section to a separate, lazily-fetched request that loads once it scrolls into view, keep "is this in the cart" as local UI state entirely separate from the server-fetched product data, and show a retry affordance scoped to just the reviews section if that particular fetch fails — without taking down the rest of the page.

Same feature, same visual mockup even — but one version is resilient to slow reviews APIs and one isn't. That's the difference frontend system design is concerned with.

<Callout type="warning">
  A common mistake in interviews (and in real codebases) is treating "frontend system design" as "draw the component tree." A component hierarchy is necessary but not sufficient — it says nothing about *when* data is fetched, *where* it's cached, *what* renders while it's loading, or *how* the page behaves when a request fails. If your design doesn't address data flow and failure modes, you've only done half the job.
</Callout>

## Why this is expected at senior and staff level

Junior and mid-level frontend work is mostly implementation: given a design and an API, build the component. Senior and staff engineers are expected to make (and defend) the decisions that junior engineers implement: should this route be server-rendered, what's the caching strategy for this data, is this state local or global, what's the fallback when the network is unreliable.

These decisions compound. A rendering strategy chosen for one page shapes how every subsequent page in that app gets built. A state management approach picked early determines how painful it is to add the next ten features. Getting these choices right — and being able to articulate the trade-offs out loud — is what separates "can build a screen" from "can be trusted to architect a product." That's the skill this course builds, one lesson at a time; see [How to Use This Course](/concepts/how-to-use-this-course) for how the lessons and case studies fit together, and [The Role of Frontend System Design in Modern Apps](/concepts/role-of-frontend-system-design-in-modern-apps) for why this discipline has become unavoidable as apps have grown.
