You've now covered a lot of ground: nonfunctional requirements, rendering and state fundamentals, performance budgets, API architecture, design patterns, security, and a six-step interview framework. It's easy to leave a course like this with a pile of disconnected facts — one module's content doesn't obviously talk to another's. This lesson is about collapsing that pile into one mental model, so that in an interview you're not mentally flipping through a table of contents, you're reasoning from a single, coherent picture.

That matters because frontend system design interviews reward *connected* thinking. An interviewer who hears you justify a rendering choice by pointing back to a latency requirement you clarified five minutes earlier is seeing something more convincing than a candidate who lists "SSR, code splitting, CDN caching" as disconnected facts. The goal of this closing lesson is to make those connections explicit, then hand you a checklist you can actually run through under pressure.

## The throughline: requirements drive architecture, architecture creates trade-offs

Every module in this course sits on one causal chain. Nonfunctional requirements (module: Nonfunctional Requirements) are not a box-ticking exercise before the "real" design work — they're the constraint set that makes some architectures correct and others wrong for this specific problem. A dashboard with a 200ms interaction budget and mostly-online users has different right answers than an offline-first field app syncing over unreliable cellular connections, even if both are "a form that saves data."

Once requirements are pinned down, the fundamentals (module: Fundamentals) — how rendering happens, where state lives, how the DOM gets updated — are what you're actually deciding on. Rendering strategy (client-rendered, server-rendered, statically generated, or some hybrid) and state architecture (local vs. lifted vs. global, client vs. server state) are the two decisions that most of your other choices hang off. Get these wrong for the requirements and no amount of later optimization saves you; get them right and a lot of performance work becomes unnecessary because you avoided creating the problem in the first place.

From there, performance techniques (module: Performance & Optimization), API design (module: API Architecture Styles, Protocols & Data Formats), UI/data patterns (module: Design Patterns & Architectures), and security practices (module: Security) are best understood not as a checklist of "good practices" but as a toolbox of levers. Each lever has a cost. Prefetching improves perceived speed but spends bandwidth and can waste server work on data nobody views. A normalized client cache keeps data consistent across screens but adds complexity that a page with one data source doesn't need. Optimistic UI updates make an app feel instant but require a rollback path when the server disagrees. None of these are "always do this" — they're "given these requirements, this lever is worth pulling, and here's what it costs."

## The six-step framework is how you execute the throughline under a clock

Understanding the throughline conceptually is different from being able to produce it live, in order, while someone watches and a timer runs. That's what the six-step framework from **A Framework for Frontend System Design Interviews** (module: Design Framework) is for — it's not new content, it's a sequencing tool for everything above:

1. **Clarify requirements and scope** — pin down the nonfunctional requirements before designing anything.
2. **Estimate scale and data** — turn vague scale ("lots of users") into numbers that constrain your choices (requests per second, payload sizes, concurrent connections).
3. **Decompose into components** — break the UI and responsibilities into pieces you can reason about independently.
4. **Design data flow and the API** — decide what data moves between client and server, in what shape, over what protocol.
5. **Choose rendering and state architecture** — the fundamentals, now grounded in steps 1-4 instead of guessed at.
6. **Evaluate performance, accessibility, security, and trade-offs** — pull the levers that matter for this specific problem and say out loud what you're giving up.

Notice the order matches the throughline: requirements first, fundamentals in the middle, levers last. That's not a coincidence — the six steps are the throughline turned into a procedure with time budgets attached, so that a concept you understand doesn't get stranded as something you forget to mention when the clock is running.

## A compact mental model to carry forward

If you remember nothing else from this course, remember this shape: **requirements constrain fundamentals; fundamentals enable or foreclose levers; levers cost something; naming the cost is the trade-off discussion.** Every module you've read is an elaboration of one node in that chain. When you're stuck mid-interview, you can always ask yourself "which node am I on, and what does the previous node tell me?" — it's a reliable way to get unstuck without needing to recall a specific fact.

## Worked example: applying the model to a "notifications feed" in 90 seconds

Say an interviewer asks you to design a notifications feed (new likes, comments, follows) shown in a dropdown. Running the model quickly: nonfunctional requirements matter first — is this near-real-time (seconds) or fine on a 30-second poll? Say the interviewer wants near-real-time. That single requirement already answers a fundamentals question: polling every 30 seconds is out, so you're choosing between long-polling, SSE, or WebSockets for the data flow (API design), and the state architecture needs a client-side store that can merge server-pushed updates into whatever's already rendered without duplicating entries. Performance follows: you don't want an unread-count badge triggering a full feed re-render, so that counter should be state that's separate from the list itself. Security follows too: the push channel needs the same auth as the REST API, and you must not leak notifications meant for other users through it. Trade-off to state out loud: WebSockets give you the lowest latency but cost more infrastructure (persistent connections, reconnect logic) than SSE, which is one-directional but simpler to operate — for a notifications feed, SSE is probably enough since the client never needs to push anything back over that channel.

That's the whole model exercised on a problem you've never seen before, in under two minutes of thinking. That's the skill this course has been building.

<Callout type="warning">
  The most common failure mode at this stage isn't forgetting a concept — it's treating the concepts as a checklist to recite rather than a chain to reason through. Saying "I'd use code splitting, a CDN, and lazy loading" without connecting each one to a requirement you established earlier sounds like a memorized list, not judgment. If you can't say *why* a lever matters for *this* problem's numbers, don't reach for it yet — go back one node in the chain instead.
</Callout>

## Final pre-interview checklist

Run through this before any mock or real interview, and during the interview itself as a running order:

- **Clarify requirements**: scale, latency/perf budget, offline support, device mix, accessibility bar.
- **Estimate scale**: rough numbers for users, request rate, payload size — even a napkin estimate beats none.
- **Decompose components**: name the major UI pieces and their responsibilities before designing internals.
- **Design data flow and API**: what moves between client and server, in what shape, over what protocol, and why.
- **Pick rendering and state architecture**: justify the choice against the requirements you clarified, not by default habit.
- **Address performance, accessibility, and security**: name the specific levers relevant to this problem, not a generic list.
- **State trade-offs explicitly**: for every major choice, say what you're giving up and why it's an acceptable cost here.
