Imagine you've just finished a component library for a checkout flow. It ships to the US, then someone asks for a German version, and the "Add to cart" button's text now runs long enough to wrap onto two lines and break the layout. Then someone asks for Arabic, and the whole page needs to read right-to-left, including the icons showing "next" and "back." Then someone asks for Japan, and your date formatter prints `12/25/2026` when it should print `2026年12月25日`. None of these are bugs in the traditional sense — they're the cost of not treating internationalization as a requirement from the start.

This is why "does this need to support multiple locales?" belongs in the same requirements-gathering pass as performance targets (see [Performance as a Requirement](/lesson/performance-as-a-requirement)) and accessibility scope (see [Accessibility & Compatibility](/lesson/accessibility-and-compatibility)). It's cheap to design for up front and expensive to retrofit, because it touches component APIs, data models, and layout assumptions all at once.

## Internationalization vs. localization

These two terms get used interchangeably in casual conversation, but they describe different work done by different people at different times.

**Internationalization (i18n)** is engineering work: structuring your app so it *can* be adapted to any locale without code changes. That means extracting every user-facing string instead of hardcoding it, using formatting APIs instead of string concatenation for dates/numbers/currency, building layouts that tolerate variable text length and both text directions, and setting up a pipeline to load locale-specific data. You do i18n once, as part of the architecture.

**Localization (l10n)** is content work: producing the actual translated strings, locale-specific formats, and cultural adaptations (currency symbols, date conventions, even imagery or color choices) for a specific target locale. You do l10n once *per locale* — and it can happen long after the initial build, often by a translation team that never touches your codebase.

The numbers in each term's abbreviation ("i18n" = i + 18 letters + n, "l10n" = l + 10 letters + n) are just a convention for shortening long words — worth knowing so it doesn't look like a typo the first time you see it.

The practical implication: if you skip i18n, l10n becomes a fight against your own architecture. A translator handing you a Spanish string file can't fix a component that concatenates `"Showing " + count + " results"` — that pattern breaks in languages with different word order or pluralization rules, and no amount of translation effort fixes a code-level assumption.

## Why clarify this as a nonfunctional requirement

Like performance or accessibility, i18n scope changes what "correct" means for the same feature, without changing what the feature does. A product card built for English-only, LTR-only usage isn't "the same component plus translations later" — it's a different component if it needs text expansion and RTL support, because those constraints shape the CSS, the markup structure, and the props the component accepts.

In an interview or a real design doc, get answers to a few questions early: **Which locales, and how many?** A right-to-left language or one with unusual pluralization rules (Russian has three plural forms; Arabic has six) is a bigger lift than adding a second similar European language. **Is RTL in scope?** Worth calling out separately from "which languages," since it's a layout concern, not just a string concern. **Are translations ready at launch, or does the UI need placeholder text with real translations arriving later?** This affects whether you can hardcode any fallback assumptions. **Who owns the translations?** An external vendor delivering files on their own schedule needs a stable key/value contract you don't casually rename.

## Text expansion and layout

Translated UI strings are rarely the same length as the source language. English strings often *grow* by 20-35% in French or German, and can grow more for short UI labels ("Save" → "Enregistrer"). CJK languages (Chinese, Japanese, Korean) usually *shrink* character count but need more vertical space per character and different line-breaking rules, since spaces don't separate words.

The fix is architectural, not cosmetic: avoid fixed-width buttons and labels, prefer `min-width` over `width`, let flex/grid containers absorb extra length, and test with a deliberately verbose fake locale (a "pseudo-locale" that wraps every string in extra characters, like `[!!! Ѕäνé ¡¡¡]`, catches overflow bugs before real translations even exist).

### Right-to-left (RTL) layouts

Arabic, Hebrew, and a handful of other languages read right-to-left, and that's a document-direction concern, not a per-string concern. Setting `dir="rtl"` on the `<html>` root flips how the browser lays out inline and block content, but it doesn't automatically fix everything:

- Directional icons (arrows, chevrons "next/back") need to be mirrored — an arrow pointing "forward" in LTR should point the other way in RTL.
- Spacing and alignment written as `margin-left`/`text-align: left` don't flip automatically. CSS logical properties (`margin-inline-start`, `text-align: start`) flip correctly under `dir="rtl"` without extra work; the old physical properties do not.
- Some things should *not* mirror — a phone number, a code snippet, or a left-to-right logo stays LTR embedded inside an RTL page (using `dir="ltr"` on that specific element).

## Formatting dates, numbers, and currency

This is the category most likely to bite silently — a hand-rolled formatter can look correct in every locale you tested and wrong in every locale you didn't. Locale-aware formatting differs in decimal separators (1,234.56 vs 1.234,56), digit grouping, calendar systems, 12h vs 24h time, and currency symbol placement (`$10` vs `10 €`).

The browser-native `Intl` API handles this with no library dependency: `Intl.NumberFormat` for numbers and currency, `Intl.DateTimeFormat` for dates and times, and `Intl.PluralRules` for pluralization logic that varies far more across languages than English's simple singular/plural split. These take a locale string (`'de-DE'`, `'ar-EG'`) and produce correct output without you needing to know each locale's rules yourself.

<Callout type="warning">
  A common pitfall: building sentences by concatenating translated pieces, like `translate('welcome_prefix') + userName + translate('welcome_suffix')`. This assumes every language shares English's word order and grammar, which is false — some languages put the name before the greeting, some inflect the surrounding words based on gender or number. Use a message-format approach instead, where the whole sentence is one translatable template with a named placeholder (`"{name} 님, 환영합니다"` in Korean vs `"Welcome, {name}"` in English), so translators control full sentence structure rather than being handed disconnected fragments.
</Callout>

## Loading locale bundles without hurting performance

Translation data adds up — a large app can have hundreds of kilobytes of strings per locale, multiplied by the number of supported locales. Two mistakes are easy to make here: bundling every locale into the main JavaScript chunk (so a Japanese user downloads French and German strings they'll never use), and blocking first paint on a network fetch for locale data before rendering anything.

The pattern that avoids both: detect or read the active locale early (from a URL segment, a cookie, or `Accept-Language`), then dynamically import only that locale's bundle as a separate chunk, in parallel with your app's critical rendering work rather than blocking it. This keeps the technique in the same family as the code-splitting and lazy-loading strategies covered later in the Performance & Optimization module — locale data is just another kind of "not-needed-immediately" payload.

## Worked example: a pricing card component

Say you're designing a `<PricingCard>` component that shows a plan name, a price, and a "Subscribe" button, and the requirement says "must support English, German, and Arabic at launch, with more locales added later."

That single sentence should change several decisions before you write any CSS:

1. **String storage**: every visible string (`planName`, button label, a "billed monthly" caption) is a translation key resolved through a formatting function, never a literal in the JSX.
2. **Price formatting**: `Intl.NumberFormat(locale, { style: 'currency', currency })` produces `"$19.99"`, `"19,99 €"`, or `"١٩٫٩٩ د.إ."` correctly, instead of a hand-built string that assumes a `$` prefix.
3. **Layout**: the card's width isn't hardcoded to fit the English button label ("Subscribe") — German's "Jetzt abonnieren" is nearly twice as long, so the button needs `min-width` and wrapping tolerance, not a fixed box.
4. **Direction**: for Arabic, the card's internal flex layout (price on one side, badge on the other) needs to flip via `dir="rtl"` and logical CSS properties, not a hardcoded left/right arrangement.
5. **Loading**: the German and Arabic string bundles load only for users in those locales, as separate chunks fetched alongside the initial render — not bundled for everyone.

Design the component this way once, and adding a fourth locale later is a content task (translate the strings, supply the currency code) rather than an engineering task (rewrite the layout).

## How this shapes later design decisions

The component and data-model choices you make because of i18n requirements echo through the rest of a frontend system design: data models need a locale-agnostic representation of dates/numbers (store as UTC timestamps or ISO strings, format at render time, not the reverse), component APIs need to accept translated strings or keys as props rather than hardcoded text, and layout primitives need flexible, direction-aware CSS from day one. Skip this early and you retrofit all three later, usually under deadline pressure from a real customer request. This is also why maintainability matters here — see [Maintainability as a Requirement](/lesson/maintainability-as-a-requirement) — a string-key contract that's easy for translators to work against without breaking your components is a long-term design investment, not a one-time task.
