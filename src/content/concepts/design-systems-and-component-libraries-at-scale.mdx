Picture a company with 40 product teams, each shipping its own React app. Team A's buttons have 6px corners and a slightly different blue than team B's. One team's date picker doesn't work with a screen reader; another team's modal traps focus incorrectly. A rebrand rolls out over eight months because "update the primary color" means editing the same CSS rule in 40 different repos. None of this is anyone's fault individually — it's what happens when every team solves the same UI problems independently, at a different level of care.

A design system is the fix: a shared, versioned source of truth for how things look and behave, packaged as tokens, components, and documentation every product team consumes instead of reinventing. Done well, "does this look right" and "is this accessible" stop being per-team judgment calls and become defaults. Done poorly, it's a bottleneck teams quietly bypass. This lesson covers the architecture that makes the difference.

## Design tokens: the single source of truth

A design token is a named, platform-agnostic value for a visual decision — `color.brand.primary`, `space.md`, `font.size.body`, `radius.card`. Tokens replace hardcoded values (`#3366FF`, `16px`) with a semantic name defined once and consumed everywhere — the layer where design decisions get made exactly once and then distributed.

- **Design tools export tokens.** A tool like Figma can export color/spacing/type styles as structured data, which a build step turns into CSS custom properties, a JS/TS object, or platform-specific formats — one source feeding every platform.
- **Rebranding becomes a token edit, not a find-and-replace.** Change `color.brand.primary` in one place, rebuild, and every consuming app updates on its next release.
- **Themes are alternate token sets.** Light and dark mode are two value sets for the same token names; a component reading `color.surface.default` never needs to know which theme is active.
- **Tokens have tiers.** Raw tokens (`blue.500 = #3366FF`) feed semantic tokens (`color.brand.primary = blue.500`), which feed component tokens (`button.background.primary = color.brand.primary`). This indirection lets you restyle one component without touching global values, and rebrand globally without touching components.

## Layered component architecture

Trying to ship one flat bucket of "components" breaks down fast — a `Button` and a full `CheckoutSummary` don't belong at the same level of abstraction, reuse, or stability guarantee. Most mature systems settle on three layers.

**Primitives** are the smallest, most generic building blocks: `Button`, `Input`, `Checkbox`, `Icon`, `Text`. Unopinionated about business logic, styled purely from tokens, and where accessibility and theming get implemented once, correctly. Primitives change rarely — everything else depends on them.

**Composed components** combine primitives into something with a specific, reusable shape: a `FormField` (label + input + error text), a `Card`, a `Modal`, a `DataTable`. These encode common layout and interaction patterns so teams don't re-derive "how do I lay out a labeled form field with an error state" every time.

**Patterns** are larger, often product-specific assemblies built from composed components — a `SearchWithFilters` panel, an `OnboardingWizard`. Patterns may live in the shared library if several teams need the exact same one, or in a product's own codebase, built *from* the shared primitives and composed components. That's the right boundary: the design system owns primitives and composed components; products own patterns.

This layering also tells you where a fix belongs. A focus-ring color bug is a token fix. A "screen reader doesn't announce this error" bug is a primitive fix. "Our checkout flow needs a different layout" is a pattern-level decision individual teams should be free to make on top of the shared layers — this is where central control should stop.

### Theming and accessibility, built in once

Accessibility retrofitted per-app never scales — 40 teams each remembering `aria-live` regions, focus trapping, and keyboard nav is a bet you'll lose. Baking these into the primitive layer means every `Button` has a correct focus state and `aria-*` attributes by construction, every `Modal` traps and restores focus and closes on `Escape` without the consumer writing any of that, and color tokens are pre-checked for contrast (e.g. WCAG AA) in every theme so `color.text.primary` on `color.surface.default` can't silently fail. Theming — light/dark, brand variants, high-contrast — becomes a token swap instead of a per-component reimplementation.

## Versioning and distribution

A design system is code that other teams' code depends on, which means it lives and dies by its versioning discipline.

**Semver is the contract.** Patch releases are bug fixes with no API change. Minor releases add things — new components, new optional props — without breaking existing usage. Major releases contain breaking changes: a renamed prop, a removed component, a changed default. Teams should be able to trust that `^2.3.0` in their `package.json` is safe to auto-update; that trust evaporates the first time a "minor" release breaks a build.

**Distribution is usually one of two shapes.** A monorepo (Nx, Turborepo) keeps the system and consuming apps in one repository, so a shared-component change and its usages land in the same review — common when teams share a release cadence. Alternatively, the system ships as a separately published package, versioned and released independently, decoupling cadence but requiring consumers to actively pull upgrades. Larger orgs with many independent teams usually prefer published packages so a slow-moving team isn't forced onto every release immediately.

**Rolling out breaking changes** to dozens of consumers needs a process, not just a version bump: ship the new behavior alongside the old one in a minor release with the old path marked deprecated (dev console warning, doc callout); give teams a real migration window — months, not days — with a codemod for mechanical changes so nobody hand-edits hundreds of call sites; track which apps are still on the deprecated path; then remove it in the next major version once adoption data shows it's safe.

<Callout type="warning">
  A common and expensive mistake: shipping a visual or behavioral change as a "patch" because "it's just a style tweak." A default-padding or focus-ring tweak is invisible in a code diff but can break pixel-sensitive layouts or visual regression tests across every consuming app at once, with no warning. If a change alters anything a consumer could observe, treat it as at least a minor release, and reserve patches for fixes that restore previously-intended behavior.
</Callout>

## Documentation as the product

A component that isn't documented gets used incorrectly, or gets reimplemented from scratch because nobody could figure out the "real" one. Living documentation — a browsable catalog, Storybook-style, showing every component in every variant/state with copy-pasteable usage code, do/don't guidance, and accessibility notes — is what makes a design system self-service instead of a support queue.

Good docs answer three questions per component: what is this for (and what isn't — "use `Modal` for blocking dialogs, `Toast` for non-blocking ones"), how do I use it correctly (props, variants, a snippet), and what does it guarantee (accessibility, responsiveness, theming). That third answer is what tells teams what they get "for free" versus what they still have to build themselves.

## Governance: avoiding both fragmentation and gridlock

Someone has to decide what goes into the shared library, and how. Two failure modes sit on either side of a healthy governance model. **Too centralized**: every new component or token needs sign-off from a small design-system team that becomes a bottleneck, so product teams under deadline pressure build their own one-off `Button` instead of waiting — recreating the exact fragmentation the system was meant to prevent, just one layer deeper. **Too decentralized**: any team can add anything with no review, so quality erodes, accessibility regressions slip in, and the "shared" library becomes an uncurated grab-bag nobody trusts.

The common working model is a small owning team plus an RFC-style contribution process: a team that needs a new pattern proposes it (often prototyping it in their own app first), the design-system team reviews for consistency/accessibility/API shape, and if it's broadly useful it graduates into the shared library with the owning team taking on its maintenance. That keeps the system growing from real product needs while keeping one team accountable for the quality bar.

## Worked example: rebranding a checkout button

Say the company decides the primary brand color changes from blue to teal, and product wants it live everywhere within two weeks. Without a design system, that means finding every hardcoded `#3366FF` (plus its shadow, hover, and disabled variants) across 40 repos, updating each one, and hoping nobody missed a spot or copy-pasted a subtly different shade eighteen months ago.

With a design system: the teal token export updates `color.brand.primary` and its derived tokens (`button.background.primary`, `link.color`, `focus.ring`) in the tokens package, which gets a minor version bump (values changed, no API changed) and is published. Each app bumps its `@company/tokens` dependency — often automatically, since minor bumps fall within its existing `^1.x` range — and every button, link, and focus ring across all 40 apps is teal on the next deploy, with zero code changes anywhere. The two-week deadline is met because the actual work was one token change, not 40 app changes.

## Tying it back to maintainability and the autonomy trade-off

Every piece here — tokens, layering, versioning, documentation, governance — serves two goals: **consistency** (one coherent product experience instead of 40 slightly different ones) and **maintainability** (a fix or rebrand happens once, centrally, instead of N times independently, with N chances to get it wrong).

The trade-off is real: every decision the system makes centrally is a decision an individual team no longer makes for itself. A team needing an unusual button variant either petitions the system team (slow), builds it locally as a pattern on shared primitives (usually fine), or forks the primitive (defeats the purpose). Getting the layering right — primitives and composed components centralized, patterns left to product teams — is how you keep most of the consistency benefit while leaving teams room to move fast on what's genuinely theirs to decide.
