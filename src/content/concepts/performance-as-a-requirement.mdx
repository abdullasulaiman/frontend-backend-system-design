Ask "does this need to be fast?" in a design interview and everyone says yes. That answer is useless — it doesn't tell you whether to reach for server-side rendering, whether a 200KB dependency is a problem, or whether you can afford a loading spinner. Performance only becomes a design input once it's a number: a metric, a target, and the conditions it's measured under. This lesson is about turning "fast" into requirements you can actually design against, and setting up the vocabulary the rest of the Performance & Optimization module builds on.

## Why "make it fast" fails as a requirement

A functional requirement tells you what the system does ("users can filter the product list by price"). A nonfunctional requirement (NFR) tells you the quality bar the system must hit while doing it. Performance is one of the most common NFRs raised in a frontend design interview, and also one of the most commonly left vague.

The problem with "make it fast" is that it can't be checked and it can't drive a decision. If someone asks "should this page render on the server or the client?", the answer depends entirely on what target you're hitting and under what conditions — a page that only needs to feel responsive on a fast corporate laptop has very different constraints than one that needs to load in a few seconds on a mid-range phone over a spotty mobile network. Without a number, every architecture choice becomes a guess.

Treat performance the way you'd treat any other measurable NFR (uptime, error rate): write it down as a target, attach a metric and a condition, and let that target constrain the choices you make later.

## Three categories of performance NFRs

Performance isn't one thing. A page can load quickly but feel sluggish once interactive; it can respond to clicks instantly but take a long time to become visible in the first place. Splitting performance into three categories keeps requirements precise and stops "performance" from becoming a catch-all.

### Load performance

How long it takes for the page to go from "nothing" to "usable" on first visit. This covers metrics like Largest Contentful Paint (how long until the main content is visible) and Time to Interactive (how long until the page actually responds to input). Load performance is dominated by network and parse/compile cost: bundle size, number of round trips, server response time, and how much JavaScript has to run before the page is usable.

### Runtime and interaction performance

How the app behaves once it's already loaded and the user is actively using it: does a click respond immediately, does scrolling stay smooth, does typing in a search box keep up with keystrokes. This is governed by main-thread work — expensive re-renders, layout thrashing, large synchronous computations — rather than network cost. A page can have great load performance and still feel terrible if every click blocks the main thread for half a second.

### Perceived performance

How fast the experience *feels*, which isn't always the same as what the raw timing numbers say. Two pages with an identical 3-second load time feel different if one shows a blank white screen the whole time and the other shows a skeleton layout and a progress indicator within 200ms. Perceived performance requirements — show a skeleton, show optimistic UI, show a spinner after some threshold — are legitimate design requirements even when they don't change the underlying metric.

## Phrasing performance requirements concretely

A well-phrased performance requirement has three parts: a metric, a target value, and the condition it's measured under.

- **Metric** — what's being measured (Largest Contentful Paint, Time to Interactive, input latency, frame rate).
- **Target** — a specific number, usually stated at a percentile rather than an average, since averages hide your worst users. "p75 under 2.5 seconds" tells you 75% of visits meet the bar; a plain average can look fine while a quarter of your users have a broken experience.
- **Condition** — the device and network the target applies to. "Fast" on a developer's laptop over office Wi-Fi and "fast" on a five-year-old Android phone over throttled 4G are different engineering problems.

Compare the two requirement statements below:

- Vague: "The dashboard should load quickly."
- Concrete: "Largest Contentful Paint under 2.5 seconds at p75, tested on a mid-tier Android device over a throttled 4G connection; interactions (filter, sort) respond within 100ms on the same device."

The second statement is checkable in a performance budget, can be tested in CI, and — critically for a design interview — tells you what to prioritize. If the number is 2.5 seconds on a mid-tier phone, you probably can't ship an unbundled client-heavy SPA with a 2MB initial payload; you're leaning toward server rendering, aggressive code splitting, or both.

## Worked example: a product listing page

Say you're asked to design a product listing page for an e-commerce site. Instead of accepting "it should be fast," push for numbers:

- **Load**: LCP under 2 seconds at p75 on a mid-tier phone over 4G, since a large share of traffic is mobile shoppers who bounce quickly on slow pages.
- **Runtime/interaction**: applying a filter or sorting the list should update the visible results within 100ms of the tap, even with a few thousand items in the list.
- **Perceived**: while a filter request is in flight, show the existing results dimmed rather than a blank loading state, so the page never looks broken.

Those three targets now drive real decisions. The load target pushes you toward server-rendering the initial listing (so the browser doesn't have to fetch data, then fetch JS, then render) and toward pagination or virtualization instead of shipping every product up front. The interaction target pushes you toward client-side filtering of an already-fetched page of results rather than a network round trip per filter click, and toward virtualizing the list so re-renders stay cheap regardless of item count. The perceived-performance target pushes you toward keeping stale results visible during a refetch instead of unmounting them. None of these decisions are obvious from "make it fast" alone — they fall out of the specific numbers.

<Callout type="warning">
  A common mistake: stating a performance target as a single average number with no condition ("average load time is 1.2 seconds"). Averages are dragged down toward your best-connected users and hide the tail — the p90 or p99 user on a slow device might be waiting 8 seconds while the average looks healthy. Always state targets at a percentile (p75 is a common default) and name the device/network condition, otherwise the "requirement" can be technically true while a large chunk of users have a broken experience.
</Callout>

## Where this leads

Once performance targets exist as numbers, they stop being an afterthought and start shaping the architecture conversation from the beginning — rendering strategy, bundling, caching, and virtualization choices covered later in Performance & Optimization all trace back to a load, runtime, or perceived-performance target set here. The other Nonfunctional Requirements lessons follow the same pattern: accessibility-and-compatibility and localization-and-internationalization both need to be scoped as concrete, checkable requirements before they can influence a design, rather than left as vague goals.
