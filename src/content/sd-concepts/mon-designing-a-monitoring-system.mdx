You've now seen why monitoring matters and how metrics get from a process to storage — push vs. pull, and the shape of a time-series database. This lesson puts the whole system together: the interview question "design a monitoring system for a few thousand hosts" isn't really about picking push or pull, it's about tracing data from a running process all the way to an on-call engineer's phone, and defending every hop under load and under failure.

That end-to-end view is what interviewers actually probe. It's easy to say "collect metrics, store them, alert on them." It's harder to say what happens when the collector falls behind, when a single bad deploy makes a metric's cardinality explode, or when the monitoring system itself needs monitoring.

## Requirements first

Before drawing boxes, pin down scale and behavior:

- **Scale**: how many hosts/services report metrics, how many distinct metrics per host, and how often (typical: 10-60 second intervals).
- **Latency**: how fresh does a metric need to be before an alert fires? Seconds for a paging alert on error rate, minutes are fine for a capacity-planning dashboard.
- **Durability vs. cost**: losing a few seconds of metrics during a blip is usually acceptable; losing an alert that should have fired is not. Storage cost matters because retention windows are long (weeks to years) while raw data volume is enormous.
- **Query patterns**: dashboards do wide time-range scans over few series; alert rules do narrow, frequent scans over many series. These have different performance profiles and often end up served differently.

## The five-stage pipeline

Break the system into stages that can each be reasoned about, scaled, and failed independently.

### 1. Collection (agents)

A lightweight agent runs alongside each monitored process (as a sidecar, a host-level daemon, or an in-process library). It reads counters, gauges, and histograms — request counts, latencies, queue depth, CPU — and holds them in memory between flushes.

The agent should do local pre-aggregation: instead of shipping every individual request latency sample, it maintains a histogram bucket count and ships the buckets. This is the single biggest lever for controlling downstream volume, because it turns "N samples per second" into "a fixed number of bucket counters per flush interval," independent of traffic.

### 2. Ingestion

Agents forward batches (push) — or a collector scrapes them (pull) — into an ingestion tier. This tier's job is narrow: validate, briefly buffer, and hand data to storage as fast as storage can absorb it. Put a message queue or write-ahead buffer here so a storage hiccup doesn't lose data or block agents; it just adds a few seconds of lag.

Ingestion is also where you should reject or drop pathological input — a client sending a metric with a `user_id` label attached, for instance, before it multiplies your series count by your user count.

### 3. Storage (time-series database)

Data lands in a time-series database, sharded by metric/series and partitioned by time. Two design choices dominate: how long full-resolution data lives before being downsampled, and how writes are batched into the underlying storage engine (almost always append-only, compacted files rather than random-write B-trees, because writes are overwhelmingly sequential-in-time).

### 4. Alerting

An alerting service periodically evaluates rules ("error rate over 5xx > 2% for 5 minutes") against storage — never against the raw ingestion stream directly. Rules need their own retry and dedup logic: if the query backend is slow for one evaluation cycle, you want the next cycle to catch up, not silently skip a firing condition.

### 5. Visualization

Dashboards run ad-hoc and saved queries against storage, usually through a caching layer since many people load the same dashboard querying the same recent time range repeatedly.

## Availability of the monitoring system itself

The uncomfortable truth about monitoring systems: they need to keep working precisely when the rest of the infrastructure is on fire. That drives a few concrete decisions:

- **Isolate the failure domain.** Don't run the monitoring stack on the same cluster, network segment, or deploy pipeline as the systems it watches. If a bad rollout takes down the primary data center, the monitoring stack in that same data center goes down with it, and you find out about the outage from customers instead of alerts.
- **Fail open on alerting, not silent.** If the alerting service can't evaluate a rule (storage is unreachable), it should raise a meta-alert ("alerting degraded") rather than just skip the cycle quietly.
- **Keep the collection path simple and dependency-light.** The agent itself should have minimal dependencies and degrade gracefully (buffer locally, drop oldest data first) rather than crash the process it's attached to.

<Callout type="warning">
  A common design mistake: routing alert evaluation through the same ingestion buffer or cache that serves live writes, to "save a hop." This couples alerting availability to ingestion availability — exactly the dependency you don't want, because ingestion is usually the first thing to degrade under a traffic spike, which is often exactly when you need alerts to keep firing. Alerting should read from durable, replicated storage (or a dedicated read replica), not the write-path buffer.
</Callout>

## Worked example: sizing the pipeline

Suppose you're monitoring 5,000 hosts, each emitting 200 metrics on a 10-second interval.

- **Ingest rate**: `5,000 hosts x 200 metrics / 10s = 100,000 data points/sec`. At roughly 16 bytes per raw point (timestamp + value + a series ID), that's about 1.6 MB/s of raw ingest, or ~140 GB/day before any aggregation.
- **Series count (cardinality)**: if each metric only varies by host, that's `5,000 x 200 = 1,000,000` distinct series — manageable. If someone adds a `customer_id` label with 50,000 distinct values to even one of those metrics, cardinality jumps by 50,000x for that metric alone, and most time-series databases will choke on the index size long before storage runs out.
- **Retention cost**: keeping 140 GB/day at full resolution for a year is ~51 TB. Downsampling anything older than 7 days from 10-second to 1-minute resolution cuts that by roughly 6x; downsampling anything older than 90 days to 1-hour resolution cuts it another 60x. A tiered retention policy (7 days full-res, 90 days at 1-min, 1+ year at 1-hour) turns an unsustainable 51 TB/year into a few TB.
- **Alert evaluation load**: if you have 2,000 alert rules each querying a 5-minute window every 30 seconds, that's `2,000 / 30s ≈ 67 queries/sec` against storage — small compared to dashboard traffic, but each query must complete well under the 30-second cycle or evaluation starts falling behind.

This is the kind of arithmetic an interviewer wants to see you do out loud: it justifies pre-aggregation at the agent, tiered retention, and cardinality limits as load-bearing design decisions, not just nice-to-haves.

## Putting it together in an interview

When asked to design a monitoring system, a strong structure is: state the scale/latency/retention requirements, draw the five-stage pipeline, then spend most of your remaining time on two things interviewers actually care about — how cardinality and storage volume are kept bounded, and how the system stays up when the thing it's watching doesn't. Naming specific numbers (like the worked example above) shows you're reasoning about capacity, not just naming components.
