The [previous lesson](/system-design/sched-task-scheduler-requirements) settled
what the scheduler needs to do: accept job definitions, run them at the
right time (once or on a recurring schedule), and guarantee each due job
gets executed exactly the number of times it's supposed to, even as workers
crash and restart. None of that is possible without deciding, concretely,
what gets stored and how "it's time to run this" turns into a worker
actually picking it up. Get the data model wrong — say, storing recurring
jobs as a single row with no concept of individual runs — and you can't
tell whether last Tuesday's 2am backup actually succeeded, or retry only
the failed attempt without also re-triggering next Tuesday's. This lesson
builds the entities and the queueing structures that make the rest of the
design (covered in the next lesson) straightforward instead of ad hoc.

## Two entities, not one: job definitions vs. job runs

The single biggest modeling mistake is conflating "the job" with "an
execution of the job." A recurring job (`send_daily_report`, cron
`0 6 * * *`) is a standing definition that produces a new execution every
day; a one-off job (`resize_image_42`) produces exactly one. Both need a
concept of "this specific attempt succeeded, failed, or is still running,"
which the definition alone can't hold without losing history on every run.

**Job definition** — the schedule itself:

- `job_id`, `owner`/`tenant_id`, `handler` (what code/queue/endpoint to
  invoke), `payload` (arguments)
- `schedule`: either a `cron_expr` for recurring jobs or a single
  `run_at` for one-off jobs
- `next_run_at` — the next time this definition should produce a run
  (computed, kept up to date)
- `status`: active, paused, disabled
- `retry_policy`: max attempts, backoff strategy
- `timeout`: how long a single run is allowed before it's considered stuck

**Job run** — one execution attempt:

- `run_id`, `job_id` (foreign key), `attempt_number`
- `scheduled_for` (when it was due), `started_at`, `finished_at`
- `state`: pending, claimed, running, succeeded, failed, dead
- `worker_id` — who currently holds (or last held) this run
- `lease_expires_at` — see the visibility timeout section below
- `idempotency_key` — derived from `job_id` + `scheduled_for` (or a
  caller-supplied key for one-off jobs), so re-delivery never causes
  double execution

Splitting these apart is what lets you answer real questions cleanly:
"show me every failed run for this job in the last 7 days" is a query over
`job_run`, not a scan of side-channel logs; "pause this recurring job
without losing history" is a single `status` flip on `job_definition` that
leaves every past run untouched.

## From "due" to "claimed": the queueing layer

Having the right rows isn't enough — workers need an efficient way to find
"which runs are ready right now" without scanning the whole table, and
exactly one worker needs to win each run. That's the job of the queueing
layer, which sits on top of the data model above.

### Priority queues: order among ready work

Not all ready jobs are equal. A payment-retry job is usually more urgent
than a nightly report regeneration. A **priority queue** orders ready runs
by a priority score (often a combination of an assigned priority tier and
how overdue the job already is, so low-priority work doesn't starve
forever behind an endless stream of high-priority arrivals). Workers pull
from the head of this ordering rather than in arbitrary or strict FIFO
order.

### Delay queues: order among not-yet-ready work

Most runs aren't ready the instant they're created — a job scheduled for
6am tomorrow needs to sit somewhere until then without workers repeatedly
checking it early. A **delay queue** (typically implemented as an index or
min-heap keyed on `next_run_at` / `scheduled_for`) holds not-yet-due work
and moves entries into the ready/priority queue only once their time
arrives. A background sweeper (or the queue's own delayed-delivery feature,
if using something like a message broker with native delay support) polls
this structure on a short interval — a few seconds is typical — and
promotes anything whose time has come.

### Visibility timeouts: surviving a crashed worker

A worker claiming a run has to make it invisible to other workers, or
you'll get duplicate execution the moment two workers grab the same due
job in a race. The standard mechanism is a **visibility timeout** (also
called a lease): claiming a run sets `state = claimed`,
`worker_id = <this worker>`, and `lease_expires_at = now + lease_duration`.
Other workers skip runs whose lease hasn't expired. The worker executing
the job must either finish (and mark it `succeeded`/`failed`) or
periodically renew the lease before it expires (a heartbeat) if the job
runs longer than one lease window. If the worker crashes and neither
happens, the lease simply expires and the run becomes claimable again —
no crash-detection logic needed, just a timestamp comparison.

This is the same mechanism as visibility timeouts in general-purpose
message queues (see the messaging queue module's delivery-semantics
lesson) applied specifically to scheduled work.

## Partitioning the schedule

A single sorted structure for "all due jobs across the whole system"
becomes a lock-contention bottleneck once you have thousands of workers
and millions of jobs — every worker is fighting over the same head of the
same queue. The fix is the same one used throughout this course:
**partition** the due-jobs structure by a shard key (hash of `job_id`, or
`tenant_id` for a multi-tenant system), so each partition has its own
delay queue and priority queue, owned by a subset of workers. A worker
only competes with the other workers assigned to its partition, not the
entire fleet — this is what lets throughput scale roughly linearly with
partition count instead of flattening out as contention grows.

## Worked example: modeling a retrying webhook-delivery job

Say a job definition sends a webhook to a customer's endpoint every time
an internal event fires, with up to 5 retries on failure using exponential
backoff (1min, 2min, 4min, 8min, 16min).

1. Event fires -> a new `job_run` row is inserted: `attempt_number = 1`,
   `scheduled_for = now`, `state = pending`,
   `idempotency_key = event_id` (not `job_id` + timestamp, since this is
   event-triggered rather than cron-triggered).
2. The run enters the priority queue immediately (it's already due) and a
   worker claims it, setting a 30-second lease.
3. The webhook call times out. The worker marks this run `failed` and
   inserts a *new* run row: `attempt_number = 2`,
   `scheduled_for = now + 1min`, `state = pending`. That new row goes into
   the delay queue, not the priority queue, since it isn't due for another
   minute.
4. After 1 minute, the sweeper promotes it to the priority queue; a worker
   claims it; suppose it succeeds this time. `state = succeeded`, and no
   further runs are created for this event.
5. If all 5 attempts fail, the last run is marked `dead` and the job
   definition's dead-letter policy fires (alerting, or writing to a
   dead-letter store for manual inspection) — you never silently drop a
   customer's webhook.

Every attempt is its own row with its own `idempotency_key`, so even if a
worker's success acknowledgment gets lost after the webhook actually fired
and a retry is triggered, the receiving endpoint (if it also checks
idempotency keys, which any well-built webhook consumer should) won't
double-process the event.

<Callout type="warning">
  A common mistake is materializing every future occurrence of a recurring
  job up front — inserting a `job_run` row for every day for the next year
  the moment a daily job is created. This doesn't scale (a handful of
  yearly, hourly, and per-minute jobs across many tenants produces an
  enormous row count for occurrences that may never even happen, since the
  schedule could be edited or paused first) and it doesn't handle daylight
  saving time or calendar edge cases (a "run on the 31st of every month"
  job) cleanly, because you computed all those dates at creation time
  under assumptions that might change. Compute `next_run_at` lazily —
  once, right after the current run completes — and only ever have at most
  one pending future run materialized per job definition at a time.
</Callout>
