Over the last four lessons you picked apart a distributed cache one concern at a time: where it sits relative to the app and the database, how writes get applied, how consistency and invalidation are handled, and how the cache itself is sharded and replicated across nodes. Each of those, on its own, is a clean two-minute answer. What actually gets tested in a system design interview is whether you can wire them together into one request path without contradicting yourself — say "write-behind" in one breath and "strong consistency" in the next, and an interviewer will (rightly) push back.

This lesson is that assembly step. No new mechanism gets introduced here; instead we trace a single read and a single write through the full stack, see exactly where each earlier lesson's decision gets invoked, and work through a sizing example that shows how a bad interaction between eviction and invalidation turns into a production incident.

## The read path, start to finish

Follow a single `GET(key)` issued by an application server:

1. **Routing.** The client library hashes `key` (typically consistent hashing with virtual nodes, from the sharding lesson) to find which cache node owns it. This is a local computation — no network round trip to "find" the shard.
2. **Hit check.** The client asks that node for `key`. If present and unexpired, that's a cache hit — return it. This is the fast path and, in a healthy system, the overwhelming majority of requests.
3. **Miss handling.** On a miss, *who* fills the cache matters. In a cache-aside design, the application itself queries the database, then writes the result back into the cache before returning. In read-through, the cache library does that transparently, so the application only ever talks to the cache. Either way, this is the moment a cold or evicted key gets re-populated.
4. **Backfill and TTL.** The newly written entry gets a TTL (and possibly jitter — see below) so it participates in eviction and expiry the same as everything else on that node.

## The write path, and where invalidation happens

A `PUT(key, value)` follows the same routing step, then diverges based on the write policy chosen earlier in the module:

- **Write-through**: the cache node writes to the database synchronously before acknowledging the client. Simple to reason about, adds write latency.
- **Write-behind**: the cache acknowledges immediately and flushes to the database asynchronously in batches. Faster writes, but a cache-node crash before flush can lose data — which is exactly why this lesson keeps stressing that cache replication is not a substitute for the database being the durable source of truth.
- **Write-around**: the write goes straight to the database and skips the cache; the next read is a deliberate miss that repopulates via the normal read path.

Whichever policy you chose, the write must also settle what happens to *other* copies of that key elsewhere in the system: invalidate the local entry, and if there's an application-tier cache in front of this distributed layer (or multiple regions each with their own cache), broadcast an invalidation message over pub/sub so those copies don't keep serving the old value until their TTL happens to expire.

## Where eviction and sharding quietly interact

Eviction (LRU, LFU, or TTL-based expiry) decides what falls out of a single node when it's full or a key has aged out. Sharding decides which node a key lives on in the first place. They look independent, but a design that ignores their interaction breaks in a specific, predictable way: **hot keys**.

If one key (a viral post, a trending product, a celebrity's profile) gets disproportionate traffic, it lives on exactly one shard under plain consistent hashing — and that shard's memory and CPU absorb all of that key's load while every other shard sits idle. Two earlier-lesson tools fix this together, not separately: replicate the hot key onto multiple nodes (so reads fan out across replicas instead of one node), and use an eviction policy that resists cheap churn (LFU over strict LRU) so a hot key isn't accidentally evicted by a burst of one-time-read cold keys.

## Worked example: a stampede after a TTL expiry

Say a product page's price and inventory blob is cached under one key, read roughly 20,000 times per second, with a 60-second TTL for freshness. At second 60, the key expires. Under a naive cache-aside implementation, all ~20,000 requests that land in the next few milliseconds see a miss simultaneously, and all ~20,000 issue the same query to the database at once — a cache stampede. The database, which was comfortably serving zero load for this key (because the cache was absorbing it), now takes a 20,000-request spike it was never sized for, and can fall over.

Three fixes, and you should be able to name all three in an interview:

- **Request coalescing (singleflight)**: the first request that misses acquires a short-lived lock for that key and fetches from the database; every other concurrent request for the same key waits on that fetch instead of issuing its own, then all of them read the result once it lands.
- **Jittered TTL**: instead of every replica of a popular key expiring at exactly 60 seconds, randomize it (e.g. 55 to 65 seconds) so expiries spread out instead of clustering at one instant.
- **Background refresh**: proactively refresh a hot key shortly before it expires (e.g. at 50 seconds) so it never actually goes cold from the client's point of view.

None of these are eviction-policy or sharding fixes — they're invalidation-and-refill fixes — which is exactly the point: assembling the cache correctly means knowing which lesson's toolbox a given failure mode belongs to.

<Callout type="warning">
  A common mistake: treating "add more cache nodes" as the answer to a cache stampede. More nodes shard the *keyspace* more finely, but a stampede is concentrated on one hot key that already lives on one node (or a small replica set) — extra unrelated shards don't help at all. The fix is request coalescing, jitter, or background refresh on that specific key's expiry behavior, not horizontal scale-out of the cluster.
</Callout>
