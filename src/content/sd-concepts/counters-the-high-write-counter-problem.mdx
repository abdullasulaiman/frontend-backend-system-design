A "like" button, a view counter, an impression tracker, a leaderboard score, a trending-posts ranker — these all boil down to the same primitive: take a number, increment it, and let people read it back. It sounds like the simplest possible piece of state in the entire system. Then a post goes viral, ten thousand people tap "like" in the same second, and the counter that used to update in a millisecond starts taking hundreds of milliseconds, then timing out, then falling behind by minutes. The data model didn't change. The write rate did — and a design that was fine at 50 writes/second quietly stops working at 50,000.

This lesson is about *why* that happens: what makes a single counter value a bottleneck no matter how much hardware you throw at the surrounding system. The next two lessons in this module (Sharded Counter Design, and Aggregation and Read Paths) build the actual fix. This one exists so you don't jump to "shard it" before you understand what problem sharding is solving.

## What makes a counter different from other writes

Most write-heavy systems scale by spreading writes across many independent rows or keys — a million users each writing their own profile row hits a million different pieces of state, so you can shard by user ID and each shard only ever sees its own slice of traffic. A counter breaks that assumption. Every single increment for "likes on post 4471" targets the *exact same piece of state*. There's no natural key to shard by, because the thing you're incrementing isn't naturally partitionable — it's one number.

That single piece of state has to be touched, in some form, by every writer. Whether that's a row-level lock in a relational database, a single key in a cache, or one partition in a distributed store, you've concentrated arbitrarily high concurrent demand onto one physical location. This is the classic **hot key** (or hot partition) problem, and a viral counter is one of its purest examples.

## Why the obvious approach falls over

The obvious implementation is a single row: `UPDATE post_stats SET like_count = like_count + 1 WHERE post_id = 4471`. This works fine at low volume. At high volume, three things compound:

- **Lock contention.** A read-modify-write increment typically takes a row lock (or an equivalent internal latch) for the duration of the update. Every concurrent writer for the same row queues behind whoever holds that lock. Add more app servers and you don't get more throughput — you get a longer queue in front of the same lock.
- **Single-writer ceiling.** Even a well-tuned database has a practical ceiling on how many writes per second one row can absorb — often in the low thousands, far below what a popular event can generate. Horizontal scaling (more database nodes) doesn't help a single hot row, because that row still lives on one node (or one leader, in a replicated setup).
- **Replication doesn't spread the write.** Adding read replicas helps read throughput, not write throughput — every increment still has to go through the primary for that row first. If anything, replication adds replica lag on top: readers on replicas may see a stale count for a noticeable window after a burst of writes.

None of this is a caching problem, either. A cache-aside layer speeds up *repeated reads* of a value; it does nothing for the write path, because every increment still needs to eventually land somewhere durable, and that "somewhere" is still one hot spot.

## Not the same problem as rate limiting

It's easy to conflate this with rate limiting, since both involve tracking counts under high request volume — but the goals are opposite. A rate limiter needs an *approximate, fast, per-request* answer ("has this key exceeded quota — yes or no") and is allowed to reset or expire its state constantly. A high-write counter needs a *durable, cumulative* total that has to survive server restarts, be queryable indefinitely, and (usually) be reasonably accurate for anyone reading it — a "likes" count that resets itself or loses history isn't just imprecise, it's a broken product feature. Don't reach for rate-limiter techniques here without checking whether durability and long-lived accuracy are actually required — they usually are.

## Stating the real requirement

Before reaching for any fix, pin down what "correct" means for this counter, because it changes the entire solution space:

- **Exact vs. approximate.** Does the count need to be exactly right at every instant (a payments ledger, an inventory count), or is "off by a few, momentarily" acceptable (a like count, a view count)? Most social/engagement counters tolerate approximation; financial counters usually don't.
- **Read freshness.** Can a read lag the true value by a few seconds, or does it need to reflect every write immediately? A view counter can lag; a "seats remaining" counter for the last few seats usually can't.
- **Write durability.** Can increments be buffered in memory and flushed periodically (risking losing the last few seconds on a crash), or must every increment be durably persisted before acknowledging the write?

These three answers determine which fix is available. If you need exact, immediately-consistent, fully-durable counts, you're stuck making that one hot spot as fast as possible (faster storage, in-memory counters with synchronous write-ahead logging) — there's a hard ceiling. If approximate and eventually-consistent is acceptable, you can spread the write load across many independent pieces of state and combine them later — which is exactly the idea the next lesson, Sharded Counter Design, develops.

## Worked example: sizing the problem

Say a post on a social feed goes viral: 2 million "like" taps arrive over a 10-minute window, unevenly distributed — a third of them land in the single busiest minute.

- Average rate over the 10 minutes: 2,000,000 / 600s ≈ 3,300 writes/second.
- Peak minute: ~666,000 likes in 60s ≈ 11,000 writes/second, all targeting one counter.

A single well-tuned relational row might sustain a few thousand increments per second before lock wait times start dominating request latency. The average rate is already close to that ceiling; the peak minute is well past it. Multiply this by the fact that a popular platform has many posts trending simultaneously, each with its own hot counter, and "just make the database bigger" stops being a real answer — the bottleneck isn't aggregate database capacity, it's concurrent access to *one specific row* at a time, and no amount of headroom elsewhere in the cluster relieves that.

<Callout type="warning">
  A common mistake is treating this as purely a database-scaling problem — adding read replicas, upgrading instance size, or adding a cache in front of the counter — without realizing none of these touch the actual bottleneck. Read replicas and caching help *reads*; they do nothing for the serialized *write* path, because every replica still traces back to one primary handling one row's writes. If write latency to a specific counter row is climbing while overall database load looks fine, that's the signature of a hot key, and the fix has to change how the write itself is distributed — not how the read path is scaled.
</Callout>
