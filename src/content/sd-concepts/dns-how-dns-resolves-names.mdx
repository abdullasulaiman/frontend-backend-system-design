Every request your system serves — an API call, a page load, a service-to-service call in a microservices mesh — almost always starts with a name lookup. Your client knows `api.example.com`; the network only knows how to route packets to an IP address. DNS is the system that bridges that gap, and it does it billions of times a second globally without most engineers ever thinking about it. That invisibility is exactly why it matters in system design interviews: when someone asks "how would you route traffic to the nearest data center" or "how do you fail over to a backup region in under a minute," the honest answer runs straight through how DNS resolution actually works and where its caching lives.

This lesson covers the mechanics of resolving a name to an address — the actors involved, the record types, and the step-by-step walk a query takes. The next lesson in this module builds on top of this to cover how DNS gets used deliberately as an infrastructure tool: caching strategy, latency-based routing, and global load balancing.

## The actors in a DNS lookup

A single lookup involves four distinct roles, each run by different organizations:

- **Stub resolver** — a small piece of software on your laptop, phone, or server that just forwards the question ("what's the address for `api.example.com`?") to a recursive resolver. It does no real work itself.
- **Recursive resolver** — the workhorse. Usually run by your ISP, or a public service like Google's `8.8.8.8` or Cloudflare's `1.1.1.1`. It does the actual multi-hop walk described below and returns a final answer to the stub resolver, caching the result along the way.
- **Root name servers** — 13 logical root servers (each backed by many physical, geographically distributed machines) that know which servers are authoritative for each top-level domain (`.com`, `.org`, `.io`, etc.).
- **Authoritative name servers** — the servers that actually hold the records for a specific domain. When you configure DNS for `example.com` in your registrar or cloud provider, you're telling the world which servers are authoritative for it.

The key structural idea is **delegation**: nobody holds the whole DNS database. Root servers delegate to TLD servers, TLD servers delegate to your domain's authoritative servers, and your authoritative servers can even delegate subdomains to yet another set of servers. This is what lets DNS scale to hundreds of millions of domains without any single organization owning all of it.

## The resolution walk, step by step

Say a client wants to reach `api.example.com` and nothing is cached anywhere yet (a "cold" lookup):

1. The stub resolver asks the configured recursive resolver for `api.example.com`.
2. The recursive resolver asks a root server: "who handles `.com`?" The root server doesn't know the answer for `api.example.com`, but it replies with a referral to the `.com` TLD servers.
3. The recursive resolver asks a `.com` TLD server the same question. It doesn't know the final answer either, but it knows which name servers are authoritative for `example.com` and refers the resolver there.
4. The recursive resolver asks `example.com`'s authoritative name server for `api.example.com`. This server actually holds the record and returns the IP address (an A or AAAA record).
5. The recursive resolver returns that IP address to the stub resolver, and caches it locally for as long as the record's TTL allows.
6. The client now opens a TCP (or QUIC) connection directly to that IP address — DNS's job is done.

In practice, steps 2 and 3 are almost always served from the recursive resolver's cache rather than a live query, since root and TLD server answers change extremely rarely. The expensive, genuinely "cold" hop is usually just step 4 against the authoritative server, and even that gets cached per the record's TTL.

## Record types you actually need

DNS stores several kinds of records per name, called a "zone" for a domain:

- **A** — maps a name to an IPv4 address (`api.example.com -> 203.0.113.42`).
- **AAAA** — same idea, for IPv6 addresses.
- **CNAME** — aliases one name to another name, not an address directly (`www.example.com -> example.com`). The resolver follows the CNAME and then resolves the target name to an A/AAAA record — one extra hop.
- **NS** — declares which name servers are authoritative for a zone; this is the delegation mechanism itself.
- **SOA** — "start of authority," carries zone-wide metadata: the primary name server, a serial number used for replication between name servers, and default TTLs.
- **MX** — mail exchange records, pointing at servers that accept email for the domain (not relevant to HTTP traffic, but shows up constantly in DNS configuration work).
- **TXT** — arbitrary text, commonly used for domain-ownership verification and email anti-spoofing policies (SPF/DKIM).

A rule worth internalizing: **a CNAME cannot coexist with other records at the same name** (you can't have both a CNAME and an A record for `api.example.com`), which is why root domains (`example.com` itself) typically use an A record or a provider-specific "ALIAS"/"flattened CNAME" extension rather than a plain CNAME.

## Caching and TTL

Every DNS record carries a **TTL (time to live)**, in seconds, set by whoever controls the zone. It tells every resolver and client along the chain how long they're allowed to reuse a cached answer before asking again. This single number is a major lever in system design:

- A **short TTL** (e.g. 30–60 seconds) means you can change where a name points and have the change take effect quickly everywhere — critical for fast failover to a backup region.
- A **long TTL** (e.g. hours or a day) means far fewer queries hit your authoritative servers, which is cheaper and more resilient to load, but a misconfiguration or failover takes much longer to propagate, since caches around the world keep serving the old answer until it expires.

Caching happens at multiple independent layers, not just the recursive resolver: many operating systems cache resolved names, and browsers keep their own short-lived DNS cache on top of that. That's why "I updated the DNS record and nothing changed" is so often actually "the change worked, but something upstream is still serving a cached answer."

## Worked example: sizing a failover TTL

Say you run `checkout.example.com` pointed at a primary region, and you want the ability to fail over to a secondary region within 2 minutes of detecting an outage. If your A record's TTL is set to 1 hour (a common default), even a perfect, instant DNS update after detecting the outage won't help most clients — resolvers around the world are holding that hour-long-valid answer and won't ask again until it expires. Some fraction of traffic could stay pointed at the dead region for up to an hour.

To hit a 2-minute failover target, you'd set the TTL to something like 30-60 seconds well ahead of time (not during the incident — TTL changes only apply to lookups that happen after the change, and any answer already cached upstream keeps its original TTL until it expires). The trade-off: at 30-second TTLs, your authoritative name servers see roughly 120x more query volume than at 1-hour TTLs for the same client population, so this is a genuine cost/latency-of-failover trade-off, not a free win — one reason large systems often pair a short TTL with a managed DNS provider built to absorb that query volume rather than rolling their own authoritative servers.

<Callout type="warning">
  A common mistake is treating a DNS-based failover as instantaneous. Even with a short TTL, DNS caching is advisory, not enforced — some resolvers and client libraries ignore TTLs or cache far longer than instructed ("TTL flouting"), and any client that already has an open connection to the old IP won't re-resolve until that connection drops. Design failover to tolerate a tail of stale traffic for minutes, not seconds, and pair DNS-level failover with health checks / connection draining at the application layer rather than relying on DNS alone for a hard cutover.
</Callout>

## Common pitfalls beyond TTL

Two more things worth knowing before an interview:

- **DNS mostly rides on UDP port 53** because most responses are small and a full TCP handshake would add needless round trips at this scale. It falls back to TCP when a response is too large for a single UDP packet (common with DNSSEC-signed responses) or for zone transfers between name servers. The UDP-first, low-verification nature of DNS is also why it's a favorite amplification vector for DDoS attacks — a small spoofed query can trigger a much larger response sent to a victim's IP.
- **Recursive resolvers do the heavy lifting so authoritative servers don't have to.** If every client on earth queried root and TLD servers directly for every lookup, they'd fall over instantly. The two-tier resolver/authoritative split, plus aggressive caching at the resolver layer, is what makes DNS's request volume tractable at internet scale.
