Every piece of hardware and every network link you depend on will eventually
fail — a disk wears out, a process gets OOM-killed, a top-of-rack switch
drops, a whole availability zone loses power. Fault tolerance is the design
property that decides what happens next: does the system keep serving
correct responses through the failure, or does the failure become an
incident? Redundancy — having more than one of the thing that can fail — is
the primary tool you reach for to get there, but simply "having two of
something" is not the same as being fault tolerant, and this lesson is about
the gap between those two ideas.

This sits next to [Availability](/system-design/nfr-availability) and
[Reliability and Durability](/system-design/nfr-reliability-and-durability) in
this module for a reason: fault tolerance is the *mechanism*, and
availability/reliability are the *measurements* you get when that mechanism
works. A system can be highly available on paper and still fail badly the
first time a real fault hits it, if the redundancy behind that number was
never actually independent or never actually tested.

## Fault, error, failure — and why the distinction matters

A useful mental model borrowed from reliability engineering: a **fault** is
the underlying defect (a bad disk sector, a bug), an **error** is the
incorrect internal state it causes (a corrupted in-memory value, a stuck
connection), and a **failure** is the externally visible consequence (the
user gets a 500, or gets stale data). Fault tolerance means containing
faults so they never escalate into errors, and containing errors so they
never escalate into user-visible failures. Every redundancy technique below
is really a strategy for cutting that escalation chain at a different link.

## Redundancy patterns

### Active-active

Multiple instances handle live traffic simultaneously, and a load balancer
or client-side router spreads requests across them. If one instance dies,
the others absorb its share with no failover delay — the system was already
running without it. The cost: every instance must be able to serve any
request, which usually means shared or replicated state, and if that state
is writable, you now have to reason about conflicting concurrent writes
(see the consistency lesson later in this module for the trade-offs that
creates).

### Active-passive (hot / warm / cold standby)

One instance (or region) serves traffic; one or more standbys sit ready to
take over. They differ by how "ready":

- **Hot standby** — already running, already has near-current data
  (typically via continuous replication), can take over in seconds.
- **Warm standby** — running but scaled down or with stale-ish data; needs
  a short scale-up or catch-up before it's fully load-bearing.
- **Cold standby** — infrastructure defined but not running; provisioning
  from scratch takes minutes to hours.

Active-passive is cheaper than active-active (the standby isn't burning
full capacity for nothing), but it introduces a **failover gap** — the time
between the primary failing and the standby serving traffic — during which
you're down or degraded. That gap is driven by detection time plus promotion
time, both of which you should measure, not assume.

### N+1, N+2, and quorum math

"N+1 redundancy" means running one more unit than the minimum needed to
handle load, so a single failure doesn't cause an overload cascade in the
survivors. This is simple capacity headroom, not consensus.

It's different from **quorum-based** replication, where a write (or read)
must be acknowledged by a majority of replicas before it counts as durable.
To tolerate `f` simultaneous replica failures under majority quorum you need
`2f + 1` replicas — a 3-node group tolerates exactly 1 failure (2 of 3 still
form a majority), a 5-node group tolerates 2. People often assume "3
replicas means I can lose 2 and be fine" — you can't, under majority quorum,
without losing write availability.

## Failure detection and failover mechanics

Redundancy only helps if the system notices a failure and reacts fast
enough. That's usually built from:

- **Health checks / heartbeats** — a liveness probe polled on an interval;
  miss `k` consecutive checks and the instance is marked down. Too
  aggressive a threshold causes flapping on transient blips; too lenient
  extends your failover gap.
- **Consensus on "who's primary"** — in active-passive setups, something
  (a coordination service like a Raft/Paxos-backed store, or a managed
  control plane) has to agree on promotion so you don't get two nodes
  both believing they're primary at once — a **split-brain** scenario that
  can cause divergent, unreconcilable writes.
- **Client-side retries and backoff** — the requesting side needs to detect
  a failed call and retry against a healthy replica, ideally with jitter so
  a mass failure doesn't produce a synchronized retry storm against the
  survivors.

## Bulkheads and blast radius

Redundancy at the instance level doesn't help if a single failing dependency
can exhaust a resource pool shared by everything else — one slow downstream
call holding every thread in a shared pool starves unrelated requests too.
**Bulkheading** (named for ship compartments that stop one hull breach from
sinking the whole vessel) means giving each dependency its own bounded pool
of threads, connections, or concurrency budget, so a failure in one is
contained to the requests that actually needed it. Combine this with
timeouts and circuit breakers and a failing dependency degrades one feature
instead of taking down the service.

## Worked example: sizing redundancy for a payment-authorization service

Say you run a payment-authorization service that must keep authorizing
transactions even if an entire AWS availability zone goes dark, and you
want to tolerate one full AZ loss without dropping write availability.

- **Compute**: run active-active behind a load balancer across 3 AZs, sized
  at N+1 per AZ so that losing one AZ's third of capacity still leaves the
  remaining two-thirds able to absorb the full load (this is capacity
  headroom, decided by your peak QPS and per-instance throughput).
- **Data**: use a replicated store with 5 replicas spread one-per-AZ across
  3 AZs (at least two AZs hosting 2 each), using majority-quorum writes.
  With `2f + 1 = 5`, you tolerate 2 simultaneous replica failures — enough
  to survive a full AZ loss (2 replicas) plus one unrelated node failure
  elsewhere, while still having a majority (3 of 5) to accept writes.
- **Failover time budget**: if your health checks flag a dead node after 3
  missed 5-second heartbeats (15s) and promotion/re-routing takes another
  10s, your realistic failover gap is ~25s — that number, not "we have
  redundancy," is what you'd quote in an interview or a postmortem.

<Callout type="warning">
  The most common redundancy mistake isn't skipping redundancy — it's
  redundancy that isn't actually independent. Two "redundant" app servers
  plugged into the same power strip, two database replicas in the same
  rack, or a disaster-recovery region that's never been failed over to in
  practice are all single points of failure wearing a fault-tolerant
  costume. Draw out your actual failure domains (rack, AZ, region, cloud
  account, DNS provider, certificate authority) and check that your
  redundant copies don't share one, and periodically exercise the failover
  path for real — a standby you've never promoted is a hypothesis, not a
  capability.
</Callout>

## Graceful degradation: the fallback for the unenumerated case

Redundancy defends against failures you anticipated and built extra
capacity for. It can't cover every failure mode you didn't think of. The
complementary technique is **graceful degradation** — designing the system
so that when things go wrong in an unanticipated way, it sheds non-critical
work and keeps the core function alive rather than failing everything at
once. A product page that can't reach the recommendations service should
render without recommendations, not 500 the whole page. This is cheaper
than redundancy (no extra replicas needed) and catches failures that
redundancy, by definition, wasn't built to anticipate.
