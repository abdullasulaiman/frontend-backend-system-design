The previous lesson made the case for watching a distributed system instead of hoping it behaves. This lesson gets concrete about the first pillar of that: metrics. Before you can design a monitoring system, you need to answer three unglamorous but decisive questions: what shape does a metric have, how does it travel from a service to a place you can query it, and what does it take to store billions of these points cheaply enough that the monitoring system doesn't cost more than the thing it's watching?

Get these wrong and the symptoms show up much later, as an interview candidate's worst nightmare: a monitoring system that itself falls over during an incident, or a storage bill that grows faster than the fleet it's monitoring.

## What a metric actually is

A metric is a numeric measurement of something at a point in time, plus enough context to slice it later. Concretely, each data point is:

- **A metric name** — `http_requests_total`, `checkout_latency_ms`, `queue_depth`.
- **A set of labels (dimensions)** — key-value pairs like `service=checkout`, `region=us-east-1`, `status_code=500`. Labels are what let you go from "requests are failing" to "requests are failing in us-east-1 for the checkout service."
- **A timestamp.**
- **A value** — a single number.

That "name + labels + timestamp + value" tuple is the atomic unit every dashboard, alert rule, and retention policy is built on. It's worth internalizing because it explains most of the design decisions later in this lesson: labels are what make a time-series database's job hard (see cardinality below), and the timestamp is what makes it fundamentally different from a general-purpose database.

### The four metric types you'll actually use

- **Counter** — monotonically increasing (total requests served, total errors). It only resets when the process restarts. You almost never read a counter's raw value; you read its *rate of change* (requests/sec over the last minute).
- **Gauge** — a value that goes up and down (current queue depth, memory in use, number of open connections). You read it directly.
- **Histogram** — buckets observations into ranges (e.g. request latency in `<10ms`, `<50ms`, `<100ms`, `<500ms` buckets) so you can estimate percentiles (p50, p95, p99) after the fact from pre-aggregated bucket counts.
- **Summary** — similar goal to a histogram (percentiles), but computes them client-side per instance before shipping, which is cheaper to query but can't be meaningfully aggregated across instances afterward.

The practical takeaway: if you need "p99 latency across the whole fleet," reach for histograms, not summaries — summaries lock in the aggregation boundary too early.

## Push vs. pull: how metrics leave the service

This is the design decision every monitoring system has to make, and it shapes almost everything downstream.

### Pull (scrape-based)

The monitoring system knows (via service discovery) which instances exist, and periodically calls an HTTP endpoint like `/metrics` on each one to fetch its current values. Prometheus is the canonical example of this model.

Advantages:
- **Centralized control of scrape frequency and load** — you can slow down scraping under monitoring-system pressure without touching every service.
- **Liveness is a side effect** — a failed scrape *is* a signal ("this instance stopped responding"), no separate heartbeat needed.
- **Easier to reason about duplicate data** — one scraper, one schedule, no risk of double-counting from retries.

Disadvantages:
- Needs service discovery to know what to scrape, which adds a moving part.
- Doesn't fit short-lived jobs well — a batch job that runs for 4 seconds may finish before it's ever scraped (commonly solved with a push gateway that jobs push a final snapshot to, which then gets scraped instead).
- The monitoring system needs network access *into* every instance, which can be awkward across trust boundaries or firewalls.

### Push (agent/client-initiated)

Each service (or a local agent/sidecar next to it) sends its metrics outbound to a collector on its own schedule. StatsD and most APM agents work this way.

Advantages:
- Works naturally through NAT/firewalls — the client only needs outbound access.
- Fits ephemeral and batch workloads well — a Lambda function or a short-lived job can push a final value right before exiting instead of waiting to be discovered.
- No service-discovery dependency for the monitoring system.

Disadvantages:
- The client owns retry and buffering logic — a network blip means every instance independently decides whether to drop, buffer, or retry.
- **A silent, dead client is indistinguishable from an idle one that has nothing to report** — you lose the free liveness signal pull gives you, and need a separate "haven't heard from X in N minutes" alert.
- Easy to accidentally overload the collector: a fleet-wide config change (e.g. lowering the push interval) fans out instantly across every instance with no central throttle.

Most large-scale systems end up running both: pull for long-lived services (steady load, easy liveness), push for batch/serverless workloads and for cases where a local agent needs to buffer during network partitions.

## Storage: why metrics need a specialized database

Metrics have a shape that makes a general-purpose relational or document database a poor fit at scale: mostly-append-only writes, timestamp-ordered access, and queries that almost always filter by a time range and aggregate (sum, average, percentile) rather than fetch individual rows. Time-series databases (TSDBs) like Prometheus's own storage engine, InfluxDB, or M3DB are built around three ideas:

1. **Columnar, per-series storage.** Points for the same metric+label combination (a "series") are stored contiguously, so a query for one series' last hour doesn't have to scan unrelated series.
2. **Delta/XOR encoding.** Adjacent timestamps and values in a series usually change by a small amount, so storing "the delta from the previous point" instead of the raw value compresses dramatically — Facebook's Gorilla paper reported roughly 90%+ compression this way, and most modern TSDBs use a variant of it.
3. **Downsampling and retention tiers.** Nobody needs per-second resolution from 18 months ago. A typical policy keeps raw (e.g. 15-second) resolution for 7–14 days, rolls up to 5-minute averages for a year, and rolls up further (or deletes) beyond that — trading query resolution for a storage bill that doesn't grow linearly forever.

### The cardinality trap

The single most common way teams accidentally break their own monitoring: putting an unbounded-cardinality value into a label. A metric like `http_requests_total{status_code=500}` is fine — a handful of status codes. A metric like `http_requests_total{user_id=12345}` is not — with a million users, that one metric name explodes into a million distinct time series, each with its own index entry, and the TSDB's memory and disk usage can grow by orders of magnitude overnight. This is exactly why labels should describe *dimensions you'd want to alert or dashboard on* (region, service, status class), not identifiers for individual entities (user ID, request ID, raw URL path with query string).

## Worked example: sizing metrics storage for a mid-size fleet

Say you run 2,000 service instances, each exposing 200 distinct time series (a mix of counters, gauges, and histogram buckets), scraped every 15 seconds.

- Series count: `2,000 x 200 = 400,000` active time series.
- Points per second: at one point per series per scrape, that's `400,000 / 15s ≈ 26,700 points/sec`.
- Raw bytes per point: roughly 16 bytes uncompressed (8-byte timestamp + 8-byte float value), before compression.
- Raw ingest rate: `26,700 x 16 bytes ≈ 427 KB/sec`, or about 37 GB/day uncompressed.
- With Gorilla-style delta/XOR compression (commonly 90%+ reduction for slowly-changing series), that drops to roughly **3–4 GB/day** for raw-resolution storage.

Keep 14 days of raw resolution and that's roughly 45-55 GB — comfortably within a single modern TSDB node, before even applying downsampling for longer retention. This is the kind of back-of-envelope math an interviewer wants to see you do out loud: it justifies *why* compression and downsampling matter, rather than just asserting that they do.

<Callout type="warning">
  Don't design the metrics pipeline as if it can never fail. A common mistake is routing every service's metrics through a single collector or scrape target with no buffering — during a real incident (the exact moment you need metrics most), that collector is also under load, and a naive push pipeline with no local buffering will drop the very data points that would explain the outage. Give push-based agents a local ring buffer with bounded retry, and give pull-based scrapers enough headroom (separate scrape budget, staggered schedules) that scraping itself doesn't become a cascading failure during a spike.
</Callout>
