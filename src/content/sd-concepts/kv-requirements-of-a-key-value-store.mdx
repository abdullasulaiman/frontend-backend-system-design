"Design a distributed key-value store" is one of the most common prompts in a system design interview, and it's also one of the easiest to fumble in the first five minutes — not because the mechanics are hard, but because candidates jump straight to consistent hashing or Dynamo-style replication before anyone has agreed on what the system actually needs to do. A key-value store that backs a session cache and one that backs a payments ledger share almost no design decisions in common, even though both expose `get`/`put`. This lesson is the one you do before any of that: pin down the requirements so every later choice — partitioning, replication, conflict resolution — has something concrete to be judged against.

This is the first lesson in the Key-Value Store module. The lessons that follow (consistent hashing, replication and quorum, conflict resolution, and putting it all together) each solve a problem that a requirement stated here creates. Get this lesson right and the rest of the module reads as "here's how we satisfy the requirement we already wrote down," instead of a grab-bag of distributed-systems trivia.

## Start with the API, not the architecture

A key-value store's functional surface is deliberately narrow, and stating it explicitly is worth doing out loud in an interview:

- `put(key, value)` — store or overwrite a value under a key.
- `get(key)` — retrieve the value for a key, or a "not found" signal.
- `delete(key)` — remove a key (sometimes via a tombstone rather than a physical delete, which matters later for replication).

Notice what's missing: no range scans, no secondary indexes, no joins, no transactions across keys. That absence is the entire point of a KV store — by refusing to support arbitrary queries, it can partition data across many machines with no cross-node coordination on reads or writes. If an interviewer's prompt later asks for "find all keys with prefix X" or "query by a non-key attribute," that's a sign the system needs a secondary index or a different data model layered on top — flag it as a scope decision rather than silently designing it in.

## Functional requirements to pin down

Beyond the basic API, clarify these before moving on:

- **Value size and shape.** Are values small (a few hundred bytes — session tokens, counters) or large (multi-MB blobs — serialized objects, small files)? This single answer decides whether the store can be a pure in-memory hash table or needs on-disk storage, compression, and possibly chunking large values across nodes.
- **Key structure.** Are keys opaque strings/UUIDs, or do they have implicit structure (e.g. `userId:sessionId`) that a partitioning scheme could exploit or accidentally break by co-locating hot keys?
- **TTL / expiry.** Does data expire (cache-like) or persist indefinitely (ledger-like)? This changes whether you need a background eviction/compaction process at all.
- **Read/write ratio.** A cache in front of a database is read-heavy; a write-heavy workload (e.g. ingesting sensor events) needs a design that optimizes the write path — different tuning for the same API.

## Non-functional requirements: where the real design decisions live

The functional requirements above are usually quick to agree on. The non-functional ones are where a distributed KV store gets interesting, because most of them are in direct tension with each other.

### Scale

State concrete numbers, not adjectives. "Web-scale" tells you nothing; "500 million keys, average value 1 KB, 200K reads/sec and 20K writes/sec, 3x replication" tells you exactly how much data one node can hold in memory, how many partitions you need, and how much network bandwidth replication will consume. Every later lesson in this module — how keys map to nodes, how many replicas per key, how conflicts get resolved — is downstream of this number.

### Availability vs. consistency

This is the crux. During a network partition, do you want every replica to keep accepting reads and writes even if that means two replicas can briefly disagree (an "AP" choice, in CAP terms), or do you want to refuse requests on a minority partition to guarantee every client sees the same value (a "CP" choice)? A shopping-cart-style KV store (Amazon's original Dynamo motivation) picks availability — a stale cart is annoying, an unavailable one loses a sale. A KV store backing distributed locks or leader election picks consistency — a stale value there causes a correctness bug, not an inconvenience. Say which one your system needs and why, before you touch replication design.

### Durability

Can an acknowledged write ever be lost? If yes (pure cache), you can skip write-ahead logs and multi-node fsync entirely. If no, every write needs to survive on at least N nodes' disks before you return success to the client — which directly shapes the replication and quorum lesson that follows this one.

### Latency

Single-digit-millisecond `get`/`put` latency is a common requirement, and it constrains you toward keeping hot data in memory, keeping the number of network hops per request low (avoid multi-hop routing through a coordinator on every request), and picking a partitioning scheme that lets a client (or a thin routing layer) go directly to the right node.

## Worked example: sizing a session-store KV cluster

Say the prompt is "design a KV store to hold web session data for a service with 50 million daily active users." A reasonable set of requirements, stated out loud:

- Each session is small: ~2 KB (user ID, permissions, a few flags).
- Sessions expire after 24 hours of inactivity — durability doesn't need to survive a full data-center loss, but losing a live session mid-request is a bad user experience, so we want it to survive a single node failure.
- Read-heavy: sessions are checked on almost every request, refreshed occasionally. Say 100K reads/sec average, 10K writes/sec.
- Availability over strict consistency: if a user's session is briefly stale on one replica after a failover, that's acceptable; refusing to serve requests during a partition is not.

From here the capacity math is quick: 50 million sessions x 2 KB ~ 100 GB of raw data. With 3x replication for durability against single-node failure, that's ~300 GB to place across the cluster. If each node comfortably holds 50 GB in memory (leaving headroom), that's 6 nodes minimum for replicated storage — round up for growth and you're proposing an 8-10 node cluster before you've drawn a single arrow. That number, and the availability-over-consistency decision, are exactly what the next lesson (consistent hashing) needs as inputs to decide how keys get distributed across those nodes.

## Putting the requirements list together

A tight requirements pass for a KV store interview question should leave you able to state, in a few sentences: the API (get/put/delete, value size ceiling), the scale (keys, QPS, replication factor), the consistency/availability choice and why, the durability guarantee, and the latency target. Everything from here forward in this module — how keys map to nodes, how many copies of each key exist and how they're kept in sync, and how conflicting writes get resolved — is just engineering in service of the numbers and trade-offs you write down at this stage.
