You've now walked through the building blocks one at a time: DNS and load balancing at the edge, caches and CDNs for speed, SQL and NoSQL stores and blob storage for durability, message queues and pub-sub for decoupling, rate limiters and unique ID generators and search and logging and monitoring for the cross-cutting concerns. Each of those lessons deliberately isolated one component so you could learn its job and trade-offs cleanly. That's not how an interview question actually arrives, though — nobody asks you to "design a cache." They ask you to design a URL shortener, a ride-hailing dispatch system, or a chat app, and the whole exercise is picking the right subset of blocks and wiring them together correctly.

This lesson is the seam between the two halves of this course. It doesn't introduce a new block — it steps back and shows the patterns that repeat *across* every block you've studied, so that when you move into full case studies next, you're combining familiar mechanisms instead of starting from zero on every problem.

## The inventory, one line each

Before combining anything, it helps to have the whole set in view at once. Here's every block from this module, reduced to its one-sentence trade-off:

| Block | Core trade-off |
|---|---|
| DNS | Resolves names to addresses; caching (TTL) trades update speed for lookup speed. |
| Load balancer | Spreads requests across servers; algorithm choice trades fairness/simplicity against session affinity. |
| CDN | Serves cacheable content from the edge; trades a bit of staleness for large latency and origin-load wins. |
| Cache | Fast key-based reads in front of a slower store; trades consistency for latency. |
| SQL database | Strong consistency and flexible queries; trades write throughput and horizontal scale for that flexibility. |
| NoSQL / key-value store | Scales writes and simple lookups horizontally; trades flexible querying and (often) strong consistency to get there. |
| Blob store | Durable storage for large, immutable objects; trades fine-grained updates for scale and cost efficiency. |
| Message queue | Decouples producer from consumer; trades immediate processing for durability and load-leveling. |
| Pub-sub | Fans one event out to many independent consumers; trades simple point-to-point delivery for broadcast flexibility. |
| Rate limiter | Protects a service from overload; trades some rejected legitimate traffic for protecting the rest. |
| Unique ID generator | Produces IDs without a central bottleneck; trades perfectly sequential IDs for distributed generation. |
| Search index | Fast full-text/filtered lookups; trades write-time indexing cost for query-time speed. |
| Logging & monitoring | Visibility into what's happening; trades storage/compute cost for the ability to detect and debug failures. |

None of these trade-offs is new information if you did the earlier lessons — the point of tabulating them together is to notice that they're all answering the same underlying question: *what am I willing to give up to get more of what I need right now?*

## The patterns that repeat across blocks

The more interesting observation is that the blocks aren't just a list of unrelated trade-offs — a handful of mechanisms show up again and again, just applied to different data:

- **Partitioning / sharding.** Databases shard by key range or hash; caches shard the keyspace across nodes; queues partition by topic/key for ordered, parallel consumption. It's the same idea every time: split data across nodes so no single node is the bottleneck.
- **Replication and quorum.** Databases replicate for durability and read scaling; caches replicate for availability; even DNS "replicates" via multiple authoritative servers. Whenever you replicate, you inherit the same question: how many copies must agree before you call a write or read successful?
- **Idempotency and deduplication.** A load balancer retries a failed request; a queue redelivers an unacknowledged message; a client retries a timed-out call. All of these assume at-least-once delivery, which means every one of your write paths needs to tolerate being executed twice.
- **Backpressure.** Rate limiters push back at the edge; queues absorb bursts so downstream services don't fall over; a cache existing at all is a form of backpressure on the database. Different placement, same goal: protect a slower or more expensive resource from a faster or cheaper one.
- **Cache-style staleness trade-offs.** This isn't limited to the block literally called "cache" — a CDN, a search index, and a read replica are all serving slightly-stale copies of a source of truth in exchange for speed or scale.

Once you see these five mechanisms, most "how would you handle X at scale" interview follow-ups become a matter of naming which mechanism applies, not inventing something new.

## Composing blocks into one request path

Here's a composite request path for a system under real load — say, a checkout flow during a flash sale — showing several blocks working together instead of in isolation:

<Mermaid client:visible chart={`
flowchart TD
    C[Client] --> LB[Load balancer]
    LB --> RL[Rate limiter]
    RL --> APP[Checkout service]
    APP --> Cache[(Cache: product/price)]
    APP --> DB[(Database: orders)]
    APP --> Q[[Queue: order events]]
    Q --> W[Worker: payment + email]
    APP --> IDGen[Unique ID generator]
    MON[Monitoring] -.watches.-> LB
    MON -.watches.-> APP
    MON -.watches.-> Q
`} />

Notice what each block is doing here and why it's there, not just that it's present: the rate limiter sits right after the load balancer because you want to reject excess load as early and cheaply as possible; the cache absorbs repeated reads of the same product/price data so the database only sees writes and cache misses; the queue exists specifically so that slow, non-critical-path work (charging a card asynchronously via a payment provider callback, sending a confirmation email) doesn't hold the customer's checkout request open; the ID generator produces order IDs without a single point of contention; and monitoring watches all of it, because during a flash sale is exactly when you'll need to see which layer is under stress.

## Worked example: scaling one path under load

Say this checkout flow currently handles 200 requests per second comfortably, and marketing tells you Black Friday will bring 20x that — 4,000 requests per second, most of it concentrated in a 30-minute window. Walk it block by block instead of reaching for "bigger machines":

- **Load balancer**: already horizontally scalable — add more app instances behind it, no redesign needed.
- **Rate limiter**: needs to move from a single in-process counter to a **distributed** rate limiter (shared state in a fast store) so the limit is enforced correctly across many app instances, not per-instance.
- **Cache**: the product/price cache was fine at 200 requests per second; at 4,000 requests per second a single cache node may become the new bottleneck, so it gets sharded across multiple cache nodes by product ID.
- **Database**: order writes are the one path that can't be cached away — this is where you'd add write-side protections (the rate limiter, plus the queue below) rather than trying to make the database itself 20x faster.
- **Queue**: this is the star of the scaling story. Instead of processing payment synchronously, accepting the order and pushing "process payment" onto a queue lets the checkout service return quickly and lets payment workers scale independently, smoothing the burst instead of transmitting it straight to a payment provider's API.
- **Unique ID generator**: already designed for distributed generation, so it doesn't need to change.

Nothing here is a new building block — it's the same inventory, applied with the sharding, replication, and backpressure patterns from the previous section.

<Callout type="warning">
  A common mistake once you know the individual blocks well: reaching for the same "add a cache, add a queue" combo on every problem without checking whether it fits the requirement. A queue that decouples a slow write is great advice for sending a confirmation email; it's actively harmful advice for confirming payment success to the user synchronously, where the customer needs to know *right now* whether their card was charged. Composition means picking the right mechanism for *this* seam, not applying your favorite two blocks everywhere.
</Callout>
