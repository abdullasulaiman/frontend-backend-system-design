You've now covered the requirements a messaging queue has to satisfy, the delivery-semantics options, how ordering and deduplication work, and how storage and retention are managed. Each of those is a clean, self-contained idea — but in an interview, being asked to "design a messaging queue" means showing how they bolt together into one system that a producer and a consumer can actually talk through. This lesson walks the full path a message takes, end to end, and points at exactly which component is responsible for which guarantee from the earlier lessons.

The core insight: none of "at-least-once delivery," "ordered per key," or "seven days of retention" is a feature you add on top of a queue. They're properties that fall directly out of *where* you put durability, *how* you assign partitions, and *when* you commit an offset. Get the architecture right and the guarantees follow; bolt guarantees on after the fact and you'll fight the design constantly.

## The four building blocks

A production message queue (think Kafka, Pulsar, or a managed equivalent like Kinesis/SQS-with-FIFO) is built from four pieces:

- **Producers** — clients that publish messages to a **topic**, optionally with a partition key.
- **Brokers** — servers that own partitions, append incoming messages to a durable, append-only log, and replicate that log to followers.
- **Partitions** — each topic is split into ordered, independent logs. A partition is the unit of both ordering and parallelism.
- **Consumers** (organized into **consumer groups**) — read from partitions starting at a tracked **offset**, process the message, and commit progress.

The topic itself is just a name; the partitions are where the actual data and ordering guarantees live. This is the single most important structural fact to internalize: "the topic is ordered" is never true — only "the partition is ordered" is true.

## The produce path

Follow one `publish(topic, key, value)` call through the system:

1. **Partition assignment.** The producer (or a client-side partitioner) hashes `key` to pick a partition — same key always lands on the same partition, which is what makes per-key ordering possible later.
2. **Append to leader.** The message is sent to the broker that leads that partition. The leader appends it to its local log — this append is the durability point: before this, the message exists only in the producer's memory or network buffer.
3. **Replication.** Follower brokers for that partition fetch the new log entries. The leader tracks which followers are "in-sync" (caught up within a configured lag).
4. **Ack.** The leader acknowledges the write to the producer once it's satisfied its durability policy — acknowledge immediately after the local append (fast, risk of loss if the leader dies before replicating), or wait for all in-sync replicas to confirm (slower, safe against single-broker failure).

That ack policy is exactly the lever the delivery-semantics lesson described: a producer that doesn't wait for any ack and doesn't retry gives you at-most-once; a producer that retries on ambiguous failures gives you at-least-once (with possible duplicates, which is why the ordering/dedup lesson's idempotency keys matter); combining idempotent producer IDs with transactional writes is what gets you exactly-once on the produce side.

## The consume path

1. **Assignment.** Each consumer in a group is assigned a disjoint subset of the topic's partitions — this is why partition count caps parallelism: five partitions means at most five consumers in a group can be actively reading at once, the rest sit idle for that topic.
2. **Fetch.** A consumer polls its assigned partitions starting from its last known offset, in strict log order.
3. **Process.** The consumer runs its business logic against the message (write to a database, send an email, update a cache).
4. **Commit.** The consumer records the offset it has processed up to, either automatically on a timer or manually after processing succeeds.

Offset commit timing is where the delivery-semantics lesson's trade-off physically lives: committing the offset *before* processing means a crash mid-processing loses that message forever (closer to at-most-once); committing *after* processing means a crash after processing but before commit causes reprocessing on restart (at-least-once — the normal default). Getting exactly-once end to end means making the processing side effect and the offset commit atomic, typically via a transactional write that includes both, or by making the downstream write idempotent so reprocessing is harmless.

## Where retention and storage fit in

The storage/retention lesson's log-segment design is what makes this whole path replayable: because the broker keeps the log (not just a single in-flight queue), a consumer can restart from any offset within the retention window, a new consumer group can start from the beginning to backfill, and a slow consumer can safely lag behind for a while. The failure mode to watch for is a consumer whose processing lag exceeds the retention window — the log truncates entries the consumer hasn't read yet, and those messages are gone regardless of how well the delivery-semantics or offset-commit logic is designed. Retention and consumer speed are a race, not independent settings.

## Worked example: an order-processing queue

Say you're designing the queue behind an e-commerce order pipeline: 5,000 orders/sec at peak, each order must be processed in the order it was placed *for that customer* (not globally), and losing an order is unacceptable but a duplicate charge is not (downstream payment writes are idempotent on order ID).

- **Partitioning key: `customer_id`.** This gives per-customer ordering for free — every order from the same customer lands on the same partition and is read in order — without paying for a single global-order queue that couldn't scale past one partition.
- **Partition count: 50.** At 5,000 orders/sec, 50 partitions means ~100 orders/sec per partition, comfortably within a single broker's throughput, and gives headroom for up to 50 parallel consumers in a group.
- **Replication factor: 3, ack policy "all in-sync replicas."** Losing an order is unacceptable, so the extra latency of waiting for replication is the right trade against a rare burst of processing duplicates (which the idempotent payment write already absorbs).
- **Retention: 3 days.** Long enough to survive a consumer outage over a bad weekend deploy and replay from scratch, short enough to keep storage cost bounded — this is a direct application of the storage/retention lesson's time-based trade-off.
- **Delivery semantics: at-least-once with idempotent consumers.** Given the payment write is already idempotent on order ID, chasing true exactly-once semantics in the queue itself would add complexity (distributed transactions across produce and commit) for no additional correctness — the cheaper at-least-once plus idempotent downstream write gets the same observable outcome.

<Callout type="warning">
  A common mistake: treating "design the queue" as listing four boxes — producer, broker, consumer, topic — with arrows between them, and stopping there. That diagram is true of nearly any messaging system and demonstrates nothing. The signal an interviewer is looking for is whether you can trace a single message through partition assignment, the append-then-replicate durability point, and the offset-commit timing — because that's where every guarantee (ordering, at-least-once vs. exactly-once, replay-ability) is actually decided. If you can't say *which specific step* enforces a guarantee you just claimed, you haven't designed the system, you've named its parts.
</Callout>
