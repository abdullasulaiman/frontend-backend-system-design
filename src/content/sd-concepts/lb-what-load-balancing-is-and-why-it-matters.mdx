Picture a service running on one server. It handles 500 requests per second comfortably. Traffic grows to 5,000 requests per second — the server pegs its CPU, response times climb, and requests start timing out. Even setting capacity aside: that one server crashes, gets rebooted for a patch, or loses its network link, and the entire service goes down with it. Buying a bigger server buys you some headroom, but it doesn't fix the second problem at all, and it eventually runs out of runway on the first one too — there's always a bigger spike than the biggest box you bought.

The fix in both cases is the same: stop routing all traffic to one server, and instead run several servers that can each handle a share of it, with something in front deciding which server gets each request. That something is a **load balancer**. It's one of the most load-bearing (pun intended) components in any backend system, which is why it's usually one of the first things you place in a system design interview's architecture diagram, right after "client" and "API."

## What a load balancer actually does

A load balancer sits between clients and a pool of backend servers (often called a "server farm," "fleet," or "backend pool"). Every incoming request or connection arrives at the load balancer first, which then forwards it to one server in the pool based on some selection rule. From the client's perspective, there's a single address to talk to; from the backend pool's perspective, the load balancer is the only thing that ever talks to them directly.

That one repositioning solves two distinct problems, and it's worth naming both explicitly because interviewers will probe whether you understand that a load balancer isn't "just for scaling":

- **Scalability.** Instead of one server absorbing all traffic, N servers each absorb roughly `1/N` of it. Need more capacity? Add another server to the pool — no rewrite, no re-architecture, just more of the same unit of compute. This is what makes horizontal scaling possible in the first place; without a load balancer (or something playing its role), clients would need to somehow know which of N servers to talk to, which doesn't scale.
- **Availability.** If a server crashes, is being deployed to, or is overloaded, the load balancer can simply stop sending it traffic and route around it. Clients never see that server directly, so they never notice it's gone — they just keep getting served by the servers that are still healthy. A single-server system has no way to survive that server's failure; a load-balanced pool does, as long as at least one healthy server remains.

Health checking (how the load balancer actually knows a server is unhealthy) and the specific algorithms used to pick a server are big enough topics that they get their own lessons later in this module — this lesson is about the concept and the shape of the problem, not the selection mechanics.

## Where load balancing happens in the network stack

Load balancers operate at different layers of the network stack, and which layer matters a lot for what the load balancer can and can't see.

**Layer 4 (transport layer)** load balancers work at the TCP/UDP level. They look at IP addresses and ports, and forward whole connections to a backend without inspecting the data inside them. They're fast and protocol-agnostic — they'll balance any TCP traffic, not just HTTP — but they're blind to anything above the transport layer: they can't route based on a URL path, an HTTP header, or a cookie, because they never parse that far into the payload.

**Layer 7 (application layer)** load balancers terminate the application protocol — almost always HTTP/HTTPS in a web backend — and can make routing decisions based on its content: send `/api/video/*` to the video-encoding pool, send requests carrying a specific `X-Beta-User` header to a canary deployment, or route based on a session cookie. That flexibility costs more CPU per request, since the load balancer has to actually parse and often terminate TLS for the request, rather than just shuffling packets.

Most real systems use both: an L4 load balancer (or the cloud provider's managed equivalent) as the outermost edge, handling raw connection volume and DDoS-scale traffic cheaply, with L7 load balancers or API gateways behind it doing the content-aware routing.

## Statelessness: the assumption load balancing quietly depends on

A load balancer that spreads requests evenly only helps if any server in the pool can actually handle any request. That's easy when servers are stateless — no request-specific data lives only in one server's memory or local disk. It gets harder the moment a server holds something a later request needs: a shopping cart built up in local memory, a WebSocket connection, an in-progress file upload.

The common workaround is **sticky sessions** (also called session affinity): the load balancer routes a given client back to the same server every time, usually via a cookie or the client's source IP. That fixes the correctness problem, but reintroduces the two problems load balancing was supposed to solve for that client — if their "sticky" server goes down, their session goes with it, and if that server happens to get more sticky clients than others, load stops being even. The more scalable fix is pushing state out of the server entirely — into a shared cache or database — so every server is interchangeable and the load balancer is free to route however it wants. We'll come back to this trade-off through the module, but it's worth internalizing now: statelessness isn't a nice-to-have, it's what makes load balancing actually work as advertised.

## Worked example: sizing a fleet

Say a service needs to sustain 12,000 requests per second at peak, and load testing shows a single server instance can sustain 1,500 requests per second before its p99 latency blows past the SLA. Naively, `12,000 / 1,500 = 8` servers.

In practice you provision more than the bare minimum, for two reasons. First, you want headroom for a single server failing — with exactly 8 servers, losing one drops capacity to 7 × 1,500 = 10,500 req/s, below the 12,000 target, so the remaining servers get overloaded right as one fails, which is exactly the moment you can least afford it. Second, deployments typically take servers out of rotation one at a time (a rolling deploy), so you need slack for that too. A common rule of thumb is to size for `N+2` (tolerate two simultaneous losses — one failure plus one deploy) rather than the bare `N`: that's 10 servers at 1,500 req/s each, giving 15,000 req/s of total capacity against a 12,000 req/s target, a comfortable ~25% margin even with two servers out.

<Callout type="warning">
  A load balancer is not, by itself, highly available — it's a new single point of failure if you only run one instance of it. Teams sometimes solve every backend server's redundancy carefully and then put a single load balancer in front of all of them, which just relocates the outage risk rather than removing it. Run at least two load balancer instances (active-passive with a health-checked failover, or active-active behind a mechanism like DNS round-robin or a floating/virtual IP), and don't treat "we added a load balancer" as automatically meaning "we removed our single point of failure."
</Callout>
