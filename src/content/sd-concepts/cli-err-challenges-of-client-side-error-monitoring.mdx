When a request fails inside your backend, you have logs, traces, metrics,
and a machine you can attach a debugger to. When a `TypeError` happens
inside a user's browser tab in a hotel with bad wifi, you have none of
that — the failure occurred on hardware you don't own, on a build you
might not recognize, and the only way you'll ever hear about it is if the
client itself notices, packages up the failure, and successfully phones
home. Client-side error monitoring is really a small distributed system
that has to survive on the least trustworthy, least controllable node in
your whole architecture: the end user's device.

This lesson covers why that's a genuinely different (and harder) problem
than server-side observability, before the next lesson in this module
designs a concrete pipeline to solve it.

## Why this isn't "just logging, but in the browser"

Server-side logging assumes things client-side monitoring can't:

- **You control the runtime.** Server fleets run a known set of OS/runtime
  versions you chose. Client errors happen across an open-ended matrix of
  browsers, OS versions, extensions, and device capabilities you never
  tested against.
- **The process is reachable while it's failing.** You can attach a
  profiler or read `/proc` on a live server. A browser tab that crashes or
  gets killed by the OS for memory pressure is just gone — whatever state
  wasn't already flushed is lost forever.
- **The network path back to you is reliable.** A server writing to a
  local log agent essentially never loses that write. A phone losing LTE
  coverage mid-crash loses the report unless the client buffered it for
  a later retry.
- **You can reproduce it.** Backend bugs are largely deterministic given
  the same inputs and the same deployed code. Client bugs are entangled
  with an ad blocker, a stale service worker, a third-party script racing
  yours, or a device-specific rendering quirk — reproduction often
  requires the exact device.

The consequence: a client-side error pipeline has to be designed
defensively at every stage, because the thing generating the telemetry
is also the thing most likely to be broken, offline, resource-constrained,
or actively hostile (bots, ad blockers stripping your script).

## The core challenges

### 1. Capturing the error at all

Not every failure surfaces the same way. You need distinct capture paths
for:

- **Uncaught exceptions** — via `window.onerror` / `window.addEventListener('error', ...)`.
- **Unhandled promise rejections** — a separate event
  (`unhandledrejection`) that plain `try/catch` never sees, and a very
  common source of silently swallowed failures in async code.
- **Framework-boundary errors** — a React error boundary, for instance,
  catches render-phase errors in its subtree but not errors in event
  handlers or effects fired outside a render — those still need the
  global handlers above.
- **Resource loading failures** — a script, stylesheet, or image that
  404s doesn't throw a catchable JS exception; it fires a `error` event
  on the element itself, which most naive setups never listen for.
- **"Silent" failures** — a promise that resolves with an error object
  instead of rejecting, or a caught exception that's logged to `console`
  and swallowed. These never reach any global handler at all; catching
  them requires instrumenting the call sites directly.

Missing any one of these categories means a whole class of production
bugs is invisible to you, no matter how good the rest of the pipeline is.

### 2. Turning a stack trace into something a human can read

Production JS is minified and bundled — the stack trace your handler
receives points at `a.js:1:48213`, not the source line a developer wrote.
**Source maps** translate minified positions back to original source, but
they introduce their own problems: they must be generated per build, kept
in lockstep with the exact deployed release (a mismatch produces a
confidently wrong stack trace, which is worse than no trace), and they
must never be served publicly, since a source map effectively hands out
your unminified source. The standard approach is to build them, upload
them privately to your error-tracking backend keyed by release/version,
and resolve them server-side when a report comes in — never ship them to
the CDN path users hit.

### 3. Getting the report off the device reliably

The device that just crashed is the same device that has to send you the
crash report, and it may be about to lose network, get backgrounded, or
be killed by the OS before the send completes. That forces some
uncomfortable trade-offs:

- Use `navigator.sendBeacon` (or a `fetch` with `keepalive: true`) so the
  browser can complete the send even as the page unloads — a normal async
  `fetch` can get cancelled mid-flight.
- Buffer reports locally (e.g. in `localStorage`/IndexedDB) so an offline
  device can retry once connectivity returns, instead of dropping the
  report the instant the first send attempt fails.
- Accept that some fraction of reports are simply lost forever — a device
  that loses power mid-crash isn't sending anything, no matter how well
  you engineer the client. Design your reliability targets around "best
  effort with retry," not "guaranteed delivery."

### 4. Volume, dedup, and grouping

A single bad deploy can turn one bug into millions of raw error reports —
one per affected page load, across every affected user. Your backend has
to solve two things the client can't:

- **Fingerprinting/grouping** — deciding which raw reports represent "the
  same underlying bug" so a human sees one issue with a count of 40,000
  occurrences, not 40,000 separate tickets. Grouping purely by error
  message is naive: `Cannot read properties of undefined (reading 'id')`
  is the generic shape of dozens of unrelated bugs, while the same root
  cause can produce slightly different messages across browsers.
  Stronger fingerprints combine the normalized stack trace (function
  names and file:line after source-mapping, not raw text) with the error
  type.
- **Sampling and rate limiting** — if 100,000 clients hit the same crash
  in the same minute, you don't need 100,000 identical payloads to know
  about it and fix it; you need one full report plus a count. Client-side
  rate limiting (e.g. "at most N reports of the same fingerprint per
  session") and server-side sampling protect both the user's bandwidth
  and your ingestion tier from a self-inflicted denial-of-service during
  an incident — precisely the moment you need the pipeline to still be up.

### 5. Privacy and payload hygiene

A useful error report wants context: the URL, recent user actions
(breadcrumbs), maybe local component state. That same context is exactly
where PII tends to hide — an email address in a query string, an auth
token pasted into a stack trace by an overly verbose error message, form
input echoed into a breadcrumb. Scrubbing has to happen client-side,
before the payload ever leaves the device, because once it's on your
server it's already been transmitted (and possibly logged by an
intermediate proxy) regardless of what you do with it afterward.

## Worked example: sizing the "storm" problem

Say your product has 2 million daily active users, and a bad deploy
introduces a crash on the checkout page that hits roughly 5% of sessions
that reach that page. If 10% of DAU reach checkout on a given day, that's
`2,000,000 * 0.10 * 0.05 = 10,000` crashing sessions. If each crash
produces one report plus 20 breadcrumb events building up to it, and the
bad deploy stays live for 30 minutes before rollback, your ingestion tier
needs to absorb roughly `10,000 * 21 = 210,000` events concentrated into
that half hour — a burst rate over 100 events/second sustained, arriving
in a spike correlated with the deploy, not spread evenly through the day.

That's the number that should drive your rate-limiting and backpressure
design in the next lesson: a pipeline sized for average daily error
volume will fall over exactly when a bad release makes it matter most.

<Callout type="warning">
  The most common mistake teams make: wrapping the error-reporting call
  itself in code that can also throw — a `JSON.stringify` on a payload
  containing a circular reference, or a network call with no try/catch
  around it. When your error handler errors, you don't just lose that one
  report; depending on how it's wired up, you can trigger an infinite loop
  of error events reporting on themselves, or crash the tab a second time
  while it's already in a bad state. Every line in the reporting path must
  be defensively coded to fail silently and cheaply — this is the one
  place in your codebase where "just log it and move on" beats any
  attempt to be clever.
</Callout>
