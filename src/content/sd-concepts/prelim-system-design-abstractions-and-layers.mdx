Every backend system you'll ever design — a URL shortener, a ride-hailing dispatch service, a chat app — is built out of the same handful of layers stacked on top of each other: something the client talks to, something that routes and balances load, something that runs your business logic, something that remembers state. The specific technology at each layer changes constantly; the layering itself barely does. That's why "system design interview" questions rarely ask you to memorize a product's internals — they ask whether you can decompose an unfamiliar problem into the right layers, reason about what each one is responsible for, and predict where it will bend under load.

This lesson isn't about any one layer in depth — the other lessons in this module cover networking, storage, and consistency in detail. It's about the mental model that ties them together: what an abstraction actually buys you, how the standard backend stack is organized, and how to move your reasoning up and down that stack deliberately instead of getting stuck at one altitude for the whole interview.

## What an abstraction actually is

An abstraction is a boundary that lets one part of a system depend on *what* another part does without depending on *how* it does it. A database gives you a query interface — `SELECT`, `INSERT`, transactions — and hides B-trees, write-ahead logs, and disk I/O behind it. A load balancer gives upstream services one virtual address and hides the fact that there are 40 machines behind it, any of which might be unhealthy right now.

The payoff is that you can change the "how" without breaking anyone depending on the "what." You can swap a single Postgres instance for a sharded cluster, or replace round-robin balancing with least-connections, without touching the code that calls the interface. That's the whole point of layering a system instead of writing one undifferentiated blob of code that reads a socket, parses HTTP, runs business logic, and writes to disk all in one function.

The cost is that abstractions hide *behavior*, not just *implementation* — and behavior differences leak through when conditions change. A function call in-process is (almost) always going to return. A function call across a network layer might time out, might succeed on the server but lose its response on the way back, might get retried and executed twice. The interface looks the same (`response = call(request)`), but the failure modes underneath are completely different. Treating a remote call like a local one is one of the most common system design mistakes there is — the sibling lesson "Network Protocols and RPC" goes deeper on exactly this leak.

## The standard backend stack

Most request-driven backend systems decompose into the same layers, even when the box-and-line diagram looks different per company:

- **Client** — browser, mobile app, or another service. Cares about latency and a stable contract, not about anything below.
- **Edge / CDN** — terminates the connection close to the user, caches static or semi-static responses, absorbs the first layer of traffic before it reaches your infrastructure.
- **Load balancer / gateway** — distributes requests across a fleet, often also handling TLS termination, routing by path or header, and basic rate limiting.
- **Application / service tier** — where your business logic lives. This is frequently split further into multiple services, each owning a bounded piece of functionality (see "microservices" trade-offs, covered elsewhere in this course).
- **Cache** — an optional but extremely common layer sitting in front of storage to absorb read load and cut latency for hot data.
- **Storage / database** — the durable source of truth: relational, key-value, document, or object storage depending on the access pattern (covered in depth in "Storage Fundamentals and Data Models").
- **Network** — not a single box, but the connective tissue between every layer above; it's the thing every layer boundary actually crosses.

Not every system needs every layer — a small internal tool might skip the CDN and edge tier entirely — but the interviewer wants to see that you know which layers exist and can justify omitting one, not that you're unaware it exists.

## Moving between altitudes deliberately

A design review or interview constantly shifts between two modes, and the biggest tell of a junior answer is staying stuck in one:

- **Zoomed out** — "which layer is the bottleneck at 10x scale?", "where would we add a queue?", "what fails over if this region goes down?" This is reasoning about the boxes in the diagram above and the arrows between them.
- **Zoomed in** — "walk me through exactly what happens when this specific request hits the app tier," "what does the cache key look like," "what index does that query use?" This is reasoning inside one box.

A strong answer explicitly signals which altitude it's operating at: "Zooming out for a second — before we pick a database, let's confirm the read/write ratio, because that decides whether caching or sharding is the bigger lever." That sentence alone tells the interviewer you have a map of the whole stack and are choosing where to spend depth, rather than free-associating into whichever layer you thought of first.

A useful habit: when asked to "design X," resist the urge to open with a schema or a specific database product. Sketch the layer diagram first — even four boxes and a network line — and only then decide, out loud, which layer the interesting problem actually lives in. Half of interview time-pressure mistakes come from going deep on a layer that turns out not to matter for the question (e.g., debating index types for 30 seconds before establishing whether the system is read-heavy or write-heavy at all).

## Worked example: sizing where the bottleneck lives

Say you're asked to design a service that serves a celebrity's profile page, viewed 50,000 times per second at peak, updated by the celebrity maybe twice a day.

Walk the stack layer by layer with that read/write ratio in mind:

- **Edge/CDN**: 50k reads/sec of nearly-static content is exactly what a CDN is for — cache the rendered page or API response with a short TTL (say, 30 seconds) and invalidate on update. That alone can absorb the overwhelming majority of the load before it reaches your infrastructure.
- **Load balancer**: after the CDN absorbs cache hits, the origin only sees cache-miss traffic — a tiny fraction of 50k/sec — so the balancer and app tier don't need to be sized for the full peak.
- **App tier**: barely does any work per request — read from cache, format a response.
- **Cache (application-level, e.g. Redis)**: a second line of defense behind the CDN for any request the CDN can't serve (cache-cold regions, personalization).
- **Database**: sees, at most, two writes a day plus occasional cache-refill reads. It is nowhere near the bottleneck, and spending interview time on sharding it would be a mistake.

The point of the exercise isn't "know that CDNs exist" — it's that naming the layers explicitly and reasoning about traffic at each one tells you, quickly, that the interesting engineering here is caching and invalidation, not database scaling. A candidate who jumps straight to "let's shard the database" without asking about read/write ratio has skipped the step that would have told them the database was never the problem.

<Callout type="warning">
  A common interview mistake: presenting a system as one flat list of technology choices ("we'll use React, a Node.js API, Postgres, and Redis") instead of a layered diagram with responsibilities per layer. That format hides whether you understand *why* each piece is there — it reads as a shopping list, not a design. Draw boxes and arrows, label what each layer is responsible for, and only then attach a specific technology to a box if the question calls for it.
</Callout>
