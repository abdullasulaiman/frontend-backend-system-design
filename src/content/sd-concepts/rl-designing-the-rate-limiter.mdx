By now you know what a rate limiter needs to do ([Requirements for Rate Limiting](/system-design/rl-requirements-for-rate-limiting)), which counting algorithm to reach for ([Algorithms: Token Bucket, Leaky Bucket, and Windows](/system-design/rl-algorithms-token-bucket-leaky-bucket-and-windows)), and how to keep counters correct across many nodes ([Distributed Rate Limiting](/system-design/rl-distributed-rate-limiting)). None of that answers the question an interviewer asks next: where does this thing actually live, what talks to what, and what does a client see when it gets throttled? This lesson puts the pieces together into a single system you could describe on a whiteboard end to end.

## Where the limiter sits

The limiter needs to run *before* a request does any real work — before it opens a database connection, calls a downstream service, or renders a response. That pushes it toward the edge of your architecture, in one of three common spots:

- **API gateway / reverse proxy** — the limiter is a plugin or built-in feature of something like an API gateway or load balancer, sitting in front of every backend service. Centralized, easy to operate, and it protects every service behind it without each one implementing its own logic.
- **Sidecar** — each service instance runs a small proxy process alongside it that intercepts inbound traffic. Common in a service-mesh setup, and useful when different services need very different rules but you still want a shared implementation.
- **In-process middleware** — a library embedded directly in the application, running as the first thing in the request-handling chain. Simplest to add to an existing service with no infrastructure change, but every service now owns its own counting logic and its own bugs.

Most production systems default to the gateway option for anything facing external clients (mobile apps, partner APIs, public REST endpoints), and reserve sidecars or middleware for internal service-to-service limits where a shared gateway doesn't exist in the request path. Whichever you pick, the counting logic itself — the algorithm and the shared counter store from the distributed lesson — is the same component; only its deployment location changes.

## The building blocks

A working rate limiter is four cooperating pieces:

1. **Rule store** — maps a key (user ID, API key, IP, or a combination) plus an endpoint/route pattern to a limit: algorithm, threshold, and window. Rules change more often than code deploys (a customer negotiates a higher quota, an endpoint gets a tighter limit after an incident), so they belong in a small config service or a cache-backed table, not hardcoded constants.
2. **Counter store** — the shared state tracking how much of each key's quota is used, typically Redis or an equivalent in-memory store, as covered in the distributed lesson. This is the component under the most write load, since every single request touches it.
3. **Decision logic** — the algorithm (token bucket, sliding window, etc.) that reads the counter, decides allow or reject, and updates the counter — ideally as one atomic operation (a Lua script in Redis, or an atomic increment-and-compare) to avoid the race conditions the distributed lesson covered.
4. **Enforcement point** — the code that actually rejects or forwards a request based on the decision: the gateway plugin, sidecar, or middleware from the previous section.

## The client-facing contract

A rate limiter isn't just an internal accounting mechanism — it's an API contract with every caller. Two things make that contract usable rather than mysterious:

**The rejection response.** When a request exceeds its limit, return HTTP `429 Too Many Requests`, not a generic `503` or a silently dropped connection — the status code itself tells the client's HTTP stack "this is a rate limit, not an outage." Attach a `Retry-After` header telling the client how many seconds to wait before trying again; a well-behaved client uses this instead of guessing a backoff interval.

**Visibility into remaining quota.** Even on successful requests, return headers so clients can self-regulate before they ever get rejected:

- `X-RateLimit-Limit` — the total quota for the current window.
- `X-RateLimit-Remaining` — how much is left in the current window.
- `X-RateLimit-Reset` — when the window resets (as a Unix timestamp or seconds-from-now).

These header names aren't standardized across every provider (some use `RateLimit-*` per the newer IETF draft, some keep vendor-prefixed names), but the three pieces of information — limit, remaining, reset — are what every serious API exposes. A client library that reads these can throttle itself proactively instead of learning its limit by getting 429s.

## Deciding what happens when the limiter itself fails

The counter store is now a dependency on the hot path of every request, which means you must decide up front what happens when it's unreachable:

- **Fail-open**: if the counter store times out or errors, let the request through. This protects overall availability — a Redis blip shouldn't take down your entire API — but temporarily removes protection exactly when your infrastructure might already be stressed. Most public-facing APIs choose this, sometimes falling back to a cheap, conservative local-only limit (e.g., a per-instance in-memory cap) rather than fully unlimited traffic.
- **Fail-closed**: if the counter store is unreachable, reject the request. This guarantees the limit is never silently bypassed, at the cost of turning a counter-store outage into a full outage of the protected service. Reasonable for a limiter guarding something that would be badly damaged by an unthrottled burst (a fragile downstream write path, a paid third-party API you're billed per call for).

Whichever you choose, make it an explicit, monitored decision — "we didn't think about it" defaults to whatever your client library or Lua script happens to do on a connection error, which is rarely the behavior you'd have picked deliberately.

## Worked example: designing limits for a public API

Say you're adding rate limiting to a public API with three tiers: free (60 requests/min), pro (600 requests/min), and enterprise (custom, negotiated). Here's how the pieces fit:

The rule store holds one row per API key: `key_id -> { tier, limit, window }`. On login/key-issuance, a key's tier is looked up once and cached at the gateway for a few minutes (rules change rarely enough that a short TTL cache avoids hitting the rule store on every request). The gateway terminates every request, extracts the API key from the `Authorization` header, and asks the decision logic: "does `key_id` have quota against a sliding-window counter with this key's limit?" The decision logic runs an atomic Redis Lua script (from the distributed lesson) against a counter keyed by `key_id` plus the current window bucket. If allowed, the request proceeds and the response carries `X-RateLimit-Remaining: 41` alongside the actual API response; if rejected, the gateway short-circuits with `429` and `Retry-After: 12`, never touching the backend at all. Because the gateway also fails open with a conservative 10 requests/min fallback if Redis itself is down, a Redis blip degrades everyone briefly to "free-tier-ish" behavior instead of taking the API down entirely.

<Callout type="warning">
  A common mistake is rate-limiting only at the outermost edge and assuming that's sufficient. A single misbehaving internal service (a batch job with a bug, a retry storm from another team) can still overwhelm a downstream dependency without ever passing through the public gateway. Defense in depth means applying limits at more than one layer — the public gateway for external clients, and a second, separate limiter (often with different keys and limits) in front of anything internal that's expensive or fragile enough to need its own protection, like a payments service or a third-party API you pay per call.
</Callout>
