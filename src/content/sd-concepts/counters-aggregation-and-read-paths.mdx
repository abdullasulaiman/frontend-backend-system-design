The previous lesson solved the write side: instead of every increment
fighting over one row, you spread increments across N shards so no single
row is ever a bottleneck. But nobody wants to see "shard 3: 812, shard 7:
1,204, shard 12: 998..." — the product needs one number. A "247K likes"
counter, a live viewer count, a rate-limit check — all of them need a single
value back, fast, and the read path is where a sharded design either pays
off cleanly or quietly reintroduces the bottleneck you just removed. This
lesson is about turning N shard values into one number without turning every
read into a full table scan.

## The naive read: sum on demand

The simplest aggregation is also the most honest: on every read, run `SELECT
SUM(count) FROM counter_shards WHERE counter_id = ?` across all shards for
that counter. It's always exactly correct at the instant it runs, and it
needs zero extra infrastructure.

The catch is that this read cost scales with shard count, and shard count
scales with write volume — the two knobs are coupled. A counter popular
enough to need 200 shards for its write rate now needs a 200-row aggregation
for every single read of that counter. If reads outnumber writes (true for
almost every "like count" or "view count" — far more people see the number
than change it), you've moved the bottleneck from the write path to the read
path instead of removing it.

This approach is fine when reads are rare relative to writes, or when the
counter absolutely must reflect every write instantly (more on that below).
It's the wrong default for anything read-heavy.

## Caching the aggregate

The standard fix: compute the sum, then cache it for a short window instead
of recomputing on every read.

- A read first checks a cache (Redis, Memcached, an in-process LRU) keyed by
  counter ID.
- On a cache hit, return the cached value immediately — no shard fan-out at
  all.
- On a miss (first read, or TTL expired), do the full shard sum, write the
  result back to the cache with a TTL, and return it.

A 2-5 second TTL is often plenty. Nobody notices that a "1,204 likes"
counter briefly shows 1,199 while five likes land in the last two seconds —
but everyone notices if the like button takes 400ms to respond because every
click triggers a 200-shard sum.

This is the same trade-off every read-through cache makes: you're trading a
small, bounded amount of staleness for a large reduction in load on the
underlying store. The shard table still exists as the source of truth; the
cache just absorbs the read traffic.

## Rollups: precomputing instead of caching

Caching handles *load*, but every cache miss still pays the full fan-out
cost, and a cache stampede (many misses at once, e.g. after a mass eviction)
can still hammer the shard table. A **rollup** goes a step further: a
background job periodically sums all shards for active counters and writes
the result into a single "current total" row or cache entry, on a fixed
schedule (every second, every 10 seconds — whatever the product tolerates).

Reads then never touch the shard table at all — they read the rollup value,
which is always precomputed and always O(1) regardless of shard count. The
trade-off is the same staleness bound as caching (bounded by the rollup
interval), but reads are now decoupled entirely from the aggregation cost;
even a cold read after a cache eviction hits the cheap rollup value, not a
200-row sum.

Rollups work best when you have a bounded, known set of "hot" counters
(trending posts, popular products) worth precomputing continuously. For the
long tail of rarely-read counters, computing a rollup nobody asks for wastes
work — cache-on-read handles the tail better since it only computes what's
actually requested.

## Choosing exactness per counter, not per system

Not every counter needs the same freshness guarantee, and treating "the
counter system" as one monolithic consistency choice usually overspends on
counters that don't need it. Split counters into two buckets:

**Approximate is fine**: like counts, view counts, follower counts, trending
scores. Users have no way to notice a few seconds of staleness, and a slight
undercount right after a burst of activity is invisible. Cache or roll up
aggressively here — seconds of staleness for orders-of-magnitude less load
is a great trade.

**Exactness matters**: inventory counts at checkout, rate-limit counters,
quota enforcement, anything gating a decision ("can this user still post?",
"is this the last item in stock?"). Here, a stale read can cause a real bug
— overselling inventory, letting a rate-limited client through. For these,
read straight from the shard table (accept the fan-out cost) or use a
strongly consistent single source alongside the sharded counter for the
gating decision specifically, and let the sharded value be advisory or
UI-only.

The key insight: exactness is a per-counter product decision, not a
system-wide architecture decision. The same counter infrastructure can serve
both a "247K views" display (rollup, 10s staleness, totally fine) and a
"3 tickets left" gate (direct shard sum or a separate strongly-consistent
check) without contradiction.

## Worked example: a live-viewer counter

Say you're building a live-stream viewer counter for a stream with 50,000
concurrent viewers, sharded across 32 shards to absorb the join/leave
traffic (each join/leave is `+1`/`-1` to a randomly chosen shard).

Without any aggregation strategy, every page load that needs to display the
current viewer count triggers a 32-row sum. If the stream's viewer page
refreshes the count every 2 seconds for all 50,000 viewers, that's 25,000
reads/second, each doing a 32-shard sum — 800,000 row reads/second just for
display purposes, dwarfing the actual join/leave write rate.

Instead: run a rollup job every 2 seconds that sums the 32 shards once and
stores the result in a single Redis key (`stream:123:viewers`). All 25,000
viewer-facing reads/second now hit that one Redis key — a workload Redis
handles trivially — instead of the shard table. The displayed count is at
most 2 seconds stale, which for a live-viewer badge is not just acceptable,
it's how every major streaming platform actually does this.

<Callout type="warning">
  A common mistake: building the aggregation logic against a hardcoded shard
  count (`for i in range(32): sum += get_shard(i)`). Sharded counter systems
  often rebalance shard count as write volume grows or shrinks for a given
  counter. If the aggregation code doesn't read the *current* shard count
  from the same metadata the write path uses, a rebalance silently produces
  undercounts — reads keep summing the old shard count and miss the new
  shards entirely. Always derive shard count from the same source of truth
  the sharding/routing logic uses, never a constant.
</Callout>

## Summary

The write path (previous lesson) and the read path are solved by different
mechanisms and optimized for different things: writes get cheap by spreading
across shards, reads get cheap by avoiding touching all those shards on
every request. Caching handles load for arbitrary counters at the cost of
small bounded staleness; rollups go further for known-hot counters, making
reads O(1) regardless of shard count. The real design skill is deciding,
counter by counter, whether "roughly right, very fast" or "exactly right,
slower" is what the product actually needs — most counters want the former,
and treating every counter like a bank balance wastes the very scalability
the sharding gave you.
