The earlier lessons in this module built an inverted index and a ranking pipeline that both quietly assumed everything fits on one machine: one postings list per term, one process scoring and sorting results. That assumption holds for a corpus of a few million documents. It falls apart at the scale search actually gets designed for in interviews — a web-scale crawl, a product catalog with hundreds of millions of SKUs, a logging platform ingesting billions of events a day. No single machine holds that index in memory, and no single machine could score every candidate document for a busy query load fast enough anyway. Scaling a search system means answering two questions the single-node design ducked: how do you split the index across many machines, and how do you turn "search my index" into "search across a fleet of machines and still return one ranked, correct-looking list in under 200ms"?

## Splitting the index: document partitioning vs. term partitioning

There are exactly two ways to cut an inverted index into shards, and the choice shapes everything downstream.

**Document partitioning** assigns each document to exactly one shard (usually by hashing a document ID), and each shard builds a complete, self-contained inverted index over just its slice of documents. A query for "distributed systems" gets sent to every shard, and each shard independently finds its own best-matching documents from the postings lists it happens to hold.

**Term partitioning** instead splits the vocabulary itself: shard 1 might own postings lists for terms starting a-h, shard 2 for i-p, and so on, with each shard holding postings for every document that contains one of its assigned terms. A query only needs to visit the shards owning its query terms — potentially far fewer than "all of them."

In practice, document partitioning wins the majority of real designs, for reasons that matter more than the query-fan-out savings term partitioning promises:

- **Independence.** Each document-partitioned shard is a fully self-sufficient search engine. You can add shards, move a shard to new hardware, or rebuild one shard's index without touching any other shard's data or code path.
- **Balanced load in practice.** Hashing document IDs spreads documents (and therefore index size and query load) evenly across shards almost for free. Term partitioning's load balance depends on query term frequency, which is wildly skewed — a shard holding common terms like "the" or "app" gets hammered while a shard holding rare terms sits idle.
- **Multi-term queries are cheap either way.** A real query like "best noise cancelling headphones" needs postings for four terms. Document partitioning sends that whole query to every shard once; term partitioning has to fetch postings for four different terms from up to four different shards and then intersect them per-shard anyway, which erodes the "fewer machines touched" advantage as queries get longer.

Term partitioning still shows up where the win is real: extremely selective, single-term-dominant lookups (log search on a fixed set of tags, for example), or when the corpus is too large to reasonably replicate across every shard for every query. For a general-purpose search interview answer, default to document partitioning and be ready to explain the trade-off if asked.

## Query fan-out: scatter-gather

However you shard, a query almost never resolves on one machine. The standard pattern is scatter-gather, coordinated by a broker (sometimes called a query aggregator or root node):

1. The broker receives the query and sends it to one replica of every shard in parallel.
2. Each shard runs its own retrieval and ranking (the work from the Querying and Ranking lesson), scoped to only the documents it holds, and returns its local top-K candidates with scores.
3. The broker merges all shards' top-K lists into one globally ranked top-N, using each candidate's score, and returns that to the client.

The subtlety interviewers probe for: merging only works cleanly if scores are **comparable across shards**. If one shard's scoring depends on corpus-wide statistics — inverse document frequency, for instance, which needs to know how rare a term is across the *entire* collection, not just one shard's slice of it — then each shard computing IDF locally against only its own documents produces scores that aren't directly comparable to another shard's. Real systems either approximate (accept the slight skew, since it washes out at scale) or maintain small periodically-refreshed global term statistics that every shard shares when scoring.

## Replication: availability and read capacity

Every shard is replicated, and the reason is two-fold, not one. Replicas obviously provide failover — if a shard's only copy dies, the whole document range it holds becomes unsearchable. But replicas are just as important for absorbing query volume: a document-partitioned shard under high read QPS needs multiple replicas serving reads in parallel the same way any read-heavy service does, entirely independent of failure tolerance. The broker load-balances each fan-out request across whichever replica of a shard is healthiest and least loaded, the same way a load balancer picks among backend instances for any service.

This is also where a coordination layer (something like a cluster metadata service tracking which nodes hold which shard replicas, and their health) earns its keep — the broker needs a live, accurate map of shard-to-replica-to-node to route each fan-out correctly and to route around a dead node without stalling the whole query.

## Keeping a sharded index fresh

Rebuilding a shard's entire index every time a document changes doesn't scale once the corpus is large — the earlier indexing lesson's batch-build process is fine for the initial corpus but far too slow to make a single new or edited document searchable within seconds. The standard fix layers two paths:

- A large, mostly-static **base index**, built in batch (or incrementally merged) and optimized for compact size and fast lookups.
- A small, frequently-updated **near-real-time segment** holding just-arrived documents, which gets searched alongside the base index and periodically merged into it once it grows large enough.

Each shard runs this two-tier structure independently. A document's write goes to its shard's near-real-time segment first (fast, but a less-optimized data structure), and becomes part of the compact base index later during a background merge — the same segment-merging idea as an LSM-tree, applied to postings lists instead of key-value pairs.

## Worked example: sizing shards for a large corpus

Say you're indexing 4 billion documents, and a single shard performs well up to roughly 20 million documents before query latency degrades past your budget (postings lists get too long to intersect and score quickly). That's `4,000,000,000 / 20,000,000 = 200` shards as a floor.

Add replication for availability and read throughput — say 3 replicas per shard for reasonable read parallelism and to survive a node loss without dropping a shard entirely. That's `200 x 3 = 600` total index-serving processes, before accounting for the broker tier, the indexing pipeline, or any caching layer in front of it. Sizing this way — starting from "how much can one shard handle" and dividing into the total corpus — is the concrete number an interviewer wants to see instead of "we'll just add more shards."

<Callout type="warning">
  A common mistake: designing scatter-gather without a per-shard timeout, then having the whole query's latency held hostage by a single slow or overloaded replica. If a broker waits unconditionally for every shard to respond, one straggler shard turns a 50ms query into a multi-second one for every user, no matter how fast the other shards were. The fix is a strict per-shard timeout with partial results — return the best answer from whichever shards responded in time, and treat late shards as empty for that request, accepting a small, rare hit to recall in exchange for a latency ceiling that actually holds.
</Callout>
