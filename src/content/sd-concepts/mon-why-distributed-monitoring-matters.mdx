A single server that starts failing is easy to notice: SSH in, run `top`,
tail a log file, and the problem is usually right in front of you. A
distributed system doesn't offer that luxury. When a request touches a load
balancer, three microservices, a cache, and a database replica, "is the
system healthy" stops being a question one person can answer by looking at
one machine. At 5 hosts you might get away with manually checking things. At
500 hosts serving traffic across three regions, a slow but silent failure in
one dependency can degrade the whole system for hours before anyone notices
— unless something is watching continuously and telling you when to look.

That "something" is a monitoring system, and it's one of the pieces of
infrastructure that separates a system that merely works in a demo from one
that survives production. This lesson covers why monitoring becomes
mandatory at scale, what signals it needs to collect, and the pitfalls that
turn a monitoring system into background noise instead of a safety net. The
next two lessons in this module get into the mechanics of collecting and
storing that data, and the architecture of a monitoring system end to end.

## What changes when a system becomes distributed

In a monolith on one box, failure is usually total: the process crashes, or
it doesn't. In a distributed system, failure is partial and constant. At any
given moment, some small fraction of a large fleet is having a bad time —
a disk is slow, a network link is dropping packets, a garbage collection
pause is stalling one JVM instance. None of that is unusual; it's the normal
operating condition of a big fleet. The question isn't "is anything broken"
(something almost always is) but "is enough broken to matter, and is it
getting worse."

That reframing is why distributed monitoring is a different problem from
"check if the server is up." You need:

- **Visibility across machines you don't individually track.** Nobody
  should need to know which of 500 hosts is unhealthy by name; the system
  should say "2% of requests are failing" and let you drill down from there.
- **Aggregation over time and across the fleet.** A single slow request
  means nothing; a p99 latency that jumped from 200ms to 2 seconds across
  the fleet over the last 5 minutes means something is actively going wrong.
- **A way to distinguish "the whole system is unhealthy" from "one dependency
  is unhealthy but we're compensating."** Retries and failover can mask a
  failing dependency from users while quietly eating your error budget —
  monitoring is often the only way this gets caught before it turns into a
  bigger outage.

## The four signals: metrics, logs, traces, alerts

Most monitoring systems are built from four kinds of signal, each answering
a different question and priced differently in storage and query cost.

**Metrics** are numeric measurements aggregated over time — request count,
error rate, CPU utilization, queue depth — usually recorded as a time series
with a name and a set of labels (e.g. `http_requests_total` labeled by
`service` and `status_code`). They're cheap to store and fast to query
because they're pre-aggregated, which makes them the right tool for
dashboards and for triggering alerts. What they can't do is tell you *why*
one specific request failed.

**Logs** are detailed, timestamped records of individual events — a request
came in, an exception was thrown, a cache miss occurred. They're the most
detailed signal and the most expensive to store and search at volume,
because you're keeping the raw event, not an aggregate. Logs are where you
go once a metric tells you something's wrong and you need to know exactly
which requests, users, or error messages were involved.

**Traces** follow a single request as it hops across services, recording how
long each hop took and where it went. In a system with a dozen
microservices, a trace is often the only way to answer "why did this one
request take 3 seconds" when no individual service looks obviously slow in
isolation — the time is hiding in the sum of many small, individually
acceptable delays, or in one slow hop buried three services deep.

**Alerts** are rules layered on top of metrics (and sometimes logs) that
turn "the data says X" into "a human should look at this now." Alerting is
where monitoring becomes actionable — collecting the other three signals
without alerting on them just produces a very detailed record of an outage
nobody was told about while it was happening.

## Detection speed is the point

The real payoff of monitoring shows up in two numbers incident responders
track: **MTTD** (mean time to detect — how long between something breaking
and someone finding out) and **MTTR** (mean time to recover — how long from
detection to the fix being live). Monitoring's main job is shrinking MTTD.
You can't start fixing a problem you don't know exists, and in a fleet of
hundreds of machines, "someone happened to notice" is not a detection
strategy.

A useful way to frame alert design: distinguish **symptom-based** signals
from **cause-based** signals. Symptoms are things users actually feel —
elevated error rate, slow response time, failed checkouts. Causes are the
underlying resource state — high CPU, a full disk, a saturated connection
pool. Page on symptoms, because that's what tells you users are affected;
keep cause-based signals available for the engineer who gets paged to
diagnose *why*, but don't wake someone up because CPU crossed 80% if nothing
downstream is actually degraded yet. A server can run hot for hours with
zero user impact if it's provisioned with headroom.

## Worked example: catching a slow leak before it's an outage

Say you run a checkout service behind a load balancer, backed by a payments
API and an inventory database. One deploy introduces a subtle bug: a
database connection isn't released after a specific, rare error path. Each
occurrence leaks one connection from the pool.

Without monitoring, here's how this plays out: connections leak slowly,
nobody notices, and three days later the pool is exhausted, every checkout
request stalls waiting for a connection, and customers start abandoning
carts before anyone on the team even opens a laptop. Detection happens when
support tickets pile up — MTTD measured in hours, and the root cause is
buried under three days of unrelated deploys.

With monitoring in place: a metric tracks `db_pool_connections_in_use` as a
percentage of pool size, and an alert fires when it stays above 80% for 10
minutes. The graph shows a slow, steady climb starting right after the bad
deploy — a saw-tooth pattern replaced by a monotonic ramp. The on-call
engineer gets paged well before exhaustion, correlates the ramp's start time
against the deploy log, and rolls back the one suspect deploy. MTTD drops
from days to minutes, and the incident never reaches a user-visible outage
at all. The bug is the same in both scenarios — the only difference is
whether anything was watching the trend.

<Callout type="warning">
  A common mistake: building elaborate dashboards and skipping alerting,
  on the theory that "we'll just check the dashboard." Nobody checks a
  dashboard continuously, and the incidents that matter most tend to start
  outside business hours. If a signal is important enough to graph, ask
  whether it's important enough to alert on — and if it is, write the
  alert rule, don't just add another panel. The inverse mistake is just as
  common: alerting on every metric that *can* fire, which trains engineers
  to ignore pages (alert fatigue) until the one page that mattered gets
  dismissed along with the noise.
</Callout>

<Callout type="note">
  Watch cardinality — the number of unique label combinations a metric can
  take. A metric labeled by `service` and `region` might have a few dozen
  combinations; the same metric labeled by raw `user_id` can have millions,
  and most time-series databases store and index every unique combination
  separately. High-cardinality labels are one of the fastest ways to make a
  monitoring system itself expensive and slow — a theme the next lesson
  covers in more depth.
</Callout>
