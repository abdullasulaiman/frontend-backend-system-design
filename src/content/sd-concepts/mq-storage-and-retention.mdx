The previous lessons in this module treated "the queue" as a black box that
accepts a message and eventually hands it to a consumer. That box has to
actually keep the message somewhere between those two events — and *how*
it stores it determines almost everything else about the system's
behavior: whether a broker crash loses data, whether a slow consumer can
fall behind without the queue running out of room, whether you can replay
last Tuesday's events to rebuild a downstream cache, and how much you pay
in disk and network for all of it. Storage and retention aren't
implementation detail you can defer to "whatever the database does" — the
storage model *is* the design decision that makes durable, replayable
messaging possible in the first place.

## Two storage models, and why one wins

A naive queue could store each message as a row in a table and delete the
row once a consumer acknowledges it. That works for a single consumer
group, but it breaks the moment you need two independent consumers to read
the same message (say, a fraud-detection service and an analytics
pipeline both subscribed to the same order-events queue) — whichever
consumer acks first deletes the message out from under the other.

The model almost every durable messaging queue uses instead is an
**append-only log**: messages are written sequentially to the end of a
file (or a set of files called **segments**), and they stay there,
untouched, until a retention policy — not a consumer ack — decides they're
old enough to discard. Consumers don't remove messages by reading them;
they track their own **offset** (a position, effectively "I've read up
through byte/record N"), and reading forward just means walking the log
past that point. Multiple consumer groups can read the same log at
completely different offsets without interfering with each other at all,
because none of them mutate the log — they only advance their own
private cursor.

This distinction matters for an interview: if you say "the queue deletes a
message once it's consumed," you've just made independent consumer groups
and replay impossible, and a good interviewer will ask how you'd support a
second consumer that needs to reprocess the last day's data. "It's a log,
consumers track their own offset, retention is separate from consumption"
is the answer that keeps those doors open.

## Segments: why the log isn't one giant file

A partition's log is split into **segments** — files capped at a size
(commonly a few hundred MB to a few GB) or a time window (e.g., a new
segment every hour). Only the newest segment is ever appended to; every
older segment is closed and immutable. This split matters for two
operational reasons:

- **Deletion is cheap.** Enforcing retention means deleting whole closed
  segment files once they age out, which is a fast file-system unlink, not
  scanning and rewriting a giant file to remove old records one by one.
- **Indexing is cheap.** Each segment gets a small companion index
  mapping offsets (or timestamps) to byte positions within that segment,
  so a consumer asking "give me everything after offset 4,522,001" or
  "give me everything after 3pm yesterday" can jump straight to the right
  segment and byte range instead of scanning from the beginning.

Sequential writes to the active segment, plus the OS page cache serving
recent reads straight from memory, are what let log-structured storage
sustain very high throughput on ordinary disks — there's no random-access
read/write pattern to fight, which is the same reason B-tree-heavy
databases often struggle to keep up with append-only logs on write-heavy
workloads.

## Retention policies: when does data actually go away

Retention decides how long a segment sticks around after it's closed,
independent of whether anyone has consumed it yet. The common policies,
usually combined:

- **Time-based**: delete segments whose newest message is older than a
  configured window (24 hours, 7 days, 30 days). Simple to reason about
  and to size capacity for.
- **Size-based**: cap total log size per partition (or per topic); when
  the cap is hit, delete the oldest segment(s) first, regardless of age.
  This protects disk from filling up if throughput spikes unexpectedly.
- **Whichever limit hits first wins.** Most production configs set both —
  a 7-day time limit *and* a size cap — so a sudden 10x traffic spike
  doesn't silently blow past the disk budget while waiting for the time
  window to kick in.

### Log compaction: a different kind of retention

Time and size-based retention delete by *age*. **Log compaction** instead
deletes by *key*: for a log where each message has a key (e.g., a user
ID) and represents "the current value for this key," compaction keeps
only the most recent message per key and discards older ones, no matter
how old the most recent one is. This is the right model for a topic
representing current state — "user 482's latest profile," "product 91's
latest price" — where you only ever care about the newest value and want
a consumer that reads the whole log from the start to end up with exactly
current state, not a full history of every intermediate update.

Compaction is the wrong tool for an event stream where every individual
event matters (every order placed, every payment attempted) — compacting
that would silently destroy history a downstream system may need to
replay or audit. Pick per-topic based on whether the topic models "facts
that happened" (keep them all, time/size retention) or "current state"
(keep only the latest, compaction).

## Storage cost and replication

Retained data has to live somewhere durable, and durability almost always
means **replication** — the same message stored on multiple broker nodes
so a single disk or node failure doesn't lose it (mechanically similar to
the replication covered in the key-value store module, applied here to
log segments instead of key-value records). That means your actual
storage budget is `retained data x replication factor`, not just the raw
retained data — a detail that's easy to forget when sizing a cluster and
expensive to discover after the fact.

### Tiered storage for long retention

Keeping months of data on the same fast local disks every broker uses for
active writes gets expensive and doesn't scale independently of
throughput. **Tiered storage** splits this: recent segments (say, the
last 24-48 hours) stay on local disk for low-latency reads, while older,
closed segments get offloaded to cheaper object storage (S3-style
blob storage). Consumers reading recent data hit local disk; consumers
replaying old history hit object storage at higher latency but far lower
cost per GB. This is how a queue can offer 90-day or 1-year retention
without every broker needing a 90-day-sized local disk.

## Worked example: sizing storage for an order-events queue

Say you're designing the order-events queue for an e-commerce platform:
50,000 messages/sec sustained, average message size 1 KB, required
retention window of 7 days, replication factor 3.

Raw ingest rate: `50,000 msg/s x 1 KB = ~50 MB/s`.

Per day: `50 MB/s x 86,400 s/day = ~4.3 TB/day`.

Retained (7 days, one copy): `4.3 TB/day x 7 = ~30 TB`.

With replication factor 3: `30 TB x 3 = ~90 TB` of total cluster disk
just for this one queue's retained data — before accounting for indexes,
in-flight segments, or headroom for traffic spikes (most teams provision
30-50% headroom above the raw retention math). This is the number that
turns into "how many brokers, how much disk per broker" — if each broker
has 4 TB of usable disk, this queue alone needs roughly 22-23 brokers'
worth of disk capacity, which is exactly why retention window is a
cost lever teams tune aggressively: dropping retention from 7 days to 3
days cuts this queue's storage need by more than half.

<Callout type="warning">
  A common mistake is assuming an acknowledged message can be deleted
  immediately, the way a traditional task queue deletes a job once a
  worker finishes it. In a log-structured durable queue, acking tells the
  broker "this consumer group is done with this message" — it does not
  free any disk, because other consumer groups may still need it and
  retention is governed by the time/size policy, not by consumption.
  Conflating the two leads to two failure modes: either engineers panic
  that "acked messages aren't being deleted, is there a leak?" (there
  isn't — that's by design), or they set retention far shorter than
  necessary assuming acked data is already gone, and then a slow or
  temporarily-down consumer group falls behind its own offset far enough
  that the messages it still needs have already expired and are
  unrecoverable.
</Callout>
