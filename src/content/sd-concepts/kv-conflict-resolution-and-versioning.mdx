The previous lesson set up quorum-based replication: a write is durable once `W` replicas acknowledge it, and a read is consistent enough once you've queried `R` replicas. That design keeps the store available even when a replica is slow or partitioned — but it opens a gap. If two clients write the same key to two different replicas during a partition, or a replica misses an update and later rejoins with stale data, you can end up with more than one "current" value for a key. Someone has to decide what the real value is. That someone is the conflict-resolution layer, and how you build it is one of the most consequential decisions in a key-value store's design.

## Why conflicts happen at all

Conflicts are the direct cost of choosing availability under partition (the AP side of CAP, covered in the NFR module). A strongly consistent, single-leader store avoids this problem by refusing concurrent writes to the same key — every write goes through one leader, in order. A store that accepts writes at multiple replicas, or that keeps serving writes even when some replicas are unreachable (sloppy quorums and hinted handoff from the replication lesson), trades that guarantee away for uptime. The result: two versions of `user:42:profile` can both be "valid" for a moment, and the system needs a rule for what happens next.

## Detecting conflicts: timestamps vs. causality

The simplest approach is **last-write-wins (LWW)**: tag every write with a timestamp, and when two versions collide, keep the one with the later timestamp. It's cheap, requires no extra metadata beyond a clock reading, and works fine for data where losing an update occasionally is acceptable — a view counter, a session cache, a "last seen online" field. The catch is that "later" depends on clocks agreeing, and clocks on different machines never agree perfectly. A write that logically happened second can carry an earlier timestamp because its server's clock drifted, and LWW will silently discard it with no error, no retry, and no signal to the client that anything was lost.

**Vector clocks** fix the underlying problem by tracking causality instead of wall-clock time. Each key's version carries a small map of `{replica_id: counter}`. Every time a replica handles a write for that key, it increments its own counter in the map. Comparing two version vectors tells you one of two things:

- One vector's counters are all `≥` the other's (and at least one is strictly greater) — the first is a **descendant** of the second. It's safe to just keep the newer one; the old one is truly obsolete.
- Neither vector dominates the other — the writes are **concurrent**. They happened without either replica knowing about the other, and there's no safe automatic choice. Both versions ("siblings") must be kept until something resolves them.

That second case is the interesting one. LWW would just pick a winner and lose data; a vector-clock-based store instead surfaces both siblings — typically on the next read — and pushes the actual decision to whoever can make it safely: the application, a user, or a merge function.

## Who reconciles: server, client, or the data type

There are three places reconciliation logic can live, and each pushes complexity somewhere different:

**Server-side, automatic (LWW).** The store decides on its own, using a total order it can compute cheaply — usually a timestamp, sometimes a fixed replica-priority tiebreak. No application code needed, but the store can silently drop a write it had no business dropping.

**Client-side, application-driven.** The store detects concurrency (vector clocks) but doesn't guess at semantics — it hands both siblings back to the application, which knows what merging *means* for that data. A shopping cart merges by unioning items. A "list of a user's devices" merges by unioning device IDs. A bank balance almost never merges automatically — that one probably shouldn't be a plain KV write in the first place. This is more work per data type, but it never silently loses information the application cares about.

**Data-structure-driven (CRDTs).** Conflict-free replicated data types bake the merge function into the type itself, so *any* two versions merge deterministically and the result is provably consistent no matter the order updates arrive in. A G-counter (grow-only counter) merges by taking the max of each replica's partial count. An OR-set merges by unioning adds and removing only elements whose specific "add tag" is also in the other side's tombstones. CRDTs are the least error-prone option when your data fits one of the known types, but they don't generalize to arbitrary values — you can't wrap "any JSON blob" in a CRDT and expect a sane merge.

Most production key-value stores mix these: LWW as the default for opaque blobs, vector clocks (or a variant) for callers who opt into sibling resolution, and CRDT-backed counters/sets as a specialized value type.

## Closing the loop: read repair and anti-entropy

Detecting and resolving a conflict on one read doesn't fix the other replicas that are still holding the stale version. Two background mechanisms handle that, both building on the quorum reads/writes from the replication lesson:

- **Read repair**: when a quorum read discovers replicas disagree, the coordinator pushes the resolved (or newer) version back to the stale replicas right then, piggybacking the fix on a read that was happening anyway.
- **Anti-entropy**: replicas periodically compare data even without a client read triggering it, using Merkle trees to diff large key ranges in `O(log n)` comparisons instead of transferring every key. Any range whose hash differs gets walked down to the actual mismatched keys, which then go through the same conflict-resolution path.

Without one of these, a replica that missed a write during a partition can stay stale indefinitely — quorum reads mask it from clients, but the underlying divergence never gets cleaned up.

## Worked example: sizing vector clock overhead

Suppose your store has 300 nodes, and hot keys typically get written through 5-10 distinct coordinators over their lifetime before you prune. A vector clock entry is roughly a node ID (8 bytes) plus a counter (4-8 bytes) — call it 16 bytes per entry. A key with 8 active entries costs about 128 bytes of clock metadata. On a value that's itself 200 bytes (a small profile record), that's a 64% overhead — not free, but tolerable. The real risk is unbounded growth: if you never prune and a key gets touched by dozens of coordinators over months, the clock can eventually outweigh the value itself. Production systems cap this by dropping the oldest entries once the vector exceeds a size threshold (accepting a small risk of re-flagging an already-resolved version as a false conflict) or by expiring entries older than a time window.

<Callout type="warning">
  The most common mistake teams make here is defaulting to last-write-wins on wall-clock timestamps for data where losing a write is actually a problem — then discovering the loss only when a customer complains that "my item disappeared from my cart" or "my settings reverted." Clock skew of even a few hundred milliseconds across data-center replicas is normal, not exceptional, and LWW has no way to distinguish "genuinely older" from "clock was behind." Reserve LWW for data where staleness is cheap (caches, presence, counters where a CRDT fits better anyway), and use causality tracking wherever a lost write would be a real, visible failure to a user.
</Callout>
