Once you've decided a CDN belongs in your architecture, the next real design
decision is how content actually gets onto the edge servers. Two strategies
dominate: **push**, where you proactively upload content to edge nodes ahead
of demand, and **pull**, where edge nodes fetch content from your origin the
first time someone asks for it, then cache it locally. Interviewers ask
"push or pull?" specifically to see whether you can reason about a
trade-off from first principles rather than name-drop a vendor. The right
answer depends on how big your content catalog is, how often it changes,
and how much cold-start latency and origin load you can tolerate.

## Push CDNs: you control when content arrives at the edge

In a push model, you (the content owner) explicitly copy files to the CDN's
edge storage — usually via an API call or a sync job — before any user
requests them. The edge node already has the object sitting in local
storage when the first request for it arrives, so that request is a local
hit with no origin round trip.

This works well when:

- **The catalog is small and finite.** A marketing site's JS/CSS bundles, a
  handful of hero images, or a fixed set of transcoded video renditions are
  all things you can enumerate and push everywhere.
- **Content changes are known events you control.** You deploy a new build,
  you push the new files, done — no need for the edge to "discover" that
  something changed.
- **You want every edge node warm before traffic arrives.** A product
  launch or a livestream you know is coming can be pre-staged across every
  region so the very first viewer in Tokyo gets the same latency as one in
  Ohio.

The cost is that you're paying storage (and possibly egress) for every
region whether or not anyone in that region ever requests the content, and
every content change requires you to actively re-push or purge — there's no
"the edge will just notice and refetch" safety net.

## Pull CDNs: the edge fetches on demand

In a pull model, the edge node does nothing until a user requests an object
it doesn't have cached. On that first request — a **cache miss** — the edge
node fetches the object from your origin (or from a nearer upstream tier),
serves it to the user, and stores a copy locally according to a TTL or
cache-control header. Every subsequent request to that same edge node for
the same object is a **cache hit** served straight from the edge, no origin
involved, until the cached copy expires or is evicted.

This works well when:

- **The catalog is large or unbounded.** User-uploaded photos, a long tail
  of product images, or per-user generated content aren't things you can
  reasonably pre-push everywhere — most of it will never be requested from
  most regions.
- **Demand is unpredictable or long-tail-shaped.** Pulling means you only
  ever cache what's actually being asked for in each region, so you don't
  waste storage on objects nobody near that edge node cares about.
- **You'd rather manage staleness with TTLs than with active pushes.** Set
  `Cache-Control: max-age=3600` once and let expiry do the work instead of
  wiring up a purge pipeline for every change.

The cost is the mirror image of push's benefit: the very first request for
any object at any given edge node pays full origin latency, and if that
object is genuinely hot (a viral post, a flash-sale product page) many edge
nodes can all miss at once and all hammer the origin simultaneously — the
classic **thundering herd** or **flash-crowd** problem pull CDNs must guard
against.

## Guarding pull CDNs against origin overload

Because pull CDNs fetch on miss, two techniques matter in practice, and
interviewers like hearing you name them:

- **Request collapsing (a.k.a. request coalescing).** If ten thousand
  requests for the same missing object arrive at an edge node within the
  same few milliseconds, the edge should send exactly one request to origin
  and hold the other 9,999 waiting for that single response, rather than
  forwarding all ten thousand. Most CDN providers do this automatically.
- **Origin shielding.** Instead of every regional edge node independently
  falling back to origin on a miss, route all misses through one
  designated "shield" cache layer sitting between the edge tier and origin.
  The shield absorbs the fan-in from many edge nodes so origin only ever
  sees one miss per object, not one miss per edge location.

Neither technique exists in a pure push model, because push never has
cache misses at request time — it front-loads all the cost into the
upload step instead.

## Worked example: rolling out a new product catalog image set

Say you run an e-commerce site with 2 million product images and you're
launching a redesign that replaces every product's primary image.

**If you push:** you'd need to upload all 2 million new images to every one
of, say, 30 global edge regions before launch — 60 million file copies,
most of which (any product with low traffic in a given region) will sit
unused. Storage cost scales with `regions × catalog size`, and you've
built an active re-upload pipeline that must run correctly on every future
catalog update.

**If you pull:** you deploy the new images to origin, set a sensible
`Cache-Control` TTL, and optionally issue purges for the old URLs. Each
edge region only ever caches the products actually browsed by users near
it — a small, regional retailer's storefront in one country might only
ever pull the 5,000 products popular there, not all 2 million. The
trade-off: the first shopper to view any given product in a freshly
deployed region pays one origin round trip; every shopper after that in
that region is fast. For a catalog this large and this regionally skewed
in popularity, pull is the clear choice — pushing 60 million mostly-unused
copies is paying for storage you'll never use.

Contrast that with pushing the redesign's shared CSS/JS bundle: that's one
small file every visitor needs regardless of region, so pushing it
everywhere ahead of launch avoids any cold-start penalty at all — a case
where push is strictly better.

<Callout type="warning">
  A common mistake in interviews: treating "push vs. pull" as a single
  binary choice for the whole system. Real systems mix both — push the
  small, universal, slow-changing assets (app shell, shared images) and
  pull the large, long-tail, unpredictable content (user uploads, product
  catalogs). Presenting only one model for every asset type signals you
  haven't thought about content shape, and it's an easy thing for an
  interviewer to probe by asking "would you push *that* too?"
</Callout>
