Say you're asked to find every document containing the word "timeout" across ten million support tickets. Scan every document, split it into words, and check: that's ten million documents times however many words each one holds, done on every single query. At web scale that's not slow — it's impossible. Every real search system, from a Postgres `tsvector` column to Elasticsearch to Google, solves this the same way: build a data structure once, ahead of time, that turns "which documents contain this word" into a direct lookup instead of a scan. That structure is the inverted index, and how you build it shapes everything downstream — what queries you can answer, how fresh your results are, and how much hardware you need.

This lesson covers how raw documents become an inverted index: the analysis pipeline that decides what a "word" even is, the index structure itself, and how it's built and updated at scale. The next lesson in this module picks up from there and covers querying and ranking those results.

## Why "inverted"

A **forward index** maps documents to the terms they contain — document 42 contains "outage", "timeout", "retry". That's the natural way to store a document, and it's useless for search: to answer "which docs contain 'timeout'" you'd still have to scan every forward index entry.

An **inverted index** flips the relationship: it maps each term to the list of documents that contain it.

```
"timeout"  -> [doc 42, doc 107, doc 3391, ...]
"outage"   -> [doc 42, doc 88, ...]
"retry"    -> [doc 42, doc 501, ...]
```

Each list is called a **postings list**. Looking up a single term is now `O(1)`-ish (a hash or B-tree lookup into the term dictionary) plus reading a list of document IDs — no scanning of document content at query time at all. A multi-term query like "timeout AND retry" becomes an intersection of two postings lists, which is fast because both lists are stored sorted by document ID.

This is the same trick a relational database's secondary index uses (see the sibling lesson on database indexing) — trade write-time and storage cost for read-time speed. The difference is *what* gets indexed: a DB index is built on a column value; a full-text inverted index is built on every distinct token extracted from unstructured text, which is why the pipeline that produces those tokens matters so much.

## The analysis pipeline: deciding what counts as a term

Before anything goes into the index, raw text passes through an **analyzer**. This step is where most of the actual design decisions in a search system live — get it wrong and no index structure will save you.

A typical pipeline:

1. **Tokenization** — split text into candidate terms. "The API returned a 500 error" becomes tokens like `the`, `api`, `returned`, `a`, `500`, `error`. Sounds trivial until you hit hyphenated words, contractions, URLs, or CJK languages with no whitespace between words at all — tokenization rules are language- and domain-specific.
2. **Lowercasing / normalization** — so "API" and "api" match the same postings list. Also handles accents, Unicode normalization forms, and sometimes number/date normalization.
3. **Stopword removal** — drop extremely common words ("the", "a", "is") that appear in nearly every document and add index size without adding discriminating power. Optional: some systems keep stopwords for exact-phrase queries.
4. **Stemming / lemmatization** — reduce words to a root form so "running", "runs", and "ran" all index under "run". Stemming is a fast heuristic (chop suffixes); lemmatization is a slower, dictionary-based reduction to the true root. This step directly trades **recall** (find more relevant docs by matching more word forms) against **precision** (avoid matching unrelated words that happen to share a stem).

The output of this pipeline is a stream of normalized tokens per document — those tokens, not the raw words, are what actually gets indexed. Two search engines can index the identical raw documents and return completely different results because their analyzers differ.

## Building the index

For each document, run the analyzer to get its token stream, then for each token, append `(document ID, position)` to that token's postings list. Storing the **position** within the document (not just "this doc contains this term") is what enables phrase queries later — "network timeout" as an exact phrase needs to confirm "timeout" appears at position immediately after "network", not just that both words appear somewhere in the document.

At small scale you can build this in memory. At scale, the standard approach is:

- Process documents in batches, building small in-memory index **segments**.
- Flush each segment to disk once it hits a size threshold, with postings lists already sorted by document ID.
- Periodically **merge** segments in the background, combining postings lists for the same term across segments — much like how an LSM-tree compacts SSTables.

This segment-and-merge design is why systems like Elasticsearch/Lucene can accept a continuous stream of writes without re-sorting the entire index on every update: new documents land in a fresh small segment, and merges happen asynchronously. It also means a document is searchable as soon as its segment is written, not only after a full index rebuild — the trade-off is that a query has to check every unmerged segment and combine results, so too many small segments slows queries down until the next merge.

## Postings list storage: why compression matters

For a corpus of any real size, postings lists dominate index size — common terms can have postings lists with millions of entries. Two techniques keep this manageable:

- **Delta encoding**: since a postings list is sorted by document ID, store the *gap* between consecutive IDs instead of the IDs themselves. Gaps are small numbers, which compress far better than arbitrary large IDs.
- **Variable-byte or bit-packed encoding**: encode each (usually small) delta using as few bytes/bits as it needs, rather than a fixed 4 or 8 bytes per entry.

Together these can shrink postings lists by 5-10x, which matters directly for cost: smaller postings lists mean more of the index fits in memory or page cache, which is the difference between a query hitting RAM and a query hitting disk.

## Worked example: sizing an index for support tickets

Say you're indexing 50 million support tickets, averaging 200 words each after analysis, with roughly 400,000 distinct terms (a realistic vocabulary size once stopwords are removed and stemming collapses word variants).

- Total tokens to index: 50,000,000 × 200 = 10 billion token occurrences.
- Each occurrence becomes one postings-list entry: a document ID (delta-encoded, say ~1-2 bytes average after compression) plus a position (another 1-2 bytes compressed). Call it roughly 3 bytes per occurrence after compression.
- Raw postings storage: 10,000,000,000 × 3 bytes ≈ 30 GB.
- Add the term dictionary (400,000 terms, mapping term to postings-list location) — tiny by comparison, low tens of MB.

So a 50M-document corpus compresses down to roughly 30 GB of postings data — small enough to shard across a handful of nodes and keep mostly in memory, which is exactly why the inverted index approach scales where a linear scan doesn't: you pay ~30 GB once at index-build time, and every query after that is a cheap lookup instead of a re-scan of the original text (which, unindexed, would itself be far larger than 30 GB once you count full document bodies rather than just tokens).

<Callout type="warning">
  A common mistake is treating the analyzer as an implementation detail you can change later without cost. In practice, changing tokenization, stemming rules, or stopword lists means every existing document's postings need to be **rebuilt from scratch** — you can't incrementally patch an inverted index to reflect a new analyzer, because the terms themselves changed. Teams that bolt on stemming after launch, or fix a tokenization bug for a new language, discover this means a full reindex of the entire corpus, which for a large corpus can take hours to days and needs a plan (dual-write to old and new indices, then cut over) rather than being a quick patch.
</Callout>

## Where this leaves you

The inverted index answers one question well: which documents contain this term, and where. It says nothing yet about which of those matching documents the user actually wants to see first, how to handle typos or synonyms at query time, or how to combine multiple terms with relevance weighting instead of a strict AND/OR. That's ranking and querying, covered in the next lesson — and it's a genuinely separate problem: two search engines can build an identical inverted index over the same corpus and still produce very different result orderings.
