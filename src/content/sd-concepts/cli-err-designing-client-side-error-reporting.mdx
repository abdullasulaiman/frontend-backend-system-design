The previous lesson laid out why client-side errors are hard to monitor in
the first place: you don't control the runtime, the network is unreliable,
minified code obscures stack traces, and a single bug can fire from millions
of devices at once. This lesson is about the answer to that problem — how
you'd actually design a system that captures those errors, gets them off the
device reliably, and turns a flood of raw JavaScript exceptions into a
short, actionable list of real bugs an engineer can triage.

Think of this as two systems glued together: a lightweight **client SDK**
that lives inside the app and does the capturing, and a **backend ingestion
pipeline** that receives, processes, and stores what the SDK sends. Get the
split right and each side can evolve independently — the SDK stays tiny and
fast, the backend does the expensive work of making sense of the data.

## What the client SDK has to do

The SDK's job is narrow: catch errors, attach context, and get the payload
off the device without hurting the user's experience. Four responsibilities
fall out of that:

**Capture.** No single hook catches every error, so a real SDK layers
several: a global `window.onerror` for uncaught exceptions, a
`window.addEventListener('unhandledrejection', ...)` for promise rejections
that nobody `.catch()`ed, framework-level error boundaries (React error
boundaries, Vue's `errorHandler`) for errors thrown during render, and
manual `try/catch` wrapping around risky call sites like third-party script
execution or `JSON.parse` on untrusted data. Each layer catches a different
class of failure; skipping any one of them leaves a blind spot.

**Enrich.** A bare stack trace is nearly useless on its own. Before an error
leaves the device, the SDK attaches: the release/build version, the user
agent and OS, a session or anonymized user ID, the URL and route at the time
of the error, and a **breadcrumb trail** — a rolling log of the last N
clicks, navigations, and network calls leading up to the crash. Breadcrumbs
are often what actually explains a bug; "TypeError: cannot read property of
undefined" means nothing alone, but "clicked 'Apply Coupon' → fetch
`/api/cart` returned 500 → TypeError" tells you exactly where to look.

**Batch, don't stream.** Firing a network request per error is wasteful and
can itself cause problems (an error handler that throws inside a fetch call
can loop). Instead, queue errors in memory and flush on a timer (e.g. every
5 seconds) or when the queue hits a size limit, sending a batch in one
request. On page unload — where a normal `fetch` can get cancelled mid-flight
— use `navigator.sendBeacon` (or `fetch` with `keepalive: true`) so the
browser guarantees the request is attempted even as the page tears down.

**Sample and rate-limit locally, before the network.** If a bug fires on
every render in a loop, you do not want ten thousand identical reports per
user per minute. The SDK should recognize a repeating error (by message +
location) and drop or heavily sample it client-side, keeping only a count.
This is the cheapest place to control volume — a dropped event costs
nothing; an ingested-then-deduped event still cost you a network request,
parsing, and storage before it got thrown away.

## What the backend pipeline has to do

Once batches start arriving from millions of devices, the backend's job is
to turn noise into signal.

**Ingest at the edge, cheaply.** The first hop should be a lightweight,
horizontally scaled collector that does almost nothing except validate the
payload shape, stamp a receive timestamp, and drop it onto a queue (Kafka,
SQS, or similar). This decouples "surviving a traffic spike" (scale the
collector) from "processing correctly" (scale the workers behind the
queue) — the same pattern you'd use for any high-volume ingestion system.

**Deduplicate by fingerprint, not raw text.** Two reports of "the same bug"
rarely have byte-identical stack traces — line numbers shift between
minor releases, and memory addresses or object IDs sometimes leak into
messages. The pipeline computes a **fingerprint**: a hash built from the
normalized error message (numbers and IDs stripped out) plus the shape of
the stack (function names and file locations, not exact line-column noise).
Reports with the same fingerprint become occurrences of one **issue**,
not a new bug each time. This single step is what turns "50,000 error
reports last hour" into "3 distinct issues, one of which spiked."

**Symbolicate stack traces.** Production JavaScript is minified, so a raw
stack trace points at `a.js:1:48213`, not a function name and line an
engineer recognizes. The build pipeline uploads a **source map** per release
to the error-reporting backend at deploy time, keyed by release version and
file hash. When a report comes in tagged with its release version, a
symbolication worker looks up the matching source map and rewrites the
stack into real file names, function names, and line numbers before it's
ever shown to an engineer.

**Alert on trend, not on raw count.** Because errors are dedup'd into
issues, alerting can compare each issue's occurrence rate against its own
baseline: a brand-new issue appearing at any volume, or an existing issue's
rate suddenly doubling, is worth paging on. A steady trickle of a known,
low-severity issue is not.

## Worked example: sizing the pipeline

Say your app has 5 million daily active users, and historically about 2% of
sessions hit at least one JS error, averaging 3 errors per affected session
once one starts (errors often cascade — one failure triggers others
downstream).

That's roughly `5,000,000 x 0.02 x 3 = 300,000` raw error events per day, or
about 3.5 events/second sustained — but error traffic is bursty, not flat: a
bad deploy can spike that 50-100x for the minutes before it's rolled back,
so the collector tier needs to be sized (and auto-scaled) for a spike of
tens of thousands of events per second, not the daily average.

Client-side sampling of known repeat errors is what keeps that spike
survivable. If a single bad deploy causes one error to fire on every page
load for 10% of active users within a 5-minute window, that's tens of
thousands of devices each wanting to report the same fingerprint
repeatedly. Capping each session to, say, the first 5 occurrences of any
one fingerprint (with a rolling count for the rest) can cut that spike's
network traffic by an order of magnitude before it ever reaches your
ingestion queue — the difference between the collector tier calmly
absorbing a deploy-triggered spike and it falling over at the exact moment
you need visibility most.

<Callout type="warning">
  A common mistake: treating the error-reporting pipeline as more important
  than the app it monitors, so a slow or down ingestion endpoint ends up
  blocking user interactions (e.g. an error handler that awaits a fetch
  response before letting execution continue) or crash-looping the SDK
  itself when the network call to report an error itself throws. Reporting
  must fail open: if the batch can't be sent, drop it (optionally keeping a
  local count) and move on. A monitoring system that can degrade the
  product it's supposed to be watching has the priority exactly backwards.
</Callout>
