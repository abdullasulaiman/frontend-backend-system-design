The [previous lesson](/system-design/uid-approaches-uuid-db-tickets-and-snowflake) compared UUIDs, database auto-increment tickets, and Snowflake-style generators, and landed on Snowflake as the usual production answer: roughly sortable, compact, and generated without a central bottleneck. Knowing the approach isn't the same as being able to build it, though. An interviewer who's satisfied you picked the right family of solution will immediately start probing the actual design: how do you carve up the 64 bits, how do multiple machines avoid handing out the same ID, and what happens the moment a server's clock does something weird. This lesson builds the generator itself, piece by piece.

## Choosing the bit layout

A Snowflake-style ID packs several fields into a single 64-bit integer (chosen because it fits natively in a `long`/`int64` and in most database bigint columns without any special handling). A typical split looks like this:

- **1 bit** — unused, or reserved as a sign bit so the value stays a positive signed 64-bit integer.
- **41 bits** — a timestamp, in milliseconds, relative to a custom epoch (not Unix epoch — see below).
- **10 bits** — a worker/machine ID, identifying which generator instance produced the ID.
- **12 bits** — a per-millisecond sequence number, incrementing for every ID generated by that worker within the same millisecond.

That's not a magic ratio — it's a budget you tune to your actual constraints. 10 worker-ID bits gives you 1,024 distinct generator instances; 12 sequence bits gives you 4,096 IDs per worker per millisecond, or roughly 4.09 million IDs/sec per worker if it's issuing them continuously. If you know you'll never run more than 256 generator instances but need higher per-node throughput, shifting bits from worker ID to sequence (8 bits worker, 14 bits sequence) buys you 16,384 IDs/ms/worker instead. The layout is a trade-off you should be able to justify with real numbers, not recite from memory.

The 41-bit timestamp field matters for longevity: measured in milliseconds since a custom epoch (say, the day your service launched, not 1970), 41 bits covers about 69 years before it overflows. Using a recent custom epoch instead of Unix epoch is what buys you those extra decades — reusing Unix epoch wastes over 50 years of that range on dates before your system existed.

## Assigning worker IDs without collisions

The worker-ID field is where distributed coordination actually shows up in this design. Every running generator instance needs a worker ID that's unique among all currently-running instances — two generators sharing a worker ID can produce identical `(timestamp, worker_id, sequence)` tuples and hand out the same ID twice.

Three common strategies, in increasing order of operational complexity:

- **Static configuration**: assign worker IDs by hand in a config file or environment variable per deployment. Simple, but fragile — a copy-paste error during a scale-out event silently duplicates an ID, and nothing catches it until two records collide.
- **Coordination service registration**: on startup, each instance registers with ZooKeeper, etcd, or a similar service and is handed the next free worker ID from a bounded pool, holding a lease that's released if the instance dies. This is the standard production approach — it self-heals when instances restart and refuses to start two generators with the same ID.
- **Derived from infrastructure identity**: hash or truncate something already guaranteed unique by the platform — a Kubernetes pod's stable ordinal index in a StatefulSet, or a hash of the host's private IP address. This avoids an extra coordination dependency but only works if your deployment platform actually guarantees that uniqueness, and you must handle the (rare but real) hash-collision case.

Whichever strategy you pick, the generator must confirm its worker ID *before* serving traffic. A generator that starts issuing IDs while its registration is still in flight can double-issue if two instances race to grab the same slot.

## Handling the sequence number and clock ticks

Within a single millisecond, a worker increments its sequence number for each ID it hands out. Once the sequence hits its maximum (4,095 for a 12-bit field), the generator has two choices: reject further requests until the next millisecond, or — the standard approach — spin-wait until the clock ticks forward to the next millisecond, reset the sequence to zero, and resume. This keeps throughput bounded and predictable rather than silently wrapping the sequence back to zero within the same millisecond, which would produce a duplicate ID.

When a new millisecond starts, the sequence resets to zero and the process repeats. Because the timestamp field always increases (or, within the same millisecond, is disambiguated by an increasing sequence), IDs from a single worker come out in increasing order — which is the "roughly sortable" property that made this approach attractive over plain UUIDs in the first place.

## Clock drift: the sharp edge of this design

The entire scheme depends on each worker's system clock only ever moving forward. NTP corrections, virtualization clock issues, or a bad manual clock set can make a machine's clock jump *backward*. If that happens mid-operation, the generator could produce a timestamp earlier than one it already used — which risks handing out an ID that collides with, or sorts before, an ID it already gave out with a higher sequence at the earlier (correct) time.

The standard defense is simple and deliberately conservative: on every request, compare the current clock reading against the last timestamp the worker used. If the current reading is *earlier*, refuse to generate — either block until the clock catches back up to the last known timestamp, or fail the request and let the caller retry. Silently generating anyway is the mistake; a short refusal window is far cheaper than a duplicate ID reaching a database's primary key.

## Running it as a service

In production this typically isn't a library each service links in-process (that would need every service to separately solve worker-ID assignment) — it's a small, dedicated ID-generation service that other services call over a fast RPC, batching requests where possible (a caller can request a batch of, say, 1,000 IDs at once to amortize the network round trip). The service itself is horizontally scaled: each instance is stateless with respect to request handling, holds its own registered worker ID, and can be load-balanced across freely, since no instance needs to know about any other instance's in-flight requests — the whole point of the worker-ID split is that instances never need to coordinate per-request.

## Worked example: sizing the layout for a real deployment

Say you're running this across 3 regions, with up to 50 generator instances per region at peak (150 total), and you've measured peak demand at 2 million ID requests/sec company-wide, unevenly spread across instances.

150 total instances fits comfortably in 8 worker-ID bits (256 slots) with room to double your fleet before running out — 10 bits (1,024) is safer still if you expect meaningful future growth, and bits are cheap to over-allocate relative to the pain of running out. For sequence bits, 2,000,000 requests/sec spread across roughly 150 instances averages to about 13,333 IDs/sec/instance, but peak traffic is never even — a hot instance could see several times the average. With 12 sequence bits (4,096 IDs/ms = ~4.09M/sec per instance), even a badly skewed hot instance has enormous headroom; you could comfortably drop to 10 sequence bits (1,024/ms ≈ 1.02M/sec/instance) and still clear a 5x skew over average with margin. That leaves 64 − 1 − 41 − 8 = 14 bits unused if you go with 8 worker bits and 10 sequence bits — spare capacity is fine to leave as reserved/sign bits, or you could push sequence bits up to 14 (16,384/ms) for extra headroom against future traffic growth, all inside the same 64-bit budget.

<Callout type="warning">
  A common mistake is treating worker-ID assignment as a one-time deploy-time detail and moving on. In practice, worker IDs need a full lifecycle: acquired on startup, held via a lease that expires if the instance crashes without deregistering, and released cleanly on graceful shutdown so the slot can be reused. Skipping the lease/expiry mechanism means a crashed instance's worker ID stays "reserved" forever in a naive static scheme, or — worse, in a lease-based scheme with too long a timeout — a replacement instance can't start until the old lease finally expires, causing an availability gap during exactly the kind of failure you built this system to survive.
</Callout>
