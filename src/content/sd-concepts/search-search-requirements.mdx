Ask "design a search engine" in an interview and most candidates jump
straight to inverted indexes and B-trees. That's premature. Before you can
justify any indexing or ranking choice, you need to know what the search
system is actually promising: how fresh does a result need to be, how
forgiving of typos, how fast, and over how much data. Get those wrong and
you'll optimize the wrong thing — a beautifully sharded index that returns
results in 20ms but doesn't find the document the user was obviously
looking for is a failed design, not a fast one.

This lesson is the first stop in the Distributed Search module. It doesn't
build anything yet — it establishes the vocabulary and the checklist the
rest of the module (inverted indexes, ranking, and the final scaled
design) builds on.

## Why search is a different problem than a database lookup

A database query like `WHERE user_id = 42` has one correct answer set: the
rows where that predicate is true. A search query like `wireless noise
canceling headphones` has no single correct answer — it has a *best*
answer, and reasonable people can disagree on what that is. That shift —
from exact match to ranked relevance — is the defining property of search
and the reason it needs its own architecture:

- **The input is fuzzy.** Users misspell words, use synonyms, and phrase
  the same intent ten different ways ("cheap flights NYC to LA" vs. "LA to
  New York budget flight").
- **The output is a ranked list, not a set.** Returning the right ten
  documents in the wrong order is still a worse product experience than
  returning nine of them in the right order.
- **"Correct" is fuzzy too.** Two documents can both legitimately match a
  query; the system has to decide which one a user is more likely to want,
  which means scoring, not filtering.

Because of this, a search system needs a step a plain database doesn't:
turning free text into a structure that supports fast, ranked, fuzzy
lookup. That structure is the inverted index — covered in the next lesson
— but you can't design it well until you know what's being asked of it.

## The core functional requirements

Every search design should answer these before touching architecture:

### 1. What's being searched

Documents, product listings, log lines, chat messages, source code — the
content type shapes almost everything downstream. A product catalog has
structured fields (price, brand, category) alongside free text; log search
is mostly free text at huge volume with a strong recency bias; code search
needs token boundaries that differ from natural language (`getUserById`
should be findable by `user` and `by id`, not just as one opaque token).

### 2. Query capability

Decide upfront what kinds of queries you support:

- **Keyword / free text** — the baseline: match documents containing the
  query terms.
- **Phrase and boolean queries** — `"noise canceling"` as an exact phrase,
  or `headphones AND wireless NOT refurbished`.
- **Fuzzy matching** — tolerate typos and near-misses (`recieve` should
  still find `receive`).
- **Faceted / filtered search** — combine free text with structured filters
  like price range or category, common in e-commerce.
- **Autocomplete / prefix search** — a related but distinct feature with
  its own latency and data-structure needs (covered briefly in the
  scaling lesson).

### 3. Freshness

How quickly must a new or edited document become searchable? A product
catalog can tolerate a few minutes of lag; a chat or social-post search
feature usually needs near-real-time (seconds); a nightly-batch document
archive can tolerate hours. Freshness directly determines whether you can
get away with periodic bulk re-indexing or need incremental index updates
— a much harder engineering problem, since most classic index structures
are easy to build once and expensive to mutate.

### 4. Scale

Two numbers matter most: **corpus size** (document count x average
document size, which determines index size and shard count) and **query
volume** (queries per second, which determines how much replication and
caching you need on the read path). A 10-million-document product catalog
serving 500 QPS is a very different system than a 50-billion-page web
index serving 100K QPS, even though both are "search."

### 5. Relevance requirements: precision vs. recall

**Precision** asks: of the results returned, how many are actually
relevant? **Recall** asks: of all the relevant documents that exist, how
many did we return? These trade off. A search that only returns exact
phrase matches has high precision but misses documents that use different
wording (low recall). A search that fuzzy-matches aggressively catches
more relevant documents but also drags in noise (higher recall, lower
precision). Different products sit at different points on this curve — a
legal-document search cares enormously about recall (missing a relevant
case is a real cost); a consumer product search cares more about precision
on the first page (users rarely scroll past result 10).

## Non-functional requirements that shape the architecture

- **Query latency** — search sits behind a live UI, so the read path
  usually has a tight budget, often under 100-200ms end to end including
  ranking. This is tighter than most write-path freshness budgets, which
  is why search systems architecturally separate the two paths.
- **Availability** — a search box returning "service unavailable" is a
  visible, embarrassing failure; most designs favor eventual consistency
  on the index (a document might take a few seconds to appear) over
  taking search down for consistency's sake.
- **Ranking consistency** — repeated identical queries should return
  stable results (modulo intentional randomization like A/B tests);
  flapping order across requests looks broken even if each individual
  ranking is defensible.
- **Cost** — inverted indexes and ranking signals both consume significant
  memory for low-latency serving; corpus size and query volume together
  drive real infrastructure cost, so back-of-envelope index size estimates
  matter early, not as an afterthought.

## The write path and read path are different problems

A useful mental model before any component diagram: search splits cleanly
into an **ingestion (write) path** that turns raw content into a queryable
index, and a **query (read) path** that turns a user's text into a ranked
result list. They have different latency budgets, different scaling
knobs, and different failure modes — conflating them is the most common
early design mistake.

The write path can absorb latency (seconds, sometimes minutes) as long as
it keeps up with ingestion volume. The read path can't — every millisecond
there is user-facing. That asymmetry is why search systems pre-compute as
much as possible during ingestion (the index, and often partial ranking
signals) so the read path does the minimum work necessary at request time.

## Worked example: scoping a job-listing search

Say the assignment is "design search for a job-listings site" with 20
million active listings, each averaging 2KB of text and metadata (title,
description, company, salary range, location), and 5,000 search queries
per second at peak.

Working through the requirements checklist:

- **Corpus size**: 20M x 2KB is roughly 40GB of raw text — small enough
  that the whole index plausibly fits across a modest cluster's memory
  once compressed, which matters a lot for the indexing lesson's
  design choices.
- **Freshness**: a new listing should be searchable within a minute or two
  of posting — good enough to not need true streaming updates, but too
  slow for a nightly batch rebuild.
- **Query capability**: keyword search on title/description, plus
  structured filters (location radius, salary range, seniority) combined
  with the free-text query — this is faceted search, not pure keyword
  match.
- **Relevance**: precision matters more than recall here. A job seeker
  scanning page one wants the ten best matches, not every technically
  matching listing across 40 pages.
- **Latency**: sub-200ms end to end at 5,000 QPS peak, since this sits
  directly behind a search box on page load.

That scoping alone — before any index structure is chosen — already tells
you this needs: an incremental (not full-rebuild) indexing pipeline, a
ranking function that can combine text relevance with structured filters,
and enough replicated read capacity to serve 5K QPS with headroom. The
next lesson picks up from here and builds the inverted index that makes
the read path fast.

<Callout type="warning">
  The most common mistake in search system design interviews is treating
  "search" as a synonym for "look up documents containing these words" and
  skipping relevance entirely. A candidate who designs a perfectly sharded
  inverted index but never discusses precision/recall trade-offs, or what
  a "good result" looks like for a sample query, has designed half a
  system. Ranking is not a nice-to-have layered on top — it's the reason
  search is a hard problem in the first place. Always state a couple of
  concrete example queries and what you'd expect back before moving to
  architecture.
</Callout>
