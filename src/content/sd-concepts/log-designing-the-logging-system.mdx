You've seen why distributed logging is hard and walked through the pipeline's building blocks. Now put them together. The interview question "design a centralized logging system for a few thousand services" isn't answered by naming Kafka and Elasticsearch — it's answered by tracing a single log line from a `print` statement on some host, through every hop, to an engineer's search query at 3 a.m., and defending each hop's failure mode and cost.

This lesson builds that end-to-end system: requirements, the five-stage pipeline, a capacity estimate with real numbers, and the mistakes that turn "just log everything" into an outage or a runaway bill.

## Requirements first

Pin down what "logging system" actually needs to do before drawing boxes:

- **Functional**: engineers can search logs by service, host, time range, and free text; they can pull every log line for a single request across services via a correlation/trace ID; recent logs are visible within seconds (near-real-time tailing during an incident).
- **Scale**: total ingest volume (lines/sec and bytes/sec) across the fleet, which is dominated by your noisiest few services, not the average one.
- **Durability vs. cost**: losing a handful of DEBUG lines during a burst is fine; losing the one ERROR line that explains an outage is not. Full-fidelity retention for months is expensive, so most systems keep raw data briefly and aggregates or samples longer.
- **Isolation**: the logging pipeline must never slow down or crash the application it instruments — a slow log write should never become a slow HTTP response.

That last point drives most of the design below.

## The five-stage pipeline

### 1. Local agent

A lightweight process on each host tails log files (or receives log lines directly from the app via a local socket/library) and forwards them. It must be non-blocking from the application's point of view: writes go to a local buffer — ideally a small disk-backed queue, not just an in-memory ring buffer — so an agent restart or a network blip doesn't silently drop a burst of logs that arrived seconds before a crash.

The agent also does the cheapest possible filtering: dropping or sampling DEBUG/TRACE lines, truncating oversized messages, and tagging each line with host, service, and environment metadata before it ever leaves the box.

### 2. Central buffer (the shipping queue)

Agents forward batches into a distributed queue (a Kafka-style log, partitioned by service or shard). This is the single most important decoupling point in the whole system: it lets thousands of agents push independently of how fast downstream processing and storage can consume, absorbs traffic spikes (a bad deploy that starts logging 50x its normal volume), and gives you a replay point if a downstream stage crashes.

### 3. Processing (parse, enrich, redact)

Consumers read off the queue and turn raw lines into structured records: parsing unstructured text into fields, attaching trace/span IDs for cross-service correlation, redacting known PII patterns, and computing derived fields (status-code buckets, latency percentile bucket) that make later queries cheap instead of computing them at read time.

Doing this here — once, in a stage you control — beats asking every service team to log perfectly structured JSON by hand, though encouraging structured logging at the source (see below) still reduces this stage's work.

### 4. Storage (tiered)

Processed records land in an indexed store for the "hot" window (typically the last few days), where an inverted index on structured fields plus a text index on the message body makes search fast. Older data moves to a "warm" tier with less indexing, and eventually to cheap object storage for compliance retention, which is rarely queried and never indexed.

### 5. Query / API layer

A query service fronts the hot and warm tiers, translating a user's "service=checkout AND trace_id=abc123 AND last 15 minutes" into index lookups, merging results, and streaming them back — including a "tail" mode that keeps a query open and streams new matching lines as they arrive, which is what an on-call engineer actually uses during an incident.

## Worked example: sizing the pipeline

Say the fleet has 5,000 hosts, each emitting an average of 200 log lines/sec at roughly 300 bytes/line (message plus metadata).

- **Raw throughput**: 5,000 x 200 = 1,000,000 lines/sec fleet-wide, or about 300 MB/sec raw.
- **After local sampling** (drop 80% of DEBUG-level lines, which are the bulk of volume): roughly 400,000 lines/sec, ~120 MB/sec hitting the queue.
- **Queue sizing**: at 120 MB/sec sustained plus headroom for a 3x burst (a bad deploy, a retry storm), the queue tier needs to absorb ~360 MB/sec peak — this is the number that sets partition count and broker throughput, not the average.
- **Hot storage, 3-day retention**: 120 MB/sec x 86,400 sec/day x 3 days ~ 31 TB/day x 3 ~ 93 TB before replication; with 3x replication for durability, roughly 280 TB of hot indexed storage.
- **Indexing cost dominates**: indexing every field of every line at that volume is usually the actual bottleneck — not the raw bytes, but the CPU cost of building inverted indexes at 400,000 lines/sec. This is why most systems index a curated set of fields (service, level, trace ID, status code) and rely on grep-style scans over compressed raw text for anything else.

The number that should scare you in a design interview isn't storage bytes — it's indexing throughput, because that's what forces the sampling and field-selection decisions above.

<Callout type="warning">
  The most common mistake: treating the queue between agents and processors as durable long-term storage, or skipping it entirely and writing straight from agents to the indexed store. Both couple ingestion rate directly to indexing rate — a slow index write during a traffic spike now backs up agents, which either blocks application threads or drops logs at the worst possible moment. The queue exists specifically to let those two rates diverge temporarily without data loss or app-side impact.
</Callout>
