You've now covered the four building blocks of a distributed key-value store one at a time: how to partition keys across nodes, how to replicate them for durability, how to reconcile conflicting versions, and how quorum reads and writes tune the consistency/availability trade-off. Individually, each piece is a well-scoped idea you can explain in two minutes. The part that actually separates a strong system design answer from a mediocre one is showing how they interlock — because none of them work in isolation.

Consistent hashing tells you *where* a key lives, but "where" is meaningless without replication deciding *how many places* it lives. Replication needs quorum rules to define what "successful" means for a write that's fanned out to multiple nodes. And quorum reads, once you allow partial failures, will occasionally return replicas that disagree — which is exactly the problem versioning solves. Pull any one of these out and the design breaks: no partitioning means no scaling, no replication means no durability, no quorum means no availability during failures, no versioning means clients see silently wrong data. This lesson walks the full request path end to end and shows where each earlier lesson's mechanism actually gets invoked.

## The write path, start to finish

Follow a single `PUT(key, value)` through the system:

1. **Routing.** The client (or a coordinator node it talks to) hashes `key` with consistent hashing to find its position on the ring, then walks clockwise to the first node — the *coordinator* for that key.
2. **Replica selection.** The coordinator is also replica 1. It identifies the next `N - 1` distinct physical nodes clockwise on the ring as the rest of the replica set (this is the mechanism from the consistent-hashing lesson — virtual nodes are what make "next distinct physical node" evenly distributed instead of clumped).
3. **Fan-out.** The coordinator sends the write, tagged with a version (a vector clock entry or a timestamp, depending on your conflict strategy), to all `N` replicas in parallel.
4. **Quorum wait.** The coordinator waits for `W` acknowledgments — not all `N` — before telling the client the write succeeded. The remaining replicas apply the write asynchronously.
5. **Degraded case.** If a replica is down, sloppy quorum lets the coordinator write to a healthy stand-in node instead, with a hint attached ("this belongs to node X, deliver it when X comes back"). This is hinted handoff — it's what keeps `W` reachable during a single-node outage instead of the write failing outright.

## The read path, and where conflicts surface

A `GET(key)` follows the same routing step, then:

1. The coordinator requests the value from `R` replicas (not necessarily the same `R` nodes every time — whichever are reachable and hold the key).
2. If all `R` responses carry the same version, return it — done.
3. If they disagree, this is a genuine concurrent-write conflict, not a bug. The coordinator applies the strategy chosen in the conflict-resolution lesson: return all conflicting versions to the client for merge (Dynamo's approach), or pick the one with the highest timestamp (last-write-wins), and — separately, on a background schedule — run anti-entropy repair (Merkle-tree comparison between replicas) so replicas that silently drifted apart get resynced even for keys nobody happens to read for a while.

This is the crux most candidates gloss over: **quorum overlap (R + W > N) does not eliminate conflicts, it only guarantees a read will see at least one up-to-date replica.** You still need a real conflict-resolution mechanism, because "see the latest version among several" and "know which one is latest" are different problems when writes happen concurrently on different coordinators.

## How membership changes ripple through the stack

The other place the pieces interact is cluster topology changes — a node joining, leaving, or dying:

- **Failure detection** runs on gossip: nodes periodically exchange "who's alive" state with a few random peers, so failure information spreads in `O(log N)` rounds without a central health-check service that would itself be a bottleneck.
- **Ring update.** Once a node is confirmed down (or a new node joins), the consistent-hashing ring updates — the joining/leaving node's virtual nodes move, and only the keys mapped to those specific ring segments need to relocate. This is the entire point of consistent hashing: without it, adding a node would remap most keys and require a mass data shuffle.
- **Replica set shift.** Because replica sets are derived live from the ring ("next `N - 1` distinct nodes clockwise"), a topology change can silently shift who's in a key's replica set. Anti-entropy is what catches a replica that's now newly responsible for a key but doesn't have the latest version yet.

## Worked example: sizing N, W, R for a session store

Say you're storing user session tokens: 50 million active sessions, each read on nearly every request and written on login/refresh. Availability matters more than perfect consistency — a session read that's a few hundred milliseconds stale is harmless, but a login that fails because of a quorum timeout is a real user-facing outage.

- **N = 3.** Enough to survive a single node failure with two copies still live, without tripling storage cost the way `N = 5` would.
- **W = 1.** Login writes should almost never block or fail on replica coordination — accept the write as soon as one node has it, and let it replicate asynchronously. This is the "sloppy" end of the trade-off: fast, highly available, and it's fine if a read races ahead of full replication for a token that's only checked, not computed from.
- **R = 1.** For the same reason — read latency matters far more here than catching a rare stale replica, and a stale-by-milliseconds session check just means an extra token refresh at worst.

Notice `W + R = 2`, which is less than `N = 3`: this design deliberately does **not** guarantee every read sees the latest write. That's the right call for session data. Contrast with an inventory-count key where overselling is expensive — there you'd push toward `W = 2, R = 2` (so `R + W > N`) and accept the added latency, because correctness now outweighs raw speed. The same three building blocks, tuned differently, produce a very different system — that's the whole exercise of this module.

<Callout type="warning">
  A common mistake in interviews: describing consistent hashing, replication, quorum, and conflict resolution as four separate slides with no connective tissue, then going quiet when asked "walk me through what happens when a write comes in." If you can't narrate the full path — hash the key, find the replica set, fan out, wait for W, handle a down replica with hinted handoff, resolve a later read conflict with vector clocks — you haven't actually assembled a system, you've memorized four topics. Practice the end-to-end narration, not just each piece in isolation.
</Callout>
