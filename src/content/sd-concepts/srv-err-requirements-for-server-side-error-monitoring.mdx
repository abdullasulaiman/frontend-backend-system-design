An unhandled exception in a checkout service, a `5xx` spike from a downstream timeout, a deploy that quietly breaks one endpoint — none of these show up to the user as a clean crash report. They show up as a log line buried in thousands of others, on one host out of hundreds, at 3 a.m. If nobody sees it, the business finds out from a customer complaint or a revenue dashboard, hours after it started. Server-side error monitoring exists to close that gap: catch the error close to where it happens, tell the right engineer fast, and give them enough context to fix it without re-deriving the failure from scratch.

This is the first lesson in the "Monitor Server-Side Errors" module. Get the requirements right here and the next two lessons — architecture/data flow, and the full system design — are just engineering in service of these constraints. Skip this step and you'll end up designing (or worse, being asked to critique) a system that logs everything but alerts on nothing useful, or alerts on everything and gets ignored.

## Two jobs, often confused for one

A server-side error monitoring system is really solving two different problems that happen to share a pipeline:

1. **Capture** — reliably collect every error, with enough context (stack trace, request ID, host, deploy version, user/tenant) to actually debug it later.
2. **Surface** — reduce thousands of raw error events down to a small number of actionable *issues*, and get the right one in front of a human fast enough to matter.

Design only for capture and you get a searchable log dump nobody proactively reads. Design only for surfacing and you get alerts with no way to dig into root cause once someone's paged. A real system has to do both, and — as you'll see below — they pull the architecture in different directions (durable storage vs. low-latency aggregation), which is exactly what the next lesson has to reconcile.

## Functional requirements

State these explicitly before sketching any architecture:

- **Ingest an error event.** At minimum: error type/message, stack trace, timestamp, service name, host/instance ID, and a request/trace ID that ties it to the request that caused it. Anything less and an engineer can't reproduce the failure.
- **Group ("fingerprint") errors into issues.** The same underlying bug (say, a `NullPointerException` in `OrderService.applyDiscount`) will fire on every affected request — potentially thousands of times a minute. The system must collapse those into a single *issue* with an occurrence count, not report 5,000 separate alerts.
- **Query and browse.** An engineer needs to search by service, time range, error type, deploy version, or affected user, and see a trend (is this issue new, growing, resolved?).
- **Alert.** Notify on-call when an issue crosses a threshold — first occurrence of a new error type, error rate above a baseline, or a spike correlated with a recent deploy.
- **Track issue lifecycle.** Mark an issue resolved, ignored, or reopened (it recurred after being marked fixed) — otherwise the same bug re-alerts forever or silently drops off a dashboard.

## Non-functional requirements

This is where the interesting design tension lives.

### Scale and burstiness

Don't just say "high volume" — put a number on it. A mid-size service fleet in steady state might emit a few hundred errors/sec; the same fleet mid-incident (a downstream dependency timing out, a bad deploy) can spike error volume 50-100x in seconds. The ingestion path has to absorb that spike without falling over or silently dropping data — which is precisely the moment the data matters most.

### The monitoring system must not depend on the thing it's watching

If application servers are failing, the error-reporting client running inside them, and the pipeline behind it, must keep working — or at minimum fail *safely* (buffer and retry, or drop with a local counter) rather than compound the outage. A monitoring pipeline that needs the very services it watches to be healthy in order to function is a circular dependency that fails exactly when you need it most.

### Latency for surfacing vs. durability for storage

These pull in different directions:

- **Alerting path** needs to be fast — seconds, not minutes, from "error starts happening" to "on-call is notified." This favors in-memory aggregation and streaming.
- **Storage/search path** needs to be durable and queryable for days or weeks after the fact, so a postmortem three days later can still pull the exact stack trace. This favors a persistent store optimized for time-range + filter queries, not raw speed.

A design that routes every single error through the same slow, durable write path before alerting will be too slow to page anyone quickly; a design that only aggregates in memory and never persists loses the detail needed for debugging.

### Retention and cost

Raw error volume, kept forever, in full detail, is not a sustainable default — it's a cost and query-performance problem waiting to happen. A realistic requirement: full-fidelity data (every occurrence, full stack trace, full context) for a short window (say 14-30 days), with older data either dropped, sampled, or rolled up into aggregate counts per issue per day.

### Noise reduction as a hard requirement

If the same underlying bug triggers 10,000 events in an hour, alerting once with an accurate count is correct behavior; alerting 10,000 times is a bug in the monitoring system itself, even though every individual alert is technically "true." Deduplication and rate-limiting on alerts are not a nice-to-have layered on top later — they're a core requirement, because an ignored alert channel is equivalent to no monitoring at all.

## Worked example: sizing requirements for a mid-size fleet

Say the prompt is "design error monitoring for a fleet of 2,000 backend instances across 150 services." A concrete requirements pass:

- **Baseline volume:** 150 services x ~2 errors/sec average each ~ 300 errors/sec steady state.
- **Incident spike:** a cascading timeout can push a handful of services to 200 errors/sec each; even 5 affected services spikes ingestion to ~1,000-1,300 errors/sec — call it a 4-5x burst the pipeline must absorb without backpressure onto the app fleet.
- **Fingerprinting target:** those 1,300 errors/sec during an incident should collapse to a handful of distinct issues (probably 1-3 root causes), not 1,300 alerts.
- **Alert latency:** a new, previously-unseen error type should page on-call within 60 seconds of its first occurrence; a spike in a known error type should alert within 2-5 minutes (fast enough to catch a bad deploy before it fully rolls out).
- **Retention:** full detail for 30 days (long enough to cover a sprint's worth of postmortems), daily aggregate counts kept for a year for trend analysis.

Those five numbers — burst ingestion rate, fingerprinting behavior, two different alert-latency targets, and a two-tier retention policy — are exactly what the architecture lesson needs as inputs to decide on a streaming aggregation layer versus a batch one, and what the full design needs to size storage and alerting infrastructure against.

<Callout type="warning">
  The most common mistake at this stage is writing "capture all errors and alert the team" as if that's one requirement. It's two, with opposite performance characteristics — durable, detailed storage vs. fast, lossy-is-acceptable aggregation for alerting — and conflating them leads to a design that's either too slow to page anyone or too shallow to debug anything once paged. Separate them explicitly before you draw a single box.
</Callout>
