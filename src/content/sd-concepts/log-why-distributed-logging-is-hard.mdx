On a single server, logging is barely a design problem. You write to a
file, rotate it before disk fills up, and when something breaks you `ssh`
in and run `tail -f` or `grep`. The information you need is in one place,
on one clock, in one process's view of the world.

Break that single server into fifty microservices running on a fleet of
containers that get rescheduled every few hours, and every one of those
assumptions collapses. The log line you need might be on a host that no
longer exists. The request you're debugging touched six services, each
writing its own file, with no shared way to tell which lines belong to the
same request. This lesson is about *why* that shift is hard — the next two
lessons in this module ("Architecture and Pipeline" and "Designing the
Logging System") cover how to actually build the system that solves it.

## Logs are scattered by default

In a distributed system, every process writes its own logs, locally, with
no built-in awareness of any other process. That's the root of almost
every problem in this space:

- **No single place to look.** A checkout failure might have touched the
  API gateway, an auth service, an inventory service, and a payment
  service — four hosts, four log files, four independent views.
- **Hosts are ephemeral.** Containers get killed and rescheduled,
  autoscaling groups shrink, spot instances get reclaimed. If a log line
  only exists on local disk, it can vanish minutes after being written,
  well before anyone goes looking for it.
- **Volume grows with fleet size, not with incidents.** One host logging
  50 lines/second is nothing. Two thousand hosts logging 50 lines/second
  each is 100,000 lines/second, all the time, whether or not anything is
  wrong.

None of this is solvable by writing better log messages — it's an
infrastructure problem. You need something that pulls logs off every host
continuously and puts them somewhere queryable before the host (and the
log) disappears.

## Correlating one request across many services

Even once logs are centralized, you're staring at a pile of lines from
unrelated requests, interleaved. The real question during an incident is
almost never "what did service X log at 3:02pm" — it's "what happened to
*this specific customer's request*, end to end."

### Correlation IDs

The standard fix is to generate a unique ID at the edge (the load balancer
or API gateway) the moment a request arrives, and pass it through every
downstream call — as an HTTP header, an RPC metadata field, or a message
attribute on a queue. Every service logs that same ID with every line it
writes about that request. Now "find everything about this request"
becomes one query: filter by correlation ID across the centralized log
store, instead of grepping N files and guessing which lines line up.

This is the same idea distributed tracing systems build on, just at the
logging layer rather than the span layer — a request ID is the thread
that ties a scattered story back together.

### Clock skew breaks ordering

Once you have all the lines for one request, you'll want to order them —
"what happened first." Timestamps seem like the obvious answer, but clocks
on different hosts are not perfectly synchronized. Even with NTP, drift of
tens to hundreds of milliseconds between hosts is normal, and a fast
service-to-service call can complete well within that window. Two log
lines from different hosts, five milliseconds apart, can display in the
*wrong* order if you sort purely by wall-clock timestamp.

Systems handle this with a mix of approaches: attaching a monotonically
increasing per-request sequence number as the request hops between
services, tolerating "approximately ordered" results and reconstructing
strict order from causal relationships (this call happened *because* that
one returned), or leaning on trace spans with explicit parent/child
relationships instead of raw timestamps.

## Structured logs vs. free text

`"User login failed for bob@example.com from 10.2.3.4"` is easy for a
human to read and nearly useless for a machine to query at scale. Once
you have millions of lines from dozens of services written by different
teams, you need consistent, structured fields — `user_id`, `ip`,
`status`, `service`, `req_id` — so the aggregation system can filter,
group, and count without parsing English prose that varies subtly from
one service to the next. Structured (JSON-like) logging is what makes
"show me the error rate for the payment service in the last 10 minutes,
broken down by error code" answerable at all, instead of an exercise in
regex archaeology.

## Cost, retention, and sensitive data

Two problems compound once volume is real:

- **Cost.** Shipping, parsing, indexing, and storing every log line from
  every host is not free — indexed log storage is meaningfully more
  expensive per byte than cold blob storage, so most systems tier data:
  hot and indexed for a few days, cheap and searchable-but-slow after
  that, deleted or archived after a retention window.
- **Sensitive data.** Logs are an easy, unintentional leak path for PII
  and secrets — emails, auth tokens, full request/response bodies. Unless
  you scrub or redact at the source (or at ingestion, before indexing),
  logs become a compliance liability that's expensive to fix after the
  fact, because by then the data has already been copied into a searchable
  store, possibly replicated to backups.

## Worked example: sizing the problem

Say your fleet has 2,000 hosts, each averaging 50 log lines/second at
roughly 200 bytes/line (a structured line with a handful of fields plus a
message). That's:

- 2,000 × 50 = 100,000 lines/second fleet-wide
- 100,000 × 200 bytes ≈ 20 MB/second
- 20 MB/second × 86,400 seconds/day ≈ 1.7 TB/day

That's before any request spikes, before verbose DEBUG logging gets left
on in production, and before you've decided how long to keep any of it
indexed. At 1.7 TB/day, "just index everything forever" is not a serious
option — this is exactly the pressure that pushes real systems toward
sampling, log-level filtering at the source, and tiered storage, which
the next lesson covers when it walks through the ingestion pipeline.

<Callout type="warning">
  The most common mistake teams make is treating logging as "add
  `console.log` / `logger.info` calls, ship them somewhere, done" and only
  discovering the correlation-ID problem during a live incident, when
  someone is trying to reconstruct a single failed request across five
  services and realizes there's no shared ID connecting any of the log
  lines. Bake a correlation ID into your request-handling middleware from
  day one — retrofitting it after logs already exist without one means
  your historical logs stay unqueryable across services forever.
</Callout>
