The previous lesson covered token bucket, leaky bucket, and fixed/sliding
windows as if a rate limiter were one process holding one counter in memory.
That's true for a single instance — and false for almost every real
deployment. A rate limiter for a public API sits behind a load balancer with
tens or hundreds of identical instances, and the algorithm you picked doesn't
matter if the counting itself is wrong. This lesson is about that counting
problem: how do independent processes agree on "how many requests has this
client made in the last second" without serializing every request through one
machine.

## The problem: local counters lie

Say your limit is 100 requests/minute per API key, enforced with an in-memory
token bucket on each server. A load balancer spreads traffic round robin
across 10 servers. A client can now send 1,000 requests/minute — 100 to each
server — and every single server will honestly report "this client is under
its limit." Each instance is correct in isolation; the system as a whole is
not enforcing the limit it advertises.

This isn't a rare edge case — it's the default outcome of combining
per-server state with any load balancer that isn't aware of the rate limiter's
keys. You have three broad ways out: pin each client to one server, share the
counter, or accept approximate enforcement.

## Option 1: Sticky routing (make local state correct again)

If the load balancer routes every request for a given client key (API key,
user ID, IP) to the *same* server — via consistent hashing on that key,
rather than round robin — then that server's local counter is once again the
true count for that client. No shared store, no network hop, no new
bottleneck. This is the cheapest fix when it's available.

The catch: it pushes the "hot key" problem onto individual servers. A client
key that generates disproportionate traffic (a big customer, a misbehaving
script) now loads one server instead of being spread out, and if that server
restarts, its in-memory counters vanish — the client effectively gets a free
reset. Consistent hashing also complicates capacity changes: adding or
removing a server reshuffles which keys land where, and you need the hash
ring (see the Load Balancing module) to keep that reshuffling minimal.

## Option 2: Shared counter store (make the state actually global)

The more common production answer: move the counter out of each server's
memory and into a shared, fast store — typically Redis — keyed by
`client_id:window`. Every server, regardless of which one the load balancer
picked, increments and reads the *same* counter for a given client and time
window.

This fixes correctness cleanly but introduces new problems:

- **Every rate-limit check is now a network round trip.** At high QPS this
  store must be fast (sub-millisecond) and itself horizontally scalable —
  it's now on the hot path of every single request in your system, not just
  the requests that get rejected.
- **Concurrent updates need atomicity.** Two servers reading the counter,
  both seeing "99, still under 100," and both incrementing, can let 101
  through. Plain `GET` then `SET` from your application code has this race.
  Redis's `INCR` is atomic for a simple fixed-window counter; for anything
  more elaborate (sliding window, token bucket with a refill calculation) you
  push the whole check-and-update as a single Lua script so Redis executes
  it atomically server-side, with no read-modify-write gap for another
  request to slip into.
- **The store is now a shared dependency for the whole fleet.** If it's
  down or slow, every rate-limited endpoint is affected, not just one
  server's worth of traffic. This is why the fail-open/fail-closed decision
  below matters so much more here than in the single-server case.

## Option 3: Approximate counting (trade accuracy for speed)

If a shared store's latency or throughput cost is unacceptable, you can loosen
the guarantee instead of tightening the architecture. Two common approximate
strategies:

- **Local counters with periodic reconciliation.** Each server keeps its own
  in-memory counter and pushes deltas to the shared store every N
  milliseconds (or pulls the global count) instead of syncing on every
  request. This turns every rate-limit check back into a cheap local memory
  read, at the cost of the global count lagging reality by up to N
  milliseconds — a client can briefly overshoot the limit by roughly (fleet
  size x local burst allowance) before the fleet catches up.
- **Probabilistic data structures.** For very high cardinality (millions of
  distinct client keys) or where "roughly right" is fine, a sketch structure
  can approximate per-key counts in a fixed memory footprint. This is
  overkill for a typical per-user API limiter but shows up in abuse-detection
  and DDoS-mitigation systems counting billions of distinct keys.

The right trade-off is entirely about what the limit *protects*. A limit
protecting your backend from overload can tolerate a client sneaking through
110 requests instead of 100 — the backend barely notices. A limit that's
actually a billing quota ("100 free API calls, then you pay") cannot tolerate
that slack; get that one wrong and you're giving away paid usage for free.

<Callout type="warning">
  A common mistake in system design interviews: proposing "just put a Redis
  counter in front of it" as if that alone solves distribution, without
  addressing the two things that actually make it correct. First, the
  increment-and-check must be atomic (a Lua script or `INCR`, never separate
  `GET` then `SET` calls from application code) — otherwise concurrent
  requests race past the limit exactly like uncoordinated local counters did.
  Second, you must state what happens when Redis is slow or unreachable: failing
  closed (deny everything) turns a rate-limiter outage into a full API outage;
  failing open (allow everything) turns it into an unprotected backend during
  exactly the traffic spike you built the limiter for. Naming this trade-off
  explicitly is what separates a strong answer from a hand-wave.
</Callout>

## Worked example: sizing the shared store

Say you're rate limiting 500,000 active API keys at up to 100 requests/minute
each, and every request needs a limiter check. Peak traffic is 200,000
requests/second across the fleet.

With a naive "one Redis round trip per request" design, your Redis cluster
now needs to sustain 200,000 ops/sec of atomic increment-and-check just for
rate limiting — on top of whatever else it's used for. A single Redis node
comfortably handles low hundreds of thousands of simple ops/sec, so this is
plausible on dedicated hardware but leaves no headroom, and Redis itself
becomes a component you now have to make highly available (replication,
failover) purely to keep serving traffic.

Compare that to the local-counter-with-reconciliation approach: if each
server syncs deltas every 100ms instead of every request, and you have 50
servers, you've cut shared-store traffic from 200,000 ops/sec to roughly
500/sec (50 servers x 10 syncs/sec), at the cost of each client being able to
transiently exceed its limit by up to (its share of traffic across 50 servers
x 100ms of unsynced local counting) — typically a handful of extra requests,
not hundreds. For abuse prevention, that's almost always an acceptable price
for a 400x reduction in shared-store load.
