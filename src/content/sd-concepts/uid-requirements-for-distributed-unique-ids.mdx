Every relational database gives you unique IDs for free, right up until it doesn't. A single Postgres or MySQL instance can hand out `id = 1, 2, 3, ...` from an auto-increment column forever, because there's exactly one place tracking "what's the next number." The problem shows up the moment that assumption breaks: you shard the table across four database instances to handle write volume, or you run active-active in two regions for availability, and now you have four (or more) places independently counting up from 1. Shard A's row 501 and shard C's row 501 are both real rows with the same ID. Anything downstream that treats an ID as globally unique — a URL, a cache key, a foreign key referenced from another service — silently breaks.

This lesson is the "requirements" step for the Unique ID Generator design problem, the same way you'd clarify requirements before designing any other system. It doesn't pick an algorithm yet — that's the next lesson, which compares UUIDs, database ticket servers, and Snowflake-style generators. Here, the goal is to nail down exactly what "unique ID" needs to mean for a given system, because that list of properties is what makes one algorithm the right choice and another the wrong one.

## Why auto-increment stops working

A single auto-increment counter is really a serialization point: every insert has to go through the one place that knows the current max value, so writes are naturally ordered and collision-free. Distributing the database removes that serialization point on purpose — that's the whole reason you sharded — but it takes the free uniqueness guarantee with it.

The naive "just have shards use disjoint ranges" (shard A starts at 1, shard B starts at 10,000,000) works until a shard runs out of its range or you add a fifth shard nobody planned for. It's a workaround, not a design; a real distributed ID generator needs to keep working as you add shards, regions, or entirely new services, without a resharding migration every time.

## The properties that actually matter

"Unique" is necessary but nowhere near sufficient — a random 128-bit value is already unique with overwhelming probability. The properties below are what separate ID generators in practice, and an interviewer expects you to raise them unprompted rather than jump straight to "I'll use Snowflake."

### Global uniqueness

No two IDs collide, ever, across every generator instance running concurrently, forever. This has to hold even if two instances generate an ID in the same nanosecond with no communication between them — coordination-free uniqueness is the entire point of doing this instead of a single counter.

### Roughly ordered by time (not always strict monotonicity)

Most systems don't need `id(n+1) > id(n)` guaranteed for every single call across every machine — they need IDs that are *roughly* increasing with wall-clock time. Why this matters concretely: a B-tree index built on a column that arrives in random order (like a UUIDv4 primary key) causes inserts to land at random pages across the whole tree, thrashing the page cache and fragmenting the index. IDs that trend upward over time make inserts append mostly to the tail of the index, which is dramatically cheaper. It also makes "give me the latest 100 rows" a cheap range scan instead of a full sort.

Decide explicitly whether your system needs strict monotonicity (this ID is always greater than every ID issued before it, no exceptions) or just rough time-ordering (IDs from an hour ago are usually smaller than IDs from now, with some jitter). Strict monotonicity across a fleet of independent generators is a much harder — and more expensive — guarantee to make.

### Compact, fixed size

A 64-bit integer fits in a single machine word, sorts cheaply, indexes cheaply, and takes half the storage of a 128-bit UUID at billions of rows. If IDs show up in URLs or get typed by a human, size and readability matter too. State the acceptable size range as a requirement before comparing algorithms — it immediately rules some out.

### No single point of failure or bottleneck

Whatever generates the ID must not become a new chokepoint that the sharding was supposed to eliminate. If every insert across every shard has to call one ID service before it can proceed, you've reintroduced the exact serialization point you were trying to remove, just one layer up — and now it's also a new thing that can go down and take writes with it.

### High throughput, low latency, generated locally when possible

Generating an ID should ideally be a local, in-process computation (nanoseconds), not a network round trip. A system doing tens of thousands of writes per second per shard cannot afford a network call per ID on the hot path — that requirement alone pushes you toward algorithms that combine information already available locally (a machine/shard identifier, the current timestamp, a per-millisecond counter) rather than asking a central service for the next value.

### Availability under clock and node failure

Generators must keep producing valid, unique IDs even if a node restarts, a clock jumps backward (NTP correction, VM migration), or a datacenter is unreachable. If your chosen scheme derives part of the ID from the local clock, you need an explicit answer for "what happens if this machine's clock goes backward" — silently allowing that produces IDs that violate whatever ordering guarantee you promised.

## A worked example: why this matters before you code anything

Say you're building a URL shortener that's been sharded across 8 database instances to handle write load, and short codes are derived from the row's numeric ID. If each shard keeps its own auto-increment counter, shard 3 and shard 7 will both eventually produce ID 42, generate the same short code, and one of your two URLs silently overwrites lookups for the other.

Walking through the requirements above for this specific system: uniqueness is non-negotiable (that's the whole bug). Strict time-ordering isn't needed — nobody cares if a code created a millisecond earlier sorts after one created a millisecond later. Compactness matters because the ID gets encoded into a short URL, so 128-bit UUIDs (encoding to a long, ugly string) are a worse fit than a 64-bit integer. No single bottleneck matters a lot, since this system may do thousands of writes per second and can't afford a network call to a central counter service per shortened URL. Local, low-latency generation matters for the same reason. Clock-skew tolerance matters somewhat, but "roughly ordered" is enough — a full monotonicity guarantee isn't worth the coordination cost here.

That's five distinct decisions, each with a concrete reason, before a single line of the generator is designed. That's the output this lesson is asking for: not "unique ID," but a specific, justified list like the one above, which the next lesson uses to actually evaluate UUIDs, database tickets, and Snowflake-style generators against.

<Callout type="warning">
  A common mistake is treating "must be unique" as the entire requirements list and jumping straight to an algorithm (usually UUIDv4, because it's familiar). That skips the trade-offs that actually differentiate the options: a random UUID is unique but not sortable by time and is twice the size of a 64-bit integer, which hurts index locality and storage at scale. An interviewer who hears "I'll just use UUIDs" with no discussion of ordering, size, or generation cost will usually push back with "what if we need to sort by creation time?" — have that answer ready by working through the properties above first, not by picking an algorithm and hoping it fits.
</Callout>
