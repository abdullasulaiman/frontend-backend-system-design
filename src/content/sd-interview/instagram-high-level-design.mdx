You've already nailed down requirements and rough scale numbers in the
previous lesson — say, hundreds of millions of daily active users, a
read-to-write ratio north of 100:1, and a hard requirement that opening the
app feels instant. Now comes the part of the interview where you actually
draw boxes. The trap most candidates fall into is treating Instagram as one
big "posts and feeds" service. It isn't. It's a handful of services with
wildly different traffic shapes bolted together, and naming that split
explicitly is what separates a strong answer from a vague one.

## Two traffic shapes, not one

Before drawing components, say out loud what's actually happening
volume-wise:

- **Posting a photo/video** is rare per user (a handful of times a day at
  most), tolerant of a second or two of processing latency, and involves
  real CPU work — resizing images into multiple resolutions, generating
  thumbnails, sometimes transcoding video.
- **Viewing a feed** happens constantly — every app open, every pull-to-refresh
  — and has to feel instant. It's a read against data that was mostly
  written by *other* people, often minutes or hours ago.
- **Social actions** (like, comment, follow) are high-frequency, low-latency
  writes, but the data they touch (counts) doesn't need strong consistency —
  nobody notices if a like count is off by one for a few seconds.

That's three different scaling problems. Keep them separate in your design
and you'll naturally reach for the right storage and consistency model for
each.

## Core services

A workable high-level design breaks into these pieces:

- **Client** (mobile app, primarily) — captures/selects media, calls the API
  layer for everything else.
- **API / edge layer** — stateless services behind a load balancer handling
  auth, rate limiting, and routing to the right backend service.
- **Upload service** — accepts the raw photo/video, writes it to a staging
  area, and kicks off asynchronous processing. Returns quickly once the raw
  file is safely stored, not once processing finishes.
- **Media processing pipeline** — workers that generate multiple resolutions
  (thumbnail, feed-size, full-size), strip EXIF data, and (for video)
  transcode into a few renditions. Covered in depth in "Media Storage and
  Delivery."
- **Object storage** — durable blob storage for every rendition of every
  photo/video ever uploaded.
- **CDN** — sits in front of object storage and serves the actual bytes to
  viewers; this absorbs essentially all read bandwidth.
- **Post metadata service** — owns the post row itself: post ID, author,
  caption, timestamp, storage pointers, visibility. Its own database.
- **Graph service** — owns the follow relationships (who follows whom). A
  distinct store from post metadata, since the access pattern is "get me
  this user's followers/following," not "get me a post."
- **Feed service** — the component that answers "what should this user see
  right now?" Reads from a precomputed per-user timeline where possible.
  Covered in depth in "Feed and Stories."
- **Social graph actions (likes/comments) service** — high write volume,
  eventually-consistent counters, backed by a queue-fed aggregation layer
  rather than synchronous counter updates.
- **Notification service** — fed asynchronously off of post, like, and
  comment events; never sits on the critical path of the action that
  triggered it.

## Walking the write path

A user taps "share." The client uploads the raw file to the upload service,
which streams it into raw storage and writes a post-metadata row marked
"processing" — then returns success immediately. It does not wait for
resizing or transcoding.

That write also enqueues two things: a media-processing job (produce the
renditions the app actually displays) and a fan-out job (push this post
into the precomputed timelines of the author's followers). Once processing
finishes, the post flips to "visible," and its renditions live in object
storage behind the CDN. The fan-out worker is the piece that makes feed
reads cheap later — more on that below.

## Walking the read path

A viewer opens the app. The client calls the feed service, which — for the
overwhelming majority of users — just reads a precomputed list of post IDs
out of a timeline cache keyed by that viewer's user ID. That's a single
fast lookup, not a live query across everyone they follow. The client then
resolves post IDs into content (fetching metadata plus signed CDN URLs) and
streams the actual media bytes straight from the CDN — never through your
application servers.

This mirrors the same principle you'd apply to any read-heavy system: the
API layer hands out pointers and small metadata; a CDN backed by object
storage does 100% of the bandwidth-heavy work.

### Fan-out-on-write vs. fan-out-on-read

This is the one design decision worth spending real interview time on:

- **Fan-out-on-write**: when a user posts, immediately push the post ID into
  every follower's timeline cache. Reads become trivial (one cache lookup),
  but a single post from an account with 50 million followers means 50
  million cache writes — a "thundering herd" on the write side.
- **Fan-out-on-read**: don't precompute anything; when a user opens their
  feed, fetch recent posts from everyone they follow and merge them live.
  This avoids the celebrity write-storm but makes every feed read
  expensive, especially for someone following thousands of accounts.

The practical answer most systems converge on is a hybrid: fan-out-on-write
for the typical user (bounded follower count, cheap to push to), and
fan-out-on-read for a small set of very-high-follower accounts, merged into
the viewer's feed at read time. Say this explicitly in an interview — it
shows you've thought about the tail, not just the average case.

## Worked example: a post that goes viral

A user with 20 million followers posts a photo that starts getting shared
widely. Trace it through the design above:

1. **Upload**: one write. The upload service stores the raw file, creates
   one post-metadata row, and returns success in well under a second — none
   of this depends on follower count.
2. **Fan-out**: because this account is flagged as high-follower (past
   whatever threshold you pick, say 1 million followers), the fan-out
   worker skips pushing into 20 million individual timeline caches. Instead
   it just marks the post as available; each follower's feed read will
   merge it in live at read time.
3. **Reads**: every one of those 20 million followers, on their next app
   open, has their feed service fetch this one post directly (cheap, since
   there are few high-follower accounts to check per user) and merge it
   with their precomputed timeline from everyone else they follow.
4. **Media delivery**: all 20 million of those viewers hit the CDN for the
   same handful of image renditions — a close-to-ideal cache-hit scenario,
   so object storage barely feels it.

Without the hybrid fan-out split, step 2 would mean 20 million cache writes
fired off the instant one person hits "share" — exactly the kind of spike
that takes down a naively fan-out-everything design.

<Callout type="warning">
  A common mistake is designing the feed as a live query — "on read, fetch
  the last N posts from every account this user follows, sort by time, and
  return it." That's simple to describe but means every single feed open
  triggers a fan-in read across potentially thousands of followed accounts,
  which does not scale to a read-heavy, latency-critical product. Precompute
  the common case (fan-out-on-write into a timeline cache) and only fall
  back to live merging for the rare high-follower accounts that would make
  precomputing too expensive.
</Callout>

## What this lesson set up

This is deliberately a skeleton view: it names the services, shows how a
post moves from upload to visible, and flags the fan-out trade-off — but it
doesn't dig into media storage internals or feed ranking logic yet. Those
get dedicated lessons next. The one idea to carry forward: almost every
follow-up question in a photo-sharing interview ("how do you handle a
celebrity account?", "how fresh does the feed need to be?", "what happens
if a post is deleted after fan-out?") is really asking you to reason about
which side of the write/read split is involved.
