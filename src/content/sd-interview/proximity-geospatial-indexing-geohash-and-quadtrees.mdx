The previous lesson sketched a proximity service's high-level shape: clients
send a location and a radius, and some "location index" answers with nearby
businesses. That box labeled "location index" is doing all the real work, and
it's the part interviewers dig into next. Latitude and longitude are just two
floating-point numbers, so it's tempting to store them as two columns and
query `WHERE lat BETWEEN x AND y AND lon BETWEEN a AND b`. That query cannot
use a standard single-column index efficiently on both dimensions at once —
the database ends up scanning far more rows than it needs to, and it gets
worse as the table grows. Geospatial indexing exists to fix exactly this: turn
a two-dimensional "what's nearby" question into something a normal index can
answer quickly. Geohashing and quadtrees are the two techniques you're
expected to know, and a strong candidate can explain not just how each works
but when to reach for one over the other.

## The core idea: collapse 2D into something indexable

Both techniques solve the same problem the same general way: divide the
world into a hierarchy of regions, and give every region an identifier such
that "nearby in space" tends to mean "similar identifier." Once that's true,
a "find nearby points" query becomes "find rows whose identifier matches
this prefix" or "walk this small part of a tree" — both are things ordinary
indexes and data structures are good at.

## Geohashing

A geohash encodes a lat/lon pair into a single string by repeatedly bisecting
latitude and longitude ranges and interleaving the resulting bits. Each step
asks "is the point in the top or bottom half of the current latitude range?"
and "left or right half of the current longitude range?", appending a `0` or
`1` for each answer, alternating between the two dimensions. The resulting
bitstream is then grouped into 5-bit chunks and base32-encoded into a short,
readable string like `9q8yy`.

The property that makes this useful: every additional character narrows the
bounding box further, and two points that share a long common prefix are
guaranteed to be close together (though, as you'll see below, the reverse
isn't quite true). This gives you a natural precision/area trade-off:

| Geohash length | Approx. cell size |
|---|---|
| 3 chars | ~150km x 150km |
| 5 chars | ~5km x 5km |
| 6 chars | ~1.2km x 0.6km |
| 7 chars | ~150m x 150m |
| 9 chars | ~5m x 5m |

To find "everyone within roughly 5km," compute the geohash of the query
point at 5-character precision and look up rows whose geohash column starts
with that prefix — a plain indexed range query (`geohash >= 'dr5ru'` AND
`geohash < 'dr5rv'`), no spatial data structure required. This is exactly why
geohash is popular: it turns a 2D problem into an ordinary string-prefix
lookup that any key-value store, relational index, or Redis sorted set
already knows how to do fast.

### The boundary problem

Prefix matching has one sharp edge: it only finds points that fall in the
*same* grid cell as the query point. Two points a meter apart, one just
east and one just west of a cell boundary, can end up with almost no common
prefix at all, even though they're neighbors in real life. If you only query
the query point's own cell, you'll silently miss real nearby matches sitting
just across a grid line.

The standard fix is to always query the point's own cell **plus its 8
surrounding neighbor cells** at the same precision (a 3x3 block), then filter
the combined candidate set by actual distance. This is a well-known, expected
part of any geohash-based design — leaving it out is one of the most common
gaps in candidate answers.

## Quadtrees

A quadtree takes a different approach: instead of a fixed grid, it builds a
tree by recursively splitting a region into four quadrants, but **only where
there's enough data to justify it**. A quadrant holding fewer than some
threshold of points (say, 100) stays a leaf; a quadrant with more points
splits into four children, and each of those is checked again, recursively.

This makes quadtrees adaptive to density in a way a fixed geohash grid isn't:
a leaf covering dense midtown Manhattan might be a tiny few-hundred-meter
square holding 100 businesses, while a leaf covering rural land might span
tens of kilometers holding the same 100. A fixed-precision geohash grid, by
contrast, uses the same cell size everywhere — too coarse to be useful in a
dense downtown, or needlessly fine (and needlessly many empty cells) out in
the countryside.

The cost of that adaptivity: a quadtree is an actual tree structure you build,
keep in memory (or in a store that supports it), and rebalance as points are
added or removed — it doesn't reduce to "one indexed string column" the way
geohash does.

To query a quadtree for "nearby points," you descend from the root, entering
only the quadrants that overlap the search radius, and collect points from
the leaves you reach — pruning away entire subtrees that don't intersect the
query area at all.

## Geohash vs. quadtree: which one, and when

Both solve the same problem; the decision comes down to what you're
optimizing for:

- **Reach for geohash** when you want to reuse existing infrastructure —
  a relational index, a plain key-value store, or Redis (which has geohash
  support with `GEOADD`/`GEORADIUS` built in) — and don't want to own a
  custom tree structure. It's the simpler answer to defend in an interview
  and the more common real-world default for exactly that reason.
- **Reach for a quadtree** when density is highly uneven and you want cells
  that shrink automatically in busy areas without needing needlessly tiny
  cells everywhere else, or when you're comfortable owning and operating a
  purpose-built in-memory spatial index (some systems keep the whole
  quadtree in memory on a fleet of index servers, rebuilt periodically from
  a source of truth).

In an interview, naming both, explaining the trade-off in one or two
sentences, and picking one to run with is worth far more than reciting every
implementation detail of either.

## Worked example: indexing 2 million businesses

Say the proximity service holds 2 million businesses and needs to answer
"what's within 2km of this point" queries. With geohashing, every business
row stores a geohash computed at, say, 6-character precision (~1.2km x
0.6km cells — close enough to a 2km query radius that a handful of
neighboring cells cover it). A query computes the 6-character geohash of the
user's location, looks up its cell plus its 8 neighbors (9 cells total) via
an indexed prefix range scan, and then does an exact distance calculation on
that (typically small) candidate set to filter out anything actually outside
2km and to rank the rest by distance.

With a quadtree instead, the same query walks down from the root, discarding
any quadrant whose bounding box doesn't intersect a 2km circle around the
point, and collects candidates only from the leaves that do intersect —
naturally landing on tiny leaves in a dense downtown and much larger ones
in a sparse suburb, without any precision parameter to tune up front.

Either index answers the query in roughly the same shape: narrow millions of
rows down to a small candidate set using the spatial structure, then do exact
math only on that small set. That's the pattern the next lesson builds the
actual service around.

<Callout type="warning">
  Don't stop at "compute a geohash prefix" and call the query done. A prefix
  match alone misses real nearby points that fall just across a cell
  boundary — always search the neighboring cells too, and always follow up
  with an exact distance check (e.g. haversine distance) on the candidate set
  before returning or ranking results, since a geohash cell's corners can be
  meaningfully farther from the query point than its center.
</Callout>
