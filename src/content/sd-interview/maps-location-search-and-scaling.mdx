Every mapping app lives or dies on one interaction: a user types "coffee"
or taps a pin and expects a ranked list of nearby places back in a couple
hundred milliseconds. That interaction looks like a text search problem,
but it isn't — it's a geospatial problem wearing a search box. Get the
indexing wrong and a query for "pizza near me" in Manhattan either scans
half the planet's restaurant data or misses a place two blocks away
because it landed in the "wrong" grid cell. This lesson covers how to
index locations for fast proximity search, and then zooms out to how the
whole system from the earlier lessons — tiles, routing, and search —
actually scales under real traffic.

## Why proximity search needs its own index

A normal text search (an inverted index mapping words to documents) tells
you *which* documents mention "coffee." It tells you nothing about
*distance*. You could intersect a text match with a location filter, but
without a spatial index, checking "is this place near the user" against
millions of rows means a full scan with a distance calculation on every
row — computing a distance formula against millions of candidates per
query using CPU-heavy geometry doesn't scale to tens of thousands of
searches a second.

The fix is the same one used for every "find nearby" problem: encode
two-dimensional location into a structure that groups nearby points
together, so a proximity query becomes a cheap lookup into a small number
of buckets instead of a scan of everything.

## Three ways to bucket the world

### Fixed grid (geohash-style)

Divide the world into a grid and encode each latitude/longitude pair into
a short string or integer that identifies which cell it falls in. Points
in the same cell share the same code; points in neighboring cells share a
common prefix, which lets you widen or narrow your search radius just by
truncating or extending the code you match against.

The catch: cells are fixed-size rectangles, so density is ignored. A
sparse cell in the Nevada desert and a packed cell in central Tokyo hold
wildly different numbers of places, and cell boundaries are arbitrary —
two coffee shops fifty meters apart can end up in different cells if a
boundary happens to run between them. Any grid-based scheme has to query
the center cell plus its immediate neighbors, never just one cell, or
it'll silently miss nearby results sitting just across a boundary line.

### Quadtree

A quadtree fixes the density problem by subdividing recursively: start
with one cell covering the whole area, and split a cell into four
quadrants whenever it holds more than some threshold of points. Dense
areas end up many levels deep with small cells; sparse areas stay
shallow with large cells. This keeps the number of candidate points per
leaf roughly constant regardless of where in the world you're searching,
which is exactly what you want for a search index's shard sizing (more on
that below).

### Spherical cell hierarchies

Grid schemes based on raw latitude/longitude distort badly near the
poles, where lines of longitude converge — a "square" cell near the
equator covers a very different real-world area than one near Greenland.
Production mapping systems typically project the globe onto a cube or
similar solid first, then apply a hierarchical cell scheme on each face,
which keeps cell areas close to uniform everywhere and avoids the polar
distortion problem entirely. The underlying idea is the same as a
quadtree — recursive subdivision into a searchable hierarchy — just
applied to a sphere instead of a flat plane.

## Serving a "near me" query end to end

A real query combines the spatial index with the text index: first
narrow to a small set of geo cells around the user's location, then
filter and rank within that set by text relevance, rating, and distance.
Doing it in the other order — text-match everything named "coffee"
globally, then filter by distance — throws away the one filter (location)
that shrinks the candidate set the fastest.

## Scaling the search service

Once places are indexed spatially, the same index shape decides how you
shard the service:

- **Shard by geography, not by a hash of place ID.** A query for
  restaurants in Chicago should hit only the shards covering the Chicago
  area, not scatter-gather across every shard on the planet. Geographic
  sharding is what makes a single "near me" query cheap.
- **Expect hot shards, and plan for them.** A cell covering Manhattan
  might hold a hundred times more places than a same-sized cell covering
  rural Montana. Use the quadtree/hierarchical approach so hot regions
  get split into many small, independently-scaled shards while cold
  regions stay as a handful of large ones — don't force every shard to
  cover equal land area.
- **Cache at the query level.** Searches for common terms ("coffee,"
  "gas station," "pharmacy") repeat constantly from users in the same
  area. A cache keyed by rounded location plus search term absorbs a large
  fraction of traffic, and search results can tolerate a few minutes of
  staleness — a newly-opened cafe missing from results for ten minutes
  isn't a user-visible failure the way a stale traffic-jam warning would
  be.
- **Replicate for both read throughput and latency.** Read replicas of
  each geo-shard handle read scaling; placing replicas in the same region
  as the users querying them cuts round-trip latency, which matters far
  more for a 200ms interactive search than for a background batch job.

This is the same pattern the rest of the system already relies on. Map
tiles (lesson 3) scale by being nearly-static and CDN-cacheable. Routing
(lesson 4) scales by keeping the road graph mostly in memory and
partitioning it geographically for the heaviest queries. Location
ingestion (lesson 1) scales by treating pings as a high-volume write
stream partitioned by trip, not by routing every ping through a
relational database. Search scaling reuses geographic partitioning too,
but its read/write ratio and cache-friendliness are different enough that
it deserves its own service, its own shard boundaries, and its own
scaling policy — resist the urge to force one global "scale everything
the same way" story onto sub-systems that behave differently.

## Worked example: sizing a search shard

Take the numbers from this module's estimation lesson: roughly 26,000
search queries per second at peak. Suppose a quadtree-based index splits
the world so that no single leaf cell holds more than about 2,000 places,
and a single search shard comfortably serves 3,000 queries per second
from memory. That's roughly nine shards needed just to absorb peak load
with no headroom — round up to say fifteen for failover and uneven
traffic distribution across time zones (peak search traffic in Tokyo and
peak traffic in New York don't overlap, so a shard sized for its own
region's evening rush has slack the rest of the day).

Now add caching: if a query-level cache absorbs 40% of traffic because
common searches repeat so often, the backend shards only need to handle
about 15,600 queries per second combined, cutting the shard count
estimate roughly in half. This is why "add a cache in front of the search
index" is one of the highest-leverage scaling moves available here — it
directly reduces how much geographic sharding you need to build and
operate.

<Callout type="warning">
  A common mistake is designing the geospatial index and then bolting
  text search on top as an afterthought — or the reverse, building a
  full-text search cluster and only later realizing every query also
  needs a location filter. Decide up front which filter narrows the
  candidate set fastest (almost always location, since it's a much
  smaller fan-out per query), and make that the first-stage lookup. Doing
  text matching first and location filtering second turns every query
  into a much bigger scan than it needs to be.
</Callout>
