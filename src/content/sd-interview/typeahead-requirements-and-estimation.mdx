Typeahead looks like the simplest feature in the product — a dropdown under
a search box — which is exactly why it's a good interview prompt. It hides
a nasty combination of constraints: it fires on almost every keystroke
across your entire user base, each response has to land in a fraction of
the time a normal page load gets, and yet the thing it's serving (which
queries are "popular" right now) barely changes minute to minute. Get the
scoping wrong and you'll spend the rest of the interview designing a
database that can't possibly answer fast enough.

This lesson sets up that scoping: what the system must do, how big it is,
and — critically — how far apart its read and write paths sit from each
other. The trie-based data structure, ranking model, and full architecture
in the rest of this module all build on the numbers established here.

## Step 1: Scope the functional requirements

State the core scope and let the interviewer redirect:

- **Return top-k suggestions for a prefix.** As a user types, the system
  returns a short, ranked list (say, 5-10 items) of likely completions for
  whatever has been typed so far.
- **Rank by relevance.** Initially, relevance means historical popularity —
  how often a given query has been searched. (Personalization and
  context-aware ranking get their own lesson later in this module.)
- **Update over time.** Newly popular or trending queries should surface
  within a reasonable window (minutes to hours), not instantly and not
  never.
- **Serve across languages/locales at a basic level.** Prefix matching
  should work for the character sets the product supports.

Explicitly defer: spelling correction and fuzzy/typo-tolerant matching,
personalized ranking signals (past searches, location, session context),
and voice-input parsing. Each is a legitimate deep-dive but would blow the
scope of a single session — flag them and move on. (The next lesson covers
the trie/data-structure question this scope implies; the one after covers
ranking beyond raw popularity.)

### Non-functional requirements

- **Latency has to feel instant.** Because a request fires on nearly every
  keystroke rather than once per page view, the server-side budget needs
  to be tight — think comfortably under 100ms, so the round trip plus
  client rendering still feels immediate.
- **Reads vastly outnumber writes, and the two are decoupled.** Suggestion
  lookups happen continuously in real time; the underlying popularity data
  only needs to change on a batch cadence. Treat these as two different
  systems with two different consistency and latency requirements, not one
  system doing double duty.
- **Availability and staleness tolerance beat strict freshness.** A
  suggestion list built an hour ago still looks correct to the user; a
  slow or missing dropdown does not. Favor caching and availability over
  guaranteeing the absolute latest counts.
- **The system must scale horizontally on the read side.** Per-keystroke
  fan-out means suggestion-serving load grows with typing activity, not
  just with the number of searches actually submitted.

## Step 2: Establish the scale

State assumptions out loud and invite correction:

- 100 million daily active users of the search product.
- Each user completes about 3 searches a day, so 300 million submitted
  queries/day.
- Average query length is about 20 characters.
- The client debounces keystrokes (waits briefly for typing to pause, and
  skips firing until at least 2 characters are typed) rather than sending
  a request on every single character. That cuts what would otherwise be
  up to ~18 raw keystroke events per query down to an average of 6 actual
  suggestion requests sent per completed query typed.
- The corpus of distinct historical queries worth tracking for suggestions
  is about 20 million entries.

  A quick confirmation here means every number that follows is defensible.
</Callout>

## Step 3: Derive the numbers for each sub-system

### Suggestion-read QPS (the hot path)

- 300,000,000 queries/day times 6 requests/query gives 1,800,000,000
  suggestion requests/day.
- Average QPS: 1,800,000,000 divided by 86,400 seconds is about
  20,800 requests/sec.
- Search traffic has a daytime/nighttime curve rather than sharp bursts
  like a flash sale, so a 3x peak multiplier is reasonable: roughly
  62,500 requests/sec at peak.

### Query-log write rate (the cold path)

- Only completed, submitted queries get logged for future ranking — not
  every keystroke request. That's 300,000,000/day, or about
  3,470 writes/sec on average — appended sequentially, not requiring any
  synchronous update to the serving structure.
- The key relationship: **suggestion reads outnumber query-log writes by
  exactly the per-query fan-out factor — 6-to-1 here** — purely because
  every submitted query generates several suggestion requests on the way
  to being typed, but only one log entry once it's submitted.
- Critically, the serving structure itself is *not* updated per write.
  Counts accumulate in the log, and a batch job periodically (say, hourly)
  recomputes top-k completions and rebuilds the structure the read path
  serves from. The online read path never touches a raw counter.

### Storage: query corpus vs. serving index

- The counters themselves are tiny: 20,000,000 distinct queries at roughly
  40 bytes each (query text, an id, a count) is under 1 GB — trivial to
  hold entirely in memory, even replicated for redundancy.
- The serving structure (a prefix-indexed lookup annotated with each
  prefix's current top-k) is the real design question, but even a rough
  upper bound stays modest: after merging shared prefixes across a
  20-million-query corpus (many queries share common prefixes like "how
  to" or "best "), a pruned structure that only materializes prefixes with
  meaningful traffic lands in the single-digit-to-low-tens-of-gigabytes
  range — small enough to replicate fully across many serving nodes for
  both redundancy and low-latency locality, unlike, say, a full-text
  search index measured in terabytes.

## Step 4: State the resulting design constraints

1. **The read path must be served from a precomputed, in-memory structure**
   — at 20,800 requests/sec average (62,500 at peak) with a sub-100ms
   budget, computing top-k completions live per request is off the table.
2. **Decouple index rebuilding from the request path entirely** — the
   batch job that recomputes rankings from the query log runs on its own
   schedule and swaps in a new version of the serving structure; the read
   path is never blocked on, or aware of, that process.
3. **Favor availability and heavy caching** — client-side local caches for
   recently-seen prefixes, CDN/edge caching for common ones, and multiple
   in-memory replicas of the serving structure all pay off here, since
   staleness costs nothing visible but a slow or dropped response does.
4. **Storage is not the hard constraint; pruning policy is** — the raw
   corpus and counters are cheap at any reasonable scale; the actual
   sizing decision is how aggressively you prune low-traffic prefixes out
   of the serving structure so it doesn't grow unbounded as the corpus
   grows.

<Callout type="warning">
  A common mistake is sizing this system off "searches per day" alone, the
  way you'd size a normal API. That misses the per-keystroke fan-out
  entirely — the number that actually determines your server fleet is
  suggestion *requests*, which ran roughly 6x higher than submitted
  queries in this estimate purely from client-side debounced fan-out. The
  opposite mistake is just as common: because the system "learns" from
  user behavior, candidates sometimes assume it's write-heavy. It's the
  reverse — reads dominate by orders of magnitude, and the write side is
  intentionally lagging and batched, never on the request's critical path.
</Callout>

## Worked example: sanity-checking a follow-up

Suppose the interviewer asks: "What if we tightened the client debounce
window so it fires twice as often — 12 requests per query instead of 6?"
Re-derive rather than guess: suggestion requests/day go from 1.8 billion to
3.6 billion, so average QPS roughly doubles, from ~20,800/sec to
~41,600/sec, and peak goes from ~62,500/sec to ~125,000/sec. Nothing else
moves: the query-log write rate stays at ~3,470/sec (still one log entry
per *submitted* query, unaffected by how many suggestion requests it took
to get there), and the corpus size and serving-index size are unchanged,
since neither depends on how chatty the client is. Naming precisely which
number a changed assumption touches — and which ones it leaves completely
alone — is what separates a candidate who understands the system from one
who's just re-running the same multiplication.

## Where this leads

The split this lesson establishes — a very high-QPS, latency-critical read
path serving a precomputed structure, decoupled from a modest, batch-driven
write path that reshapes that structure on its own schedule — is the shape
every later lesson in this module builds on. The next lesson covers the
trie (and trie variants) that make the read path fast; the one after covers
how "top-k" gets decided once you move past raw popularity counts.
