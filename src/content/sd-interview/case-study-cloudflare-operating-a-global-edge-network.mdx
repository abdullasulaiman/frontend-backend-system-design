Most system design case studies you'll study — Netflix, DynamoDB, Discord — are about scaling **one company's own product**. Cloudflare is a different shape of problem: it operates infrastructure that sits in front of millions of *other people's* websites and APIs, in over 300 cities, and has to be simultaneously a CDN, a DDoS scrubber, a DNS resolver, and (increasingly) a place to run arbitrary application code — all while adding as little latency as possible to a request that was already going to happen anyway.

That combination forces a specific architectural stance: every edge location must be a complete, self-sufficient replica of the whole system, reachable by the nearest possible route, with no single choke point that an attacker or an outage can target. This lesson looks at how anycast routing, a homogeneous edge fleet, and edge compute combine to deliver that. It pairs well with the Netflix lesson earlier in this module — both push work to the edge, but for different reasons and with different trade-offs.

## The core idea: anycast instead of DNS-based geo-routing

Most multi-region services route users to the nearest data center using DNS: a client resolves `api.example.com`, the DNS server looks at the client's approximate location (via GeoIP), and returns the IP of the nearest regional cluster. This works, but it has two structural weaknesses: DNS answers get cached (by resolvers, by OS stacks, by browsers) for minutes to hours, so failover is slow, and "nearest" is only ever a GeoIP guess, not an actual network-topology measurement.

Cloudflare instead uses **anycast**: the *same* IP address is announced, via BGP, from every one of its edge locations simultaneously. Routers across the internet don't know or care that dozens of physical servers claim to own that address — BGP's path-selection algorithm just routes each packet toward whichever announcement is topologically closest, hop-count and route-cost wise, to the sender. Two users on opposite sides of the planet, both connecting to `1.1.1.1`, transparently land on two different physical servers without either of them (or Cloudflare's DNS) doing anything geo-aware.

This gets you two things DNS-based routing can't cheaply give you:

- **Sub-second failover.** If a data center goes dark, it simply stops announcing its BGP routes. The internet's routers converge on the next-nearest announcement within seconds — no TTL to wait out, no client-side retry logic required.
- **Free DDoS dispersion.** A volumetric attack aimed at one IP doesn't concentrate on one data center — the flood is split across every location currently announcing that route, roughly in proportion to the attacker's own network topology. A 2 Tbps flood arriving at 300 locations is a very different (survivable) problem per-location than 2 Tbps arriving at one.

## A homogeneous edge: every PoP does everything

The second key decision is that Cloudflare doesn't split its stack into "edge does caching, core does everything else." Every point of presence (PoP) runs the full software stack: TLS termination, the WAF (web application firewall), rate limiting, DDoS scrubbing, DNS resolution, cache, and the Workers runtime for edge compute. A request landing in any of the 300-plus cities gets a functionally identical experience.

This matters for two reasons a candidate should be able to articulate:

1. **No coordination tax.** If edge and origin logic had to agree on WAF rules or cache-invalidation state, every rule change would need a rollout protocol across regions with consistency guarantees. Because each PoP independently runs the same code against (mostly) the same configuration, a rule push is "replicate this config object to every PoP," not a distributed transaction.
2. **Uniform failure domain.** Any PoP can absorb any other PoP's traffic during an outage or an anycast re-route, because there's no PoP that's "the DNS one" or "the WAF one." Losing a location is a capacity problem, not a missing-capability problem.

The trade-off is config propagation lag: a WAF rule or cache-purge pushed centrally still takes time (typically seconds, not milliseconds) to reach every PoP, so there's a brief window where different users see different behavior. Cloudflare accepts that window in exchange for never needing synchronous cross-region coordination on the request path.

### Keeping cache misses fast

A CDN only helps on a cache hit. On a miss, Cloudflare still has to fetch from the customer's origin server — but it doesn't do that over the open internet per-request. The edge terminates the client's TLS/TCP (or QUIC) connection locally, then reuses an already-open, kept-warm connection to the origin over Cloudflare's own private backbone. This "connection coalescing" avoids paying TCP and TLS handshake round-trips on every miss, and it lets Cloudflare route the origin-bound leg over links it controls and has already provisioned capacity on, rather than at the mercy of public internet congestion between the PoP and the customer's data center.

## Edge compute: pushing logic, not just bytes, to the edge

Workers extends the same "every PoP does everything" philosophy to application logic. Instead of virtual machines or containers per request, Workers run customer JavaScript/WASM inside **V8 isolates** — the same lightweight sandboxing primitive V8 uses to isolate browser tabs from each other. An isolate starts in low single-digit milliseconds (no OS boot, no container image pull) and only needs a few KB of memory overhead, which is what makes it economical to have every one of hundreds of PoPs ready to run arbitrary customer code with no pre-warming.

The trade-off is capability, not just performance: isolates share a process and don't get their own OS-level sandbox, so the isolation model relies on V8's JS/WASM sandbox rather than OS-level virtualization, and long-running or heavily stateful workloads (a multi-second batch job, a large in-memory dataset) don't fit the model — Workers are built for short, stateless-ish request/response logic (auth checks, header rewriting, A/B routing, small key-value lookups), not for replacing your origin's application server.

## Worked example: sizing DDoS absorption capacity

Say you're asked, in an interview, "estimate how anycast dispersion helps absorb a large DDoS attack." Walk through it like this:

- Assume a 3 Tbps volumetric attack — large but realistic for a major incident.
- Assume the attacking botnet's traffic is roughly proportional to global internet population density, and the anycast fleet has ~300 PoPs.
- If dispersion were perfectly even, each PoP would see roughly 3 Tbps / 300 = 10 Gbps of attack traffic.
- A single edge server's NIC and local scrubbing pipeline handling 10 Gbps of junk traffic while continuing to serve legitimate 1-10ms cache-hit responses is a tractable, already-provisioned-for problem — versus one data center trying to absorb the full 3 Tbps alone, which would saturate almost any single site's uplink.

The real distribution isn't perfectly even — attackers and legitimate users don't share the same geography, and some PoPs are bigger than others — but the estimate captures the mechanism: anycast turns "defend against the whole attack" into "defend against attack-size divided by PoP-count," which is why volumetric DDoS mitigation at this scale is a *routing* strategy as much as a filtering one.

<Callout type="warning">
  A common mistake in interviews is describing anycast as if it were a smarter, IP-layer version of DNS geo-routing — "so it picks the closest server, like a load balancer." It isn't a load balancer and it isn't connection-aware: BGP makes a route decision per-packet-path, not per-session, so if the internet's routing tables change mid-connection (a link flaps, a peer reconverges), a long-lived TCP or QUIC connection can get silently rerouted to a *different* physical server with no memory of that session. Any state a request depends on (a TLS session, an in-progress upload) has to either be re-derivable at any PoP or accept the rare reconnection. Say this explicitly if you bring up anycast — it signals you understand the mechanism, not just the marketing term.
</Callout>

## How this compares to other lessons in this module

Where Netflix (earlier in this module) pushes *content* to the edge but keeps personalization and control logic centralized, and DynamoDB replicates *data* across nodes within a service's own control, Cloudflare pushes both *routing* (via anycast) and *computation* (via Workers) to the edge, and treats every edge node as interchangeable. It's a useful third point on the "how much do you push to the edge, and what do you push" spectrum that shows up repeatedly in system design interviews — worth having a one-sentence contrast ready for any of the three.
