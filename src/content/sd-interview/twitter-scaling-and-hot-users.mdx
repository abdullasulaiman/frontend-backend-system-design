The previous lesson solved the celebrity fan-out problem with a push/pull threshold: small accounts get fanned out on write, huge accounts get pulled at read time. That's necessary, but it's not sufficient. A hybrid fan-out design tells you *which accounts* skip the write storm — it says nothing about what happens when a single tweet ID, a single user row, or a single counter becomes the most-requested piece of data on the entire platform. That's a different failure mode, and it's the one that actually takes services down in production: not "too many users" in aggregate, but one specific key getting hit at a rate no single node can serve.

This lesson works through that problem at three layers — caching, storage partitioning, and counters — plus how to isolate hot traffic so it degrades gracefully instead of taking shared infrastructure down with it.

## Hot keys aren't a sharding problem

Sharding distributes load by spreading *different* keys across *different* nodes, on the assumption that traffic is roughly even across keys. A hot key breaks that assumption: one key (a viral tweet's ID, a celebrity's user record) receives orders of magnitude more traffic than any other key on the same shard. Sharding doesn't help here — the hot key still lives on exactly one node, however you've partitioned the keyspace, because a consistent-hash or range-based scheme routes every request for that ID to the same place by design.

Concretely: your tweet-content cache stores each tweet under `tweet:<id>`. A normal tweet gets fetched a few hundred times as it's read out of a handful of followers' timelines. A viral tweet from a huge account gets fetched by tens of millions of timeline renders within minutes, all mapping to the same cache key on the same node. That node's network and CPU capacity, not the cluster's aggregate capacity, becomes the bottleneck.

The fix is to stop treating that key as if it lived on one node:

- **Replicate the hot value across several cache nodes** and route reads round-robin (or by request hash) across the replicas, instead of always hitting the one node the standard hashing scheme picks.
- **Add a local, in-process cache** in front of the distributed cache for the small set of currently-hot IDs — a request that never leaves the app server is the cheapest possible read.
- **Detect "hot" automatically** with a request-rate counter per key (or per shard) so replication kicks in without a human flipping a flag mid-incident.

## Hot partitions: the same problem one layer down

The identical issue shows up in storage, not just cache. If you shard tweets or follower lists by user ID, every row belonging to one user — including a celebrity's entire follower list or engagement history — lands on one partition. A partition holding a 100-million-follower account's data takes disproportionate read and write load compared to a partition holding a thousand ordinary accounts, even though both partitions hold "one shard's worth" of rows by count.

The standard mitigation is to split known-hot rows further: append a random or hashed suffix (say, 0–19) to the shard key for a hot user's follower-list entries, so that one logical list is physically spread across 20 partitions instead of 1. Reads have to fan out across those 20 partitions and merge results, which is more expensive per read than a single-partition lookup — but it's a bounded, known cost, versus one partition melting under unbounded load. This is the same push/pull trade-off from the previous lesson, recurring one layer down: spread cost predictably now, rather than let it concentrate unpredictably later.

That last piece in the diagram — **request coalescing** — matters as much as replication. On a cache miss for a hot key (say, right after the cache entry expires), thousands of concurrent requests can all miss at once and all hammer the origin database for the identical row. Coalescing means the first miss triggers one database fetch, and every other concurrent request for that same key waits on that in-flight fetch instead of issuing its own — turning a thundering herd into a single query.

## Counters at viral scale

Like and retweet counts are the clearest example of "small data, huge contention." A viral tweet's like counter might receive tens of thousands of increment operations per second. Modeling it as one row with one integer column, updated with `UPDATE ... SET likes = likes + 1`, serializes every one of those writes against a single row lock — the database becomes a queue of one.

Two standard fixes, usually combined:

- **Shard the counter itself.** Instead of one row, keep N sub-counters (say, 20) for the same tweet, and increment a randomly chosen one per like event. The displayed count is the sum across all N, computed periodically or cached and refreshed on a short TTL — reads don't need to be perfectly real-time to the millisecond.
- **Batch increments in memory before flushing.** A stream-processing layer (or even an in-memory buffer per app instance) accumulates increments for a short window (a few hundred milliseconds) and flushes one batched update instead of one write per like. This trades a small, bounded staleness for a large reduction in write volume.

Exact real-time counts down to the last like are rarely a real product requirement — "approximately 48.3k likes, updated within a couple of seconds" is what users actually see on any large platform, and that's exactly the looseness that makes sharded, batched counters acceptable.

## Isolating hot traffic so it degrades gracefully

Everything above reduces the *cost* of hot keys, but you should also isolate their *blast radius*. Route pull-tier reads (celebrity timeline merges), fan-out jobs, and counter updates for known-hot accounts through separate queues and worker pools from normal traffic. If a sudden viral spike does overwhelm that isolated tier, the failure mode is "hot content is briefly stale or delayed" — not "the whole platform's write path backs up because one queue is saturated." Circuit breakers that fall back to a cached, slightly-stale value (an old like count, a timeline that's a few seconds behind) are far better than a request that hangs waiting for a system under load to respond exactly.

## Worked example: a tweet goes viral

Say an account with 80 million followers posts a tweet that gets picked up by news outlets and starts trending. Within 10 minutes, 30 million distinct users open the app and their timeline reads pull in that tweet. That's roughly 50,000 tweet-content lookups per second for one tweet ID, sustained for minutes — several orders of magnitude above the "a few hundred reads" a normal tweet sees.

Without hot-key handling, all 50,000 requests/second hit one cache node keyed on that tweet ID, and that node's network interface saturates well before the cluster's aggregate cache capacity is anywhere near its limit. With detection and replication across, say, 10 cache replicas plus per-app-server local caching absorbing a large fraction of reads before they even reach the distributed tier, that 50,000/second gets spread thin enough that no single node sees more than a few thousand requests/second — solidly within normal operating range. The fix isn't more total capacity; it's making sure the existing capacity is actually reachable by the requests that need it.

<Callout type="warning">
A common mistake is believing the push/pull fan-out threshold from the previous lesson "solves scaling for celebrities" and stopping there. It solves the *write* fan-out problem. It does nothing about the *read* side: a pull-tier tweet is still one row, one cache key, one database record, and every follower's timeline read still has to fetch it. Teams that only address fan-out often get blindsided the first time a pull-tier tweet goes viral, because the read path was never designed for a single key receiving tens of thousands of requests per second. Hot-key and hot-partition handling is a separate, necessary piece of the design — mention it explicitly even if the interviewer only asked about fan-out.
</Callout>
