The previous lesson framed the Lambda-vs-Kappa decision at the architecture
level: do you run two pipelines or one? This lesson goes one level down, into
the two execution models that decision is actually choosing between. Batch
and stream processing aren't just "slow" and "fast" versions of the same
thing — they make different assumptions about what data you have, how
complete it is, and what "done" even means. An interviewer who hears you say
"we'll just stream everything" without understanding those assumptions will
immediately ask what happens to a message that arrives four minutes late, and
that's exactly the kind of question this lesson prepares you to answer.

## Batch processing: bounded input, recompute freely

A batch job operates on a bounded dataset: a day's worth of log files, an
hour's partition in a data lake, a full table snapshot. Because the input is
finite and known ahead of time, batch systems get to make simplifying
assumptions that streaming systems can't:

- **Completeness is assumed.** By the time the job runs, the data for that
  window is considered final. There's no "what if more arrives later" — if
  it does arrive later, it belongs to the *next* run.
- **Failure recovery is coarse-grained.** If a batch job fails halfway
  through, you typically just re-run the whole job (or the failed
  partition). There's no per-record checkpoint to resume from because the
  whole computation is one atomic unit of work.
- **Throughput over latency.** A batch job optimizes for processing the most
  data per unit of compute, not for getting any single record through
  quickly. A nightly job that takes 3 hours to process 500GB is a success if
  it finishes before the 8am report deadline.

This is the model behind tools like Spark batch jobs, Hadoop MapReduce, and
scheduled SQL transforms in a warehouse. It's also the right default when the
business requirement doesn't actually need freshness — most financial
reconciliation, billing runs, and daily analytics dashboards fall into this
bucket, and building a streaming pipeline for them is over-engineering.

## Stream processing: unbounded input, decide as you go

A stream processor operates on data that never stops arriving. There's no
"end of the dataset" to wait for, which forces a different set of decisions:

- **You have to decide when a window is "done" without ever being sure.**
  Since events can be delayed by network partitions, retries, or a mobile
  client that was offline, the system has to make an explicit, revisable
  guess about completeness — this is what watermarks are for (more below).
- **State lives across the life of the job, not one run.** A streaming
  aggregation (e.g. "clicks per user per 5-minute window") keeps that
  partial count in memory or in a local state store for as long as the
  window is open, potentially across process restarts.
- **Failure recovery is fine-grained.** Instead of re-running everything,
  streaming engines checkpoint offsets and operator state periodically (Flink
  does this with distributed snapshots; Kafka Streams with changelog
  topics) so a crashed worker resumes near where it left off, not from zero.

This is the model behind Flink, Kafka Streams, Spark Structured Streaming,
and managed services like Kinesis Data Analytics. It's the right choice when
the business need is genuinely "seconds to low-minutes fresh": fraud
scoring on a payment, a live dashboard for an ops team, triggering an alert
when error rates spike.

## Event time vs. processing time

This is the single most important distinction to get right, and the one
interviewers probe hardest.

- **Event time** is when the thing actually happened — a click, a sensor
  reading, a payment — timestamped at the source.
- **Processing time** is when your pipeline actually observes that event.

Under perfect conditions these are the same. In practice, mobile clients
batch and flush later, retries happen, network queues back up, and clock
skew exists between producers. If you window by processing time, a burst of
delayed events all lands in whichever window happens to be open when they
finally arrive — corrupting your aggregate for that window and silently
fixing nothing about the window they actually belonged to. Windowing by
event time is almost always the correct choice for anything resembling an
analytical aggregate; processing time is only appropriate when you
explicitly care about system throughput or arrival rate itself.

### Watermarks: a bet about lateness

A watermark is the stream processor's running estimate of "how far behind
could the slowest-in-flight event still be." When the watermark for a window
passes the window's end, the engine closes it and emits a result — even
though, technically, a later event could still show up. That's the trade-off:
a tight watermark (assume little lateness) closes windows fast but drops or
misroutes genuinely late data; a loose watermark waits longer, catches more
stragglers, but delays every result. Most engines let you configure a
"grace period" — accept late data up to N minutes past the watermark and
update the result, then truly close it.

## Delivery guarantees and idempotency

"Exactly-once" is the phrase every candidate reaches for and few explain
correctly. Almost no real system delivers a message exactly once end to end
at the network layer — brokers like Kafka give you **at-least-once**
delivery (a consumer that crashes after processing but before committing its
offset will re-read the same message). Exactly-once *processing* is
achieved on top of that by combining at-least-once delivery with:

- **Idempotent writes** — the output operation can be applied twice with the
  same effect as once (e.g. `UPSERT` keyed by event ID, or a counter keyed
  by a dedup ID rather than a blind increment).
- **Transactional output** — some engines (Kafka's transactional producer,
  Flink's two-phase-commit sinks) atomically commit the processed offset and
  the output write together, so a crash can't leave you with output written
  but the offset uncommitted (a duplicate) or the reverse (data loss).

Whichever you use, design the sink to tolerate replay. This matters just as
much for batch jobs that get re-run after a failure — the same idempotency
discipline applies there too.

## Worked example: sizing a clickstream aggregation

Say the requirement is "unique visitors per product page, updated within 30
seconds, for a site doing 50,000 clicks/second at peak." Two engineering
choices follow directly from that 30-second number:

1. **This rules out batch.** Even a very fast micro-batch job scheduled
   every 30 seconds spends most of its budget on job startup, shuffle, and
   scheduling overhead at this volume — you need a long-running streaming
   job with incremental state, not repeated short jobs.
2. **Window size and watermark follow the freshness target.** A 1-minute
   tumbling window with a 10-second watermark grace period gives you a
   result at most ~70 seconds after a window closes in the worst case
   (60s window + 10s grace) — too slow. Dropping to a 30-second tumbling
   window with a 5-second grace period gets you inside the 30-second-ish
   budget for typical traffic, accepting that pages with unusually delayed
   mobile clients occasionally get a slightly stale correction.
3. **State size is bounded by cardinality, not event volume.** Unique
   visitors per page needs a HyperLogLog sketch (or exact set, if the
   product catalog is small) keyed per page per window — at, say, 10,000
   active product pages, that's 10,000 small sketches in memory per open
   window, not 50,000 events/second of raw state. This is what makes the
   streaming approach tractable rather than a memory nightmare.

<Callout type="warning">
  A common mistake: treating stream processing as strictly "the fast
  version" of batch and reaching for it by default. Streaming systems carry
  real, ongoing operational cost — watermark tuning, state store sizing,
  exactly-once plumbing, and 24/7 on-call for a job that never finishes. If
  the actual requirement is "data ready by the time someone opens the
  dashboard in the morning," a batch job is simpler to write, cheaper to
  run, and dramatically easier to debug (you can just re-run it). Reach for
  streaming when the requirement genuinely needs sub-minute freshness, not
  because it sounds more impressive in an interview.
</Callout>

## Where this leaves you

Batch and stream aren't rival technologies to pick once — most real data
platforms run both, for different pipelines, chosen per use case. What
matters for the interview is being able to say, for any given requirement,
which model it actually needs and why: is "freshness" a real product
requirement measured in seconds, or a nice-to-have that a scheduled job
satisfies at a fraction of the operational cost? The next lesson takes this
further and puts both models together into one coherent platform design.
