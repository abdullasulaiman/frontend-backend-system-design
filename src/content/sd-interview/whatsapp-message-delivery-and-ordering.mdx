The high-level design gave you boxes: chat servers, a message store, a
pub-sub layer for fan-out. This lesson is about what happens to one message
inside those boxes, because that's where interviewers push hardest on a chat
system. Mobile networks drop connections mid-send. Phones go to sleep with a
message half-delivered. Two devices on the same account can both be typing.
None of that is exotic — it's every message, every day — and the difference
between a chat app that feels reliable and one that silently drops or
duplicates messages comes down to a small number of concrete decisions:
what delivery guarantee you actually provide, who decides message order, and
how you handle a recipient who isn't listening right now.

## What "reliable delivery" actually means

Three delivery semantics get discussed in distributed systems, and only one
of them is realistic here:

- **At-most-once** — send it, don't retry. Simple, but any dropped packet or
  server hiccup silently loses a message. Not acceptable for chat.
- **Exactly-once** — the message arrives precisely once, no drops, no
  duplicates. This is not achievable over a network that can fail mid-request
  (the sender can never be sure whether a timeout meant "never arrived" or
  "arrived, but the ack was lost"). Be wary of claiming this in an interview
  without qualifying it.
- **At-least-once** — retry until acknowledged. Messages might arrive more
  than once, but never zero times.

What chat systems actually build is at-least-once delivery plus **idempotent
deduplication** on the receiving end, which behaves like exactly-once from
the user's point of view without requiring the impossible guarantee. The
trick is entirely in how duplicates get recognized and dropped, covered
below.

## The three acks: sent, delivered, read

A message moves through three distinct states, each driven by a separate
acknowledgment, which is exactly what those familiar check-mark icons are
tracking:

1. **Sent** — the chat server accepted the message from the sender's client
   and durably persisted it. This is the sender's own client-server ack; it
   says nothing about the recipient yet.
2. **Delivered** — a recipient's device received the message over its own
   connection and sent back its own ack. The server relays this back to the
   sender.
3. **Read** — the recipient opened the conversation and the client fired a
   read receipt, again relayed back to the sender.

Each transition is a distinct event flowing in the opposite direction from
the original message: recipient to server to sender. In a group, this gets
tracked per recipient — "delivered" and "read" aren't single booleans on the
message, they're a small map of recipient-to-state, which the next lesson
covers in more depth when it deals with group fan-out.

## Store-and-forward: offline is the default case, not an exception

A recipient's device is frequently not connected when a message arrives —
backgrounded, asleep, or on a dead network. Treat this as the expected path,
not an edge case:

1. The chat server persists the message to a durable per-recipient inbox
   (or appends it to the conversation's message log, indexed for that
   recipient) regardless of whether the recipient's connection is currently
   live.
2. If the recipient has an open connection, push immediately over it.
3. If not, trigger a platform push notification (APNs/FCM) — not to carry
   the message content reliably, but purely to wake the app so it
   reconnects and pulls what it missed.
4. On reconnect, the client doesn't wait passively for pushes — it asks the
   server for everything after the last sequence number it has locally per
   conversation ("sync me from cursor `N`"). This single mechanism handles a
   dropped connection, a cold app launch, and a lost push notification with
   one code path, since the push is just a wake-up hint, not the source of
   truth.

## Ordering: per-conversation, not global

You don't need a single global order across every message every user on the
platform ever sends — nobody reads across conversations. What you need is a
consistent order **within** each conversation, agreed on by every
participant and every one of their devices.

The clean way to get this: make one component the single point that assigns
order for a given conversation, and have it hand out a monotonically
increasing sequence number as each message is durably accepted. This can be
a per-conversation counter in a database with a unique, ordered key, or a
single partition per conversation in a log like Kafka (the partition's
offset is the sequence number for free). Either way, the sequence number the
server assigns — not any client's timestamp — is the source of truth for
order.

Client timestamps are still useful for optimistic UI: show the message in
the thread immediately, ordered by local clock, the instant the user hits
send, before any round trip completes. Once the server's ack arrives with
the real sequence number, reconcile silently. What you must not do is use
client timestamps as the final ordering signal once multiple devices or
users are involved — phone clocks drift by seconds to minutes, and a
message sent a beat later by clock time can easily have an earlier
timestamp than one sent just before it on a different device.

## Deduplication: the other half of at-least-once

At-least-once delivery means retries happen, and retries can produce
duplicates: the sender's request times out, retries, but the first attempt
had actually already succeeded server-side. To make this invisible to the
user, the client attaches a unique ID to every outgoing message **before**
it's ever sent (a UUID generated client-side, not a server-assigned one, since
the whole point is surviving the case where the client doesn't know if the
server saw the first attempt).

The server treats this client message ID as an idempotency key: if a message
with that ID was already persisted, it returns the existing sequence number
instead of creating a second entry. The same ID travels with the message to
recipients, so a recipient's client that somehow receives the same message
twice (say, once via push-triggered sync and once via a live connection that
reconnected moments later) can drop the second copy on sight rather than
rendering it twice.

## Worked example: a retried send during a network blip

A sender's phone sends a message, the request reaches the server and gets
durably persisted with sequence number 4821, but the reply gets lost as the
phone briefly loses signal. From the client's perspective, this looks
identical to "the request never arrived" — it has no ack. After a short
timeout, the client retries the same message, with the **same client
message ID** attached.

The server sees a message with a client ID it's already persisted, does not
create a second entry, and simply returns the existing sequence number 4821
again. The sender's client reconciles its locally-shown message with that
sequence number and moves on — the user never sees a duplicate, and the
message's position in the conversation (4821) was decided once, not twice.
Without the shared client message ID, this retry would have created a
second message at, say, sequence 4830, and the recipient would see the same
text twice.

<Callout type="warning">
  A common mistake is ordering messages by the timestamp each client
  attaches locally, especially once multiple devices or a group chat are
  involved. Client clocks aren't synchronized, so two messages sent a second
  apart by two different phones can arrive with timestamps in the wrong
  order, and everyone's client would render a different order depending on
  which timestamps it trusts. Use client timestamps only for immediate,
  optimistic local display before the round trip completes; the
  server-assigned per-conversation sequence number is what every
  participant's client should actually sort by once it's known.
</Callout>

Delivery and ordering are the mechanics that make a chat thread trustworthy:
messages don't vanish when a phone drops signal, don't duplicate when a
request is retried, and appear in the same order for everyone reading the
same conversation. The next lesson builds on this same message pipeline to
cover presence, typing indicators, and how these per-recipient delivery
states scale once a "recipient" is a group of hundreds of people.
