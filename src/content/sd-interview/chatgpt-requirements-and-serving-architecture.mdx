Interviewers increasingly ask candidates to design a ChatGPT-style system,
and it's a different animal from a typical CRUD-and-cache interview. There's
no database schema to obsess over and no clever sharding key to find. The
hard resource is GPU compute, the workload has an unusual shape (a huge,
lumpy compute burst per request instead of a quick key lookup), and users
expect a conversational, incrementally-appearing response rather than a
single JSON blob. If you walk in and start whiteboarding a Postgres schema,
you're solving the wrong problem. This lesson builds the requirements and
the request-serving architecture; the next lesson in this module goes deep
on how you scale the inference layer itself.

## Clarifying the requirements

Start by narrowing scope out loud — the interviewer wants to see you frame
the problem, not just recite an architecture.

### Functional requirements

- A user sends a message in a conversation; the system streams back a
  model-generated response token by token.
- Conversations are multi-turn: each new message includes (or references)
  prior turns as context.
- Responses should be moderated — both the user's input and the model's
  output — for disallowed content.
- Users can view, continue, and delete their conversation history.

Deliberately out of scope for this lesson (call this out explicitly in an
interview): fine-tuning the model, training infrastructure, tool-use/agent
orchestration, and retrieval-augmented generation over private documents.
Those are worth a sentence ("I'd bolt a retrieval step onto the prompt
before it reaches inference") but they're not the core serving problem.

### Non-functional requirements

- **Time to first token (TTFT)**: the perceived "did it start responding"
  latency. Target under 300–500ms for a warm request.
- **Inter-token latency**: how quickly tokens keep streaming once started.
  Roughly 20–50ms/token reads as fluent; slower feels like it's stalling.
- **Throughput**: total tokens/second the fleet can generate across all
  concurrent users — this is the metric that determines GPU fleet size and
  cost.
- **Availability**: a degraded mode (shorter responses, a smaller model, or
  a queue with an honest wait estimate) beats a hard failure under load.
- **Cost**: GPU-hours are the dominant cost line by a wide margin — every
  architectural choice trades against tokens-per-dollar.

<Callout type="tip">
  Say this trade-off out loud early: "This system is compute-bound, not
  storage-bound." It reframes the whole interview and signals you understand
  what's actually being asked, versus applying a generic web-service
  template.
</Callout>

## Why LLM serving doesn't behave like a normal request

A typical backend request does a small, roughly constant amount of work: a
few index lookups, maybe a cache hit, serialize a response. An LLM request
does a variable amount of GPU work proportional to (prompt length + response
length), and that work happens in two distinct phases with very different
performance characteristics:

- **Prefill**: the model processes the entire input prompt in one shot,
  computing attention over all prompt tokens in parallel. This is
  compute-bound — it saturates the GPU's matrix-multiply units efficiently
  because there's a lot of parallelizable work per token.
- **Decode**: the model generates the response one token at a time. Each
  step depends on the previous token (that's what "autoregressive" means),
  so tokens cannot be parallelized within a single request. Decode is
  memory-bandwidth-bound — the GPU spends most of its time re-reading the
  model's weights and the growing key-value (KV) cache from memory, not
  doing arithmetic.

This split matters because it tells you where the money goes and what
"utilization" even means here. A single user's decode step barely uses the
GPU's compute capacity — which is exactly why serving many users'
decode steps *together*, in a batch, is the core scaling technique (covered
in depth in the next lesson). For this lesson, just internalize: prefill is
a one-time burst per request, decode is the long tail, and the KV cache
generated during prefill has to stay resident in GPU memory for the entire
decode phase (and across a conversation's follow-up turns).

## High-level serving architecture

Split the system into a **control plane** — everything that's cheap,
stateless, and horizontally scalable on commodity CPUs — and a **data
plane** — the GPU inference fleet, which is expensive, stateful per
request, and the actual bottleneck.

  Q --> GPU1[GPU Node: prefill + decode]
  Q --> GPU2[GPU Node: prefill + decode]
  GPU1 --> MOD2[Output moderation<br/>on streamed tokens]
  GPU2 --> MOD2
  MOD2 --> STREAM[Token stream<br/>SSE / WebSocket]
  STREAM --> U
  ROUTER --> HIST[(Conversation<br/>history store)]

Walk through the pieces:

- **API gateway**: authenticates the user, applies per-user rate limits
  (both requests/minute and tokens/minute — a single huge prompt can be as
  expensive as a hundred small ones), and terminates the client connection.
- **Input moderation**: a lightweight classifier (much cheaper than the main
  model) screens the prompt before it ever reaches an expensive GPU. Reject
  or flag early — never spend a GPU cycle on a request you're going to
  block anyway.
- **Session router**: routes the request to a specific GPU node and,
  critically, tries to route follow-up turns of the *same conversation*
  back to a node that already has (or can cheaply reload) that
  conversation's KV cache. This is the "stickiness" that makes chat serving
  different from a stateless REST API.
- **Request queue / scheduler**: admits requests into the GPU fleet's
  batching window rather than firing them straight at a GPU. This is where
  continuous batching decisions get made (next lesson).
- **GPU nodes**: run prefill and decode, and stream tokens out as they're
  produced rather than buffering the full response.
- **Output moderation**: runs on the streamed output — often on a rolling
  window of the last few tokens — so it can catch a response going off the
  rails mid-stream and cut it off, without waiting for the full response to
  complete first.
- **Conversation history store**: a plain key-value or document store
  keyed by conversation ID, holding the message log (not the KV cache,
  which lives in GPU memory and is far too large and short-lived to
  persist). On a new turn, prior messages are re-fetched from here and
  re-tokenized if the node serving this turn doesn't already hold a warm
  KV cache for the conversation.

## Streaming: why it's not optional

A ChatGPT-style response can take 5–15 seconds to fully generate. Returning
it as one blob after generation completes means the user stares at a
spinner for the entire duration. Streaming over Server-Sent Events or a
WebSocket sends each token (or small batch of tokens) to the client the
instant it's decoded, so the user sees the response materialize in
real time.

This changes what you optimize for. **Time to first token** becomes the
metric users actually feel — a system with an 8-second TTFT and instant
subsequent tokens feels slower than one with a 400ms TTFT and a steady
30ms/token trickle, even if the second one takes just as long to finish
the full response. Design the prefill path to prioritize getting that first
token out fast; everything after is about sustaining a smooth per-token
cadence, not front-loading more work.

## Worked example: sizing time to first token

Say your model needs roughly 1ms of prefill compute per prompt token per
GPU (a simplified but reasonable ballpark for a mid-size model on a single
modern accelerator, ignoring batching for a moment). A user pastes in a
600-token prompt.

Prefill time ≈ 600 tokens × 1ms = 600ms of raw compute, before the first
output token can be decoded. Add ~50-100ms of network and moderation
overhead, and you're looking at a ~650-700ms TTFT for this one request in
isolation — already over the 300-500ms target from the requirements.

Two levers fix this, and both show up as themes in the next lesson: (1)
batch prefill for several incoming requests together so the GPU's
parallelism isn't wasted on one request at a time, and (2) cap or truncate
extremely long prompts (or summarize older turns instead of resending them
verbatim) so a single pathological input doesn't blow the latency budget
for everyone sharing that GPU's queue. Notice the tension: batching helps
throughput but can hurt TTFT for an unlucky request that lands right after
a batch closes — a scheduling trade-off you should be ready to discuss.

<Callout type="warning">
  A common mistake: designing the moderation and history layers as if they
  sit "after" the real system, then bolting them on as an afterthought.
  Interviewers will push on safety and history retrieval specifically
  because they're easy to hand-wave. Put input moderation before the GPU
  (protect expensive compute), output moderation on the streamed tokens
  (don't wait for full generation to catch a bad response), and be explicit
  that conversation history is a cheap CPU-side store, separate from the
  GPU-resident KV cache — conflating the two makes your storage estimates
  wildly wrong.
</Callout>
