The previous lesson settled the requirements and sketched the major pieces: an editor extension, a backend that talks to an LLM, and some notion of "understanding the codebase." That sketch hides the two hardest problems in this system. First, the model doesn't know your codebase — every request has to hand it *just enough* of the right code to be useful, out of a repo that's almost always far bigger than the context window. Second, "AI coding assistant" is really two products wearing one name: an inline completion that has to feel instantaneous, and a chat/agent flow that can afford to think. Get either one wrong and the tool feels broken, even if the model itself is excellent.

This lesson works through how context gets built and budgeted, and how the latency split between completion and chat drives the rest of the design.

## Two products, two latency budgets

A developer accepts or rejects an inline suggestion in the time it takes to glance at it — anything much past 100-150ms of added typing latency reads as lag, and past 300-400ms people stop trusting the feature and turn it off. A chat question ("why is this test flaky?") tolerates a few seconds; users expect to wait for a real answer, the same way they wait for a search result.

That gap forces different engineering choices at almost every layer:

| Concern | Inline completion | Chat / agentic |
|---|---|---|
| Latency budget | ~100-300ms end-to-end | 1-10s+ acceptable |
| Model | small, fast, often local/edge | larger, more capable |
| Context | tight, cursor-local | broader, multi-file, multi-turn |
| Cancellation | constant — keystrokes race requests | rare — user waits for the answer |

Treating these as one pipeline with one model and one context-assembly path is the most common design mistake in this problem. They share infrastructure (the same repo index, the same auth and billing) but diverge sharply in the request path.

## Building context: what actually goes in the prompt

The model only knows what you send it. For a repo with hundreds of thousands of lines, deciding what fits in a context window of, say, 8K-32K tokens is a ranking problem, not a retrieval-everything problem. A reasonable priority order, richest signal first:

1. **Cursor-local code** — the current function, its enclosing class, and a window of lines around the cursor. This is almost always the highest-value context and costs the fewest tokens.
2. **Open editor state** — other tabs the developer has open, and recently edited files. A developer working across two files is telling you, implicitly, that both are relevant.
3. **Symbol resolution** — if the code references a function, type, or import from elsewhere in the repo, pull that definition in. This needs a symbol index (built from parsing/AST, similar to what a language server maintains), not just text search.
4. **Semantically related code** — a vector search over embeddings of code chunks (functions, classes) to find code that's conceptually related but not textually or structurally linked — useful for "is there already a helper that does this?" style completions and for chat questions about unfamiliar parts of the codebase.
5. **Project-level context** — README, style conventions, a short repo summary — low volume, included by default since it's cheap and stable.

Chat and agentic requests can afford to go several levels deep into (3) and (4), including multi-hop retrieval ("find the caller of this function, then find what calls that"). Inline completion mostly stays at (1) and (2) because there's no latency budget left for a retrieval round-trip once you've spent it on model inference.

### Indexing: symbol index and vector index, kept separate

A single index rarely serves both "jump to the exact definition of `parseInvoice`" and "find code related to invoice parsing" well. Exact/structural lookups (go-to-definition, references, imports) are served by a symbol table built from parsing each file's AST — cheap to build, updated incrementally as files change, and precise. Semantic lookups are served by an embedding index over chunked code (typically per-function or per-class, with some overlap) stored in a vector database, queried with the embedding of the current context or the user's question. Production assistants run both and merge results, rather than picking one.

Re-indexing has to be incremental. On save, only the changed file's symbols and embeddings get recomputed and upserted — re-embedding an entire multi-million-line repo on every keystroke or even every save doesn't scale, and it isn't necessary since most of the repo didn't change.

## Latency inside the completion path

Once context is assembled, the request still has to travel through retrieval, prompt construction, model inference, and back. For the completion path specifically, three techniques matter most:

- **Prompt/prefix caching.** The system instructions and stable repo context (file summary, imports) are usually identical across many consecutive keystrokes in the same file. If the inference engine caches the KV state for that shared prefix, each new request only has to encode the small delta — the few new characters typed — instead of re-processing the whole prompt from scratch. This is frequently the single biggest latency lever available, because it turns an `O(prompt length)` cost into something close to `O(new tokens)`.
- **Debouncing and cancellation.** A user typing at normal speed fires a keystroke every 50-150ms. Firing a completion request per keystroke wastes GPU capacity on requests that are obsolete before they return. Debounce briefly (a short quiet window, or triggering only at natural pause points like after a `.` or newline), and — critically — cancel any in-flight request the moment the cursor moves or new input invalidates it, so the GPU slot frees up rather than finishing a suggestion nobody will see.
- **Small, fast models on the hot path.** Inline completion typically runs a smaller model (sometimes distilled or quantized, sometimes served at the edge closer to the developer) chosen for latency over raw capability, reserving the larger model for chat where the budget allows it.

## Worked example: budgeting an inline completion

Say the product target is a 200ms end-to-end budget for inline completion, measured from keystroke to suggestion rendered. A rough breakdown: 20ms for the editor extension to detect the pause and send the request, 30ms of network round-trip to the nearest inference region, 100ms for model inference itself (a small model, short output — a line or two of code), 20ms to stream the result back, and 30ms of buffer for the editor to render it. That's already the full 200ms with almost nothing spent on retrieval.

This is exactly why cursor-local context and prefix caching matter more here than fancy repo-wide retrieval: if a vector search adds even 50ms, it consumes a quarter of the entire budget for a feature that's judged on feeling instant. Contrast this with a chat request answering "explain how retries work in this service" — a 2-3 second budget comfortably covers a multi-hop symbol lookup, a vector search across several files, and inference on a larger model, because the user's expectation for that interaction is closer to a targeted search than to typing feedback.

<Callout type="warning">
A common mistake is designing one context-assembly pipeline and one model tier for "the AI assistant" as a single feature, then discovering in review that inline completion is unusably laggy because every request pays for a full semantic search and a large model. Be explicit in the interview that completions and chat are different latency contracts requiring different models, different context budgets, and different cancellation behavior — sharing the underlying indexes is fine and expected, sharing the request path usually isn't.
</Callout>
