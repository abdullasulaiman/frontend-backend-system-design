You've picked a trie to store prefixes and a ranking approach to decide which
completions to show first. Neither of those, on its own, is a system. An
interviewer who's happy with "I'll use a trie with popularity scores" will
push further: where does that trie live, how does a keystroke actually reach
it, who rebuilds it as query patterns shift, and what happens under 50,000
requests per second from users who are each typing five separate letters for
a single search? This lesson wires the pieces from the last two lessons — the
data structure and the ranking signal — into one coherent architecture, split
cleanly into a read path that serves suggestions and a write path that keeps
them current.

## Two paths, two very different jobs

Typeahead has an unusual property compared to most CRUD-shaped systems: the
"write" that matters (a user's search query) and the "read" it eventually
feeds (someone else's typeahead suggestions) are almost never the same
request, and they can be arbitrarily far apart in time. That decoupling is
the single most important design decision in this system.

- **The read path** serves suggestions for a prefix in single-digit to
  low-double-digit milliseconds. It's read-only, extremely latency-sensitive,
  and must never wait on anything resembling a database write.
- **The write path** collects what people actually searched for, aggregates
  it, and periodically produces a new version of the trie for the read path
  to serve. It can tolerate delay measured in minutes to hours — nobody
  expects a query typed once to instantly change global suggestions.

Treating these as one system (e.g., incrementing a counter in the live trie on
every keystroke) couples a hot, latency-critical path to a write workload,
and is the fastest way to make `p99` latency unpredictable.

## The read path

1. The client debounces keystrokes (roughly 100-200ms of no typing) so it
   isn't firing a request per character.
2. The request — a prefix like `"des"` — hits a cache first. Short prefixes
   (1-3 characters) are few in number (26, then 676, then ~17,000
   combinations) and get hit by a huge fraction of all users, so a cache in
   front of the trie service absorbs most traffic cheaply.
3. On a cache miss, the request reaches the **trie service**, which is
   sharded by prefix range so any one shard's trie fits comfortably in memory
   on a single node.
4. The shard walks down to the node for the given prefix and returns its
   precomputed top-K list — computed once when the trie was built, not
   recomputed per request (see the ranking lesson for how that list is
   scored).
5. Results are cached (prefix -> top-K list) and returned to the client.

Because the top-K list at each node is precomputed, a request is just "find
the node, return its cached list" — no scoring happens on the request path at
all. That's what makes single-digit-millisecond responses realistic even at
very high QPS.

## The write path

1. Every completed search query is logged — just the raw query text and a
   timestamp, appended to a log or a queue (e.g., Kafka). This is cheap and
   asynchronous; it never blocks the user's actual search.
2. A batch job (commonly hourly or daily) aggregates logs into query counts:
   how many times was `"design patterns"` searched in this window.
3. Those counts feed into the trie-build job, which merges new counts with
   existing frequency data (often with time-decay, so last month's spike
   doesn't dominate forever), recomputes each node's top-K list, and produces
   a new trie snapshot.
4. The new snapshot is pushed out to trie service shards, usually with a
   rolling swap so no shard goes offline to reload.

This works well for organic, gradually shifting query popularity, but it's
too slow for anything breaking *right now* — a news event or a viral topic
can spike in minutes, and waiting for tomorrow's batch job means suggestions
stay stale exactly when they matter most.

### The fast lane for trending queries

A common addition is a lightweight, separate real-time counter — a sliding
window count per query term, updated as logs stream in — that can inject a
term into a prefix's suggestion list within minutes, bypassing the full
rebuild. It doesn't replace the batch pipeline; it's a small, fast overlay
that the trie service checks alongside the precomputed list, blended in with
a boost so a genuinely spiking term can surface even before it's "earned" its
place through the slower aggregation.

## Sharding and fault tolerance

Splitting one giant trie across nodes usually means sharding by prefix range
(`a-i` on shard 1, `j-r` on shard 2, and so on), so a client's request for a
given prefix always routes to exactly one shard — no fan-out needed for a
single keystroke's lookup. Each shard is replicated for read throughput and
failover, the same as any other stateless-ish read service (the trie itself
is effectively read-only between rebuilds, so replicas can be trivially
kept in sync by just shipping them the same snapshot).

<Callout type="tip">
  If certain letters are far more common as starting characters than others
  (English text skews heavily toward a handful of starting letters), a naive
  alphabetic split creates lopsided shards. Rebalance by query volume, not by
  letter count — a shard boundary can be `a-c` if those three letters carry
  as much traffic as `t-z` combined.
</Callout>

## Worked example: a 500ms search from "d" to "design"

A user types "design" one character at a time. With a 150ms debounce, typing
at a normal pace (roughly 200ms between keystrokes) means most individual
keystrokes fire their own request — say the client actually sends requests
after `"d"`, `"des"`, and `"design"` (the debounce coalesces the fastest
bursts, but three round trips is realistic for a six-letter word typed at
normal speed).

- `"d"` — a 1-character prefix. Near-certainly a cache hit; the fronting
  cache returns the top-10 completions for "d" in under 5ms.
- `"des"` — a 3-character prefix, still common enough to likely be cached;
  if not, it's one hop to the trie shard covering `d`, a node lookup, and a
  precomputed top-10 list — maybe 8-12ms including network.
- `"design"` — a longer, more specific prefix. Less likely to be cached,
  same trie-shard lookup applies, similarly fast, because the cost is
  dominated by the node walk, not by how long the prefix is.

Total: three requests, each independently fast, each of which could fail
without breaking the search box — if the third request times out or the
service is degraded, the client just keeps showing the results from `"des"`
until the user presses enter and runs an actual search. Meanwhile, none of
this activity touches the write path at all; "design" being searched adds one
line to a log that's aggregated hours later, alongside every other query from
every other user that hour.

<Callout type="warning">
  A frequent design mistake: describing the trie as something that gets
  updated live, on the request path, whenever a user searches something (an
  "increment the counter and re-rank on every query" design). At real
  traffic volumes this turns every read into a write, forces locking or
  contention on hot nodes near the root of the trie, and makes latency
  unpredictable exactly where it needs to be most reliable. Keep writes
  entirely on their own asynchronous path — logging now, aggregating and
  rebuilding later — and let the read path stay a pure, contention-free
  lookup against an immutable snapshot.
</Callout>

## Where this leaves you

You now have the complete request lifecycle: a debounced client request hits
a cache, falls through to a sharded trie service that returns a precomputed
ranked list with no scoring on the critical path, while a completely
separate pipeline logs queries, aggregates them, and periodically republishes
new trie snapshots — with an optional fast lane for genuinely trending terms.
The final lesson in this module pushes on what breaks as this design scales
further: how shard counts and rebuild frequency change under 10x or 100x the
traffic, and how to keep rebuilds cheap as the underlying dataset grows.
