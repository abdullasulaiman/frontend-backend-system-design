"Design a customer support bot" is one of the fastest-growing prompts in
system design interviews, because every company with a product now wants
one, and it forces you past generic LLM-serving concerns into a genuinely
different problem: how do you get a model to answer accurately about
*your* product — your refund policy, your API rate limits, your shipping
cutoffs — none of which it saw enough of during pretraining, and some of
which changed last week? Fine-tuning a fresh model on your docs every time
a policy changes doesn't scale. The standard answer is retrieval-augmented
generation (RAG): keep the model as-is, and feed it the relevant facts as
context at answer time. This lesson frames the requirements and builds the
RAG pipeline; the next lesson in this module goes deep on serving it as a
full support-bot product, including escalation to a human agent.

## Clarifying the requirements

### Functional requirements

- A user asks a question in natural language (in a chat widget, over
  email, or via an API) about the product, an order, or an account issue.
- The bot answers using the company's own knowledge base — help-center
  articles, API docs, policy pages, and (optionally) the specific user's
  order/account data.
- Answers should cite the source article(s) they're grounded in.
- The bot should recognize when it doesn't know the answer, or when the
  request needs a human (a billing dispute, an account security issue),
  and escalate instead of guessing.
- Support staff can add, edit, and remove knowledge-base articles, and
  those changes should show up in bot answers promptly, not after a
  multi-day lag.

Explicitly out of scope for this lesson: fine-tuning a custom model,
voice/phone support, and multi-turn agent tool-use (placing a refund,
canceling an order on the user's behalf) — worth a sentence in an
interview, but the deep-dive here is retrieval and grounding.

### Non-functional requirements

- **Answer latency**: a support chat should feel conversational — under
  ~2-3 seconds to start streaming a response is a reasonable target,
  which has to include retrieval time, not just generation time.
- **Groundedness / low hallucination rate**: the dominant quality metric.
  A wrong answer about a refund policy is worse than a slow one — it's a
  support ticket and a trust problem, not just a UX complaint.
- **Freshness**: knowledge changes (a new policy, a fixed bug) should
  reach the bot within minutes to hours, not require a retraining cycle.
- **Scale**: a knowledge base of thousands to tens of thousands of
  articles, serving potentially millions of queries a day at peak.
- **Auditability**: every answer should be traceable back to which
  documents were retrieved, for both user trust (citations) and
  post-incident debugging ("why did it say that?").

<Callout type="tip">
  Say out loud early: "the model doesn't need to *know* the answer, it
  needs to be *given* the answer and asked to phrase it." That's the whole
  RAG mental model, and it reframes the rest of the design around a search
  problem instead of a model problem.
</Callout>

## Why RAG instead of fine-tuning

Fine-tuning bakes knowledge into the model's weights through additional
training — it's expensive, slow to iterate (a new fine-tuning run per
content change is untenable), and notoriously bad at precise factual
recall; a fine-tuned model can still confidently state a shipping cutoff
that's three months stale. RAG instead treats the model as a fixed
reasoning-and-writing engine and supplies facts as part of the prompt at
query time, retrieved fresh from a knowledge base that's just data you can
update instantly. The trade-off: RAG adds a retrieval step and a hard
latency/quality dependency on search working well, whereas fine-tuning
(if it works) needs no runtime lookup. For a support bot, where content
changes constantly and factual precision matters more than stylistic
nuance, RAG is close to a default choice — most production support bots
you'll discuss in an interview use it, sometimes layered with a light
fine-tune purely for tone.

## The RAG pipeline

RAG splits cleanly into an **offline ingestion path** that prepares the
knowledge base for search, and an **online query path** that runs per
user question.

Walk through each stage:

### Ingestion (offline)

- **Chunking**: split each document into passages small enough to be
  specific (a whole 3,000-word article embedded as one vector loses too
  much granularity — a search for "refund window" and a search for
  "return shipping label" both match the same giant blob) but large
  enough to keep context intact. 200-500 tokens with some overlap between
  chunks is a reasonable starting point; overlap prevents a fact from
  being split exactly across a chunk boundary.
- **Embedding**: run each chunk through an embedding model that maps text
  to a dense vector such that semantically similar text lands near each
  other in vector space. This runs once per chunk, offline, in bulk.
- **Indexing**: store the vectors in a vector index (approximate nearest
  neighbor structures like HNSW are standard) alongside the chunk text
  and metadata (source article, last-updated timestamp, product area) so
  results can be filtered and cited.
- **Re-indexing on change**: when an article is edited or deleted, its
  chunks need to be re-embedded and the index updated — this is the
  mechanism that satisfies the freshness requirement, and it should be
  triggered by a content-management webhook, not a slow batch job.

### Query time (online)

- **Query embedding**: embed the user's question with the same embedding
  model used for ingestion (a mismatched model here silently produces
  poor matches — it's a common integration bug).
- **Vector search**: fetch the top-k (often 20-50) most similar chunks
  from the index. This is a fast approximate search, optimized for
  recall over precision at this stage.
- **Re-ranking**: run a slower, more accurate model (a cross-encoder that
  jointly scores the query against each candidate, rather than comparing
  precomputed vectors) over those top-k candidates to reorder them, then
  keep only the top 3-5 to actually use. This two-stage "cheap broad
  search, then expensive narrow re-rank" pattern is the same idea search
  engines and recommender systems use, applied here to retrieval quality.
- **Prompt construction**: assemble a prompt containing the user's
  question plus the retrieved passages (with their source metadata), and
  an instruction to answer only from the provided context and cite
  sources.
- **Generation**: the LLM produces the answer, and the serving layer
  attaches citations back to the source articles used.

## Worked example: sizing a knowledge base's index

Say the knowledge base has 8,000 articles averaging 1,200 words each.
At roughly 1.3 tokens per word and a 350-token chunk size with light
overlap, that's about 1,200 × 1.3 ÷ 300 (net of overlap) ≈ 5 chunks per
article, so roughly 40,000 chunks total. If the embedding model produces
1,536-dimensional vectors stored as 4-byte floats, each vector is
1,536 × 4 ≈ 6KB, so raw vector storage is 40,000 × 6KB ≈ 240MB — small
enough to fit comfortably in memory on a single node, well before you
need to think about sharding the index. The real scaling question for
most support bots isn't index size, it's query volume: at 50 queries/sec
peak, each needing an embedding call plus a vector search plus an LLM
generation call, the LLM generation step (hundreds of milliseconds to a
few seconds) dominates the latency budget by an order of magnitude over
the sub-50ms vector search — which tells you where to spend optimization
effort first if the bot feels slow.

<Callout type="warning">
  A common mistake: treating retrieval as a solved detail and pouring
  design effort into prompt engineering instead. If the right passage
  never lands in the top-k candidates — because chunks are too coarse,
  the embedding model is a poor fit for your domain's vocabulary, or
  there's no re-ranking stage — the LLM has nothing correct to work with,
  and no amount of prompt tuning fixes a missing fact. In an interview,
  spend your deep-dive time on chunking, embedding choice, and re-ranking
  before you talk about prompt wording.
</Callout>
