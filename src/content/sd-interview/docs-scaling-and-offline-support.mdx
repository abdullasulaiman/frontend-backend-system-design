Every design so far in this module has quietly assumed two things: that a
document has a handful of concurrent editors, and that every client stays
connected. Neither holds at Google Docs' actual scale. Some documents — a
company-wide OKR doc, a live event run-of-show, a viral shared spreadsheet —
get hundreds or thousands of people looking at them at once. And every
client, no matter how good your WebSocket infrastructure is, will lose its
connection sometimes: a laptop lid closes, a phone drops onto cellular, a
flight takes off. A design that only works with five editors and a perfect
network isn't a real design. This lesson covers the two problems that show
up once you relax those assumptions, and both problems turn out to lean
directly on decisions made earlier in this module.

## The scaling problem isn't "more documents" — it's "one huge document"

Scaling the number of documents is the easy part of this system, and it's
worth saying so explicitly: shard by document ID, spread sequencers and
storage across as many machines as you have documents-worth of load, and a
typical CRUD-style scaling story applies. That is not where collaborative
editors get into trouble.

The hard problem is a single document with an unusually large number of
simultaneous editors. Recall from the architecture lesson that one document
is owned by exactly one sequencer, which broadcasts every accepted operation
to every connected client on that document. That fan-out cost scales with
`editors times edit rate`, not with how many documents exist in the system.

Do the arithmetic on a genuinely hot document: 500 people have a live
planning doc open during an all-hands, each producing roughly 2 operations
per second during active typing bursts (keystrokes, cursor moves that carry
metadata, occasional formatting). That's 1,000 incoming operations per
second into one sequencer, and — because every operation gets broadcast to
every other open connection — up to 500,000 outbound messages per second
out of that same single process. No single machine's network stack or
socket-management loop comfortably sustains that, and you can't fix it by
adding more sequencers, because a document can only have one sequencer
without reintroducing the divergent-state problem from the architecture
lesson.

### Fixing hot-document fan-out

Three techniques compose well here, and none of them change who owns the
document:

- **Batch broadcasts.** Instead of pushing every operation to every client
  the instant it's sequenced, coalesce operations arriving within a small
  window (20-50ms) into one message per client. A user typing at normal
  speed produces far fewer network round-trips than keystrokes, and nobody
  perceives 30ms of batching as lag.
- **Add a fan-out tier.** Instead of the sequencer holding a direct
  connection to every one of 500 clients, it broadcasts once to a small
  number of relay nodes, each of which fans out to its own slice of
  connected clients. The sequencer's job shrinks to "sequence and send N
  copies" where N is the relay count, not the editor count.
- **Degrade gracefully past a threshold.** Past some editor count (say,
  100+ simultaneous active editors), many products switch very-large
  documents into a lighter-weight mode — visible presence for everyone, but
  full live-cursor detail only for a recently-active subset — because the
  UI value of showing 500 live cursors is close to zero anyway.

Notice what didn't change: there is still exactly one sequencer for
document D, still one canonical order of operations, still the same
OT/CRDT merge logic from earlier lessons. Scaling a hot document is a
fan-out and batching problem layered on top of the architecture, not a
different architecture.

## Offline support: the client keeps a private branch

The second scaling axis isn't about load at all — it's about time. A client
that loses connectivity shouldn't stop working. The user is still typing;
the editor still needs to feel instant. The only thing that changes is that
outgoing operations can't reach the sequencer yet.

The mechanism is a straightforward extension of the optimistic-apply
pattern from the architecture lesson: the client keeps applying its own
operations locally and queuing them (persisted to local storage, not just
memory, so a closed tab doesn't lose them) instead of sending them
immediately. Each queued operation still carries its base version — the
document state the client believed was current when it made the edit. The
client can keep doing this indefinitely; nothing about local editing
requires a live connection.

### Reconnecting: resync is just a bigger merge

When connectivity returns, the client doesn't need a special "offline
recovery" protocol — it runs the same merge logic used for live concurrent
edits, just against a bigger batch. The client tells the sequencer its last
known version; the sequencer replays every operation accepted since then;
and the client's queued local operations get transformed (OT) or merged
(CRDT) against that replayed history, exactly like reconciling one
concurrent edit, except there might be forty of them instead of one.

    participant C as Client (was offline)
    participant S as Sequencer

    Note over C: baseVersion stays pinned at 57

    S->>C: replay ops 58..112 (from other editors)

    S->>C: broadcast final merged state to all clients

This is exactly where the collaboration model choice from earlier in the
module stops being an abstract trade-off and starts mattering concretely.
A CRDT's merge doesn't care how many operations happened in the gap — union
the sets, done — so it tolerates a client being offline for hours without
extra risk. OT's transform step has to walk the client's queued operations
through every operation in the gap one at a time; a bigger gap means more
transform calls and more chances to hit an edge case the transform function
didn't handle cleanly. Real OT-based systems bound this by forcing a full
resync (discard the transform chain, refetch a fresh snapshot, then
reapply only operations still meaningfully "unsent") once the gap crosses
some threshold, rather than transforming across an unbounded history.

## Worked example: three hours on a flight

Say a user opens a document, boards a flight, and edits offline for three
hours, producing 40 queued operations against `baseVersion=200`. Meanwhile,
five other collaborators keep editing normally, and by the time the flight
lands the document is at `baseVersion=650` — 450 operations happened while
this client was gone.

On reconnect, the client sends `lastKnownVersion=200`. The sequencer streams
back all 450 missed operations. Under a CRDT, the client's 40 queued
operations already carry stable IDs relative to their neighbors, so merging
them into the now-much-longer document is a constant amount of work per
operation regardless of the 450-operation gap — the client renders the
merged result and sends its 40 operations up, done. Under OT, each of the 40
queued operations has to be transformed against some slice of those 450
intervening operations before it's safe to apply, which is real
computational work and real risk surface; most production OT systems handle
this by snapshotting the document at reconnect and replaying only what's
needed to get the queued operations into a valid final position, rather
than transforming through all 450 one by one.

<Callout type="warning">
  A common mistake is treating offline support as "queue writes and retry
  when online," the same pattern used for a typical CRUD app's failed API
  calls. That pattern assumes each write is independent and safe to replay
  as-is. A document editor's queued operations are not independent — they
  are relative to a base version that may be completely stale by the time
  the client reconnects, and naively replaying them against the current
  document (instead of resolving them through the transform/merge step)
  silently corrupts text or drops other editors' concurrent work. Offline
  resync must go through the same collaboration-model logic as live
  editing, not around it.
</Callout>
