The first two lessons in this module built a ChatGPT-style chat system from
the ground up: the requirements and serving architecture (sessions, streaming
responses, the split between the stateless inference layer and the stateful
conversation store), and then how to scale that inference layer with
batching, KV-cache reuse, and GPU capacity planning. That's the toolkit. The
real test of whether it's a *transferable* toolkit — not just a memorized
diagram of "how ChatGPT works" — is whether you can point it at a prompt that
looks similar on the surface but adds a requirement you haven't designed for
yet.

This lesson is that test: a full mock interview, a rubric, and a self-graded
reflection, no walkthrough. Set a timer for 35–40 minutes, talk out loud, and
only look at the rubric after you've committed to a design.

## What this prompt is actually testing

The prompt below asks you to design an AI support assistant embedded in a
product: it chats with a customer, answers using the company's own help-center
content rather than the model's general training data, and hands off to a
human agent when it isn't confident. That's still a chat system built on an
LLM — sessions, streaming, an inference fleet — but it adds two things
neither prior lesson covered in depth:

- **Retrieval-augmented generation (RAG).** The assistant has to answer from
  a specific, current knowledge base (return policies, product docs), not
  just whatever the base model memorized during training. That means a
  retrieval step — typically a vector search over embedded document
  chunks — has to run *before* the model call, and its output becomes part
  of the prompt.
- **Confidence-gated escalation.** Unlike a general-purpose chatbot, wrong
  answers here have a business cost (a customer told the wrong return
  window). The design needs a way to decide "this answer isn't grounded
  enough — route to a human" instead of always answering.

Everything else carries over directly: the stateless request/response
inference tier from lesson 1, the batching and autoscaling ideas from lesson
2, and the general pattern of streaming tokens back to the client as they're
generated rather than waiting for the full response.

## The request path, with retrieval and escalation added

The key structural change versus the base design is where retrieval sits:
before the model call, not after. The context assembled from conversation
history plus retrieved chunks becomes the actual prompt sent to inference.

<Mermaid client:visible chart={`
flowchart TD
    U[Customer message] --> G[API gateway]
    G --> S[Session service: loads conversation history]
    S --> R[Retrieval: vector search over KB embeddings]
    R --> P[Prompt assembler: history + retrieved chunks + system prompt]
    P --> I[Inference fleet: batched, streaming tokens]
    I --> C[Confidence / groundedness check on the response]
    C -->|confident| Strm[Stream tokens to customer]
    C -->|low confidence| Esc[Enqueue to human agent, show partial answer as draft]
`} />

Notice the branch after inference: this is the design's new decision point,
and it's exactly what separates this system from a plain chatbot. A strong
answer explains what feeds that confidence signal — commonly some mix of
retrieval score (did we find chunks that actually match the query), a
model-reported uncertainty or a lightweight classifier, and simple heuristics
(e.g., the model asked a clarifying question rather than committing to an
answer).

## Token budget: the constraint everyone underestimates

Say the model's context window is 8,000 tokens and the system prompt (tone,
policies, output format) takes a fixed 400 tokens. A support conversation
might carry 1,500 tokens of prior turns by message six or seven. If the
retrieval step returns five chunks at ~300 tokens each, that's another 1,500
tokens — total so far: 3,400 tokens of input before the model has generated a
single word of the response, leaving roughly 4,600 tokens for retrieved
context growth, longer conversation history, and the response itself.

This is where truncation policy becomes a real design decision, not a detail
to wave past: do you drop the oldest conversation turns first, cap the
number of retrieved chunks and keep only the highest-scoring ones, or
summarize older history into a shorter running summary? Each answer trades
off differently — dropping old turns loses continuity, summarizing costs an
extra model call (and thus latency and money) but preserves more information
per token. Naming this trade-off explicitly, with real numbers like the ones
above, is a stronger answer than saying "we manage the context window."

<Callout type="warning">
  A common mistake in this interview: describing retrieval and generation as
  two independent, parallel systems ("the vector DB team owns search, the
  LLM team owns chat") without addressing that they share one token budget
  and one latency budget. If retrieval alone takes 400ms and the interviewer
  asks for a 2-second time-to-first-token, you've already spent 20% of the
  budget before the model has processed a single token — say so, and explain
  how you'd keep retrieval fast (approximate nearest-neighbor search, a
  small pre-filter on document metadata) rather than treating it as free.
</Callout>
