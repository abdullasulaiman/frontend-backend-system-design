Every design so far in this module has assumed traffic behaves the way the
back-of-envelope numbers suggest: smoothly distributed, roughly uniform load
per video, per user, per shard. Real traffic doesn't behave that way. A
handful of videos get 90% of the views. A creator posts a clip that gets
picked up by a news outlet and goes from 200 views/hour to 200,000
views/minute in under ten minutes. A regional evening peak dumps twenty
thousand uploads on your transcoding fleet within the same hour every day.
None of these are edge cases - they're the normal operating conditions of a
video platform at scale, and this is usually where an interview shifts from
"draw the architecture" to "now it's getting hammered, what breaks first and
what do you do about it."

This lesson takes the architecture built up over the last four lessons -
metadata service, blob storage, transcoding pipeline, CDN - and asks where
each piece buckles under skewed, bursty, real-world load, and what you
actually add to keep it standing.

## The hot-key problem: when caching alone isn't enough

The most common trap is treating "add a cache" as a universal fix. A cache
absolutely helps when load is spread across many keys - a thousand
distinct videos each getting a thousand requests/sec is exactly what a
distributed cache cluster is built for, since that load is naturally
sharded across cache nodes by key.

It stops helping the moment one key (one video_id) is the target of the
overwhelming majority of traffic. If a single viral video pulls 200,000
requests/sec, every one of those requests hashes to the *same* cache node
and the *same* database shard behind it. Adding more replicas of that shard
doesn't help - each replica still serves the identical key at the identical
rate, so you've multiplied capacity for a problem that isn't about
aggregate capacity, it's about concentration on one node.

The fix is defense in depth, applied in the order a request actually
travels:

1. **CDN edge cache** absorbs almost all of it for video *segments* (see
   the streaming lesson) - but metadata requests (view count, like count,
   comment list) for that same video still have to go somewhere.
2. **A local, in-process cache on each app server** serves the hottest
   handful of keys out of memory with no network hop at all - a small LRU
   cache of the top few hundred video_ids by recent traffic catches most of
   a viral spike before it leaves the box.
3. **Request coalescing (single-flight)** in front of the distributed
   cache: when a key is missing or its TTL just expired, only the *first*
   concurrent request for that key is allowed to go fetch it from the
   database; every other concurrent request for the same key waits on that
   one in-flight fetch and shares the result. Without this, a cache
   expiry on a hot key causes thousands of simultaneous requests to all
   miss at once and all hit the database together - a self-inflicted
   thundering herd.
4. **Sharding by video_id hash** keeps this contained to one hot shard
   instead of one hot database - the rest of the system is unaffected, and
   you can add targeted capacity (a dedicated replica, a pinned cache
   entry with no TTL) to just that shard if it's identified as
   persistently hot.

## Counters are a bottleneck of their own

View counts, like counts, and comment counts look like simple integers but
are a classic hidden bottleneck. If every single view increments a row in
the metadata database synchronously, that row becomes a hot write target
under exactly the same viral scenario - now it's write contention, not read
contention, and writes to a single row don't parallelize the way reads
from replicas do.

The standard fix is to stop treating these as exact, synchronous counters.
Batch increments in memory (or in a stream like Kafka) per video_id and
flush an aggregate delta to the database every few seconds, rather than
one write per view. For "likes," this is usually fine to show as
eventually consistent - a user doesn't need to see the count update
within milliseconds of their own click. For genuinely approximate metrics
like unique viewers, a probabilistic structure (HyperLogLog) trades exact
precision for a fixed, tiny memory footprint regardless of scale.

## Upload bursts and transcoding backlog

The write side has its own scaling story, decoupled from the read side by
design (see the upload/transcoding lesson). The bottleneck here isn't a
hot key - it's burstiness. Uploads cluster around regional evenings and
around real-world events (a live sports moment, a product launch), so a
transcoding fleet sized for average throughput will queue up a large
backlog the moment a burst hits.

Because upload already sits behind a queue, this is more tractable than
the read-side hot-key problem: autoscale transcoding workers off queue
depth (not off API request rate, which barely moves during an upload
burst), and prioritize the queue so that, say, a paid/verified creator's
video or a video predicted to be high-traffic gets transcoded ahead of a
backlog of low-view-count uploads. Users tolerate "your video is
processing" for a few extra minutes far better than they tolerate a
playback failure, so pushing delay into the queue rather than into the
read path is the correct trade.

## Replication lag and read-your-writes

Read replicas fix aggregate read capacity but introduce lag - a write to
the primary might take tens to hundreds of milliseconds to appear on a
given replica. That's invisible for other users watching an unrelated
video, but it's very visible to the one user who just uploaded a video or
posted a comment and refreshes the page to see it missing. The usual fix
is a short-lived affinity: route that specific user's reads to the primary
(or to a cache entry explicitly invalidated on write) for a brief window
after they act, then let them fall back to normal replica routing once the
write has almost certainly propagated.

## Worked example: a video goes viral

Say a 2-minute clip normally gets 50 views/sec, comfortably served by one
cache node and one database shard. A news outlet embeds it and, within
eight minutes, it's at 150,000 views/sec - a 3,000x jump on one video_id.

Without any of the above: the video's cache entry's TTL expires mid-spike,
150,000 concurrent requests all miss at once, all hit the same database
shard simultaneously, and that shard's connection pool and CPU saturate -
taking down metadata lookups for every *other* video that happens to share
the shard, an outage with a much wider blast radius than the one video that
caused it.

With the layered defenses: the local per-server cache absorbs most of it
immediately since the same app servers keep re-serving the same hot
video_id from memory. On the TTL expiry, the request coalescer ensures
exactly one request repopulates the distributed cache while the other
149,999 wait on that result instead of re-querying the database. The
database shard sees, at most, a handful of requests instead of 150,000 -
and because sharding is by video_id, every other shard (every other video)
never notices this happened at all.

<Callout type="warning">
  A common mistake is announcing "we'll add more read replicas" as the
  fix for any read-scaling problem without asking whether the load is
  spread across many keys or concentrated on one. More replicas divide
  load that's already distributed across keys - they do nothing for a
  single hot key, because every replica of a shard serves that same key at
  the same rate. State explicitly in the interview that you're
  distinguishing "more aggregate reads, evenly spread" from "one video_id
  taking almost all the traffic," since the fix (more replicas vs. request
  coalescing and local caching) is different for each.
</Callout>

## Where this leads

Scaling problems in a video platform rarely show up as "the whole system
is slow" - they show up as one hot shard, one saturated queue, or one row
under write contention, with everything else running fine. Diagnosing
*which* resource is concentrated (a key, a shard, a queue, a row) is what
determines the right fix, and that diagnostic instinct is exactly what the
final lesson in this module - a mock interview on a short-video feed - will
ask you to demonstrate live.
