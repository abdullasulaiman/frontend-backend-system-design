The previous lesson scoped the crawler's requirements and sketched the
high-level pipeline: seed URLs feed a frontier queue, fetcher workers pull
URLs and download pages, a parser extracts links and content, and both
feed back into the system. That pipeline works fine for a demo that
crawls a few thousand pages from a handful of sites. It falls apart the
moment you point it at the real web, for three reasons: you'll get your
IP banned for hammering someone's server, you'll waste enormous compute
re-crawling and re-storing pages you've already seen, and a design that
only runs on one machine can't touch anything close to web scale. This
lesson covers all three: politeness, deduplication, and horizontal
scaling — the concerns that separate a toy crawler from one that could
actually ship.

## Politeness: crawling without becoming a denial-of-service attack

A crawler that fetches as fast as its network allows will, for any
individual site, look indistinguishable from an attack. Politeness is
the set of rules that keep a crawler a welcome (or at least tolerated)
visitor instead of an incident in someone else's on-call rotation.

### Respecting robots.txt

Before fetching anything from a host, a crawler should fetch and cache
that host's `/robots.txt`, which lists paths the site owner disallows
crawling and, often, a `Crawl-delay` directive suggesting a minimum gap
between requests. Treat this as a hard rule, not a suggestion: ignoring
robots.txt is the single fastest way to get an entire IP range
blocklisted, which can take down crawling for every other host sharing
that egress IP too.

### Enforcing rate limits at the host level, not globally

The mistake that's easy to make in a first design is a single global
rate limiter — "no more than 1,000 requests per second, crawler-wide."
That number does nothing to protect any individual site: at 1,000
QPS spread unevenly, a single popular host with many extracted links can
still receive hundreds of requests per second, while a small host gets
none. The correct unit of enforcement is **per host**: track a last-fetch
timestamp and a minimum delay (from `Crawl-delay`, or a conservative
default like one request every 1-2 seconds) per hostname, and only allow
a worker to fetch from that host once its delay window has elapsed.
Because a crawl of the whole web touches millions of distinct hosts, this
still adds up to very high aggregate throughput — it just requires
spreading load across hosts instead of concentrating it.

## Deduplication: don't fetch or store the same page twice

The web is full of the same content reachable through different URLs:
`example.com/page`, `example.com/page/`, `example.com/page?utm_source=x`,
and `www.example.com/page` are frequently the exact same document.
Without dedup, a crawler burns fetch budget, storage, and index space on
copies of pages it has effectively already processed.

### URL normalization and the seen-URL set

Before a URL ever reaches the frontier, normalize it: lowercase the
scheme and host, drop default ports (`:80` for `http`, `:443` for
`https`), remove the fragment (everything after `#`, since it's
client-side only), strip known tracking parameters, and sort remaining
query parameters into a canonical order. Then check the normalized URL
against a **seen-URL set** before enqueuing it. At small scale that set
can be an actual hash set in memory or Redis; at billions of URLs, an
exact set becomes too large to hold cheaply, so crawlers typically use a
**Bloom filter** instead — a probabilistic structure that answers
"definitely not seen" or "probably seen" using a fraction of the memory
of an exact set, at the cost of an occasional false positive (a new URL
incorrectly treated as already-seen and skipped).

### Content fingerprinting for near-duplicates

URL dedup alone still lets duplicate *content* through: mirrors,
syndicated articles, and printer-friendly or AMP versions of a page often
live at genuinely different URLs but carry nearly identical content.
For this, fingerprint the page content itself — a fast approach is
**SimHash** or **MinHash**, which produce a fixed-size fingerprint such
that near-identical documents produce fingerprints that differ in only a
few bits, unlike a cryptographic hash where a one-character change
scrambles the whole output. Comparing a new page's fingerprint against
recently stored fingerprints (using bit-distance rather than exact
match) catches near-duplicates that URL-level dedup can never see.

## Scaling the crawler horizontally

### Partitioning the frontier by host

To run on more than one machine, the frontier queue itself has to be
partitioned. The natural partition key is a hash of the hostname: every
URL for `example.com` is routed to the same partition (and, within it,
into a per-host sub-queue), regardless of which worker discovered the
URL. This single design choice is what makes politeness enforceable in a
distributed system — the worker or queue owning a host's partition is
the only place tracking that host's last-fetch time, so the rate limit
can't be silently bypassed by two different machines fetching the same
host in parallel.

### Keeping the seen-set and storage consistent

The Bloom filter (or sharded exact set) for URL dedup, and the page
store itself, need to be shared or sharded consistently across workers —
otherwise two workers can both decide a URL is new and fetch it twice.
Shard the seen-set the same way as the frontier (by host hash) so
membership checks stay local to the worker that owns that host, avoiding
a cross-network round trip on every single URL discovered.

### Crawler traps and other scale hazards

Some sites generate effectively infinite URL spaces on purpose or by
accident: a calendar with a "next month" link that never terminates, or
a session ID embedded in every URL that makes each page look unique.
Guard against these with hard caps — a maximum crawl depth per host,
a maximum number of URLs enqueued per host per day, and normalization
rules that strip session-style parameters before they ever multiply the
frontier.

## Worked example: sizing the politeness budget and the dedup filter

Say the target is 1 billion pages crawled per month, and you've settled
on a conservative default politeness delay of one request every 2
seconds per host (0.5 requests/sec) for hosts that don't specify their
own `Crawl-delay`.

**Required throughput:** 1 billion pages over a 30-day month is about
2,592,000 seconds, giving a target average of roughly 386 pages/sec.

**Host parallelism needed:** since no single host can be fetched faster
than 0.5 requests/sec, hitting 386 pages/sec requires at least
`386 / 0.5 = 772` distinct hosts being actively fetched from at any given
instant. This is the number that matters for capacity planning — not
"how many fetcher threads do we run," but "how many hosts can we keep in
flight simultaneously while respecting each one's delay." In practice
you'd run several thousand hosts in flight to leave headroom for slow
responses and retries.

**Bloom filter size for URL dedup:** at web scale, assume 10 billion
distinct URLs need to be tracked over the crawler's lifetime. A Bloom
filter tuned for a 1% false-positive rate needs roughly 9.6 bits per
element, so `10,000,000,000 x 9.6 bits ≈ 96 billion bits`, or about
12 GB. That's a strikingly small footprint for 10 billion URLs — an exact
hash set storing even short URL hashes at that scale would run into
hundreds of gigabytes. The 1% false-positive cost is a small number of
new pages incorrectly skipped as "already seen," which is an acceptable
trade for the memory savings at this scale.

<Callout type="warning">
  A common mistake is treating deduplication as a single problem solved
  by one hash check. Relying only on an exact URL string match misses
  the huge volume of URLs that differ trivially (trailing slash, query
  parameter order, tracking parameters) but resolve to the same page —
  fix this with normalization before the seen-check, not after. And
  relying only on URL-level dedup misses content duplicates reached
  through genuinely different URLs (mirrors, AMP pages, syndicated
  copies) — that requires a separate content-fingerprinting step. Treat
  URL dedup and content dedup as two distinct layers, not one.
</Callout>
