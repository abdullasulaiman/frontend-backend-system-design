The previous lesson pinned down the numbers: hundreds of millions of daily
active users, tens of billions of messages a day, and a delivery latency
budget measured in low hundreds of milliseconds. Those numbers rule out the
architecture most engineers reach for first — a REST API where the client
polls "any new messages?" every few seconds. Polling that frequently at that
scale would mean billions of mostly-empty requests an hour, and it still
can't deliver a message the instant it's sent. WhatsApp-style chat is a
**server-push** problem: the server needs a way to reach a specific client
the moment something happens, which means the architecture has to be built
around persistent connections from the ground up, not bolted on top of a
stateless request/response API.

## The connection problem comes first

Before naming a single service, settle how a message actually reaches a
device that isn't currently asking for anything. Three options, in
increasing order of how well they fit this problem:

- **Short polling** — client asks "anything new?" every few seconds. Simple,
  but the request volume is enormous and latency is bounded by the poll
  interval, not by when the message was actually sent.
- **Long polling** — client opens a request and the server holds it open
  until there's something to say (or a timeout). Better latency, but each
  waiting client still ties up a connection and a request cycle repeats
  constantly.
- **Persistent connections** — client opens one long-lived connection
  (a WebSocket, or a raw TCP socket speaking a lightweight protocol like
  MQTT) and keeps it open for as long as the app is active. The server
  pushes a message down the same socket the instant it arrives. This is
  what real chat systems use, because it's the only option where "message
  sent" and "message pushed to the recipient" can be milliseconds apart
  without wasteful request churn.

Persistent connections change the shape of the whole backend: a server
holding open a socket for a user is now **stateful** — it has to remember
who's connected to it — which is a fundamentally different scaling problem
than a stateless HTTP API server that can treat every request as
independent.

## Major components

### Client apps

Phone, web, and desktop clients each hold one persistent connection when
active. A single account can have several connections open simultaneously
(phone plus web, say), which matters for every downstream component: nothing
in this design should assume "one user equals one active socket."

### Connection gateway (the connection plane)

A tier of stateful servers that terminate persistent client connections,
handle auth on connect, and do nothing else clever — they're a thin, fast
layer between the network and the rest of the system. Because a connection
is sticky to whichever gateway instance accepted it, this tier is scaled by
adding more instances behind a load balancer that only cares about spreading
*new* connections evenly; it has no say over where an *existing* connection
lives.

### Session / presence directory

The piece that answers "which connection-gateway instance (if any) is user
`U` currently attached to?" Backed by a fast key-value store (something like
Redis) rather than a relational database, because it's a high-write,
low-latency lookup table, not a system of record — losing an entry just
means a brief "reconnect" blip, not lost data. Every connect/disconnect
updates this directory; every outbound message consults it first. Presence
semantics (online/offline/last-seen) build on this same directory and get
their own treatment in the next-but-one lesson.

### Message service

Owns the actual send path: validates a message, assigns it an ID and a
sequence position, writes it durably, and hands it to the routing layer for
delivery. This is the one component in the design that must never lose a
write — everything upstream (retries, dedup, ordering) covered in the next
lesson assumes the message service got the write right the first time.

### Message store

A durable, horizontally-partitioned store (a wide-column or log-structured
database fits well) holding message history per conversation, partitioned so
that a hot group chat doesn't overload a single shard. This is what backs
"scroll up and see history," multi-device sync (a new device fetches history
it missed), and offline delivery (undelivered messages wait here until the
recipient reconnects).

### Routing / delivery layer

Given a message and a recipient's user ID, this layer asks the session
directory where that user's connections live and pushes the message to each
one. If the directory says "not connected anywhere," the message stays in
the message store and delivery is deferred until the recipient's client
reconnects (at which point it fetches everything it missed) or a push
notification wakes the app.

### Push notification service

For a recipient whose app is backgrounded or fully closed — no open socket
at all — this is the only way to reach the device: hand off to
platform-level push (APNs, FCM) so the OS wakes the app or shows a
notification. It's a separate concern from in-app delivery and gets its own
lesson later in this module.

### Media and metadata stores

Photos, videos, and voice notes don't ride through the same path as text —
they're uploaded to blob storage out of band, and the message that
references them just carries a URL/handle. Covered in depth two lessons from
now; for this lesson, the only thing to note is that the message service
never inlines large binary payloads into the message pipeline itself.

## Worked example: one message, two cases

Trace a single 1:1 message through the boxes above, in both the online and
offline case. The sender's app has a persistent connection open to
**gateway A**; it sends the message over that socket. Gateway A forwards it
to the **message service**, which assigns it an ID, writes it to the
**message store**, and immediately acks the sender — that ack is what turns
the message bubble's checkmark solid, and it must not fire before the write
is durable.

The message service now hands the recipient's user ID to the **routing
layer**, which asks the **session directory** where that user is connected.

Case one: the recipient is online, attached to **gateway B**. The routing
layer pushes the message to gateway B, which delivers it down the
recipient's open socket in well under the interview's target latency budget
— no polling, no delay beyond one network hop and one lookup.

Case two: the recipient's app is closed and the directory has no entry for
them. The message already sat down safely in the message store when the
sender's write succeeded, so nothing is lost — the routing layer instead
calls the **push notification service**, which wakes the recipient's OS-level
push channel. When the user opens the app minutes later, their client
reconnects, and a sync step against the message store fetches everything
that arrived while they were away.

Notice what didn't have to change between the two cases: the message
service's write path is identical either way. Online/offline is purely a
routing-layer decision made *after* durability is already guaranteed — which
is exactly the property you want to point out out loud in an interview,
since it's what makes offline delivery a non-event instead of a special
case bolted on afterward.

<Callout type="warning">
  A common mistake is drawing one connection-gateway box and treating it
  like a stateless HTTP server that can be scaled by just adding replicas
  behind a round-robin load balancer. It can't: a given user's socket lives
  on exactly one instance, so anything that needs to reach that user has to
  know *which* instance — that's the whole reason the session directory
  exists. If your design has connection gateways but no session directory
  (or equivalent), an interviewer will ask "how does a message sent from
  gateway A reach a recipient connected to gateway B?" and there won't be an
  answer. Draw the directory in from the start.
</Callout>

## Where this leaves you

This lesson named the services and drew the boundary between the connection
plane (stateful, ties directly to a device) and the message plane (durable,
partitioned, indifferent to which gateway a user happens to be on). It
deliberately glossed over the hard parts: what happens when two messages
arrive out of order, how duplicate sends get deduplicated after a retry, how
group chats fan a single send out to dozens of recipients, and how presence
and typing indicators layer on top of the session directory. Those are the
next two lessons. Media handling and end-to-end encryption — which change
what actually flows through the message service — come after that.
