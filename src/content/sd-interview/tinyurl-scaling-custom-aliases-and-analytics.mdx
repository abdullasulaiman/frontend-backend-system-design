The previous lesson nailed down the core of TinyURL: generate a short code,
store the mapping, redirect on lookup. That design works fine for a
weekend project. It falls over the moment real traffic shows up, and it's
missing three features every interviewer expects you to raise on your
own: letting users pick their own alias, expiring links, and reporting how
many times a link got clicked. This lesson covers both halves of "make it
real" — the product features, and the scaling changes needed to serve them
at TinyURL's actual traffic shape: overwhelmingly reads, with writes as a
rounding error.

## Custom aliases

A custom alias (`tiny.url/my-launch` instead of a random `tiny.url/aZ9k2`)
sounds like a small feature, but it changes a core assumption from the base
design. The base-62 counter approach guarantees a collision-free code by
construction — you never have to check if a generated code is already
taken. A user-supplied alias has no such guarantee, so you're back to
handling collisions explicitly:

1. On creation, if the request includes a custom alias, look it up in the
   key store first.
2. If it exists, reject the request (`409 Conflict`) — don't silently
   overwrite someone else's link.
3. If it's free, insert the mapping keyed by that alias directly, skipping
   the counter entirely for this row.

This means your key store needs a uniqueness constraint on the short code
regardless of whether it came from the counter or a user, and the
"check-then-insert" for custom aliases must be atomic (a unique index plus
a single insert that fails on conflict, not a separate read followed by a
write) or two users racing for the same alias can both think they
succeeded.

## Expiration

Most links don't need to live forever, and letting every link live forever
means your key store only grows. Add an `expires_at` timestamp (nullable —
not every link expires) and handle it at two points:

- **On lookup**: if `expires_at` is in the past, return `404`/`410` instead
  of the stored long URL, even if the row is still physically present.
- **On a background sweep**: a periodic job deletes expired rows from the
  hot store (and, if you're archiving, moves them to cold storage first).
  Don't delete synchronously as part of every lookup — that turns your
  cheapest, highest-volume request into a conditional write.

This is the same "check lazily, clean up asynchronously" pattern you'll
see all over distributed systems: correctness on the read path doesn't
require the delete to have already happened, only that expired data is
never served.

## Click analytics

Product wants to know how many times a link was clicked, from where, and
on what device. The tempting-but-wrong approach is to `UPDATE clicks =
clicks + 1` (or insert a click-event row) inside the redirect handler,
synchronously, before responding. Don't — the redirect path is your
highest-QPS endpoint by a wide margin, and a synchronous database write
there means every redirect now waits on a write, and a hot link can turn
into the same hot-row contention problem you'd see in any heavily-voted
system.

Instead, treat analytics the way you'd treat any high-volume event stream:

1. The redirect handler fires an asynchronous event (append to a queue or
   log stream: short code, timestamp, referrer, user-agent, IP) and
   immediately issues the redirect — the event send should not block the
   response.
2. A downstream consumer batches and aggregates these events (clicks per
   link per hour, top referrers, geographic breakdown) and writes
   aggregates to an analytics store, separate from the key-value store
   serving redirects.
3. A dashboard or API reads from the analytics store, never from the
   redirect path's hot store.

This decouples "serve the redirect fast" from "count it accurately," the
same separation of concerns you'd use for likes, views, or votes in any
other read-heavy system.

## Scaling the redirect path

Redirects are reads: given a short code, fetch the long URL and respond.
At scale this is a classic cache-in-front-of-key-value-store problem:

- **Cache the hot set.** Put a Redis or Memcached layer in front of the
  primary store, keyed by short code. Because link popularity follows a
  power law — a small number of links (viral posts, ad campaigns) account
  for most traffic — an LRU cache with even a modest size relative to the
  total link count can absorb the vast majority of lookups.
- **Read replicas for cache misses.** A miss shouldn't always hit a single
  primary; route cache-miss reads to replicas so read volume scales
  independently of the small trickle of writes (new links, alias claims).
- **Shard once one database can't hold the data or throughput.** Short
  codes shard cleanly — hash the code (or use the code's own bits if it's
  derived from a counter) to pick a shard. Unlike a system keyed by a
  single popular entity, there's no natural "everyone hits shard 3" problem
  here, because each short code is its own independent key.
- **CDN/edge caching for redirects.** Since a redirect response for a given
  short code rarely changes, you can cache the 301/302 response itself at
  the edge, not just the underlying database lookup — this serves repeat
  visits to the same link with zero trips to your infrastructure at all.

## Worked example: sizing the cache and estimating write load

Say the service handles 500 million redirects a day and 5 million new
links created per day — a 100:1 read/write ratio, typical for a URL
shortener. That's roughly 5,800 redirects/second average (much higher at
peak, say 3-5x, so plan for 20,000-30,000/second) against only about 58
creations/second average.

If 20% of links account for 80% of clicks (a reasonable power-law
assumption), caching just that top 20% of the active link set can absorb
80% of the 20,000/second peak redirect load — leaving only about
4,000/second hitting the database tier, which read replicas handle
comfortably. Contrast that with the write side: even generously assuming
every creation also does a uniqueness check for a custom alias, you're
still under 100 writes/second at peak, which a single sharded primary
handles without breaking a sweat. This asymmetry is exactly why the
scaling story for TinyURL is "cache and replicate the read path
aggressively" — the write path was never the bottleneck.

<Callout type="warning">
  A common mistake: designing custom aliases and the counter-based short
  code generator as if they're independent systems with separate
  namespaces. If a user claims the alias `abc123` and your counter later
  happens to generate `abc123` as a "random" code for someone else, you get
  a silent collision — one user's link overwrites or is blocked by the
  other's, depending on your insert logic. Both paths must check and
  insert against the *same* unique short-code space, with a single
  uniqueness constraint enforced at the database level, not two
  independent code paths that each assume the other doesn't exist.
</Callout>
