Once you've pinned down requirements and scale — as we did in the previous
lesson — the next move in the interview is to sketch a system that could
plausibly hit those numbers. This is the moment where a lot of candidates
freeze up, because "design YouTube" feels too big to draw on a whiteboard in
five minutes. The trick is to notice that a video platform isn't one system —
it's two systems glued together by a shared catalog: a pipeline for getting
video *in*, and a pipeline for getting video *out* to millions of viewers.
Keeping that split explicit is what turns an overwhelming problem into a
manageable one.

## Start from the two paths, not the boxes

Before drawing any component, say out loud (or write on the board) that
uploads and playback have almost nothing in common operationally:

- **Upload path**: low volume compared to views, tolerant of multi-minute
  latency, write-heavy, needs heavy CPU work (transcoding) done once per
  video.
- **Watch path**: enormous volume, latency-critical (a viewer expects
  playback to start in under a second), overwhelmingly read-heavy, and the
  same bytes get served to millions of different viewers unchanged.

This asymmetry is the single biggest design decision in the whole system: you
optimize the two paths completely differently, and you should never let a
slow upload-side operation sit anywhere near the read path that serves
playback.

## The major components

A reasonable high-level design breaks into these pieces:

- **Client** (web, mobile, TV app) — plays video via an adaptive bitrate
  player, calls APIs for metadata, search, comments, and recommendations.
- **API / edge layer** — a set of stateless services behind a load balancer
  handling auth, request routing, and rate limiting.
- **Upload service** — accepts raw video files (often via resumable/chunked
  upload), writes them to a staging bucket, and enqueues a transcoding job.
- **Transcoding pipeline** — a fleet of workers (often a job queue plus
  autoscaled compute) that takes a raw upload and produces multiple
  resolutions/bitrates/codecs, thumbnails, and extracted captions. Covered in
  depth in the "Video Upload, Transcoding, and Storage" lesson.
- **Object storage** — durable blob storage (the S3/GCS-style store) holding
  both the raw upload and every transcoded rendition.
- **CDN** — caches and serves the transcoded video segments close to
  viewers; this is what actually absorbs the read traffic. Covered in depth
  in "Streaming and CDN Delivery."
- **Metadata database** — titles, descriptions, channel ownership,
  visibility, per-rendition storage pointers, and denormalized counters like
  view count.
- **Search index** — a separate index (inverted index / search engine)
  built from metadata, kept eventually consistent with the database.
- **Recommendation / ranking service** — reads precomputed features and
  serves a ranked list for the home page and "up next"; it's fed by an
  offline pipeline, not computed live from raw events.
- **Comments / social service** — its own read/write path, since comments
  have very different consistency and volume characteristics than video
  metadata.
- **Analytics / counters pipeline** — ingests playback events (view started,
  watch time, likes) through a queue and aggregates them in the background.

## Walking the two paths end to end

**Upload path.** A creator's file goes to the upload service, which streams
it into raw storage and immediately returns success to the client — it
doesn't wait for transcoding. That kicks off a job on a queue. Transcoding
workers pull the job, produce renditions (say, 240p through 4K, in a couple
of codecs), write each rendition to object storage, and write pointers plus
final metadata (duration, available resolutions, thumbnail URL) into the
metadata database. Only once metadata says "ready" does the video become
visible to viewers. Search indexing and recommendation feature extraction
happen asynchronously off of that same metadata write, not synchronously in
the upload request.

**Watch path.** A viewer opens a video page. The client calls the API for
metadata (title, channel, available renditions, an initial recommendations
list) — this is a small, latency-sensitive read against the metadata
database, usually behind a cache. The player then requests video *segments*
directly from the CDN using URLs derived from that metadata, not through your
application servers at all. This is the part people get wrong most often:
your API layer should never be in the hot path for actual video bytes — it
only ever hands out pointers. The CDN, backed by object storage on a cache
miss, does 100% of the bandwidth-heavy work.

## Worked example: tracing a single "watch" request

Say a video suddenly goes viral and jumps to 2 million concurrent viewers.
Trace what happens with the split above in mind:

1. Each viewer's client hits the API layer once for metadata — that's 2
   million small, cacheable reads. Put a cache (e.g., an in-memory or Redis
   layer) in front of the metadata database keyed by video ID, and this
   barely dents the database, since the metadata for a given video is
   identical for every viewer.
2. Each client then streams video segments from the CDN, not from your
   servers. The CDN's edge caches already hold the popular renditions after
   the first few requests, so object storage sees a tiny fraction of the 2
   million requests — effectively just the cache-fill traffic.
3. Playback events (watch time, view increments) get pushed onto a queue
   instead of writing to the metadata database synchronously per viewer. A
   background aggregator batches those into periodic counter updates, so the
   database sees thousands of batched writes instead of 2 million individual
   `UPDATE` statements.

Without steps 1–3, a viral video would mean 2 million requests slamming a
single database row and 2 million requests hitting your storage origin
directly — exactly the kind of design that collapses in an interview
follow-up question ("what happens when this video goes viral?").

<Callout type="warning">
  A common mistake is drawing one big "backend" box that handles uploads,
  serves metadata, *and* streams video bytes. That box would need to scale
  for both a low-QPS, CPU-heavy workload (transcoding) and a massive,
  bandwidth-heavy workload (playback) at the same time, with completely
  different scaling knobs. Always separate the control plane (metadata,
  search, recommendations — needs correctness and reasonable latency) from
  the data plane (video bytes — needs raw throughput and lives in object
  storage plus a CDN, not your application servers).
</Callout>

## What this lesson set up

This lesson is deliberately a skeleton: it names the components and shows how
traffic flows through them, but doesn't yet dig into schemas, transcoding
internals, or CDN cache strategy — those get their own lessons next. The one
idea worth carrying forward is the upload/watch split: almost every follow-up
question in a video-platform interview ("how do you handle a re-upload?",
"how do you avoid re-encoding on every request?", "how does seeking work?")
is really asking you to reason about which of the two paths is involved and
what its latency and volume characteristics are.
