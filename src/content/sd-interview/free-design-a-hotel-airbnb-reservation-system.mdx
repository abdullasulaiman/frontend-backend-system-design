Picture two people opening the same Airbnb listing at 9:00pm on a Friday,
both looking at the same weekend, both hitting "Reserve" within a second of
each other. Only one of them can get the room. Get this wrong and you've
either sold the same bed twice — an angry guest showing up to a locked
door — or you've falsely told a guest a room is unavailable when it isn't,
losing a booking for no reason. Every other feature of a reservation system
(search, pricing, reviews, messaging) is standard product engineering. This
one guarantee — **no two overlapping bookings for the same unit** — is the
part that makes this a genuinely interesting systems design problem, and
it's usually where interviews spend most of their time.

This lesson designs a booking platform in the shape of Airbnb or a hotel
chain's reservation system: search for available inventory, hold it briefly,
confirm it with payment, and never let two holds turn into two confirmed
bookings for the same dates. (If you've read the
[Ticket Booking System](/system-design/design/free-design-a-ticket-booking-system-ticketmaster)
lesson in this module, the "hold then confirm" shape will feel familiar —
the difference here is the resource being reserved is a *date range* on a
specific room, not a single seat at a single showtime, which changes how
the availability check works.)

## Requirements

**Functional**

- Search for available listings/rooms by location, date range, and guest
  count.
- View a specific listing's calendar (which dates are open).
- Reserve a room for a date range: hold it temporarily, then confirm with
  payment.
- Cancel a reservation, releasing the inventory back to availability.
- Host/hotel-side: create and update listings, block out dates, adjust
  pricing.

**Non-functional**

- Correctness above all: never confirm two overlapping bookings for the
  same room. This is a hard invariant, not a best-effort target.
- Search is read-heavy and can tolerate a few minutes of staleness (a room
  that was just booked can briefly still show up in search results, so long
  as the actual booking attempt correctly rejects it).
- Booking confirmation must be strongly consistent and low-latency (under
  ~500ms end to end, excluding payment processor round-trip).
- Scale: a large platform handles on the order of a few million listings
  and tens of thousands of bookings per minute at peak (holiday booking
  rushes) — write-heavy compared to most content systems, but nowhere near
  the throughput of an ad-click or telemetry pipeline.

## High-level architecture

Three responsibilities need to be pulled apart because they scale
differently: **search** (find candidate rooms), **availability/booking**
(the transactional core), and **pricing/payment** (mostly external, with a
thin coordination layer).

- **Search service** queries a denormalized index (Elasticsearch or similar)
  built from listing metadata plus a coarse availability signal. It answers
  "which of these 500 listings in this city have *no known conflict* for
  these dates" quickly, but it is allowed to be a little stale.
- **Booking service** owns the actual transactional guarantee. Every
  confirmed booking goes through it, and it is the only thing allowed to
  write to the authoritative inventory store.
- **Inventory store** is a relational database (Postgres/MySQL) — not a
  NoSQL store — because the overlap check is fundamentally a constrained
  write, and relational engines give you row locks, transactions, and
  constraints for free instead of requiring you to hand-roll them.
- **Hold store** is a short-TTL cache (Redis) holding "soft locks": a
  reservation the user has started but not yet paid for.

## The core problem: preventing double-booking

There are two common ways to model availability, and the choice matters a
lot for how the overlap check works.

### Option A: a bookings table with date ranges

Store one row per booking: `room_id, start_date, end_date`. To check
availability you query for any existing booking on that room whose range
overlaps the requested range. This is intuitive, but "does this range
overlap any existing range" is a range query, and preventing a race between
two concurrent range checks needs either a database-level exclusion
constraint (Postgres's `EXCLUDE USING gist` with a range type) or an
explicit table/row lock around the check-then-insert. Without one of those,
two transactions can both read "no conflict" before either commits its
insert — a classic time-of-check-to-time-of-use (TOCTOU) race.

### Option B: a per-night inventory row

Store one row per `room_id, date` (or `room_id, date, unit_index` if a
listing has multiple identical units, like a hotel room type). Booking N
nights means locking and decrementing N rows. This turns the overlap check
into N simple row-level operations instead of one range query, and it
composes naturally with `SELECT ... FOR UPDATE` — the database's normal row
locking handles the concurrency for you. It costs more storage (a row per
night per room, not per booking) but that's cheap relative to correctness.

Most production systems lean toward B, or a hybrid: per-night inventory
counts for the fast path, with a bookings table for the human-readable
record (who booked what, for receipts and cancellation).

The key move: the transaction that locks the rows and the transaction that
flips them from available to held happen atomically, inside one database
transaction, before payment is even attempted. Payment can take seconds
(3D Secure, bank round-trips); you never want to hold a row lock open for
that long, so the hold state — not an open transaction — is what protects
the inventory while payment runs.

<Callout type="warning">
  A common mistake is implementing availability as "SELECT to check if
  free, then, in application code, INSERT the booking" without wrapping both
  in a single transaction with row locking. Under low concurrency this works
  every time in testing, which is exactly why it's dangerous — it passes QA
  and then double-books during a real traffic spike, because two requests
  can both pass the SELECT check before either INSERT lands. Always make the
  check-and-reserve step one atomic operation (a transaction with `FOR
  UPDATE`, or a database constraint that rejects the second insert
  outright), never two separate round-trips.
</Callout>

## Holds, expiry, and idempotency

A hold is a soft reservation: inventory rows marked `HELD` with an
expiration timestamp (commonly 10-15 minutes). Two things have to be true
for holds to work correctly:

- **Expiry must be enforced by a background sweep or lazily on read** — a
  scheduled job (or a check every time the row is touched) that flips
  expired `HELD` rows back to `AVAILABLE`. Relying on the client to "release"
  the hold is not safe; browsers close, apps crash, users abandon carts.
- **Confirmation must be idempotent.** The client may retry the "confirm
  booking" call after a timeout, not knowing whether the first attempt
  succeeded. Require an idempotency key (e.g. a client-generated UUID) on
  the confirm endpoint, and store it with a uniqueness constraint — a
  retried request with the same key returns the already-created booking
  instead of creating a second one.

## Search and read scaling

Search doesn't need the same consistency guarantee as booking — showing a
listing that got booked 30 seconds ago is a minor annoyance (the booking
attempt will correctly reject it), not a correctness bug. That lets you
serve search from a denormalized index updated asynchronously (via
change-data-capture from the inventory DB, or an event the booking service
emits on state changes), cache aggressively at that layer since popular
destinations and dates are read far more often than any one room is booked,
and push the final, authoritative check to booking time, where it's cheap
because search already narrowed the field to a handful of candidates.

This search/booking split is the same pattern you'll see in the
[Ticket Booking System](/system-design/design/free-design-a-ticket-booking-system-ticketmaster)
lesson: decouple the expensive, latency-tolerant "browse" path from the
narrow, strongly-consistent "commit" path.

## Worked example: estimating the hot path

Say a platform has 5 million active listings and averages 20,000 confirmed
bookings per minute at peak (roughly 333/second) — modest compared to a
flash-sale ticket drop, because demand for a specific room on specific
dates is naturally spread out rather than everyone racing for the same
resource at once. Each booking touches, say, 3 nights: that's about 1,000
row locks per second at peak, easily handled by a properly indexed
relational database, as long as the index is on `(room_id, date)` so a lock
only ever touches the handful of rows for that room's requested nights
instead of scanning the whole table.

Contrast that with search: the same platform might see 200,000 queries per
minute (over 3,000/second), each browsing dozens of candidate listings —
roughly 10x booking's volume, at much lower staleness sensitivity per
query. That gap is exactly why search gets its own cached, asynchronous
index instead of sharing the inventory database, where it would contend
for the same locks the booking path depends on for correctness.

## Trade-offs and further considerations

- **Strong consistency vs. overbooking on purpose.** Airlines and hotel
  chains sometimes intentionally overbook by a small margin (e.g. 2-3%)
  based on historical no-show rates, accepting a rare compensation cost
  (upgrade, refund, relocation) in exchange for higher utilization. That's
  a business decision layered on top of a correctness-preserving system,
  not a reason to relax the underlying no-double-book guarantee.
- **Multi-region.** A global platform can't put every region's writes
  through one database without adding latency for distant guests.
  Partitioning inventory by geography (a listing's bookings are handled by
  its home region) keeps the transactional path local, at the cost of more
  complex cross-region search aggregation.
- **Cancellations and refund windows** add their own state machine (pending
  cancellation, refunded, dispute) but don't change the core availability
  model — a cancellation is just a transaction that flips nights back to
  `AVAILABLE`.
