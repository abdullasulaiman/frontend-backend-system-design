Plenty of backend problems disappear once you can say "only one process touches this at a time." A batch job that must not run twice concurrently, a leader election among ten worker nodes, an inventory decrement that must not double-sell the last item in stock — all of these are one `acquire lock` away from being simple. The catch is that "acquire a lock" is trivial on one machine (a mutex, a semaphore) and surprisingly hard across a fleet of machines that can crash, pause, or lose network connectivity mid-operation.

A distributed lock service is infrastructure that many other systems in this course quietly depend on: a leaderboard's rebalancing job, a ticket-booking system's seat reservation, a payment service's "don't double-charge this order" guard. This lesson designs that service directly, and spends most of its time on the failure mode that breaks naive implementations — a lock holder that looks dead but isn't.

## Requirements

**Functional:**

- `acquire(resource_id, holder_id, ttl)` — grant exclusive ownership of `resource_id` if nobody else holds it, for at most `ttl`.
- `release(resource_id, holder_id)` — voluntarily give up a held lock.
- `renew(resource_id, holder_id, ttl)` — extend an active lease (a heartbeat, so long-running work doesn't lose the lock mid-task).
- Locks must be reentrant-safe to reason about: only the current holder can release or renew.

**Non-functional:**

- **Safety above all**: at most one holder at any instant, even during network partitions or node failures. A lock service that occasionally grants two holders is worse than no lock service — it gives false confidence.
- **Liveness**: if a holder crashes without releasing, the lock must eventually become acquirable again — no permanent deadlock.
- **Low latency**: acquire/release round trips in the single-digit milliseconds, since locks often sit on a request's critical path.
- **Availability**: the lock service itself must survive node failures — if it's a single point of failure, everything that depends on it inherits that fragility.

Safety and liveness are in tension here: a strict "never release early" policy gives perfect safety but risks deadlock forever; a "release after 5 seconds no matter what" policy gives perfect liveness but risks releasing while the original holder is still working. The rest of this lesson is about managing that tension, not eliminating it — it can't be eliminated.

## High-level design

The lock service sits between clients and the resource they're protecting. It doesn't touch the resource itself — it only answers "who, if anyone, currently owns this lock." At its core it needs:

- A **replicated, consistent store** for lock state (who holds each lock, and until when), so a node failure doesn't lose or duplicate that state.
- A **consensus layer** (Raft or Paxos) so that a majority of replicas agree on every acquire/release/renew before it's considered committed — this is what prevents two nodes from each thinking they granted the same lock during a network partition.
- A **lease/TTL mechanism** so abandoned locks self-expire instead of requiring an external process to detect dead holders.

In practice you don't build the consensus layer yourself — you build on top of ZooKeeper, etcd, or Consul, all of which already implement Raft/Paxos-style replication and expose primitives well-suited to locking (ZooKeeper's ephemeral sequential znodes, etcd's lease API). The "design a lock service" interview question is really "show me you understand what a correct lock service needs from its underlying consensus store, and where the sharp edges are" — not "implement Raft from scratch."

### Acquire/release flow

1. Client sends `acquire(resource_id, ttl)`.
2. The lock service checks, via its replicated log, whether an unexpired lock entry exists for `resource_id`.
3. If none exists, it writes a new entry `(resource_id, holder_id, expires_at, fencing_token)` through consensus (a majority of replicas must ack) and returns success plus the fencing token.
4. If one exists and hasn't expired, it returns "denied" (or blocks/queues, depending on API design).
5. The holder either finishes and calls `release`, or calls `renew` periodically to push `expires_at` forward while work continues.
6. If the holder never renews or releases, the entry expires at `expires_at` and the lock becomes acquirable again — no manual intervention needed.

## The core problem: fencing tokens

Here's the failure that makes naive distributed locks dangerous. Client A acquires a lock with a 10-second TTL, then pauses — a long GC pause, a hypervisor stealing its CPU, a slow disk write, whatever. Ten seconds pass. The lock service, correctly, expires A's lock and grants it to client B. B starts doing work on the shared resource. Then A wakes up, still believing it holds the lock, and also writes to the resource. Now two writers are active — exactly what the lock existed to prevent, and the lock service did nothing wrong; A's clock and process scheduling did.

The fix isn't a longer TTL (that just delays the same problem and hurts liveness) — it's giving the *resource itself* a way to detect and reject stale writers. That's a fencing token: a number that increases every time the lock is granted (1, 2, 3, ...). The resource being protected must check that any incoming write carries a fencing token greater than the last one it accepted, and reject anything older.

This shifts the safety guarantee from "the lock service says only one holder exists" (which it cannot actually guarantee once you admit clocks and schedulers are imperfect) to "the resource never accepts a stale write, even if two clients briefly both believe they hold the lock." That second guarantee is achievable; the first one, without fencing, isn't.

<Callout type="warning">
  A distributed lock built on TTL expiry with no fencing token is not actually safe against the pause/GC scenario above — it just makes the failure rare enough that it's easy to miss in testing and painful in production. If the resource being protected can enforce a monotonic token check (most datastores can — a conditional write against a version column, an `expected_token` field), always add it. If it truly cannot (e.g., an external API with no such concept), the lock alone cannot give you the safety guarantee you probably think it does — you need a different mitigation, like making the operation itself idempotent.
</Callout>

## Design choices and trade-offs

**TTL-based lease vs. session-based lock.** A TTL lease (Redis-style `SET key value NX PX 10000`) is simple but ties correctness to clock assumptions — bounded drift, bounded pause times. A session-based lock (ZooKeeper ephemeral znode) ties the lock to a live heartbeated connection instead: the lock releases when the session dies, detected by missed heartbeats rather than wall-clock expiry. Session-based locks handle slow-but-not-dead clients more gracefully (the session just needs to keep heartbeating) but add the complexity of session management and still need a bounded session timeout somewhere.

**Single Redis node vs. quorum-based store.** A single Redis instance hands out locks fast, but it's a single point of failure — a crash mid-operation either loses lock state (two clients can now both acquire) or fails every request until recovery. Redlock (multi-node Redis locking) tries to fix this without full consensus, and it's genuinely controversial precisely because it substitutes clock/timing assumptions for the safety proofs a Raft/Paxos-based store gives for free. Where correctness actually matters, prefer a consensus-backed store (ZooKeeper, etcd, Consul) over ad hoc multi-node Redis schemes.

**Lock granularity.** Locking one row/resource (`order-42`) versus locking a whole table or partition is a contention-versus-complexity trade-off. Fine-grained locks (one per resource ID) scale better under high concurrency because unrelated requests never wait on each other, but you pay in the number of lock entries the service tracks. Coarse-grained locks are simpler to reason about but turn the lock into a throughput bottleneck the moment traffic grows — watch for this specifically when a candidate proposes "one global lock" for convenience.

**Blocking acquire vs. fail-fast acquire.** Some callers want to queue and wait for the lock (a batch job that just needs to run eventually); others want an immediate "someone else has it, try again later" (a request on the user-facing critical path, where blocking would tie up a thread/connection). Exposing both modes, or at minimum a bounded wait, keeps the API useful for both cases.

## Worked example: preventing a double-charge

Say a payment service processes "capture payment for order 42" requests, and a retry (from a flaky client, a load balancer replay, or an over-eager timeout) can plausibly send that request twice within a few hundred milliseconds. Without coordination, both requests could pass a "has this order been charged?" check simultaneously (both read "no" before either writes "yes"), and the customer gets charged twice.

With the lock service: request 1 calls `acquire("order-42-capture", ttl=5s)`, gets fencing token 9, does the charge, writes `payment_status = captured, token = 9` to the orders table (a conditional write requiring `token > current_token`), then releases. Request 2, arriving 50ms later, calls `acquire` on the same resource ID and is denied immediately (lock still held) — it returns a "capture already in progress, retry" response rather than proceeding. If request 1's process died mid-charge instead of finishing cleanly, the 5-second TTL expires, a retry (or a reconciliation job) acquires with token 10, and the conditional write on the orders table still protects against any stale write from request 1 showing up late.

Note what the lock is and isn't doing here: it prevents *concurrent* captures, but it doesn't replace the idempotency key needed to safely retry a genuinely-failed capture. In production you want both — the lock for mutual exclusion during the operation, an idempotency key (keyed on a client-supplied request ID) so a retry can return the cached result instead of re-executing. Many "don't double-process" problems elsewhere in this course lean on idempotency keys alone; only the ones with a true read-then-write race, like the capture example here, actually need mutual exclusion too.
