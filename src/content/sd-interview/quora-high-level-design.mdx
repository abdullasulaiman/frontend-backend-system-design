With requirements and scale pinned down in the last lesson, the next step is
sketching a system that can plausibly hit those numbers. "Design Quora" sounds
like it should be one big "questions and answers" service, but that framing
hides the two problems that actually make this system hard: fanning a single
piece of content out to many readers (a viral answer, a followed topic) and
keeping a running score (votes) correct and fast under contention. Get the
component boundaries right around those two problems, and the rest of the
design falls into place quickly.

## Start from the two access patterns

Before drawing boxes, separate what a user *writes* from what a user *reads*,
because they stress completely different parts of the system:

- **Write path**: posting a question, posting an answer, casting a vote,
  following a topic or a person. Lower volume than reads, but votes in
  particular can spike hard on popular content and need to stay correct under
  concurrent writes.
- **Read path**: loading a home feed, opening a question page, searching for a
  topic. Enormously higher volume than writes — every question view is a read,
  every feed scroll is a read — and it's where latency actually gets judged by
  the user.

This mirrors the read/write asymmetry you'd sketch for any content platform,
but Quora adds a wrinkle: a single write (one answer) can fan out to a huge
number of reads (everyone following that question, that topic, or that
author). How you handle that fan-out is the single biggest architectural
decision in this lesson.

## The major components

- **Client** (web, mobile) — renders feeds, question pages, and the
  ask/answer composer; calls a single API layer for everything else.
- **API / edge layer** — stateless services behind a load balancer handling
  auth, rate limiting, and request routing.
- **Content service** — owns questions and answers as durable records: create,
  edit, delete, fetch by ID. This is the source of truth for the actual text.
- **Vote/scoring service** — owns upvotes, downvotes, and the derived score
  per answer. Split out from the content service because its write rate and
  contention profile are completely different — a popular answer can take
  thousands of votes a minute while its text never changes again.
- **Follow graph service** — who follows which users, topics, and questions.
  Read constantly (to build feeds) and written rarely (a follow/unfollow
  click) — a classic asymmetric read/write service.
- **Feed service** — assembles the ranked list of items for a user's home
  page. It consumes the follow graph and either precomputed ("push") or
  on-demand ("pull") candidate items. The actual ranking formula is deferred
  to the "Ranking and Feed Generation" lesson — here we only decide *how
  candidates get to the feed service* in the first place.
- **Search / topic index** — a separate index (inverted index) over question
  titles, topics, and answer text, kept eventually consistent with the
  content service via an event stream, never queried synchronously on write.
- **Notification service** — tells a user "your followed question got a new
  answer" or "someone answered your question" — driven off the same event
  stream as the search index.
- **Event bus / queue** — the backbone connecting the write path to every
  downstream consumer (search indexing, notifications, feed fan-out, vote
  aggregation) without making the writer wait for any of them.
- **Primary datastore** — a relational or document store holding questions,
  answers, users, and the follow graph, usually sharded by question/user ID
  once volume demands it (that sharding strategy belongs in the "Scaling"
  lesson).
- **Cache layer** — in front of hot question pages, assembled feeds, and vote
  counts, since the read volume dwarfs the write volume by orders of
  magnitude.

## Walking the write path: posting an answer

A user submits an answer to the content service, which validates it and
writes it to the primary database as the durable record — that write returns
success immediately once it's persisted. It does **not** wait for search
indexing, notifications, or feed updates to finish; instead it publishes an
"answer created" event onto the event bus. Three independent consumers react
to that event asynchronously: the search index updates its entry for that
question, the notification service messages everyone following the question,
and a feed fan-out worker decides how this new answer should reach followers'
home feeds.

That last step is the interesting one. If the question's author (or the
question itself) has a modest number of followers, pushing the new item
directly into each follower's precomputed feed on write is cheap and keeps
reads fast. If it has a huge follower count — a heavily-followed topic or a
well-known writer — pushing to every follower on every single answer becomes
its own write storm. The practical answer most real systems land on is
hybrid: push for normal-sized follower counts, and fall back to pulling
high-fan-out sources into the feed at read time, merging both at feed
assembly. The exact ranking of that merged list is the next lesson's job —
here we're only deciding which items become candidates at all.

## Walking the read path: opening a question page

A question page is a fan-*in* read rather than a fan-out one: one question,
potentially thousands of answers, sorted by score. The content service
fetches the question and a page of answers (already filtered/sorted by the
vote service's stored score, not recomputed live), and the whole assembled
page is cached, because the same question page gets viewed by many different
users who all see essentially the same content. A user's own vote state on
that page is small and specific to them, so it's fetched separately and
overlaid on the cached page rather than busting the shared cache per viewer.

## Worked example: a question goes viral

Say a question about a breaking news event suddenly gets 50,000 new answers
and 5 million upvotes across those answers within an hour. Trace it through
the design above:

1. Each answer submission is one write to the content service and one event
   onto the bus — 50,000 writes is trivial for the primary database, so the
   content path barely notices.
2. Votes are the real stress test: 5 million vote clicks would be 5 million
   row-level `UPDATE`s if handled naively, and a large fraction of them land
   on the same handful of top answers — a hot-row problem. Instead, votes get
   buffered through the vote service's own write path (in-memory counters or
   a queue) and flushed as batched increments, so the database sees periodic
   bulk updates instead of millions of point writes to the same rows.
3. The question's page is read millions of times as the story spreads. Because
   that page is cached and only invalidated/refreshed on a schedule (or when
   the batched vote flush lands), those millions of reads hit the cache, not
   the database or the vote service directly.
4. Feed fan-out for this question follows the hybrid rule from above: it
   likely has far more followers than a typical question, so it's pulled into
   feeds at read/merge time rather than pushed to every follower's
   precomputed feed the instant each of the 50,000 answers lands.

Without steps 2–4, a single viral question would turn into millions of
synchronous writes against a handful of hot rows and millions of uncached
reads — exactly the kind of design that falls apart the moment an interviewer
asks "what happens when this goes viral?"

<Callout type="warning">
  A common mistake is putting votes directly on the same row and the same
  write path as the answer's text — for example, an `UPDATE answers SET
  score = score + 1 WHERE id = ?` executed synchronously per click. That
  couples a low-frequency operation (editing an answer) to an extremely
  high-frequency, high-contention one (voting), and it means every vote is a
  blocking write against a row that popular content will be hitting
  constantly. Split scoring into its own service/table with a buffered,
  batched write pattern, and let the content record itself stay
  write-light.
</Callout>

## What this lesson set up

This is deliberately a skeleton: component names and how traffic flows
between them, not schemas (next lesson), not the ranking formula behind the
feed (the lesson after that), and not sharding/replication numbers (the final
lesson). The one idea worth keeping in your head walking into a follow-up
question is the fan-out choice: almost every "what if this gets popular"
question in this interview is really asking whether you picked push, pull, or
a hybrid, and whether you know why.
