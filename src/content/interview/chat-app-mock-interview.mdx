You've scoped a chat application, sketched its architecture around a persistent connection, and gone deep on ordering, deduplication, offline queuing, and long-thread performance across the previous three lessons. This lesson is where you put it together under interview conditions: one open-ended prompt, a strict time box, and a rubric you'd actually be graded against.

The goal isn't reciting a script back. It's practicing the specific skill that separates a strong answer from a mediocre one on this case study: naming a concrete connection and reconnection strategy instead of waving at "WebSockets," and having a real mechanism for message ordering and offline handling instead of saying "we'd queue it and retry." Set a timer, talk out loud as if an interviewer is sitting across from you, and only look at the rubric after you've committed to a full answer.

## How to run this mock interview

Give yourself 35-40 minutes, uninterrupted. A reasonable time split:

- **Minutes 0-5**: Clarifying questions and stated scope.
- **Minutes 5-15**: High-level architecture — connection strategy, component tree, data flow between the WebSocket and the REST/GraphQL API.
- **Minutes 15-30**: Deep dive on two or three of the hardest sub-problems: ordering/dedup, offline/optimistic send, long-thread performance.
- **Minutes 30-40**: Edge cases, trade-offs, and leaving room for follow-ups.

The most common failure mode on this specific prompt is spending ten minutes drawing a nice box-and-arrow diagram of "client, server, database" and then discovering with five minutes left that you haven't said anything concrete about what happens when a message is sent while offline. The diagram is necessary but not sufficient — the deep dive is where the signal is.

## What "strong" looks like, briefly

A strong answer opens with two or three questions that actually change the design — not "what devices do we support" as a throwaway, but things like "is this 1:1 only, or does group messaging need to work too, since that affects fan-out" and "do messages need to sync across a user's phone and laptop simultaneously, since that's a different consistency problem than single-device delivery." It then states the resulting scope as constraints before drawing anything.

From there, it presents a connection strategy with a name attached: a persistent WebSocket connection for live message delivery and presence, paired with a REST or GraphQL API for paginated history and search, and a reconnection policy that's more specific than "we'd retry" — something like exponential backoff with a cap, plus a resync step on reconnect that asks the server "what have I missed since sequence number N."

The deep dive is where weak answers fall apart. A strong candidate explains message ordering with a concrete mechanism: the client generates a temporary ID and renders the message immediately (optimistic send), the server assigns a durable sequence number or timestamp once it accepts the message, and the client reconciles its optimistic copy with the server's authoritative version when the acknowledgment arrives — including what happens if the ack never comes (retry, then mark failed after some timeout, don't retry forever silently). Offline handling extends the same idea: queue unsent messages in a durable local store, show the user an explicit state per message (sending, sent, delivered, failed), and flush the queue on reconnect in a way that can't produce duplicates if the same message was already delivered before the connection dropped. Performance gets a concrete answer too: virtualize the message list so the DOM only holds what's visible, and handle the specific interaction between "new message arrives at the bottom" and "user has scrolled up to read history" — new messages shouldn't yank the viewport out from under a reading user.

Weak answers substitute vague verbs for mechanisms: "we'd use WebSockets," "we'd queue messages and sync later," "we'd virtualize the list for performance" — each true, none of it demonstrating that the candidate has actually thought through what breaks and how the mechanism handles it.

<Callout type="warning">
  The single most common gap in this interview is answering "how do you handle ordering" with just "we timestamp each message and sort by timestamp." That falls apart the moment two clients on slightly different clocks send messages close together, or a message sent offline arrives at the server minutes after one sent later by someone else. A strong answer names client-generated IDs for optimistic rendering plus a server-assigned monotonic sequence number (or per-conversation counter) as the source of truth for final ordering — client clocks are for display only, never for correctness.
</Callout>

<Callout type="interview">
  If the interviewer pushes on multi-device sync ("what if the same user has the chat open on their phone and laptop at once?"), don't freeze — narrate the trade-off: "I'd treat each device as an independent WebSocket connection subscribed to the same conversation stream, so both get the live message; for read/typing state I'd need the server to broadcast those events to all of a user's connected devices too, not just the sender's. That's more fan-out on the server, but keeping read state device-local would mean marking something read on your phone doesn't clear the unread badge on your laptop, which feels broken." Reasoning out loud about the cost, not just naming the solution, is what interviewers are listening for.
</Callout>

## Worked example: how a strong answer opens

Here's roughly how the first two minutes of a strong answer might sound (paraphrased — not a script to copy):

"Before I design anything, a few questions. First, is this 1:1 messaging only, or do I need to support group conversations too — group fan-out and read receipts across multiple participants are a meaningfully bigger problem than 1:1. Second, does a single user need their messages and read state synced live across multiple open devices, or is single-device usage an acceptable simplification for this session? Third, is end-to-end encryption in scope, since that changes where message content can be inspected, cached, or searched."

Suppose the interviewer answers: group messaging up to a moderate group size is in scope, multi-device sync is expected, and end-to-end encryption is out of scope for this session. A strong candidate restates that immediately as a constraint: "Okay — so I'm designing for group conversations with live delivery, read receipts and typing indicators that need to reach every device a user has open, and I don't need to worry about the client being unable to read message content server-side." Every architectural decision that follows should visibly trace back to that sentence.
