You've scoped the chat app (`chat-app-requirements-and-scope`) and laid out the architecture (`chat-app-high-level-architecture`): a WebSocket for live messages, a REST/GraphQL API for history, a local store, and a component tree. That's the skeleton. What actually gets asked about in the interview's second half — and what breaks in production if you hand-wave it — is the data flow around that skeleton: how you know messages are in the right order, how you avoid showing the same message twice, what happens to a message typed while offline, and how a thread with fifty thousand messages still scrolls at 60fps. This lesson is that deep dive.

## Message IDs: client-generated vs. server-assigned

Every message needs two identities, and conflating them is where most designs go wrong.

- **Client-generated ID** — a UUID (or similar) created the instant the user hits send, before any network round trip. This ID is what the optimistic UI renders immediately, and it's what the server echoes back in its acknowledgement so the client can match "the message I just sent" to "the message the server confirmed," even across a slow or retried request.
- **Server-assigned sequence number** — an integer (often per-conversation) the server assigns only once the message is durably accepted. This number is the actual sort key for display order, because it reflects the order the server saw messages arrive, not the order any one client's clock claims.

Why not just use a timestamp for ordering? Clocks drift between devices, and two people typing at the "same" millisecond on different phones can produce out-of-order timestamps that don't match the order either message was actually delivered or should logically appear. A server-assigned sequence number sidesteps this entirely: the server is the single authority on order, and every client defers to it.

### Reconciling optimistic sends

The flow for a single outgoing message looks like this:

1. User hits send. Client generates `clientId`, appends an optimistic bubble to the thread with a "sending" status, and stores the pending message locally.
2. Client sends `{ clientId, conversationId, body }` over the WebSocket (or POSTs it, if the transport falls back to HTTP).
3. Server persists the message, assigns it a `sequenceNumber`, and sends back an ack: `{ clientId, sequenceNumber, serverTimestamp }`.
4. Client looks up the pending message by `clientId`, updates its status to "sent," and now sorts it by `sequenceNumber` instead of local insertion order.

If the ack never arrives (dropped connection, app backgrounded), the message stays in "sending" state and becomes a candidate for retry — which is exactly the offline-queue problem below.

## Offline queuing and retry on reconnect

A chat app has to assume the network will disappear mid-conversation — a subway tunnel, a flaky wifi handoff, an app backgrounded for an hour. The design pattern is a durable outbox:

- Every outgoing message is written to a local persistent queue (IndexedDB on web, not just an in-memory array) the moment the user sends it, before the network call is even attempted. If memory-only, a killed tab loses unsent messages permanently.
- While offline, new sends just append to the queue and render optimistically; no network attempt is made until connectivity returns.
- On reconnect, the client flushes the queue **in order**, waiting for each ack (or a small pipeline of a few in flight) before considering that message settled. Order matters here — sending queued messages out of order defeats half the point of having a sequence number in the first place.
- Each retry reuses the same `clientId` generated at compose time. That's what makes a retried send safe: if the first attempt actually succeeded server-side but the ack got lost on the way back, the server sees a duplicate `clientId` and returns the *existing* `sequenceNumber` instead of creating a second message.

This last point is the crux of avoiding duplicate messages: **idempotency by client ID**, not by hoping the network never repeats itself.

## Deduplication: the client's job, not just the server's

Even with idempotent sends, duplicates show up on the *receiving* end too. A common cause: a client reconnects and re-subscribes to a conversation, and the server — unsure exactly which messages the client already has — resends the last few messages defensively to avoid a gap. Handling this purely server-side is fragile, since the server can't always know precisely what a given device already rendered (multiple tabs, missed acks, etc.).

The robust fix lives on the client: maintain a `Set` (or map) of message IDs already rendered per conversation. Any incoming message — from the initial history fetch, a live push, or a reconnect replay — gets checked against that set before being appended. If it's already there, update it in place instead of appending a second bubble.

<Callout type="warning">
  A frequent mistake: deduplicating only by array index or by "don't add if it's the last message," which silently fails the moment two messages get delivered slightly out of order or a batch of three duplicates arrives at once. Dedup by message ID against a proper set, and treat every incoming message — no matter which channel it arrived on — as needing that same check. Skipping this "because the server shouldn't send duplicates" is a bet you'll lose in production.
</Callout>

## Out-of-order delivery

Because the WebSocket and the REST history endpoint are two separate channels, a client can genuinely receive messages out of order: a live push might arrive before a background history-page fetch finishes backfilling earlier messages, or a brief reconnect gap might mean a "future" message shows up before the "past" ones that filled the gap. The fix is the same sequence number used for reconciliation: never trust arrival order for display order. Buffer incoming messages, insert each one at its correct position by `sequenceNumber` (not by appending to the end), and re-render the affected slice of the thread. This also means your message list's data structure should support efficient sorted insertion — a plain array with `push()` and no sort is the wrong choice once out-of-order delivery is a first-class scenario.

## Virtualizing long threads

A popular group chat can accumulate tens of thousands of messages. Rendering all of them as DOM nodes is a guaranteed performance problem — layout and paint cost scale with node count, and scrolling through that many elements will drop frames well before a user notices anything else wrong.

The standard fix is **list virtualization**: only the messages currently within (or just outside) the visible viewport are mounted as real DOM nodes; everything else is represented by a placeholder of the correct height, so total scroll height stays accurate without every row existing in the DOM. Two practical wrinkles specific to chat:

- **Variable row heights.** Unlike a feed of uniform cards, messages vary wildly in height (one line of text vs. a multi-line message vs. an image attachment). A virtualizer needs to either measure rows as they mount and cache the result, or accept an estimated height and correct it once the real height is known — get this wrong and the scrollbar/scroll position jumps as the user scrolls.
- **Anchoring scroll position on new messages.** When a new message arrives while the user is scrolled up reading history, you don't want the thread to yank them down to the bottom. The common pattern: track whether the user is near the bottom already; if so, autoscroll to the new message; if not, leave their scroll position untouched and show an unobtrusive "new messages" affordance instead.
- **Bidirectional loading.** A thread needs to load older history when scrolling up *and* accept live new messages appended at the bottom — most virtualization libraries are built assuming one-directional infinite scroll, so chat threads often need to manage the "prepend older page without shifting visible content" case explicitly (capture scroll offset before prepending, restore it after).

## Syncing read and typing state across devices

Modern chat apps assume a user might have the same conversation open on a phone and a laptop simultaneously. Two different kinds of state need to sync, and they have very different reliability requirements.

**Read state** needs to be reliable and idempotent, just like messages: represent it as "conversation X is read up to sequence number N" rather than as a per-message flag, and broadcast that single number whenever any device marks messages read. Every open session — including the device that didn't do the reading — receives the update and adjusts its own unread badge and read-receipt UI. Because it's expressed as a monotonically increasing number, applying an older update after a newer one is harmless (just take the max), which makes this state naturally resilient to reordering or duplicate delivery.

**Typing state** is the opposite: it's fine, even correct, for it to be lossy. A typing indicator is a "user is actively typing right now" signal with a short TTL (a few seconds); if a typing event gets dropped or arrives late, the worst outcome is a typing dot that's a second stale or missing, not a bug worth chasing with retries or persistence. Design typing indicators as fire-and-forget: send on a debounce while the user types, let the receiving client auto-expire the indicator if no follow-up arrives within the TTL, and don't queue them in the offline outbox at all — a "user was typing 20 minutes ago while offline" message is meaningless by the time it would be delivered.

## Worked example: reconnecting after a dropped connection

Trace a concrete scenario: a user is mid-conversation on a train, the WebSocket drops for 90 seconds as the train enters a tunnel, and they typed two messages during the outage.

1. Both messages get client IDs, render optimistically as "sending," and get written to the local outbox — no network attempt happens while offline.
2. Connectivity returns. The client reconnects the WebSocket and, as part of its reconnection handshake, tells the server the last `sequenceNumber` it has seen for this conversation (covered in the architecture lesson's reconnection strategy).
3. The server replies with any messages the client missed (say, three messages from the other participant sent during the outage) *and* separately processes the two queued outgoing messages, acking each with a real `sequenceNumber`.
4. The client's dedup set ensures none of the three incoming messages get double-rendered even if the server's replay slightly overlaps what the client already had cached locally.
5. All five new messages (three incoming, two outgoing) get inserted into the thread sorted by `sequenceNumber`, not by arrival order — so even though the acks for the user's own messages might arrive after the other participant's replayed messages, the thread displays them in the order they logically occurred.

That's the whole story in miniature: client IDs make sends idempotent, sequence numbers make order authoritative, and a dedup set makes replay safe — three small mechanisms that together handle a genuinely messy real-world scenario cleanly.
