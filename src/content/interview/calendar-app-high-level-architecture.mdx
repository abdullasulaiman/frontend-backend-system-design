Once you've scoped the calendar interview question (see `calendar-app-requirements-and-scope`), the interviewer wants to see a concrete architecture, not just a list of features. The trap in this case study is treating "events" as one flat list you fetch and render directly. That falls apart the moment recurring events enter the picture — a single "Team standup, every weekday" record isn't something you can hand straight to a grid; something has to turn it into a specific instance on Monday, another on Tuesday, and so on, only for the dates currently on screen.

This lesson lays out the architecture that makes that tractable: a rendering layer that only cares about laying out a grid of cells for a date range, a data layer that turns "give me events between date A and date B" into a flat list of concrete instances, a component tree built around that split, and a caching strategy keyed by date range so switching views or paging forward doesn't mean re-fetching the world.

## Two layers, one clean boundary

The core architectural idea is separating **what to draw** from **what data exists**:

- **The date/grid rendering layer** knows about calendar structure: how many rows and columns a month view needs, which date each cell represents, how a week view lays out 24 hourly rows, how a day view stacks overlapping events into columns. It has no idea what a "recurrence rule" is — it just receives, for each date or time slot, a list of events to draw.
- **The event data layer** knows about fetching and recurrence, and nothing about pixels or grid cells. Given a visible date range, it returns a flat, already-expanded list of event instances, each with a concrete start and end time. It has no idea whether that instance is being drawn in a day, week, or month view.

This boundary matters because the two layers change for different reasons and at different rates. Swapping month view for a two-week view is a pure rendering change; the data layer's contract ("give me instances for this range") doesn't move. Changing how recurrence is stored (a rule vs. pre-materialized rows — covered in `calendar-app-deep-dives`) is a pure data-layer change; the grid never notices, because it only ever sees flat instances.

## The event data layer: range in, instances out

The data layer's single responsibility is answering one question: **"which concrete event instances fall between this start date and this end date?"** Internally it does three things:

1. **Fetch raw events** that overlap the range — both one-off events and any recurring event whose series could produce an occurrence in that window (a daily standup created a year ago still needs to be considered for next week).
2. **Expand recurrence rules into instances.** A single stored record like "every Monday and Wednesday at 10am, starting January 1st" gets turned into one instance object per actual occurrence inside the requested range — each with its own concrete date, start time, and end time, plus a reference back to the parent recurring event (needed later for "edit this occurrence vs. the whole series").
3. **Merge and sort** those instances with one-off events into a single flat, time-ordered list scoped to the range — this is the only data shape the rendering layer ever consumes.

Nothing downstream — the grid, a day cell, an event chip — ever sees a "recurrence rule." By the time data reaches them, recurrence has already been resolved into plain, dated instances. That's the whole point of the layer: it absorbs the one genuinely gnarly piece of this domain (recurrence math) behind a boring, flat output shape.

## The component tree

With that data contract in place, the UI splits along the same lines:

- **`CalendarGrid`** — the top-level view component. It knows the current mode (day/week/month) and the resulting visible range, requests instances for that range from the data layer, and lays out the structural grid (rows/columns, hour lines for day/week, week rows for month). It doesn't know or care what an event actually is beyond "something with a start and end time to place."
- **`DayCell`** / **`WeekRow`** — a slot representing one date (month view) or one date-and-hour-range (week/day view). Each receives just the instances that land in its slot — already bucketed by the grid — and decides only about overflow (e.g. "show 3 chips and a `+2 more` link" when a day is packed).
- **`EventChip`** — renders one event instance: title, color, time label if relevant. It takes a plain instance object as a prop and has no awareness of recurrence, timezone conversion, or fetching — all of that already happened upstream. This is what keeps it trivially reusable and testable: pass it any instance-shaped object and it renders correctly.
- **`EventEditorModal`** — opens on creating or clicking an event. It's the one component that does need to know about recurrence, because saving a change to a recurring instance requires asking "just this occurrence, or the whole series?" It writes back through the data layer, which is responsible for translating that save into the right update (a per-instance override vs. a change to the underlying rule).

Each layer only needs the shape of data one level below it — `CalendarGrid` needs a flat instance list, `EventChip` needs one instance, `EventEditorModal` needs one instance plus enough context to know its parent series. None of them needs to reach past that boundary.

## Client-side caching by date range

Calendars are heavily range-driven: a user pages forward a week, switches from month to week view, jumps back to today. Re-fetching and re-expanding every event from scratch on every one of those interactions is both slow and wasteful, since large chunks of the range usually overlap what's already been fetched.

The fix is a cache keyed by **date range**, not by view mode or by a single global "all events" blob:

- Normalize each fetch to a canonical `(start, end)` window (e.g. always UTC day boundaries) and store the resulting expanded instance list under that key.
- Before fetching, check whether the requested range is already covered by cached ranges. A month view showing June and a week view showing the last week of June and first few days of July can share the June portion instead of duplicating it.
- Fetch a slightly wider buffer than what's strictly visible — a few extra days on each side of a month view, for instance — so paging forward by one step (or switching from month to the adjacent week) usually hits cache instead of triggering a new network round trip.
- On writes (create, edit, delete), invalidate only the cached ranges the affected event actually falls into. Deleting one Tuesday meeting shouldn't force a re-fetch of the entire year; it should just drop or patch the cache entries for the range(s) containing that instance.

A simple mental model: think of the cache as a set of non-overlapping "known-good" intervals, each mapped to its expanded instance list. A new range request either falls entirely inside a known interval (serve from cache, no fetch), partially overlaps one (fetch only the uncovered portion, then merge), or falls entirely outside any known interval (fetch fresh, then record the new interval).

## Worked example: paging from June to July

A user has the month view open on June, which triggered a fetch for roughly May 28 to July 2 (May and June's grid, plus the buffer) and populated the cache under that range. They click "next month."

The new visible range is July 1–31. The cache check finds July 1–2 already covered by the June fetch, so only July 3 onward through the buffer (say, through August 3) needs a fresh fetch. That request goes out, gets expanded (any recurring "every Monday" event produces its July occurrences here), and the result merges with the already-cached July 1–2 data to produce the full flat instance list `CalendarGrid` needs for July. The user perceives this as a fast page-forward, not a full reload, and the two days of overlap were never fetched twice.

If they then create a new recurring event starting in July, the data layer only needs to invalidate the cached ranges from July onward — May and June's cached instance lists are untouched, since the new series can't produce any occurrence before its start date.

<Callout type="warning">
  A common mistake: caching the *raw* recurring-event records instead of the *expanded* instances per range. If you cache "the recurrence rule" and re-run expansion on every render, you've moved the expensive work from the network to the render path and it now reruns on every scroll or re-render. If you cache expanded instances but key the cache by "all events" instead of by range, you lose the ability to invalidate or refresh part of the calendar without throwing away everything. Cache the *expanded, flat instance list, keyed by the specific date range it was computed for* — that's what makes both incremental fetching and targeted invalidation possible.
</Callout>
