You've now scoped the ride-hailing problem, sketched its high-level
architecture, and gone deep on location smoothing and edge cases across the
last three lessons. This lesson is the assembly test: can you deliver all of
that as one coherent answer inside a 35-45 minute window, in an order that
makes sense to an interviewer hearing it live, while still leaving room to
handle follow-ups that push on the parts you glossed over.

Run this as an actual mock interview, not a reading exercise. Set a timer,
talk out loud, and write down your own answer before you look at the rubric.
Reading the rubric first and then reverse-engineering an answer to match it
teaches you nothing about how you perform under real interview pressure.

## Why this prompt is different from a typical CRUD-heavy design

Most frontend system design prompts are dominated by "fetch data, render it,
keep it in sync" concerns. Ride-hailing shares that, but layers on two things
that trip up candidates who haven't practiced them: a trip lifecycle that is
genuinely a state machine (not just a status string you overwrite), and a
continuous stream of noisy, low-frequency location data that has to look
smooth and trustworthy on a map despite arriving unevenly and sometimes not
arriving at all. A rider staring at a driver's car icon that jumps, freezes,
or contradicts the trip's actual status reads as "this app is broken" far
faster than a stale list of posts would.

That's exactly why interviewers use this case study: it separates candidates
who can reason about time-based, asynchronous, partially-unreliable systems
from those who can only design around clean request/response APIs.

## How to run your 35-40 minutes

A reasonable allocation, adjustable to however the interviewer steers you:

1. **5-7 min — clarify and scope.** Rider app, driver app, or both? How
   tight does the ETA need to be? Single ride type for v1, or several?
2. **10-12 min — architecture.** Sketch the map layer, the trip state
   machine, and where location updates flow in. Name the states out loud.
3. **10-12 min — the deep dive the interviewer pushes on.** Usually location
   smoothing or reconnect/edge-case handling — this is where most of the
   signal is generated, so don't rush past it to get to a tidy conclusion.
4. **5-8 min — edge cases and trade-offs.** Backgrounded app mid-trip, GPS
   loss, mid-match cancellation, and what you'd measure to validate this in
   production.

## Worked example: answering the "phone loses signal mid-trip" follow-up well

A near-guaranteed follow-up is some version of "the driver enters a tunnel
and loses both GPS and network for 20 seconds — what does the rider see?"

A weak answer says "we retry" and stops there. A strong answer separates the
two failures and narrates each one specifically. GPS loss on the driver's
device means the phone itself has no new coordinate to send — the driver
app should keep the last known position, heading, and speed, and can
optionally dead-reckon a short extrapolated path from that data for a few
seconds before it stops trusting its own guess and instead flags "GPS
signal weak" locally. Network loss means even a valid GPS reading has
nowhere to go — the driver app should queue recent position samples locally
(a small ring buffer, not an unbounded one) so it can flush them in order
once connectivity returns, rather than only sending the single latest point
and losing the path in between. On the rider's side, the map shouldn't
freeze silently: once updates go stale past some threshold (say, three
missed intervals), show a visible "driver's location is delayed" state
instead of pretending the last position is still current. And whichever
side of the connection recovers first, the client should not assume its
locally-held trip state is still correct — it re-fetches authoritative trip
state from the server and reconciles, because the trip may have advanced
(or been cancelled) while it was disconnected.

That level of detail — which failure, which device, what the UI actually
shows, and how state gets reconciled afterward — is what separates "I know
that networks can fail" from "I could actually ship this."

<Callout type="interview">
  Don't let this follow-up turn into a monologue about GPS hardware or cell
  tower handoff. The interviewer is listening for client-side decisions:
  what state you hold locally, what you show the user, and how you
  reconcile once connectivity returns — not a lecture on how GPS chipsets
  work.
</Callout>

<Callout type="warning">
  A common mistake in this interview: presenting the trip lifecycle as a
  single `status` string the client overwrites in place, then improvising
  when asked "what if the rider cancels while the driver is already en
  route?" If you haven't named your states and the valid transitions
  between them up front, edge-case questions like that will expose the gap
  live. Draw the state machine early, even roughly, so every "what if"
  question becomes "that's a transition from state X to state Y" instead of
  a new problem you're solving from scratch.
</Callout>

## After you finish

Score your own answer against the rubric above, point by point, and be
honest about which parts you covered fully versus mentioned in passing. If
you jumped straight into "we poll every few seconds" without naming the
trip's states first, that's the most common gap in this round — practice
starting with the state machine before any data-flow detail. If your
location-smoothing answer stayed at "we interpolate" without saying what
you interpolate between or why raw GPS alone looks jittery, revisit the
[deep dives lesson](/interview/ride-hailing-deep-dives) before your next
attempt.
